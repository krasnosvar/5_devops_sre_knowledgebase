# Процессная модель Linux

## Процесс — основная единица выполнения

Каждый процесс — изолированный контекст с:
- собственным адресным пространством (виртуальная память)
- таблицей открытых файловых дескрипторов
- PID (идентификатор), PPID (родитель), UID/GID (права)
- рабочей директорией, environment variables
- одним или несколькими потоками (threads)

```bash
# посмотреть дерево процессов
pstree -p
ps auxf                      # ASCII-дерево с командами

# информация о процессе
cat /proc/1234/status        # PID, PPID, UID, threads, memory
cat /proc/1234/cmdline       # командная строка (разделитель \0)
cat /proc/1234/environ       # environment variables
ls -la /proc/1234/fd/        # открытые файловые дескрипторы
```

## fork() и exec()

Новый процесс создаётся через два системных вызова:

```
fork()  — создаёт точную копию текущего процесса (copy-on-write)
exec()  — заменяет образ процесса новой программой
```

```
bash (PID 100)
    │
    ├─ fork() ──► bash-copy (PID 101, родитель: 100)
                      │
                      └─ exec("ls") ──► ls (PID 101, образ заменён)
```

Именно так работает каждый shell-вызов: `bash` делает fork, потомок
делает exec нужной программы. Это же механизм запуска Docker контейнера —
containerd делает fork+exec для runc.

## Жизненный цикл процесса

```
created → running → waiting (I/O) → running → ...
                                            │
                                      exit(code)
                                            │
                                    zombie (ждёт wait())
                                            │
                              родитель вызвал wait() → исчезает
```

**Zombie** — процесс завершился, но запись в таблице процессов ещё есть:
родитель не вызвал `wait()`. Потребляет только запись, не память.
В контейнерах это проблема: PID 1 должен уметь reap child processes.
Именно поэтому используют `tini` или `dumb-init` как PID 1 в контейнерах.

**Orphan** — родитель умер раньше потомка. Автоматически переусыновляется
процессом с PID 1 (init / systemd).

## Сигналы

Механизм асинхронной коммуникации с процессом:

| Сигнал | Номер | Действие по умолчанию | Перехватывается? |
|--------|-------|----------------------|------------------|
| SIGTERM | 15 | Завершение | Да |
| SIGKILL | 9 | Принудительное завершение | **Нет** |
| SIGINT | 2 | Завершение (Ctrl+C) | Да |
| SIGHUP | 1 | Завершение / reload конфига | Да |
| SIGSTOP | 19 | Пауза | **Нет** |
| SIGCONT | 18 | Продолжение | Да |
| SIGUSR1/2 | 10/12 | Пользовательские | Да |

```bash
kill -SIGTERM 1234     # попросить завершиться (graceful)
kill -9 1234           # принудительно (не перехватить!)
kill -SIGHUP 1234      # reload (nginx, prometheus)
kill -0 1234           # проверить существование процесса (не посылает сигнал)

# посмотреть обработчики сигналов процесса
cat /proc/1234/status | grep Sig
```

**Graceful shutdown** в контейнерах: Docker/k8s посылает SIGTERM,
ждёт 30 сек (grace period), затем SIGKILL. Приложение должно перехватить
SIGTERM и завершить in-flight запросы.

## Exit codes

```bash
echo $?   # код завершения последней команды

# Стандарт:
# 0   — успех
# 1   — общая ошибка
# 2   — неправильное использование shell built-in
# 126 — команда найдена, но не исполняема
# 127 — команда не найдена
# 128+N — завершён сигналом N (128+9=137 — SIGKILL, 128+15=143 — SIGTERM)
```

В k8s `OOMKilled` = exit code 137 (SIGKILL от OOM killer).

## /proc — файловая система процессов

`/proc` — виртуальная ФС, интерфейс ядра для чтения состояния системы:

```bash
/proc/PID/           # директория каждого процесса
/proc/PID/maps       # карта памяти (адресное пространство)
/proc/PID/net/       # сетевые соединения процесса
/proc/sys/           # изменяемые параметры ядра (sysctl)
/proc/meminfo        # информация о памяти
/proc/cpuinfo        # информация о CPU
/proc/loadavg        # load average (1/5/15 мин, running/total processes, last PID)
```
