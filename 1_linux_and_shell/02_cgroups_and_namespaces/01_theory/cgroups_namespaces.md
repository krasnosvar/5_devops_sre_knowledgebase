## 1. Введение: Из чего состоит контейнер?

В Linux **не существует сущности "контейнер"**. Контейнер (в понимании Docker или Kubernetes) — это всего лишь обычный Linux-процесс, к которому применены две ядерные фичи:
1. **Namespaces** — отвечают за **изоляцию** (что процесс может *видеть*).
2. **Cgroups** — отвечают за **ограничения** (сколько ресурсов процесс может *потребить*).

Вспомогательными технологиями являются OverlayFS (слоистая файловая система) и Capabilities (ограничение прав root).

## 2. Namespaces (Пространства имен)

Namespaces изолируют глобальные системные ресурсы. Когда процесс помещается в namespace, ему кажется, что он один владеет всей системой. Всего в ядре 8 основных namespaces:

1. **PID (Process ID)**: Изолирует дерево процессов. Внутри контейнера процесс видит себя как `PID 1`. На хосте этот же процесс может иметь `PID 34125`.
2. **NET (Network)**: Изолирует сетевой стек. У процесса появляются свои сетевые интерфейсы (например, свой `eth0` и `lo`), своя таблица маршрутизации и правила iptables.
3. **MNT (Mount)**: Изолирует точки монтирования файловых систем. Контейнер видит свою rootfs (свой `/bin`, `/etc`), не видя реального жесткого диска хоста.
4. **UTS (UNIX Time-Sharing)**: Позволяет иметь собственный hostname и domainname.
5. **IPC (Inter-Process Communication)**: Изолирует очереди сообщений и разделяемую память. Процесс в одном IPC namespace не может читать Shared Memory процесса в другом.
6. **USER**: Самый важный для безопасности. Позволяет маппить пользователей.
   Процесс может быть `root` (UID 0) *внутри* контейнера, но ядро
   транслирует его в непривилегированный UID *снаружи* на хосте (например,
   `100000` по `/proc/<PID>/uid_map`). `nobody` (65534) видно только для
   UID, у которых маппинга нет.
7. **TIME** (появился недавно): Позволяет иметь собственное время, отличное от времени хоста.
8. **CGROUP**: Скрывает от процесса реальную структуру cgroups хоста.

Создаются они флагами при вызове `clone(CLONE_NEWPID | CLONE_NEWNET...)`. Войти в чужой namespace можно через утилиту `nsenter`.

## 3. Cgroups (Control Groups)

Cgroups позволяют ограничивать, измерять и изолировать потребление
физических ресурсов группами процессов. Управление cgroups происходит через
виртуальную файловую систему, смонтированную в `/sys/fs/cgroup/`.

Сегодня практически все актуальные дистрибутивы (и Kubernetes на них)
работают на **cgroups v2**: одна общая иерархия, смонтированная в
`/sys/fs/cgroup/` (тип ФС `cgroup2`). Каждая cgroup — это директория, а
лимиты — файлы внутри неё. Проверить версию на хосте:

```bash
stat -fc %T /sys/fs/cgroup/        # cgroup2fs -> v2, tmpfs -> v1/hybrid
cat /proc/self/cgroup              # v2: одна строка вида 0::/user.slice/...
cat /sys/fs/cgroup/cgroup.controllers   # какие контроллеры доступны
```

Ключевые контроллеры и их файлы в v2:
- **cpu**: `cpu.weight` (1-10000, по умолчанию 100) — относительная доля CPU
  при конкуренции, из неё делаются `requests` CPU в k8s. `cpu.max` в формате
  `"<quota> <period>"` (например, `"50000 100000"` = половина ядра,
  `"max 100000"` = без лимита) — жёсткий лимит CFS Bandwidth Control, из него
  делаются `limits` CPU. Счётчики троттлинга — в `cpu.stat`
  (`nr_throttled`, `throttled_usec`).
- **memory**: `memory.max` — жёсткий лимит; при его достижении ядро сначала
  пытается вытеснить page cache, а если не получилось — вызывает OOM Killer
  внутри этой cgroup (контейнера). `memory.high` — мягкий порог: выше него
  процессы агрессивно reclaim'ятся и замедляются, но не убиваются. События
  (`high`, `max`, `oom`, `oom_kill`) считаются в `memory.events`.
- **pids**: `pids.max` — защита от fork-бомб (максимум процессов и потоков
  в группе); текущее значение — `pids.current`.
- **io**: `io.max` — лимиты IOPS и байт/сек на блочное устройство
  (в v1 этот контроллер назывался `blkio`).

Контроллер должен быть включён у родителя: список контроллеров, доступных
детям, задаётся в `cgroup.subtree_control`, а процесс переносится в
группу записью его PID в `cgroup.procs`.

**Legacy cgroups v1** (встретится на старых нодах и в старых статьях):
у каждого контроллера своя иерархия (`/sys/fs/cgroup/cpu/...`,
`/sys/fs/cgroup/memory/...`) и свои имена файлов — `cpu.shares` (аналог
`cpu.weight`, по умолчанию 1024), `cpu.cfs_quota_us` + `cpu.cfs_period_us`
(аналог `cpu.max`), `memory.limit_in_bytes` (аналог `memory.max`).
Если в статье или скрипте видите эти имена — это v1, на хосте с v2 таких
файлов нет.

## 4. Cgroups v1 vs v2

- **cgroups v1** (Legacy): Использовал раздельную иерархию для каждого контроллера. Один и тот же процесс должен был быть добавлен в `/sys/fs/cgroup/cpu/docker/X` и `/sys/fs/cgroup/memory/docker/X`. Было сложно синхронизировать состояния при завершении процессов.
- **cgroups v2** (Unified): Использует единую (unified) иерархию. Процесс находится ровно в одной директории (например, `/sys/fs/cgroup/system.slice/docker-X.scope`), и там же настраиваются все лимиты (cpu, memory, io). Cgroups v2 полностью поддерживается Kubernetes начиная с версии 1.25. В v2 улучшена работа с OOM, появилась поддержка eBPF и Memory QoS (например, `memory.high` — порог троттлинга перед жестким OOM).

## 5. eBPF в управлении ресурсами

В современных Linux, cgroups v2 плотно интегрированы с **eBPF (Extended Berkeley Packet Filter)**.
Например, вместо старого механизма *Device Cgroup* (ограничение доступа к `/dev/sda` или GPU), в v2 eBPF-программы прикрепляются напрямую к cgroup. При любом системном вызове открытия устройства, ядро выполняет BPF-байткод, который разрешает или блокирует действие, не требуя переключения контекста и сложных парсеров путей.

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Что такое контейнер с точки зрения ядра Linux?**
*Ответ:* В ядре нет понятия "контейнер". Контейнер — это обычный Linux-процесс (или дерево процессов), к которому применены механизмы изоляции (Namespaces) и ограничения ресурсов (Cgroups). Программы вроде Docker или containerd (через runc) просто подготавливают файловую систему (rootfs) и дергают системный вызов `clone()` с нужными флагами namespaces.

**2. Чем отличается Cgroups от Namespaces?**
*Ответ:* Namespaces отвечают за изоляцию ("Что я могу видеть?"). Они скрывают чужие процессы, чужие сети и чужие файлы. Cgroups отвечают за лимитирование ресурсов ("Сколько я могу потребить?"). Они не дают процессу занять больше CPU, RAM или I/O, чем ему разрешено, защищая остальных соседей на сервере (Noisy Neighbor problem).

**3. Как Docker/Kubernetes задают CPU Limits и CPU Requests под капотом?**
*Ответ:* Через контроллер `cpu` в cgroups. В v2 `requests` превращаются в
`cpu.weight` (относительный вес: гарантирует долю CPU, когда процессор
загружен на 100%, и ничего не ограничивает, когда CPU свободен). `limits`
превращаются в `cpu.max` (CFS Bandwidth Control: квота микросекунд CPU на
период, обычно 100 мс). Если квота за период израсходована, ядро
приостанавливает (троттлит — CPU throttling) процессы контейнера до
следующего периода; это видно в `cpu.stat` (`nr_throttled`). В legacy v1
те же механизмы назывались `cpu.shares` и `cpu.cfs_quota_us` /
`cpu.cfs_period_us`.

**4. Контейнер упал с ошибкой OOMKilled (Exit Code 137). Кто его убил — Docker или ядро Linux?**
*Ответ:* Ядро Linux. Docker (или kubelet через container runtime) лишь
записывает лимит в cgroup — в v2 это файл
`/sys/fs/cgroup/<путь контейнера>/memory.max` (в legacy v1 —
`memory.limit_in_bytes`). Когда процессы внутри cgroup суммарно пытаются
выделить больше памяти и reclaim не помогает, ядро запускает OOM Killer в
пределах этой cgroup, и он убивает процесс сигналом SIGKILL (9), отсюда
код выхода 128 + 9 = 137. Счётчик `oom_kill` в `memory.events` растёт;
runtime читает это событие и рапортует `OOMKilled`.

**5. Как работает PID Namespace и почему процессы в контейнере всегда видят себя как PID 1?**
*Ответ:* При использовании `CLONE_NEWPID` ядро создает новую изолированную ветку идентификаторов. Процесс инициализации контейнера получает внутри этого namespace номер 1. Однако на самом хосте (в корневом PID namespace) этот процесс имеет реальный системный PID (например, 34500). Ядро прозрачно транслирует внутренние PID во внешние.

**6. Зачем нужен User Namespace и как он повышает безопасность?**
*Ответ:* User namespace позволяет маппить идентификаторы UID/GID. Если процесс в контейнере запущен от имени `root` (UID 0), User Namespace транслирует этот UID 0 в непривилегированный UID на хосте (например, 100000). Таким образом, внутри контейнера приложение думает, что у него права суперпользователя (может менять права файлов), но если оно сбежит из контейнера на хост (container breakout), ядро
воспримет его как обычного бесправного пользователя с UID 100000.

**7. Если запустить команду `top` внутри Docker-контейнера без настройки lxcfs, какие ресурсы (RAM/CPU) она покажет?**
*Ответ:* Она покажет **ресурсы всего хоста (сервера)**, а не лимиты контейнера. Дело в том, что `top` читает данные из файловой системы `/proc` (например, `/proc/meminfo`), а в Linux эти файлы по умолчанию не cgroup-aware. Приложение увидит 128 ГБ ОЗУ хоста, попытается выделить 64 ГБ под кэш базы данных, упрется в лимит cgroup (например, 2 ГБ) и будет мгновенно убито OOM Killer'ом.

**8. В чем ключевое отличие Cgroups v1 от Cgroups v2?**
*Ответ:* В v1 каждый ресурс (CPU, Memory, IO) имел свою отдельную иерархию папок, и процессы приходилось распределять по нескольким деревьям одновременно. В v2 используется "Unified Hierarchy" — единое дерево. Процесс добавляется в один узел, и там же применяются все правила и контроллеры. В v2 также интегрирован eBPF и лучше работает OOM-управление.

**9. С помощью какой команды можно зайти в Network Namespace запущенного контейнера прямо с хоста, чтобы, например, запустить там `tcpdump`?**
*Ответ:* С помощью утилиты `nsenter`. Вы находите системный PID контейнера на хосте, а затем выполняете: `nsenter -t <PID> -n tcpdump -i eth0`. Флаг `-n` указывает ядру войти только в Network Namespace данного процесса. Это стандартный способ дебага сети без установки утилит в сам контейнер.

**10. В Kubernetes часто встречаются `Init Containers`. Требуют ли они создания отдельного Namespace для работы?**
*Ответ:* Нет, не отдельного. Все контейнеры в рамках одного k8s Pod'а делят (share) общие Network и IPC namespaces (и опционально PID namespace). Init-контейнер запускается в тех же пространствах имен, что и основной контейнер, но последовательно до него. У него лишь своя собственная RootFS (MNT namespace).
