## 1. Всё есть файл (и файловый дескриптор)

Ключевая философия UNIX: **"Всё есть файл"** (или если точнее, "Всё имеет файловый интерфейс").
Жесткий диск, текстовый документ, клавиатура, сетевое соединение, мышь, межпроцессный pipe — ядро предоставляет программам абстракцию файла. Чтобы прочитать или записать данные в любую из этих сущностей, процесс получает **Файловый Дескриптор (File Descriptor, FD)**.

Файловый дескриптор — это просто неотрицательное целое число (0, 1, 2, 3...), которое служит индексом в таблице открытых файлов конкретного процесса.

По умолчанию у каждого процесса при запуске есть 3 стандартных дескриптора:
- `0` — **stdin** (стандартный ввод)
- `1` — **stdout** (стандартный вывод)
- `2` — **stderr** (стандартный поток ошибок)

## 2. Жизненный цикл FD и таблица дескрипторов

Когда процесс делает системный вызов `open()`, ядро проверяет права доступа, создает структуры данных в памяти и возвращает процессу новый FD (число, например `3`).

У каждого процесса есть **лимит на количество открытых файлов** (`ulimit -n` или `LimitNOFILE` в systemd). Обычно это 1024, чего критически мало для высоконагруженных веб-серверов или баз данных. Если процесс попытается открыть 1025-й файл/сокет, ядро вернет ошибку `Too many open files` (EMFILE).

Увидеть все дескрипторы процесса можно через псевдо-файловую систему:
`ls -la /proc/<PID>/fd/` (там лежат симлинки на реальные файлы или сокеты `socket:[12345]`).

## 3. Модели ввода-вывода (I/O Models)

Чтение данных (например, из сети) состоит из двух фаз:
1. Ожидание данных в буфере ядра (сетевая карта получает пакеты).
2. Копирование данных из буфера ядра в буфер приложения (User Space).

**1. Blocking I/O (Блокирующий):** По умолчанию. Приложение делает `read()` и полностью засыпает (переходит в Sleep state), пока данные не придут. Проблема: нельзя делать ничего другого.
**2. Non-blocking I/O (Неблокирующий):** Приложение делает `read()`. Если данных нет, ядро мгновенно возвращает ошибку `EAGAIN` или `EWOULDBLOCK`. Приложение не спит, но вынуждено постоянно спамить ядро вызовами (polling) в цикле, тратя 100% CPU. Это неэффективно.
**3. Asynchronous I/O (AIO / io_uring):** Приложение говорит "прочитай данные и сообщи мне, когда закончишь", а само идет заниматься своими делами. Самый быстрый, но сложный в реализации метод (в Linux новый стандарт — `io_uring`).

## 4. Мультиплексирование I/O: select, poll, epoll

Что если у вас Nginx, который держит 100 000 открытых подключений (100k FD)? Создавать 100 000 потоков (threads) с Blocking I/O убьет сервер (контекст-свитчи съедят весь CPU). 

Нужно **мультиплексирование**: один поток просит ядро "разбуди меня, если хоть на одном из этих 100 000 FD появятся данные".

- **`select()` / `poll()`** (Устаревшие): Приложение передает ядру весь список из 100 000 FD при *каждом* вызове. Ядро пробегает по всему списку (O(N)), и возвращает его обратно. Очень медленно при большом числе соединений. У `select` есть хард-лимит в 1024 FD.
- **`epoll()`** (Современный Linux стандарт): Приложение регистрирует свои FD в ядре один раз (`epoll_ctl`). Ядро само следит за событиями (через аппаратные прерывания) и кладет готовые FD в очередь (red-black tree). При вызове `epoll_wait()` приложение мгновенно забирает только те FD, где реально появились данные (О(1) или О(активных FD)). Nginx, Redis, Node.js работают именно на `epoll`.

## 5. Сетевые Сокеты (Sockets)

Сокет — это конечная точка (endpoint) сетевого взаимодействия. Для ядра это такой же файловый дескриптор.
Жизненный цикл серверного TCP сокета:
1. `socket()` — создать FD.
2. `bind()` — привязать к IP и Порту (например 0.0.0.0:80).
3. `listen()` — перевести сокет в режим ожидания (появляется backlog очередь).
4. `accept()` — забрать новое подключение. **Важно:** `accept` возвращает *совершенно новый* файловый дескриптор для общения с конкретным клиентом. Старый сокет (порт 80) продолжает слушать новые подключения.

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Что означает ошибка "Too many open files"? Как её исправить на современном сервере?**
*Ответ:* Процесс исчерпал свой лимит файловых дескрипторов (FD). В Linux всё есть файл (сокеты, коннекты к БД, файлы логов), поэтому веб-сервер при 1025-м подключении упадет с этой ошибкой, если лимит (soft limit) равен 1024. Исправляется изменением `LimitNOFILE=65535` в unit-файле systemd этого сервиса (или через `/etc/security/limits.conf` для шелл-сессий).

**2. В чем разница между `stdout` (1) и `stderr` (2), и как перенаправить ошибки в тот же лог-файл в bash?**
*Ответ:* И то, и другое выводит текст на экран терминала, но ядро различает эти потоки (FD 1 и FD 2). Это нужно, чтобы можно было перенаправить "полезный" вывод в пайп или файл, а ошибки оставить на экране. Для перенаправления `stderr` туда же, куда и `stdout`, используют конструкцию `2>&1` (например, `command > log.txt 2>&1`).

**3. Как Nginx может обслуживать 50 000 одновременных подключений, используя всего 4 worker-процесса?**
*Ответ:* Благодаря механизму мультиплексирования I/O, а именно системному вызову `epoll` в Linux. Nginx не создает отдельный поток на каждого клиента (как это делает старый Apache). Рабочий процесс делает сокеты неблокирующими, регистрирует их в `epoll` и засыпает. Когда ядро сообщает, что на каких-то сокетах появились данные, worker просыпается, быстро их обрабатывает и снова ждет. Это событийно-ориентированная архитектура (Event Loop).

**4. В чем архитектурная разница между `select()` и `epoll()`?**
*Ответ:* `select()` при каждом вызове копирует весь массив файловых дескрипторов из User Space в Kernel Space, ядро линейно проверяет их все (O(N)), и копирует массив обратно. При 10,000 соединений это колоссальный оверхед. `epoll` хранит состояние внутри ядра. Приложение только подписывается на новые сокеты, а когда данные приходят, забирает из ядра только список тех дескрипторов, в которых реально есть данные, без линейного перебора (O(1)).

**5. Что произойдет, если два процесса попытаются читать один и тот же файл одновременно?**
*Ответ:* Чтение пройдет успешно для обоих. Каждый процесс делает системный вызов `open()` и получает **собственный File Object** внутри ядра со своим собственным указателем смещения (offset). Они будут читать данные независимо друг от друга, даже с разной скоростью.

**6. Что такое Pipe (Пайп) под капотом ядра?**
*Ответ:* Pipe (канал) — это механизм IPC. Под капотом это кольцевой буфер (обычно 64 КБ) в оперативной памяти (в пространстве ядра), у которого есть два конца: один файловый дескриптор только для чтения, другой только для записи. Данные пишутся на одном конце и извлекаются на другом в порядке FIFO (First In, First Out). На диск эти данные не попадают.

**7. Объясните жизненный цикл сокета на сервере при приеме TCP-подключения (системные вызовы).**
*Ответ:* Сервер вызывает `socket()` для создания дескриптора, затем `bind()`, чтобы занять порт (например, 80). Затем `listen()` создает очередь (backlog) для входящих SYN-пакетов. Когда клиент устанавливает TCP-handshake, сервер вызывает `accept()`. В этот момент ядро отдает приложению **новый** файловый дескриптор, привязанный конкретно к этому клиенту. Исходный слушающий сокет продолжает висеть на 80 порту и принимать новые соединения.

**8. Если приложение не успевает вызывать `accept()`, что происходит с новыми входящими TCP-запросами?**
*Ответ:* Соединения скапливаются в очереди, размер которой задается параметром `backlog` в вызове `listen()`, и ограничивается параметром ядра `net.core.somaxconn`. Если очередь переполняется (syn flood или тормозящее приложение), ядро начинает отбрасывать (drop) новые пакеты, и клиенты видят таймауты подключения.

**9. Разница между блокирующим (Blocking) и неблокирующим (Non-blocking) сокетом?**
*Ответ:* Вызов `read()` на блокирующем сокете усыпит процесс до тех пор, пока из сети не придут пакеты. Вызов `read()` на неблокирующем сокете вернет данные, если они уже есть в буфере ядра, а если их нет — мгновенно вернет ошибку `EAGAIN / EWOULDBLOCK`, позволяя процессу продолжить свою работу и не висеть в ожидании.

**10. Можно ли передать открытый файловый дескриптор другому процессу?**
*Ответ:* При использовании `fork()` дочерний процесс автоматически наследует копии всех открытых дескрипторов родителя (с общими смещениями/оффсетами). Передать дескриптор *уже запущенному неродственному* процессу сложнее, но возможно — это делается через отправку специальных управляющих сообщений (`SCM_RIGHTS`) через UNIX-доменные сокеты.
