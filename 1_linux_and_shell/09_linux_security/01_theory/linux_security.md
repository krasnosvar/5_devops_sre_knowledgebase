## 1. UID/GID и классические права: SUID/SGID/sticky bit, ACL

Каждый процесс в Linux имеет реальный (`ruid`) и эффективный (`euid`) UID. Ядро проверяет права доступа именно по эффективному UID — на этом построена вся модель повышения привилегий.

**Специальные биты прав:**
- **SUID (`chmod u+s`)**: при запуске бинарника процесс получает `euid` владельца файла, а не запустившего пользователя. Так работает `passwd` (обычный пользователь должен уметь писать в `/etc/shadow`, которым владеет root).
- **SGID (`chmod g+s`)**: то же самое, но для группы. На каталоге SGID означает, что новые файлы наследуют группу каталога, а не основную группу создателя — так делают общие рабочие директории.
- **Sticky bit (`chmod +t`)**: на каталоге разрешает удалять файл только его владельцу (или root), даже если у остальных есть право записи в каталог. Классика — `/tmp` (`drwxrwxrwt`).

SUID-бинарники — стандартный вектор privilege escalation: если бинарник с SUID root имеет баг (или можно подсунуть ему переменные окружения/аргументы), можно выполнить произвольный код от root. Поэтому аудит `find / -perm -4000` — первый шаг pentest'а и первый шаг hardening'а (см. упражнение 01).

**ACL (Access Control List, `setfacl`/`getfacl`)**: классические права `rwx` для owner/group/other не позволяют дать права конкретному второму пользователю или группе без создания отдельной группы. ACL решает это точечно:
```bash
setfacl -m u:alice:rx /opt/app/config.yaml   # alice может читать файл, не входя в его группу
getfacl /opt/app/config.yaml
```

## 2. sudo и PAM: как на самом деле работает аутентификация

`sudo` — это не отдельный механизм, а SUID-бинарник (владелец root), который сверяется с политикой в `/etc/sudoers` (редактировать только через `visudo` — валидирует синтаксис перед сохранением, иначе можно необратимо сломать sudo для всех).

Аутентификация пользователя (пароль, отпечаток, 2FA) в Linux не встроена в каждую программу отдельно — за это отвечает **PAM (Pluggable Authentication Modules)**. `sudo`, `sshd`, `login`, `su` — все они просто вызывают PAM-стек, описанный в `/etc/pam.d/<имя-сервиса>`.

Ключевые модули:
- `pam_unix.so` — проверка пароля через `/etc/shadow`.
- `pam_faillock.so` — блокировка аккаунта после N неудачных попыток (защита от brute-force).
- `pam_limits.so` — применяет лимиты из `/etc/security/limits.conf` (ulimit на процессы пользователя — nofile, nproc).
- `pam_google_authenticator.so` — 2FA (TOTP) поверх пароля.

Практическое следствие: если нужно добавить 2FA для SSH-логина, правильное место — не `sshd_config`, а PAM-стек `/etc/pam.d/sshd` (плюс `ChallengeResponseAuthentication yes` в sshd_config).

**Правила `sudoers`, о которых часто забывают:**
```
# Плохо: полный root без пароля
alice ALL=(ALL) NOPASSWD: ALL

# Хорошо: конкретная команда, конкретному пользователю
deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart myapp.service
```
Wildcard `NOPASSWD: ALL` в sudoers эквивалентен выдаче root-пароля — это то же самое, что убрать sudo вообще.

## 3. SSH hardening

`sshd_config` по умолчанию (особенно на старых дистрибутивах) далёк от безопасного. Минимальный чеклист:

```
PermitRootLogin no              # root никогда не логинится напрямую по SSH
PasswordAuthentication no        # только ключи, брутфорс пароля бессмысленен
PubkeyAuthentication yes
AllowUsers deploy alice          # белый список — вместо блокировки всех остальных
MaxAuthTries 3                   # обрубить попытки подбора в рамках одной сессии
ClientAliveInterval 300          # закрыть подвисшие сессии
ClientAliveCountMax 2
X11Forwarding no                 # если не нужен GUI-форвардинг
```

`PermitRootLogin no` не значит "нельзя стать root" — это значит "нельзя *залогиниться* как root по SSH". Администратор заходит своим пользователем и повышает права через `sudo`, оставляя аудиторский след (kто именно выполнил команду), в отличие от общего root-логина.

**fail2ban** — не замена правильному конфигу, а дополнительный слой: парсит `journalctl`/`/var/log/auth.log`, считает неудачные попытки логина с IP и добавляет временный `iptables`/`nftables` DROP-правило для этого IP. Защищает не от целевой атаки, а от массового автоматического перебора ботами.

## 4. Mandatory Access Control: SELinux vs AppArmor

Классические UNIX-права (DAC — Discretionary Access Control) отвечают на вопрос "кто владелец файла и что ему разрешено". Проблема: если процесс скомпрометирован (RCE в веб-сервере), он получает **все** права своего владельца — DAC не ограничивает, что именно процесс *должен* делать.

**MAC (Mandatory Access Control)** добавляет второй, независимый от DAC слой: даже если DAC разрешает доступ, MAC может его запретить.

- **SELinux** (RHEL/CentOS/Fedora): каждому процессу и файлу присваивается **контекст** (`user:role:type:level`, например `httpd_t`). Политика описывает, какой `type` процесса может обращаться к какому `type` файла. Даже если `nginx` (запущенный от root по ошибке) технически может прочитать `/etc/shadow` по DAC, политика SELinux заблокирует это, потому что `httpd_t` не имеет права на `shadow_t`.
  ```bash
  getenforce                      # Enforcing / Permissive / Disabled
  ls -Z /var/www/html             # посмотреть контексты файлов
  ausearch -m avc -ts recent      # найти, что именно заблокировал SELinux (см. auditd ниже)
  ```
- **AppArmor** (Debian/Ubuntu/SUSE): проще концептуально — профиль привязан не к типам, а напрямую к **пути бинарника** и описывает, к каким путям файловой системы и capabilities этот конкретный процесс имеет доступ.
  ```bash
  aa-status                       # какие профили загружены и в каком режиме
  aa-genprof /usr/sbin/myapp      # сгенерировать черновик профиля по логам
  aa-enforce /etc/apparmor.d/usr.sbin.myapp
  ```

Оба режима имеют `enforcing`/`permissive` (SELinux) или `enforce`/`complain` (AppArmor) — режим логирования нарушений без блокировки, обязательный этап перед включением enforce в проде: сначала смотрят, что бы заблокировалось, потом включают блокировку.

## 5. auditd: аудит на уровне syscalls

`auditd` — демон ядра Linux, который логирует системные вызовы по правилам (`auditctl`/`/etc/audit/rules.d/`). В отличие от `journald` (логи приложений) или `sshd`-логов (события конкретного сервиса), auditd видит **любое** обращение к файлу или вызов syscall, независимо от того, какой процесс это сделал.

```bash
# Следить за изменениями конкретного файла
auditctl -w /etc/shadow -p wa -k shadow_changes

# Следить за всеми попытками смены прав доступа (chmod/chown) в системе
auditctl -a always,exit -F arch=b64 -S chmod,fchmod,chown -k perm_changes

# Посмотреть, кто и когда трогал файл
ausearch -k shadow_changes

# Человекочитаемая сводка
aureport -f -i
```

Практическое применение: инцидент "кто-то изменил sudoers на проде" расследуется не по логам приложения (их нет), а именно через `auditctl -w /etc/sudoers -p wa` + `ausearch`. Это же используется для расследования того, что заблокировал SELinux/AppArmor (`avc: denied` события идут через тот же аудит-лог).

## 6. Kernel hardening: sysctl и systemd sandboxing

**sysctl** — рантайм-параметры ядра (`/proc/sys/`), часть из которых напрямую влияет на защиту:

```bash
# ASLR (Address Space Layout Randomization) — обязателен, рандомизирует адреса в памяти
kernel.randomize_va_space = 2

# Запретить ptrace одним непривилегированным процессом другого (кроме своих детей)
kernel.yama.ptrace_scope = 1

# Защита от IP spoofing (reverse path filtering)
net.ipv4.conf.all.rp_filter = 1

# Не принимать ICMP redirect — защита от MITM на уровне сети
net.ipv4.conf.all.accept_redirects = 0

# Игнорировать broadcast ICMP (защита от Smurf-атак)
net.ipv4.icmp_echo_ignore_broadcasts = 1
```
Постоянные значения задаются в `/etc/sysctl.d/99-hardening.conf` и применяются `sysctl --system`. Это ровно тот же механизм, который k8s выставляет через `securityContext.sysctls` в поде — sysctl неk8s-специфичен, это ядро хоста (или контейнера, если namespaced sysctl).

**systemd sandboxing** — большинство security-директив, которые видно в проде, лежат не в отдельном security-модуле, а прямо в unit-файле сервиса (см. [`../05_systemd/`](../../05_systemd/)):
```ini
[Service]
NoNewPrivileges=true        # процесс не может повысить привилегии через SUID/SGID (аналог allowPrivilegeEscalation: false в k8s)
ProtectSystem=strict        # весь / доступен только на чтение
ProtectHome=true            # /home, /root, /run/user недоступны сервису
PrivateTmp=true             # свой изолированный /tmp (mount namespace)
ProtectKernelModules=true   # запрет загрузки/выгрузки модулей ядра
RestrictAddressFamilies=AF_INET AF_INET6   # запрет unix-сокетов, netlink и т.д., если не нужны
```
Это тот же принцип "минимальных привилегий", что и Pod Security Standards в Kubernetes — только systemd применяет его к обычным сервисам на хосте, без контейнеров.

## 7. Типовые вопросы на собеседовании (Interview Q&A)

**1. Зачем нужен SUID-бит на бинарнике `passwd`, если это потенциальная дыра в безопасности?**
*Ответ:* Обычный пользователь не имеет прав на запись в `/etc/shadow` (владелец — root, права `640`). Но пользователю нужно уметь менять свой собственный пароль. SUID на `passwd` временно повышает эффективный UID процесса до владельца файла (root) на время выполнения именно этого бинарника — сам бинарник при этом написан так, чтобы разрешать менять только пароль вызвавшего пользователя, а не производить произвольные операции. Это компромисс: узкий, тщательно проверенный код получает root ровно на одну операцию, вместо выдачи пользователю полного root-доступа.

**2. В чём разница между `PermitRootLogin no` в sshd_config и реальным запретом root пользоваться системой?**
*Ответ:* `PermitRootLogin no` запрещает только *интерактивный вход* по SSH напрямую от имени root. Пользователь root по-прежнему существует, у него есть пароль/хэш в `/etc/shadow`, и через `sudo -i` или `su -` любой авторизованный администратор может получить root-шелл. Смысл настройки — не убрать root, а заставить каждого администратора логиниться под своим именем и повышать права осознанно, оставляя аудиторский след в auth.log/journald о том, кто именно выполнил привилегированное действие.

**3. Сервер поставлен без SELinux (`Disabled`). Администратор поменял на `Enforcing` через `setenforce 1` и перезагрузил сервер — часть сервисов перестала стартовать. В чём типичная причина и как её избежать?**
*Ответ:* Когда SELinux отключен, при создании и изменении файлов не проставляются security-контексты — они либо отсутствуют, либо становятся некорректными (`unlabeled_t`). При резком включении `Enforcing` политика начинает блокировать доступ процессов к файлам с неправильным контекстом. Правильная процедура: сначала включить режим `Permissive` (логирует нарушения, но не блокирует), прогнать все сценарии использования системы, посмотреть через `ausearch -m avc` какие `avc: denied` накопились, восстановить корректные контексты (`restorecon -Rv /path`), и только потом переключаться в `Enforcing`.

**4. Чем принципиально отличается модель политик AppArmor от SELinux?**
*Ответ:* SELinux строит политику вокруг абстрактных **типов** (`type`) — контекст присваивается и процессу, и файлу, а политика описывает связи между типами независимо от конкретных путей. Это мощнее, но сложнее в написании и отладке. AppArmor привязывает профиль напрямую к **пути исполняемого файла** и описывает разрешённые пути и capabilities простым, читаемым синтаксисом. За гибкость SELinux платит сложностью; за простоту AppArmor платит меньшей выразительностью (например, сложнее описывать политику для процессов с одинаковым путём, но разным поведением).

**5. В чём разница между политикой sudoers `NOPASSWD: ALL` и полным отсутствием sudo для пользователя?**
*Ответ:* `NOPASSWD: ALL` — это фактически выдача пользователю root-доступа без единого барьера: он может выполнить любую команду от root без ввода пароля, включая `sudo su -`, после чего у него полноценный root-шелл. Разница с "дать пароль root напрямую" — только в том, что действия остаются привязаны к его логину в auth.log (пока он не станет root явно). Единственный безопасный паттерн — точечные правила: конкретная команда, конкретному пользователю, желательно с полным путём к бинарнику, чтобы нельзя было подставить свой скрипт с тем же именем через PATH.

**6. Зачем нужен auditd, если у systemd уже есть journald, который логирует запуск и остановку сервисов?**
*Ответ:* journald логирует то, что сервис сам решил вывести в stdout/stderr, и события жизненного цикла unit'ов systemd. auditd работает на уровне ядра и видит **syscalls** — обращения к файлам, смену прав, попытки chmod/chown, exec — вне зависимости от того, какое приложение их сделало и логирует ли оно что-то само. Это единственный способ достоверно ответить на вопрос "кто и когда читал /etc/shadow" или "какой процесс изменил /etc/sudoers", если сам процесс не пишет об этом в свои логи (а вредоносный процесс точно не будет).

**7. Что делает sysctl-параметр `kernel.yama.ptrace_scope = 1` и от какой атаки он защищает?**
*Ответ:* `ptrace` позволяет одному процессу инспектировать память другого (читать регистры, переменные, даже инжектить код) — это легитимный механизм для отладчиков (gdb, strace). Значение `0` разрешает любому процессу пользователя делать ptrace над любым другим процессом того же пользователя. Значение `1` (рекомендуемое по умолчанию в современных дистрибутивах) разрешает ptrace только процессу-родителю над своими прямыми потомками. Это защищает от атак, где скомпрометированный процесс (например, через уязвимость в браузере) пытается через ptrace вытащить пароли из памяти соседнего процесса того же пользователя (например, ssh-agent).

**8. В чём разница между директивами `Requires=`/`After=` в systemd unit-файлах (управление зависимостями) и security-директивами вроде `ProtectSystem=strict`?**
*Ответ:* `Requires=`/`After=` управляют **порядком запуска и зависимостями** между сервисами — это про то, когда и в каком порядке стартовать юниты. `ProtectSystem=strict`, `NoNewPrivileges=true`, `PrivateTmp=true` и подобные — это **security sandboxing**, ограничивающий, что уже запущенный процесс может делать с файловой системой, привилегиями и ресурсами ядра. Первое отвечает за оркестрацию запуска, второе — за уменьшение поверхности атаки конкретного сервиса, вне зависимости от того, когда он стартовал.

**9. ACL (`setfacl`) кажутся более гибкими, чем классические Unix-права. Почему тогда классическая модель `rwx` для owner/group/other до сих пор основная?**
*Ответ:* Классическая модель компактна (хранится прямо в inode, 9 бит), быстро проверяется ядром и понятна всем UNIX-инструментам "из коробки". ACL решают конкретную точечную проблему (дать доступ ещё одному пользователю/группе без создания новой Unix-группы), но требуют файловой системы с поддержкой extended attributes, чуть медленнее в проверке и не все инструменты их учитывают одинаково корректно при копировании/архивации (`cp -p`, `tar` без специальных флагов могут потерять ACL). Поэтому ACL используют точечно, поверх базовой модели, а не вместо неё.

**10. AppArmor-профиль сервиса стоит в режиме `complain`. Разработчик утверждает, что "AppArmor включён и защищает сервис". Прав ли он?**
*Ответ:* Нет. В режиме `complain` AppArmor только логирует нарушения политики (что было бы заблокировано), но **не блокирует** ни одно действие — это диагностический режим для настройки профиля перед включением защиты. Реальную защиту даёт только режим `enforce` (аналог `Enforcing` в SELinux). Разработчик путает "профиль загружен и видим в `aa-status`" с "профиль реально ограничивает процесс" — это разные вещи, и подмена одного другим — частая причина ложного чувства защищённости в проде.
