# Ответы — упражнения "Пользователи, группы, ACL"

## Ответ 01
```
alice:x:1000:1000:Alice Smith:/home/alice:/bin/bash
svc_backup:x:999:999::/home/svc_backup:/usr/sbin/nologin
```
`alice` создана обычным `useradd -m` — UID берётся из диапазона `UID_MIN`/`UID_MAX` в `/etc/login.defs` (обычно 1000-60000). `svc_backup` создана с флагом `-r` — UID берётся из диапазона `SYS_UID_MIN`/`SYS_UID_MAX` (обычно ниже 1000, в примере получила 999). Это не два случайных числа, а сознательный, настраиваемый в `login.defs` водораздел между "живыми людьми" и "сервисными аккаунтами".

## Ответ 02
После `usermod -G developers alice` (без `-a`) вывод `id alice` покажет `groups=1000(alice),1002(developers)` — группа `docker` **исчезла**. `-G` без `-a` заменяет весь список supplementary-групп на переданный список целиком, а не добавляет к нему. Восстановить: `usermod -aG docker alice` ещё раз (теперь уже с `-a`).

## Ответ 03
```
alice        <- id -gn ДО newgrp (primary group = alice)
developers   <- id -gn ПОСЛЕ newgrp developers
-rw-rw-r--. 1 alice developers 0 ... /tmp/f_via_newgrp
```
Файл `f_via_newgrp` получил группу-владельца `developers`, а не `alice` — `newgrp developers` временно подменяет ТЕКУЩУЮ (primary) группу процесса на `developers` для всех команд внутри этой сессии/подшелла, включая то, какая группа станет владельцем НОВЫХ файлов. Сама учётная запись alice при этом не меняется — это временное состояние конкретного процесса, а не постоянное изменение группы пользователя (постоянные supplementary-группы правятся только через `usermod -aG`).

## Ответ 04
`report.txt` уже содержит ACL-запись для alice, потому что на директории `/opt/shared/` была установлена **default ACL** (`setfacl -d -m ...`). Default ACL не даёт прав на саму директорию напрямую — это шаблон, автоматически копирующийся в ACL любого НОВОГО файла/поддиректории, создаваемых внутри, начиная с момента установки. Файлы, созданные ДО установки default ACL, её не получат — наследование работает только вперёд по времени.

## Ответ 05
После `setfacl -m mask::r-- /opt/config.yaml`, `getfacl` покажет для alice:
```
user:alice:rwx	#effective:r--
```
Сама ACL-запись alice (`rwx`) физически не изменилась — но `mask` ограничивает ЭФФЕКТИВНЫЕ права всех именованных записей (кроме owner/other) сверху. Чтобы вернуть alice реальные `rwx`, не трогая её персональную запись, нужно поднять сам mask: `setfacl -m mask::rwx /opt/config.yaml`. Частая практическая ловушка — обычный `chmod g-w file` на файле с ACL меняет именно mask, а не права владельца-группы напрямую, что выглядит так, будто ACL "перестала работать".
