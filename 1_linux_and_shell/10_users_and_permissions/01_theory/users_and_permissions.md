## 1. /etc/passwd, /etc/shadow, /etc/group: анатомия учётной записи

```
# /etc/passwd — один пользователь на строку, 7 полей через ":"
alice:x:1000:1000:Alice Smith,,,:/home/alice:/bin/bash
#     ^ ^    ^    ^              ^            ^
#     |  UID GID  GECOS          home        login shell
#     пароль (историческое место, см. ниже)
```

Поле пароля в `/etc/passwd` всегда `x` — сам хэш переехал в `/etc/shadow`, который читается **только root**:
```
alice:$6$rounds=...hash...:19800:0:99999:7:::
#     ^                    ^     ^ ^     ^
#     хэш (SHA-512, $6$)   |     | |     warn (за сколько дней предупредить)
#     дата последней смены (дни от 1970) | max age (дней)
#                                min age
```
`/etc/passwd` должен оставаться доступным на чтение всем (`ls -l` каждый раз резолвит UID в имя через него), а хэш пароля — секрет, поэтому его физически вынесли в отдельный файл с правами `640 root:shadow`.

`/etc/group` — тем же принципом, но для групп:
```
docker:x:998:alice,bob
#      gid  список участников (supplementary, см. §3)
```

## 2. useradd/usermod/userdel: системные vs логин-пользователи

UID не выбирается произвольно — диапазоны заданы в `/etc/login.defs` (`UID_MIN`/`UID_MAX`, обычно 1000-60000 для обычных пользователей):
- `0` — root, всегда.
- `1-999` (или `1-99` в старых схемах) — **системные** учётные записи для демонов (`www-data`, `postgres`, `nginx`) — не предназначены для интерактивного входа.
- `1000+` — обычные логин-пользователи (реальные люди).

```bash
useradd -m -s /bin/bash -c "Alice Smith" alice   # -m: создать домашнюю директорию из /etc/skel
useradd -r -s /usr/sbin/nologin svc_backup       # -r: системный аккаунт (низкий UID, без интерактивного входа)
userdel -r alice                                  # -r: удалить и домашнюю директорию, и mail spool
```

`/usr/sbin/nologin` вместо шелла — вежливый отказ ("This account is currently not available.") при попытке войти, в отличие от `/bin/false` (тоже блокирует логин, но молча, без сообщения) — оба одинаково НЕ дают интерактивный шелл, `nologin` просто явно документирует намерение в логах.

`/etc/skel/` — шаблон: всё, что там лежит (`.bashrc`, `.profile`), копируется в домашнюю директорию нового пользователя при `useradd -m`.

## 3. Primary vs supplementary группы: ловушка usermod -G

У пользователя ровно одна **primary group** (записана в `/etc/passwd`, используется как группа-владелец для НОВЫХ файлов по умолчанию) и ноль или больше **supplementary groups** (список в `/etc/group`, дают дополнительные права — например, группа `docker` дающая доступ к `/var/run/docker.sock`).

```bash
usermod -aG docker alice     # -a (append!) добавить alice В docker, сохранив остальные группы
usermod -G docker alice      # БЕЗ -a: ЗАМЕНИТЬ весь список supplementary-групп alice на ["docker"]
```
Пропущенный `-a` — одна из самых частых практических ошибок в реальных runbook'ах: пользователь молча теряет членство во всех остальных группах (`sudo`, `adm`, и т.д.), кроме той, что вы только что добавили.

Изменение группы применяется только к НОВЫМ процессам пользователя — уже открытая shell-сессия не увидит новую группу, пока пользователь не перелогинится или не выполнит `newgrp docker` (временно "переключает" текущую сессию на указанную группу без выхода).

## 4. NSS: откуда ОС на самом деле берёт пользователей

Утилиты вроде `useradd`/`getent`/`id` не читают `/etc/passwd` напрямую в обход системного механизма — они идут через **NSS (Name Service Switch)**, настроенный в `/etc/nsswitch.conf`:
```
passwd: files sss
group:  files sss
```
Порядок источников читается слева направо: сначала локальные файлы (`files` → `/etc/passwd`), затем, если не найдено — `sss` (SSSD, обычно проксирует в LDAP/Active Directory/FreeIPA). Именно поэтому `getent passwd alice` — правильный способ проверить существование пользователя (учитывает ВСЕ источники NSS), а `grep alice /etc/passwd` покажет только локальных пользователей и ничего не скажет про доменных.

```bash
getent passwd alice     # найдёт alice, откуда бы она ни резолвилась (локально или через SSSD/LDAP)
id alice                 # UID, GID, все группы — тоже через NSS
```

## 5. ACL по-настоящему: default ACL, mask, POSIX vs NFSv4

Классические права `rwx` (owner/group/other) не могут дать точечный доступ ВТОРОМУ конкретному пользователю без создания отдельной группы под каждый такой случай. **POSIX ACL** решает это:

```bash
setfacl -m u:alice:rx /opt/app/config.yaml    # alice читает файл, не входя в его группу
getfacl /opt/app/config.yaml                   # посмотреть все ACL-записи файла
```

**Default ACL** (флаг `-d`) — задаётся на директории и автоматически наследуется всеми НОВЫМИ файлами/поддиректориями, создаваемыми внутри (обычные ACL на директории только контролируют доступ К САМОЙ директории, не влияя на её будущее содержимое):
```bash
setfacl -d -m u:alice:rx /opt/shared/          # alice получит rx на КАЖДЫЙ новый файл внутри /opt/shared/
setfacl -R -m u:alice:rx /opt/shared/          # применить рекурсивно к УЖЕ существующим файлам
```

**mask** — верхняя граница эффективных прав для всех именованных ACL-записей (кроме owner и other) одновременно:
```bash
setfacl -m mask::r-- /opt/app/config.yaml
# теперь ДАЖЕ ЕСЛИ у alice в ACL записано rwx, эффективно у неё останется только r--
```
`mask` часто меняется незаметно при обычном `chmod g-w` (chmod на файле с ACL двигает именно mask, а не права владельца-группы напрямую) — частый источник "я же давал права через setfacl, а они не работают".

**POSIX ACL vs NFSv4 ACL**: POSIX ACL (описанный выше) — набор из allow-only записей, без явного deny и без гибкого наследования разных типов (только "default" для директорий целиком). NFSv4 ACL (используется в ZFS, поддерживается в NFSv4-протоколе) выразительнее: явные ALLOW/DENY на каждую запись, тонкая настройка наследования (только для файлов/только для директорий/не наследовать) — но менее распространён в типичном Linux-дистрибутиве вне NFS/ZFS-контекста.

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему `/etc/passwd` должен оставаться доступным на чтение всем пользователям системы, если он хранит информацию об учётных записях?**
*Ответ:* Огромное количество обычных операций (`ls -l`, `ps aux`, любая программа, резолвящая UID процесса в читаемое имя) должно уметь превратить числовой UID в имя пользователя БЕЗ привилегий root — для этого нужен доступ на чтение к `/etc/passwd`. Именно поэтому исторически опасное поле (хэш пароля) было вынесено в отдельный файл `/etc/shadow` с правами `640 root:shadow` — сама структура учётных записей осталась публично читаемой, а секрет (хэш) закрыт.

**2. Администратор выполнил `usermod -G developers alice`, ожидая ДОБАВИТЬ alice в группу developers. После этого alice перестала иметь доступ к Docker (была в группе docker). Что произошло?**
*Ответ:* Без флага `-a` (append) команда `usermod -G` **заменяет** весь список supplementary-групп пользователя на переданный, а не добавляет к существующему. `alice` была в группах `docker` и других — после `usermod -G developers alice` она осталась ТОЛЬКО в `developers`, потеряв членство во всех остальных группах, включая `docker`. Правильная команда — `usermod -aG developers alice` (append + group).

**3. Почему `grep username /etc/passwd` может не найти пользователя, который при этом успешно логинится по SSH и виден в `id username`?**
*Ответ:* Если пользователь приходит из внешнего источника (LDAP, Active Directory, FreeIPA через SSSD), его записи физически нет в локальном `/etc/passwd` — она резолвится динамически через NSS (`/etc/nsswitch.conf`, строка `passwd: files sss`). `grep`/`cat` читают только локальный файл, а `id`/`getent passwd` идут через полный NSS-стек и находят пользователя независимо от источника.

**4. В чём разница между обычной ACL-записью на директории и default ACL на той же директории?**
*Ответ:* Обычная ACL-запись (`setfacl -m u:alice:rx /dir/`) контролирует доступ только К САМОЙ директории (можно ли alice туда зайти, посмотреть список файлов) — она никак не влияет на права НОВЫХ файлов, которые кто-то создаст внутри. Default ACL (`setfacl -d -m u:alice:rx /dir/`) — это шаблон, который автоматически наследуется каждым новым файлом/поддиректорией, создаваемой внутри `/dir/`, начиная с момента установки — без него пришлось бы вручную прописывать ACL на каждый новый файл отдельно.

**5. Вы дали пользователю alice через ACL права `rwx` на файл (`setfacl -m u:alice:rwx file`), но она всё равно не может в него писать. В чём может быть причина?**
*Ответ:* Скорее всего, эффективные права ограничены значением `mask` файла — mask задаёт верхнюю границу для ВСЕХ именованных ACL-записей (кроме владельца и other) одновременно, независимо от того, что записано в конкретной ACL-записи пользователя. Если `mask::r--`, alice эффективно получит только чтение, даже если её персональная ACL-запись говорит `rwx`. Проверяется и правится через `getfacl`/`setfacl -m mask::rwx file`.

**6. Зачем нужен `/usr/sbin/nologin` как shell пользователя, если можно было бы просто удалить у него право на SSH-логин через конфиг sshd?**
*Ответ:* `nologin` работает на уровне самой учётной записи (любой способ входа — SSH, локальная консоль, su) и не зависит от конфигурации конкретного сервиса. Ограничение через `sshd_config` защитило бы только SSH-доступ, но пользователь всё ещё смог бы, например, зайти через `su - servicename` локально или через другой механизм аутентификации. `nologin`-shell — универсальный, не зависящий от способа входа барьер именно для сервисных аккаунтов, которым интерактивный доступ вообще не нужен.

**7. Пользователя добавили в группу `docker` (`usermod -aG docker bob`), но `docker ps` в уже открытом терминале bob всё ещё выдаёт `permission denied`. Сессия — не свежая, есть ли способ подхватить группу без выхода из системы?**
*Ответ:* Список групп пользователя фиксируется в момент старта его сессии/шелла и не обновляется автоматически задним числом. Полный релогин — самый надёжный способ. Без выхода из текущей сессии можно временно переключиться на нужную группу командой `newgrp docker` (откроет новый подшелл с этой группой активной) — но это работает только в текущем терминале, а не глобально для всех процессов пользователя.

**8. Чем POSIX ACL принципиально уступает NFSv4 ACL в выразительности?**
*Ответ:* POSIX ACL поддерживает только allow-записи (нет явного DENY — единственный способ "запретить" — не выдавать право вообще) и упрощённое наследование (только один флаг "default" — наследуется директориями целиком на всё их будущее содержимое). NFSv4 ACL поддерживает явные ALLOW и DENY записи в одном списке с точным порядком приоритета, а также тонкую настройку наследования (например, "наследовать только файлам, но не поддиректориям", или "унаследовать один раз и не распространять дальше") — что ближе по возможностям к ACL в Windows NTFS, чем классический POSIX-вариант.

**9. Почему `useradd` для сервисного аккаунта (например, для демона мониторинга) обычно вызывают с флагом `-r`, а не как обычного пользователя?**
*Ответ:* Флаг `-r` создаёт системную учётную запись: UID берётся из отдельного диапазона (`SYS_UID_MIN`/`SYS_UID_MAX` в `/etc/login.defs`, обычно ниже 1000), что визуально и программно отличает сервисные аккаунты от людей при аудите (`awk -F: '$3<1000' /etc/passwd` мгновенно покажет все системные записи). Дополнительно `useradd -r` по умолчанию не создаёт домашнюю директорию и часто не требует expiry-политики пароля, применяемой к обычным пользователям.

**10. Файл имеет ACL-записи (`getfacl` показывает несколько `user:` строк), но простой `ls -l` этого никак не показывает. Как заметить, что у файла вообще есть ACL, глядя только на вывод `ls -l`?**
*Ответ:* `ls -l` добавляет символ `+` сразу после строки прав доступа (`rwxr-xr-x+`), если у файла есть дополнительные ACL-записи сверх классических owner/group/other. Отсутствие `+` гарантированно означает отсутствие ACL; наличие `+` — сигнал, что нужно проверить `getfacl`, чтобы увидеть полную картину — иначе легко ошибиться, посчитав видимые в `ls -l` права единственным источником правды о доступе к файлу.
