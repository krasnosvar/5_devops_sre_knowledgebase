## 1. Анатомия сбоев Pod: CrashLoopBackOff, OOMKilled и Probes

Когда под не переходит в статус `Running`, SRE обязан точно понимать цепочку
вызовов в связке `kubelet -> Container Runtime (CRI) -> Linux Kernel
(cgroups)`.

### 1.1 `CrashLoopBackOff`: причины и чтение артефактов
Статус `CrashLoopBackOff` — это не ошибка сама по себе, а сообщение от
Kubelet о том, что он пытается перезапустить контейнер, завершающийся с
ненулевым exit code или падающий сразу после старта, с экспоненциальной
задержкой (10s, 20s, 40s ... до 300s).

**Диагностический алгоритм:**
1. **Смотреть логи ПРЕДЫДУЩЕГО падения:**
   ```bash
   kubectl logs <pod-name> -c <container-name> --previous
   ```
Обычный `kubectl logs` часто возвращает пустоту или лог запуска нового, еще
не упавшего инстанса.
2. **Проверить причину завершения и Exit Code:**
   ```bash
   kubectl get pod <pod-name> -o jsonpath='{.status.containerStatuses[*].lastState.terminated}'
   ```
   - **Exit Code 1 / 2:** ошибка в логике приложения (невалидный конфиг,
     отсутствие переменной окружения, ошибка синтаксиса).
   - **Exit Code 137 (128 + 9):** принудительное завершение через `SIGKILL`
     (OOMKilled или принудительный таймаут grace period).
   - **Exit Code 143 (128 + 15):** штатное завершение по `SIGTERM` (kubelet
     выселяет под, но приложение не успело корректно завершиться).
   - **Exit Code 126:** контейнер не может выполнить команду (нет прав на
     исполнение, ошибка прав доступа).
   - **Exit Code 127:** бинарный файл не найден (ошибка в `command:` или
     `ENTRYPOINT`).

### 1.2 `OOMKilled`: cgroups v1 vs cgroups v2
Контейнер убивается ядром при превышении `resources.limits.memory`.
- **В cgroups v1:** ядро отслеживает память в файле `memory.limit_in_bytes`.
  При превышении лимита срабатывает OOM контроллер cgroups и шлет `SIGKILL`.
- **В cgroups v2:** структура унифицирована, метрика фиксируется в
  `memory.events: oom_kill <count>`.

```bash
# Диагностика OOMKilled событий в неймспейсе
kubectl get events --field-selector reason=OOMKilling --sort-by='.lastTimestamp'

# В describe пода ищем:
# Last State: Terminated
#   Reason: OOMKilled
#   Exit Code: 137
```

> [!IMPORTANT]
> Приложения на JVM или Go, запущенные на старых версиях рантайма, могут не
> определять лимиты cgroup контейнера и считывать `MemTotal` хостовой ноды.
> При лимите пода в 2 ГБ на 64 ГБ ноде JVM пытается аллоцировать 16 ГБ heap,
> мгновенно вызывая `OOMKilled`. Для Java обязательны флаги
> `-XX:+UseContainerSupport -XX:MaxRAMPercentage=75.0`.

### 1.3 Сбои Liveness, Readiness и Startup Probes
Путаница между проверками — одна из главных причин ложных деградаций в
проде:
- **Startup Probe:** блокирует все остальные пробы, пока приложение
  инициализируется (прогрев кэша, миграции БД). Если приложение стартует
  дольше `failureThreshold * periodSeconds`, kubelet убивает контейнер.
- **Liveness Probe:** проверяет, «живо» ли приложение. Если проверка падает:
  **Kubelet принудительно перезапускает контейнер**.
*Критическая ошибка:* вешать liveness probe на внешние зависимости (проверка
доступности БД или стороннего API). Если падает внешняя БД, liveness probe
убивает все поды бекенда, превращая частичную деградацию в полный каскадный
коллапс.
- **Readiness Probe:** проверяет, готово ли приложение принимать трафик.
  Если проверка падает: kubelet выставляет поду condition `Ready=False`,
  а **EndpointSlice controller** (в kube-controller-manager), увидев это,
  помечает endpoint пода как `ready: false` — kube-proxy и
  Ingress-контроллеры перестают слать на него трафик. Сам kubelet
  EndpointSlice не трогает. Контейнер НЕ перезапускается.

## 2. Проблемы планирования: отладка статуса Pending и предикатов Scheduler

Если под завис в статусе `Pending`, он даже не начал скачиваться на ноду.
Его судьба решается в цикле планирования `kube-scheduler`.

### 2.1 Фазы планировщика: Filtering и Scoring
Планировщик выполняет две стадии:
1. **Filtering (Предикаты):** отсеивает ноды, которые физически не подходят.
2. **Scoring (Приоритеты):** ранжирует оставшиеся ноды по оптимальности
   размещения.

Причина зависания пода в `Pending` всегда пишется прямым текстом в секции
`Events`:
```bash
kubectl describe pod <pending-pod-name> | grep -A 10 Events:
```

### 2.2 Четыре частые причины Pending:
1. **Недостаток ресурсов (`Insufficient cpu/memory`):**
`kube-scheduler` рассчитывает емкость ноды **только по сумме
`resources.requests`**, а не по реальной утилизации! Если на ноде сумма
requests равна 100% от Allocatable, планировщик отклонит под, даже если
физический процессор утилизирован всего на 5%.
2. **Конфликт Taints и Tolerations:**
Нода помечена `Taint` (например, `node.kubernetes.io/unreachable:NoSchedule`
или кастомным `dedicated=gpu:NoSchedule`), а у пода отсутствует
соответствующий `tolerations`.
3. **Невозможность привязать PersistentVolume (`FailedScheduling: 0/3 nodes
   available: 3 node(s) had volume node-affinity conflict`):**
Облачный диск (например, AWS EBS) создан в конкретной зоне доступности (`us-
east-1a`). Если поды пытаются запуститься на нодах в зоне `us-east-1b`,
планировщик заблокирует их планирование из-за топологических ограничений
CSI.
4. **Нарушение PodAntiAffinity / PodTopologySpreadConstraints:**
Указано жесткое правило `topologyKey: kubernetes.io/hostname` с
`requiredDuringSchedulingIgnoredDuringExecution`. Если реплик 5, а нод всего
3, оставшиеся 2 пода навсегда останутся в `Pending`.

## 3. Сбои Worker Node: Node NotReady, PLEG и Eviction

Когда с ноды перестают приходить heartbeat'ы, контроллер
`node-lifecycle-controller` по истечении `node-monitor-grace-period`
(порядка 40-50 секунд в зависимости от версии) помечает её `NotReady` и ставит
на неё taint
`NoExecute`. Это ещё не выселение — поды реально начинают вытесняться
только после ОТДЕЛЬНОГО тайм-аута терпимости к этому taint'у
(`tolerationSeconds`, по умолчанию около 5 минут), то есть у ноды есть
дополнительное время "на реабилитацию", прежде чем её поды уедут на
другие серверы.

```bash
# Просмотр причин неготовности нод
kubectl get nodes -o wide
kubectl describe node <node-name> | grep -A 8 Conditions:
```

### 3.1 PLEG (Pod Lifecycle Event Generator) is not healthy
Классический кошмар инженера:
`PLEG is not healthy: pleg was last seen active 3m ago; threshold is 3m0s`
**Что происходит:** Kubelet периодически опрашивает рантайм
(containerd/CRI-O) через gRPC-вызов `ListPodSandbox` и `ListContainers`,
чтобы синхронизировать состояние подов. Если рантайм не отвечает дольше 3
минут:
- PLEG объявляется нездоровым, kubelet помечает ноду как `NotReady`.
- **Первопричины:**
  - Высокая задержка дисковой подсистемы (`iowait` 100%) на системном диске,
    где лежит `/var/lib/containerd`.
  - Утечка дескрипторов или дэдлок в модулях cgroups v1 ядре при тысячах
    созданных/удаленных контейнеров.
  - Огромное количество зомби-контейнеров, заставляющих containerd
    сканировать тысячи объектов.

Диагностика на самой ноде:
```bash
# 1. Проверить статус демонов
systemctl status kubelet
systemctl status containerd

# 2. Посмотреть последние ошибки kubelet
journalctl -u kubelet -e --no-pager | tail -50

# 3. Проверить отзывчивость containerd напрямую через crictl
crictl pods
crictl ps
crictl stats
```

### 3.2 Kubelet Node Eviction (Pressure Conditions)
Kubelet имеет встроенный демон выселения (`eviction manager`), который
следит за ресурсами ноды по жестким порогам (`evictionHard`):
- `DiskPressure`: свободно <15% на файловой системе образов (`imagefs`) или
  <10% на корневом разделе (`nodefs`). Kubelet сначала удаляет
  неиспользуемые контейнеры и образы (Garbage Collection), а если место не
  освободилось — начинает убивать поды.
- `MemoryPressure`: свободная память ноды опустилась ниже порога (обычно
  100-200 МБ).
- `PIDPressure`: исчерпаны PID на ноде (`/proc/sys/kernel/pid_max`).

## 4. Сетевой траблшутинг: сбои Service, флапающие Endpoints и CoreDNS

### 4.1 Трассировка проблемы: «Сервис недоступен»
Если `curl http://my-service` внутри кластера не работает:

```
[Client Pod] 
      │
      ▼
 1. DNS Resolution (CoreDNS) ──► Не вернул IP? ──► Проблема в DNS
      │
      ▼ (Вернул ClusterIP 10.96.15.20)
 2. kube-proxy (iptables/IPVS) ─► Нет правил трансляции? ──► Проблема в kube-proxy
      │
      ▼ (Выбран Pod IP 10.244.2.45)
 3. EndpointSlice ──────────────► Список пуст? ──► Упали Readiness Probes
      │
      ▼
 4. CNI (Calico/Cilium/Flannel) ─► Пакет дропнут? ──► Блокировка NetworkPolicy / MTU drop
      │
      ▼
[Target Pod]
```

**Пошаговый чек-лист:**
1. **Проверить Endpoints сервиса:**
   ```bash
   kubectl get endpoints <service-name>
   kubectl get endpointslice -l kubernetes.io/service-name=<service-name>
   ```
Если в `ENDPOINTS` стоит `<none>`: селектор сервиса `spec.selector` не
совпадает с лейблами подов, либо все поды провалили `readinessProbe`.
2. **Проверить сетевые политики (NetworkPolicy):**
   ```bash
   kubectl get networkpolicy -n <namespace>
   ```
Проверить, не применилась ли политика `default-deny-ingress`, блокирующая
входящий трафик на порт пода.

### 4.2 Проблема CoreDNS и таймауты `ndots:5`
В конфигурации `/etc/resolv.conf` внутри любого пода по умолчанию прописано:
```
nameserver 10.96.0.10
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```
**Эффект `ndots:5`:** если имя хоста содержит менее 5 точек (например,
`api.stripe.com` — 2 точки), resolver пода обязан СНАЧАЛА последовательно
опросить все суффиксы из списка `search`:
1. `api.stripe.com.default.svc.cluster.local` -> NXDOMAIN (отказ)
2. `api.stripe.com.svc.cluster.local` -> NXDOMAIN (отказ)
3. `api.stripe.com.cluster.local` -> NXDOMAIN (отказ)
4. `api.stripe.com.` -> SUCCESS (ответ получен)

Это умножает DNS-нагрузку на CoreDNS в 4–5 раз! При пиковой нагрузке CoreDNS
начинает троттлить запросы по CPU, а ядро Linux на нодах теряет UDP-пакеты
из-за race conditions в таблице conntrack (известный баг ядра Linux с DNS).
**Решение:** использование **NodeLocal DNSCache** (демон на каждой ноде,
кеширующий DNS-запросы и переводящий их на TCP) или завершающая точка в
запросе приложения (`api.stripe.com.`).

## 5. Ingress и L7 ошибки: природа 502 Bad Gateway и 504 Gateway Timeout

Когда внешний пользователь видит 502/504 ошибку, Ingress Controller (Nginx,
Envoy, Traefik) сигнализирует о сбое взаимодействия с бэкенд-подами.

### 5.1 Ошибка 502 Bad Gateway
Означает, что Ingress Controller установил TCP-соединение с Pod IP, но
соединение было сброшено или вернуло некорректный ответ:
- **Keep-Alive Mismatch:** самая частая причина спорадических 502 ошибок под
  нагрузкой. Nginx Ingress держит открытый пул keep-alive соединений к подам
  приложения. Если таймаут keep-alive на бэкенде (например, в Node.js / Go
  `IdleTimeout = 5s`) меньше, чем таймаут в Ingress (`keepalive_timeout =
  60s`), бэкенд разрывает сокет (шлет `TCP FIN/RST`) ровно в тот момент,
  когда Nginx отправляет в этот сокет новый запрос.
*Решение:* таймаут keep-alive на бэкенде должен быть ВСЕГДА больше, чем на
Ingress (например, 65s на бэкенде против 60s на Ingress).
- **Под упал во время обработки запроса:** контейнер получил OOMKilled или
  упал с panic, сокет закрылся ядром до формирования HTTP-ответа.

### 5.2 Ошибка 504 Gateway Timeout
Означает, что Ingress Controller отправил запрос в Pod, но бэкенд не ответил
в течение установленного лимита времени (`proxy-read-timeout` / `proxy-
connect-timeout`, по умолчанию 60 секунд).
- Долгий SQL-запрос или блокировка в бэкенде.
- Бэкенд перегружен и не успевает вычитывать запросы из очереди.

## 6. Инструменты отладки: kubectl debug, Ephemeral Containers и crictl

В минималистичных контейнерах (Distroless, Scratch, Alpine) отсутствуют
`bash`, `curl`, `netstat`, `ping`. Классический `kubectl exec` бесполезен.

### 6.1 Ephemeral Containers (`kubectl debug`)
Механизм позволяет динамически подключить контейнер со всеми необходимыми
утилитами прямо в Network и Process пространство работающего проблемного
пода без его перезапуска:

```bash
# Подключение netshoot контейнера в сетевой неймспейс проблемного пода
kubectl debug -it <pod-name> \
  --image=nicolaka/netshoot \
  --target=<target-container-name> \
  -- bash
```

Флаг `--target` подключает отладочный контейнер к пространству процессов
(PID namespace) целевого контейнера. Внутри можно выполнить `ps aux` и
увидеть процессы целевого контейнера, а также запустить `strace -p <PID>`
или `gdb`.

### 6.2 Отладка ноды на уровне хоста
Если нода сломана, но API-сервер доступен:
```bash
# Запуск привилегированного пода на целевой ноде с доступом к хостовой ФС
kubectl debug node/<node-name> -it --image=busybox

# Внутри отладочного пода получаем полный root в хостовой ОС:
chroot /host
journalctl -u kubelet -n 100
```

## 7. Типовые вопросы на собеседовании (Interview Q&A)

**1. Под находится в статусе `CrashLoopBackOff`. Вы вводите `kubectl logs
<pod-name>` и вывод абсолютно пустой. Каковы ваши дальнейшие действия по
локализации проблемы?**
*Ответ:* Пустой вывод означает, что запущенный в данный момент инстанс
контейнера еще не успел ничего записать в stdout/stderr перед очередным
падением или вообще не смог запуститься. Первый шаг: выполнить `kubectl logs
<pod-name> --previous` — это покажет логи предыдущего упавшего контейнера.
Второй шаг: изучить `kubectl describe pod <pod-name>`, проанализировав
секцию `State` и `Last State` (причина завершения, время падения и точный
Exit Code: например, 127 при отсутствии бинарника или 137 при OOM). Третий
шаг: проверить секцию `Events` на предмет сбоев монтирования
секретов/конфигмапов (`MountVolume.SetUp failed`) или сбоев liveness probe.

**2. Чем принципиально отличается реакция Kubelet на провал Liveness Probe
от провала Readiness Probe? Почему неправильная настройка Liveness Probe
может «положить» весь кластер?**
*Ответ:* При сбое `Readiness Probe` kubelet переводит condition пода
`Ready` в `False`, а EndpointSlice controller в kube-controller-manager
помечает endpoint этого пода в `EndpointSlice` соответствующего Service
как не готовый (`ready: false`), и kube-proxy исключает его из
балансировки. Под перестает
получать пользовательский трафик, но контейнер продолжает жить и выполнять
фоновые задачи. При сбое `Liveness Probe` Kubelet считает контейнер
безнадежно зависшим и принудительно убивает его (перезапуск контейнера с
увеличением счетчика restarts). Опасность заключается в привязке Liveness
Probe к внешним зависимостям (например, к базе данных) или слишком низких
таймаутах под высокой нагрузкой. Если БД кратковременно замедляется,
Liveness Probes проваливаются на всех репликах микросервиса одновременно.
Kubelet начинает массово перезапускать все поды сервиса, создавая
лавинообразную нагрузку на CPU/диск при старте и приводя к полному даунтайму
(cascading failure).

**3. Нода внезапно перешла в статус `NotReady`. В `describe node` видно
сообщение: `PLEG is not healthy`. Объясните, что такое PLEG, почему он
ломается и как это диагностировать на сервере?**
*Ответ:* PLEG (Pod Lifecycle Event Generator) — это внутренний механизм
Kubelet, который с заданной периодичностью опрашивает Container Runtime
через CRI (gRPC вызовы к containerd/CRI-O) о текущем состоянии всех
контейнеров на ноде, вычисляет дельту изменений и генерирует события для
воркеров Kubelet. Если этот цикл синхронизации не может завершиться за
пороговое время (по умолчанию 3 минуты), Kubelet считает рантайм зависшим и
переводит ноду в `NotReady`. Причины: тяжелое насыщение дисковой подсистемы
хоста (высокий `iowait`, блокирующий операции containerd с метаданными на
диске), взаимные блокировки (deadlocks) в модулях ядра при работе с cgroups,
либо накопление тысяч зомби-контейнеров. Для диагностики подключаются по SSH
на ноду, проверяют `vmstat 1` и `iostat -xz 1`, анализируют системный журнал
`journalctl -u containerd` и тестируют скорость ответа рантайма через
`crictl pods` и `crictl ps`.

**4. Вы развернули новый Deployment из 10 реплик. Все поды находятся в
статусе `Pending`. При этом утилизация CPU и Memory на воркер-нодах кластера
не превышает 15%. В чем причина?**
*Ответ:* `kube-scheduler` принимает решения о размещении подов исключительно
на основе суммарных значений `resources.requests` (гарантированных
резервов), а не на основе текущей физической утилизации ресурсов ноды. Если
предыдущие поды на нодах имеют завышенные requests (overprovisioning), но
реально простаивают, суммарный запрошенный лимит ноды может быть исчерпан на
100%. Планировщик видит, что свободного резерва под requests нового
деплоймента нет, и переводит поды в `Pending` с ошибкой `Insufficient
cpu/memory`. Подтверждение находится в `kubectl describe nodes` в секции
`Allocated resources`, где сумма Requests CPU/Memory равна или превышает
Allocatable объем.

**5. Приложение в поде падает с ошибкой `OOMKilled` (Exit Code 137). При
этом мониторинг Prometheus показывает, что потребление памяти контейнером
составляло всего 60% от установленного лимита. Как объяснить это
расхождение?**
*Ответ:* Prometheus обычно скрапит метрики (через cAdvisor) раз в 15–30
секунд. Сброс метрик и их агрегация являются дискретными. Если в приложении
происходит резкий всплеск аллокации памяти (spike, например, выгрузка
мегабайтного файла целиком в RAM без буферизации или неконтролируемая
рекурсия), ядро Linux и OOM-контроллер cgroups реагируют мгновенно (в
течение миллисекунды), убивая процесс сигналом `SIGKILL`. Этот всплеск
происходит и завершается между интервалами сбора метрик Prometheus, поэтому
на графиках отображается усредненное значение 60%, хотя в момент убийства
лимит был превышен на 100%.

**6. Клиенты периодически получают ошибку `502 Bad Gateway` от Nginx Ingress
Controller. При этом бэкенд-поды не падают, а CPU и память в норме. Назовите
наиболее частую причину этой проблемы.**
*Ответ:* Наиболее распространенная причина — рассинхронизация таймаутов
Keep-Alive между Ingress-контроллером и приложением (Keep-Alive Race
Condition). Nginx Ingress поддерживает постоянные TCP-соединения к бэкендам
в upstream-пуле. Если таймаут простоя соединения на стороне приложения
(например, `keepAliveTimeout` в Node.js / Spring / Go) меньше, чем таймаут
keep-alive в Nginx Ingress, приложение закрывает TCP-соединение (отправляя
`FIN`), когда считает, что оно простаивало. Если в этот же микросекундный
интервал Nginx решает отправить новый запрос клиента в этот сокет, пакет
натыкается на закрывающийся сокет, приложение отвечает `TCP RST`, а Nginx
возвращает клиенту ошибку `502 Bad Gateway`. Решение: таймаут `keep-alive` в
конфигурации веб-сервера приложения обязан быть на 5-10 секунд больше, чем
таймаут upstream keep-alive в Ingress.

**7. Разработчик добавил в контейнер liveness probe вида `exec: cat
/tmp/healthy`. Со временем нода начинает тормозить, а количество процессов
на ней зашкаливает. Что пошло не так?**
*Ответ:* Каждый вызов `exec` пробы заставляет Kubelet через CRI обращаться к
рантайму и порождать новый процесс (`fork`/`exec`) внутри контейнера (а
также сопутствующие sh/bash процессы). Если период опроса частый (например,
каждые 2-3 секунды) и на ноде запущены десятки таких подов, ядро вынуждено
непрерывно выполнять тысячи переключений контекста, аллоцировать PID и
структуры процессов. Если в контейнере процесс `cat` зависает из-за проблем
с I/O, эти процессы накапливаются в таблице процессов, исчерпывая системный
лимит `pid_max` (`PIDPressure`) и перегружая ядро. Best practice: избегать
exec-проб и использовать легковесные HTTP или TCP пробы, опрашиваемые
напрямую сетевым демоном Kubelet без порождения процессов.

**8. После удаления пода трафик от Ingress Controller продолжает идти на
старый удаленный Pod IP еще 2-3 секунды, вызывая всплеск 502/503 ошибок у
пользователей. Как устроен жизненный цикл удаления Pod и как устранить эту
проблему?**
*Ответ:* При удалении пода API-сервер параллельно запускает два независимых
асинхронных процесса: 1) Kubelet получает команду на удаление, посылает поду
сигнал `SIGTERM` и запускает таймер `terminationGracePeriodSeconds`; 2)
EndpointSlice controller помечает endpoint пода как terminating/не готовый
(а Endpoints controller убирает его из legacy-объекта Endpoints). Ingress
Controller должен получить этот event через watch API и обновить
свой пул апстримов. Если приложение завершается мгновенно по сигналу
`SIGTERM` (до того, как Ingress обновил конфигурацию), Ingress продолжает
отправлять запросы в уже мертвый сокет. Решение: добавить в конфигурацию
контейнера хук `preStop` с небольшой задержкой:
```yaml
lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 5"]
```
Хук блокирует отправку сигнала `SIGTERM` на 5 секунд, давая Ingress-
контроллеру время гарантированно удалить Pod IP из маршрутизации до
остановки приложения.

**9. В кластере микросервис периодически теряет связь с внешними доменами,
возвращая таймауты DNS-резолвинга (задержки строго по 5 секунд). С чем
связано это поведение и как его исправить?**
*Ответ:* Поведение вызвано комбинацией параметра `ndots:5` в
`/etc/resolv.conf` пода и историческим багом гонки (race condition) в
Netfilter/conntrack ядра Linux при параллельных DNS-запросах по UDP
(одновременная отправка запросов типа `A` и `AAAA` через один и тот же
эфемерный порт приводит к конфликту вставки в таблицу состязающихся записей
conntrack, в результате чего один из ответов молча отбрасывается ядром и
клиент ждет стандартный DNS таймаут 5 секунд до повторной отправки).
Решения: 1) Внедрение **NodeLocal DNSCache**, который агрегирует UDP-трафик
локально и шлет запросы в CoreDNS по надежному TCP; 2) Добавление опции
`single-request-reopen` в `dnsConfig.options` пода, разделяющей порты для
запросов A и AAAA.

**10. Вам необходимо отладить production-контейнер, собранный на базе
scratch/distroless, в котором нет никаких системных утилит (отсутствуют даже
`/bin/sh` и `cat`). Как исследовать сетевой стек и файлы процесса без
остановки пода?**
*Ответ:* Используется механизм Ephemeral Containers через команду:
`kubectl debug -it <pod-name> --image=nicolaka/netshoot --target=<container-
name> -- bash`
Благодаря флагу `--target`, отладочный контейнер с богатым набором утилит
запускается внутри того же сетевого пространства (`Network Namespace`),
пространства межпроцессного взаимодействия (`IPC Namespace`) и пространства
процессов (`PID Namespace`), что и целевой distroless-контейнер. Внутри
отладочного шелла становятся доступны утилиты `tcpdump`, `ss`, `curl`, а
файловая система целевого процесса доступна через
`/proc/<TARGET_PID>/root/`, что позволяет исследовать конфиги и дескрипторы
без перезапуска критичного продакшн-сервиса.
