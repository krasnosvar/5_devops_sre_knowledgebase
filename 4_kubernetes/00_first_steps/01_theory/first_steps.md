## 1. Что такое кластер Kubernetes и зачем он нужен

Docker умеет запустить контейнер на одной машине. Но в работе почти
сразу появляются вопросы, на которые один `docker run` не отвечает:

- контейнер упал ночью — кто его перезапустит;
- машина сломалась — кто перенесёт приложение на другую;
- нужно 10 копий приложения на 5 серверах — кто решит, куда их ставить;
- копии постоянно пересоздаются с новыми IP — как клиентам их находить;
- нужно выкатить новую версию без простоя — кто будет менять копии
  по одной.

**Kubernetes** (k8s) — система, которая отвечает на все эти вопросы.
**Кластер** — это набор машин (физических или виртуальных), которыми
Kubernetes управляет как единым целым. Вы не говорите "запусти контейнер
на сервере 3", вы описываете **желаемое состояние**: "хочу 3 копии
приложения из образа `nginx:1.27-alpine`". Kubernetes сам выбирает
серверы, запускает контейнеры и постоянно сверяет реальность с
описанием: если копий стало 2, он создаёт третью. Этот бесконечный цикл
"сравнить желаемое с реальным → исправить разницу" называется
**reconciliation loop**, и на нём построен весь Kubernetes.

Желаемое состояние обычно записывают в YAML-файлы (манифесты) и
отправляют в кластер командой `kubectl apply`.

## 2. Control plane и рабочие ноды

Машины кластера называются **нодами** (nodes) и делятся на две роли.

**Control plane** — "мозг" кластера. Он ничего не запускает для ваших
приложений сам, он принимает решения и хранит состояние:

- **kube-apiserver** — единственная "дверь" в кластер. Все команды
  `kubectl` и все остальные компоненты общаются только с ним.
- **etcd** — база данных, где хранится всё состояние кластера (какие
  объекты созданы и как они настроены).
- **kube-scheduler** — решает, на какую ноду поставить новый под.
- **kube-controller-manager** — набор контроллеров, которые и выполняют
  reconciliation loop: следят, чтобы реальность совпадала с описанием.

**Рабочие ноды** (worker nodes) — "руки" кластера. На каждой работают:

- **kubelet** — агент, который получает от API-сервера список подов
  для своей ноды и запускает их контейнеры;
- **container runtime** (обычно containerd) — то, что реально
  запускает контейнеры (как Docker, только без лишнего);
- **kube-proxy** (или его замена в CNI-плагине) — настраивает сетевые
  правила, чтобы работали Service.

Важное следствие: если control plane недоступен, уже запущенные
приложения продолжают работать — просто никто не сможет ничего
изменить. Подробно компоненты разобраны в
[01_architecture](../../01_architecture/).

## 3. Pod, Deployment, Service — первое знакомство

Три объекта, с которых начинается любая работа с Kubernetes:

- **Pod (под)** — минимальная единица запуска. Это один или несколько
  контейнеров, которые всегда запускаются вместе на одной ноде и делят
  один IP-адрес. Чаще всего в поде один контейнер. Под "смертен": если
  его удалить или нода умрёт, сам по себе он не вернётся.
- **Deployment** — описание "хочу N одинаковых подов из такого шаблона".
  Deployment следит за числом копий (через промежуточный объект
  ReplicaSet), пересоздаёт удалённые поды и умеет обновлять версию
  приложения постепенно, без простоя. В работе голые поды почти не
  создают — создают Deployment.
- **Service** — стабильное имя и IP для группы подов. Поды постоянно
  пересоздаются с новыми IP, а Service по имени (например, `web`)
  всегда ведёт на живые поды, выбирая их по **labels** (меткам).

Связь между ними держится на labels: Deployment ставит подам метку
`app: web`, а Service в `selector` говорит "веди трафик на поды с
меткой `app: web`". Опечатка в метке — самая частая причина, почему
"Service есть, а трафик не идёт".

Детали жизненного цикла подов и других контроллеров — в
[02_workloads](../../02_workloads/), сеть и типы Service — в
[03_networking](../../03_networking/).

## 4. kubeconfig, контексты и namespace

`kubectl` — это просто клиент, который ходит в kube-apiserver по HTTPS.
Куда ходить и с какими учётными данными — записано в файле
**kubeconfig** (по умолчанию `~/.kube/config`, другой путь можно задать
переменной `KUBECONFIG`). В нём три списка:

- **clusters** — адреса API-серверов и их CA-сертификаты;
- **users** — учётные данные (клиентский сертификат, токен и т.п.);
- **contexts** — пары "кластер + пользователь (+ namespace по
  умолчанию)" под удобным именем.

Один из контекстов — текущий (`current-context`): именно в этот кластер
уйдёт следующая команда. Это главный источник аварий у новичков:
команда, предназначенная для тестового кластера, уходит в рабочий.

```bash
kubectl config get-contexts          # все контексты, текущий помечен *
kubectl config current-context       # какой сейчас активен
kubectl config use-context kind-first   # переключиться
```

**Namespace** — "папка" внутри кластера для разделения объектов
(например, по командам или окружениям). Если namespace не указан,
используется `default`. Системные компоненты живут в `kube-system`.

```bash
kubectl get pods -n kube-system      # поды в конкретном namespace
kubectl get pods -A                  # во всех namespace
kubectl config set-context --current --namespace=dev  # сменить namespace по умолчанию
```

kubeconfig хранится только у вас на машине: удаление контекста из файла
никак не влияет на сам кластер.

## 5. Локальный кластер: kind или minikube

Для обучения не нужен облачный кластер — достаточно локального:

- **kind** (Kubernetes IN Docker) — каждая нода кластера является
  Docker-контейнером. Быстро стартует, легко поднять несколько нод.
  Рекомендуемый вариант для упражнений этого раздела.
- **minikube** — один (или несколько) узлов в VM или в Docker, много
  встроенных аддонов (`minikube addons enable ingress`).

Установка и сравнение вариантов — в
[0_lab_setup/03_local_k8s](../../../0_lab_setup/03_local_k8s/). Минимум
для старта с kind:

```bash
kind create cluster --name first --config ../02_examples/kind-config.yaml
kubectl get nodes          # 3 ноды в статусе Ready
kind delete cluster --name first   # удалить, когда закончили
```

`kind create cluster` сам добавляет в kubeconfig контекст
`kind-<имя>` и делает его текущим.

## 6. kubectl: базовые команды

Общий вид: `kubectl <глагол> <тип ресурса> [<имя>] [флаги]`. Тип можно
писать сокращённо: `po` (pods), `deploy`, `svc`, `ns`.

### 6.1 Посмотреть: get и describe

```bash
kubectl get pods                     # список подов в текущем namespace
kubectl get pods -o wide             # + IP пода и нода, где он запущен
kubectl get pod hello -o yaml        # полный объект, как его видит API
kubectl get deploy,svc               # несколько типов сразу
kubectl describe pod hello           # человекочитаемо + Events внизу
```

`describe` — первое, что делают, когда под не стартует: в разделе
`Events` видно, на какую ноду его назначили, скачался ли образ и почему
контейнер не запустился.

### 6.2 Изменить: apply и delete

```bash
kubectl apply -f pod.yaml            # создать или обновить по файлу
kubectl apply -f ./manifests/        # все манифесты в каталоге
kubectl delete -f pod.yaml           # удалить то, что описано в файле
kubectl delete pod hello             # удалить по имени
```

`apply` — декларативный способ: вы правите файл и применяете его снова,
Kubernetes сам вычисляет разницу. `kubectl create` — императивный: на
уже существующем объекте он вернёт ошибку `AlreadyExists`.

### 6.3 Заглянуть внутрь: logs, exec, port-forward

```bash
kubectl logs hello                   # stdout/stderr контейнера
kubectl logs hello --previous        # логи предыдущего (упавшего) запуска
kubectl logs deploy/web -f           # следить за логами одного из подов
kubectl exec -it hello -- sh         # shell внутри контейнера
kubectl exec hello -- nginx -v       # одна команда без shell
kubectl port-forward svc/web 8080:80 # localhost:8080 -> порт 80 в кластере
```

`port-forward` строит туннель через API-сервер с вашей машины к
одному поду (даже если указан Service — kubectl выбирает один под за
ним). Это инструмент отладки, а не способ публиковать приложение.

### 6.4 Сгенерировать и подсмотреть: --dry-run и explain

Писать YAML с нуля не нужно — его можно сгенерировать:

```bash
kubectl create deployment web --image=nginx:1.27-alpine --replicas=2 \
  --dry-run=client -o yaml > deployment.yaml
kubectl run hello --image=nginx:1.27-alpine --dry-run=client -o yaml
```

`--dry-run=client` ничего не отправляет на сервер, а только печатает
объект. `--dry-run=server` отправляет запрос, сервер проходит все
проверки (включая admission), но не сохраняет объект — полезно, чтобы
поймать ошибку до реального применения.

Если забыли, какие поля есть у объекта, не нужно идти в браузер:

```bash
kubectl explain deployment.spec
kubectl explain pod.spec.containers.resources
```

`explain` показывает описание полей прямо из схемы API вашего кластера
(то есть ровно для вашей версии Kubernetes).

## 7. Первый путь: Pod → Deployment → Service

Готовые манифесты — в [02_examples/](../02_examples/). Порядок:

1. **Pod.** `kubectl apply -f pod.yaml`, затем `kubectl get pods -o
   wide` — под получил IP и ноду. Удалите его (`kubectl delete pod
   hello`) — он не вернётся: голый под никто не защищает.
2. **Deployment.** `kubectl apply -f deployment.yaml` — появились 2 пода
   с именами вида `web-<хэш>-<хэш>`. Удалите один из них — Deployment
   (точнее, его ReplicaSet) тут же создаст замену с новым именем и
   новым IP.
3. **Service.** `kubectl apply -f service.yaml` — у Service есть
   постоянный `CLUSTER-IP` и имя `web`. Проверьте, какие поды за ним:
   `kubectl get endpointslices -l kubernetes.io/service-name=web`.
   Достучаться можно изнутри кластера по имени (`http://web`) или с
   вашей машины через `kubectl port-forward svc/web 8080:80`.

Пройдя эти три шага руками, вы увидите главное свойство Kubernetes:
вы описываете результат, а не действия, и кластер сам удерживает его.

## 8. Удобные инструменты: k9s, kubectx и kubens

- **k9s** — терминальный интерфейс поверх kubectl: список подов,
  логи, `describe`, `exec` по горячим клавишам. Удобен в работе, но
  сначала стоит освоить сами команды kubectl — k9s показывает то же
  самое.
- **kubectx / kubens** — быстрое переключение контекста и namespace по
  умолчанию (`kubectx kind-first`, `kubens kube-system`) вместо длинных
  `kubectl config ...`.

Эти и другие инструменты экосистемы собраны в
[12_k8s_ecosystem](../../12_k8s_ecosystem/).

## 9. Типовые вопросы на собеседовании (Interview Q&A)

**1. Чем Pod отличается от контейнера?**
*Ответ:* Контейнер — это процесс, изолированный namespaces и cgroups.
Pod — объект Kubernetes, обёртка над одним или несколькими
контейнерами, которые всегда запускаются на одной ноде, делят один
сетевой namespace (один IP, общий `localhost`) и могут делить тома.
Kubernetes планирует и перезапускает именно поды, а не отдельные
контейнеры.

**2. Вы удалили под, а через секунду появился новый с другим именем.
Почему, и как удалить его "насовсем"?**
*Ответ:* Под принадлежит Deployment (через ReplicaSet). Контроллер
видит, что подов меньше, чем `replicas`, и создаёт новый. Удалять нужно
владельца: `kubectl delete deployment web` или уменьшить число копий
`kubectl scale deployment web --replicas=0`. Кто владелец — видно в
`metadata.ownerReferences` пода.

**3. У каждого пода и так есть IP. Зачем нужен Service?**
*Ответ:* IP пода живёт столько же, сколько под: при пересоздании он
меняется. Кроме того, копий обычно несколько. Service даёт одно
постоянное имя и виртуальный IP, а за ним — актуальный список готовых
подов, выбранных по labels. Клиенты обращаются к `web`, не зная IP
конкретных подов.

**4. Чем `kubectl apply` отличается от `kubectl create`?**
*Ответ:* `create` — императивная команда "создай": на существующем
объекте вернёт `AlreadyExists`. `apply` — декларативная: если объекта
нет, создаёт; если есть, вычисляет разницу с файлом и применяет только
её. Поэтому в работе манифесты хранят в Git и применяют через `apply`.

**5. `kubectl get pods` возвращает "No resources found", хотя коллега
уверяет, что приложение работает. Что проверить в первую очередь?**
*Ответ:* Текущий контекст и namespace. Возможно, вы смотрите не в тот
кластер (`kubectl config current-context`) или не в тот namespace
(приложение в `dev`, а вы в `default`). Быстрая проверка —
`kubectl get pods -A | grep <имя>`.

**6. Под в статусе `Running`, но в колонке READY стоит `0/1`. Что это
значит и получает ли он трафик через Service?**
*Ответ:* Контейнер запущен, но не прошёл readinessProbe. Пробу
выполняет kubelet на ноде и выставляет в статусе пода условие
`Ready=False`. Контроллер EndpointSlice в control plane видит это и
помечает адрес пода как неготовый, поэтому трафик через Service на
него не идёт, пока проба не пройдёт.

**7. Вы сделали `kubectl port-forward svc/web 8080:80` к Service с
тремя подами. Будут ли запросы распределяться между подами?**
*Ответ:* Нет. kubectl при старте выбирает один под за Service и строит
туннель именно к нему через API-сервер; kube-proxy и балансировка
Service в этом не участвуют. Если этот под умрёт, port-forward
оборвётся. Для проверки балансировки нужно обращаться к Service
изнутри кластера.

**8. Контейнер перезапустился, и `kubectl logs` показывает только пару
строк старта, без ошибки, из-за которой он упал. Где ошибка?**
*Ответ:* `kubectl logs` по умолчанию показывает текущий запуск
контейнера. Логи предыдущего (упавшего) запуска — `kubectl logs <под>
--previous`. Причину завершения (например, `OOMKilled` и код выхода)
дополнительно видно в `kubectl describe pod` в блоке `Last State`.

**9. Вы удалили контекст кластера из своего kubeconfig. Что стало с
кластером и его приложениями?**
*Ответ:* Ничего. kubeconfig — локальный файл клиента: адреса, учётные
данные и имена контекстов. Кластер о нём не знает. Вы просто потеряли
удобный способ подключиться; если удалили и учётные данные, нужно
получить их заново (например, `kind get kubeconfig --name <имя>`).

**10. Чем `--dry-run=client` отличается от `--dry-run=server`, и почему
манифест, прошедший client dry-run, может не создаться?**
*Ответ:* `client` вообще не ходит на сервер за проверкой объекта:
kubectl только собирает и печатает его. `server` отправляет запрос, и
API-сервер выполняет все стадии — схему, defaulting, admission
(включая webhooks политик), но не сохраняет объект в etcd. Поэтому
client dry-run не поймает, например, отказ Pod Security Admission или
неправильное поле, которое знает только сервер.
