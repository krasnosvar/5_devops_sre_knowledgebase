## 1. Три аксиомы сетевой модели Kubernetes (IP-per-Pod)

Сетевая модель Kubernetes базируется на концепции **"IP-per-Pod"** — у
каждого Pod'а свой уникальный IP-адрес — и трёх строгих аксиомах:

1. Любой Pod может связаться с любым другим Pod'ом на любой ноде кластера
   напрямую, **без NAT** (Network Address Translation).
2. Агенты на ноде (kubelet, системные демоны) могут общаться с любым Pod'ом
   на этой же ноде без NAT.
3. IP-адрес, который Pod видит как свой собственный, должен совпадать с
   IP-адресом, по которому его видят все остальные Pod'ы в кластере.

Зачем это нужно: без таких гарантий каждому приложению пришлось бы самому
разбираться с динамическим маппингом портов (как в обычном Docker с мостом
`docker0`, где один хост-порт нужно явно пробрасывать в контейнер). Три
аксиомы убирают эту возню и позволяют приложениям работать так, будто они
запущены на физических серверах в единой плоской L3-сети — сервис просто
ходит по IP:порт соседнего пода напрямую, без знания о NAT-трансляциях.

## 2. Pause-контейнер и сетевой namespace пода

Pod — это логическая абстракция, а не отдельный процесс ядра. Физически
изоляция и общий сетевой стек пода реализуются через обычные Linux
Namespaces (Network, UTS, IPC), и кто-то должен этот namespace СОЗДАТЬ и
удержать открытым, пока живёт под — это и есть работа **Pause-контейнера**:

1. При создании пода рантайм (containerd/CRI-O) первым делом запускает
   специальный инфраструктурный контейнер — Pause Container (образ
   `registry.k8s.io/pause`).
2. Pause-контейнер создаётся с новым сетевым пространством имён
   (`CLONE_NEWNET`) и сразу же "засыпает" в системном вызове `pause()`,
   удерживая дескриптор этого netns открытым в ядре.
3. Все прикладные контейнеры пода запускаются НЕ со своим отдельным netns,
   а присоединяются к уже существующему netns Pause-контейнера через
   системный вызов `setns()`.

Благодаря этому все контейнеры одного пода делят один сетевой стек, один
IP-адрес, одну таблицу маршрутизации и один интерфейс `lo` — и этот общий
netns переживает перезапуск отдельного прикладного контейнера (контейнер
может упасть и пересоздаться, а IP пода не поменяется), потому что
netns держит именно Pause-контейнер, а не само приложение.

## 3. Обмен трафиком внутри одного пода (Container-to-Container)

Поскольку все контейнеры пода разделяют один сетевой namespace (§2):

- Связь между ними идёт через виртуальную петлю `localhost` (`127.0.0.1`/
  `::1`) — как между двумя процессами на одной машине.
- Пакеты не покидают стек ядра ноды и не выходят на физические интерфейсы:
  драйвер loopback мгновенно копирует буфер `sk_buff` из очереди отправки
  в очередь приёма сокета соседнего процесса.
- Контейнеры одного пода **не могут** слушать один и тот же TCP/UDP порт —
  возникнет `bind: address already in use`, потому что порт делится на
  уровне общего сетевого стека, а не изолирован per-контейнерно.
- Контейнеры могут общаться и через стандартный Linux IPC: общую память
  (POSIX shared memory `/dev/shm`), семафоры и очереди сообщений.

## 4. Как CNI настраивает сеть пода: veth-пары и IPAM

Когда kubelet получает команду создать под, после запуска Pause-контейнера
(§2) он вызывает установленный CNI-плагин (Calico, Flannel, Cilium) через
бинарный интерфейс CNI (команда `ADD`) — именно CNI отвечает за то, чтобы
у пода появился реальный, маршрутизируемый IP и связность с остальным
кластером:

1. CNI обращается к модулю **IPAM** (IP Address Management), который
   выделяет свободный IP-адрес из диапазона подсети ноды (`podCIDR`).
2. В ядре создаётся виртуальная пара интерфейсов **veth** (Virtual
   Ethernet pair) — она работает как двунаправленная виртуальная труба:
   всё, что входит в один конец, мгновенно выходит из другого.
3. Один конец пары (`eth0`) перемещается внутрь сетевого namespace пода,
   получает выделенный IP-адрес и настраивает шлюз по умолчанию.
4. Второй конец пары (например, `veth1234abcd` или `cali1234abcd`)
   остаётся в корневом сетевом пространстве имён хостовой ноды.
5. CNI-плагин либо подключает хостовый конец к программному мосту (Linux
   bridge, Open vSwitch), либо настраивает для него прямой маршрут в
   таблице маршрутизации хоста, либо навешивает eBPF-программу.

## 5. Путь пакета Pod-to-Pod на одной ноде

Когда Pod-A отправляет IP-пакет к Pod-B, расположенному на том же хосте:

1. Процесс в Pod-A шлёт пакет в сокет. Ядро внутри netns Pod-A смотрит
   свою таблицу маршрутизации и направляет пакет в интерфейс `eth0`.
2. Пакет выходит из виртуального кабеля veth и мгновенно оказывается на
   хостовой ноде на парном интерфейсе `vethA`.
3. Дальше путь зависит от архитектуры CNI:
   - **Linux Bridge (Flannel)**: интерфейсы `vethA` и `vethB` воткнуты в
     программный мост `cbr0`. Мост работает как L2-коммутатор: изучает
     MAC-адреса и пересылает кадр в интерфейс `vethB`.
   - **Маршрутизация L3 (Calico)**: хостовый конец `caliA` имеет
     включённый `proxy_arp`. Ядро хоста делает route lookup по таблице
     маршрутизации, видит правило `10.244.1.5 dev caliB` и пересылает
     пакет в `vethB`.
   - **eBPF (Cilium)**: программа на уровне хука `tc` (Traffic Control) на
     интерфейсе `vethA` смотрит BPF-карту эндпоинтов и через вызов
     `bpf_redirect_peer()` пересылает пакет напрямую в сокет Pod-B, минуя
     большую часть сетевого стека ядра хоста.
4. Пакет входит в `eth0` внутри Pod-B и доставляется целевому процессу.

## 6. Путь пакета Pod-to-Pod между нодами через Overlay (VXLAN)

Overlay-сеть строит виртуальную L2/L3 сеть поверх существующей физической
L3-сети (underlay), инкапсулируя оригинальный пакет пода в UDP-пакет —
это нужно, потому что физическая сеть дата-центра не обязана знать
маршруты до внутренних `podCIDR` каждой ноды:

1. Pod-A (на Node-1, IP `10.244.1.2`) шлёт пакет к Pod-B (на Node-2, IP
   `10.244.2.3`). Пакет покидает Pod-A через veth-пару и попадает в
   сетевой стек Node-1.
2. Маршрутизатор ядра Node-1 видит, что сеть `10.244.2.0/24` доступна
   через виртуальный туннельный интерфейс (например, `vxlan.calico` или
   `flannel.1`).
3. **Инкапсуляция**: драйвер VXLAN ядра берёт исходный IP-пакет Pod-A →
   Pod-B, добавляет VXLAN-заголовок (VNI id) и оборачивает его в
   стандартный UDP-пакет, где IP источника/назначения — это физические
   IP нод (Node-1/Node-2), а порт назначения UDP — 4789 (стандарт IANA).
4. Пакет летит через физические коммутаторы и маршрутизаторы дата-центра
   как обычный UDP-трафик между двумя физическими серверами.
5. **Декапсуляция**: сетевая карта Node-2 получает UDP-пакет на порт
   4789, передаёт драйверу VXLAN, который снимает внешние заголовки
   IP/UDP/VXLAN и восстанавливает оригинальный IP-пакет Pod-A → Pod-B.
6. Ядро Node-2 пересылает распакованный пакет в интерфейс `vethB` пода
   Pod-B.

**Важно для SRE**: из-за добавления VXLAN-заголовков (~50 байт) MTU на
поде обязан быть МЕНЬШЕ физического MTU хоста (например, 1450 вместо
1500) — иначе любой пакет, который итогово превысит физический MTU после
инкапсуляции, либо фрагментируется (если разрешено), либо теряется с
ошибкой `Fragmentation needed` при установленном флаге `DF` (Don't
Fragment) — а приложения внутри TCP-сессий часто выставляют этот флаг,
получая необъяснимые зависания именно на крупных пакетах.

## 7. Путь пакета Pod-to-Pod между нодами без Overlay (BGP/Direct Routing)

В сетях с прямой маршрутизацией (Calico в режиме BGP, Cilium Native
Routing) инкапсуляции нет вообще, что даёт максимальную производительность
(line-rate) и нулевой оверхед по MTU и CPU — ценой требования, что
физическая сеть дата-центра должна уметь маршрутизировать `podCIDR` сама:

1. Каждая нода кластера получает уникальный CIDR-блок под поды (например,
   Node-1: `10.244.1.0/24`, Node-2: `10.244.2.0/24`).
2. На каждой ноде запускается BGP-демон (например, BIRD в Calico). Ноды
   устанавливают BGP-соседство (BGP Peering) либо друг с другом (Full
   Mesh), либо с физическими ToR-коммутаторами (Top-of-Rack/Route
   Reflectors).
3. Нода анонсирует соседям: "сеть `10.244.1.0/24` доступна через меня
   (Next-Hop: IP Node-1)".
4. Когда Pod-A отправляет пакет к Pod-B на Node-2: пакет выходит на хост
   Node-1 с реальным IP источника (`10.244.1.2`) и реальным IP назначения
   (`10.244.2.3`) — физическая сеть уже знает маршрут до `10.244.2.0/24`
   через IP Node-2, и пакет идёт в физическую сеть БЕЗ обёртки в
   UDP/VXLAN. Node-2 принимает "чистый" пакет и сразу переправляет его в
   veth-интерфейс пода Pod-B.

## 8. ClusterIP и маршрутизация Pod-to-Service через iptables

`ClusterIP` — виртуальный IP-адрес: у него нет физического или даже
виртуального сетевого интерфейса, он не отвечает на ARP-запросы и не
может быть прописан в сетевую карту. Весь смысл Service в том, чтобы
дать стабильный адрес набору подов, которые постоянно пересоздаются —
поэтому маршрутизация к нему реализуется не маршрутизатором, а
демоном **kube-proxy** через подсистему Netfilter ядра Linux:

1. kube-proxy слушает API-сервер. При создании Service и появлении за ним
   Endpoints (IP подов) kube-proxy генерирует цепочки правил в таблице
   `nat` iptables.
2. Когда под отправляет пакет на адрес ClusterIP (`10.96.0.15:80`):
   пакет попадает в хук `PREROUTING`/`OUTPUT` ядра ноды, ядро переходит в
   цепочку `KUBE-SERVICES`; если dst IP совпадает с ClusterIP, управление
   передаётся в цепочку сервиса `KUBE-SVC-XXXXX`. Эта цепочка содержит
   набор правил с модулем `statistic --mode random --probability 1/N`,
   ведущих в цепочки конкретных эндпоинтов `KUBE-SEP-YYYYY` (Kubernetes
   Service Endpoint). В цепочке эндпоинта выполняется **DNAT**
   (Destination NAT): IP назначения ClusterIP подменяется на реальный IP
   выбранного пода (`10.244.2.45:8080`).
3. Ядро выполняет обычный route lookup для нового IP назначения и
   отправляет пакет в CNI-сеть по стандартным правилам Pod-to-Pod (§5-7).
4. Ответный пакет проходит через механизм **conntrack** (Connection
   Tracking), где выполняется обратная операция UN-DNAT: IP источника
   подменяется обратно на виртуальный ClusterIP, чтобы клиентский под
   получил ответ от того же адреса, к которому обращался.

## 9. Почему iptables деградирует на масштабе: IPVS и eBPF

**Проблема iptables**: правила хранятся в виде последовательного связного
списка (сложность поиска `O(N)`). Если в кластере 5000 сервисов по 10
реплик, таблица `nat` разрастается до 50 000+ правил — на каждый пакет
ядро должно последовательно перебрать тысячи правил. Любое обновление
хотя бы одного пода заставляет kube-proxy блокировать всю таблицу
(`iptables-restore` с глобальным мьютексом), вызывая всплески CPU и
latency на всей ноде, а не только для изменённого сервиса.

- **IPVS** использует хэш-таблицы (`ipset`), обеспечивая сложность поиска
  `O(1)` независимо от числа сервисов, и поддерживает развитые алгоритмы
  балансировки (Least Connections, Weighted) — но всё ещё требует
  Netfilter и conntrack, то есть решает проблему скорости поиска правила,
  но не убирает накладные расходы самого NAT-слоя.
- **eBPF (Cilium, kube-proxy replacement)** решает задачу иначе: вместо
  того чтобы переписывать уже сформированный пакет (DNAT как в iptables/
  IPVS), Cilium перехватывает сам системный вызов `connect()` приложения
  через BPF-программу на cgroup-хуке `connect4`/`connect6`
  (`BPF_PROG_TYPE_CGROUP_SOCK_ADDR`) ещё на уровне сокета. Трансляция адреса
  происходит ДО ТОГО, как пакет вообще сформирован и покинул пространство
  пользователя — сокет сразу подключается к реальному IP пода, и запросу
  вообще не требуется проходить через Netfilter/iptables/conntrack.
- **nftables-режим kube-proxy** (GA с 1.33) решает проблему iptables
  внутри самого kube-proxy: map-структуры вместо линейных цепочек и
  инкрементальные обновления; IPVS-режим объявлен deprecated в 1.35.

## 10. Входящий трафик: NodePort, LoadBalancer и externalTrafficPolicy

Для приёма внешнего (North-South) трафика есть два типа Service:

1. **NodePort**: открывает одинаковый порт (30000–32767) на ВСЕХ нодах.
   Трафик, пришедший на `Node_IP:NodePort`, транслируется kube-proxy
   сначала в ClusterIP, а затем в Pod IP — тем же механизмом, что и §8.
2. **LoadBalancer**: облачный контроллер создаёт внешний балансировщик
   (AWS NLB/GCP LB), который шлёт трафик на `Node_IP:NodePort` — то есть
   LoadBalancer технически надстройка над NodePort, а не отдельный
   механизм доставки пакета.

Критична разница режимов `externalTrafficPolicy`, потому что от неё
зависит, сохранится ли реальный IP клиента:

- **Cluster** (по умолчанию): если внешний запрос прилетел на Node-1, а
  под находится на Node-2, Node-1 пересылает пакет на Node-2 вторым хопом.
  Чтобы Node-2 знала, куда вернуть ответ, Node-1 выполняет **SNAT**,
  затирая реальный IP клиента и подставляя свой собственный. Минусы:
  лишний сетевой хоп между нодами, потеря реального Client IP в логах
  приложения.
- **Local**: NodePort принимает трафик ТОЛЬКО если на этой конкретной
  ноде уже запущен хотя бы один готовый под данного сервиса (облачный
  балансировщик через HealthCheck опрашивает только такие ноды). Плюсы:
  нет межсерверного хопа, нет SNAT — приложение видит настоящий IP
  клиента. Минус: возможен перекос нагрузки, если под 1 реплика на одной
  ноде и 3 реплики на другой — каждая нода всё равно получит около 50%
  внешнего трафика независимо от числа реплик за ней.

## 11. Почему Ingress Controller обходит ClusterIP

Интуитивно кажется, что Ingress Controller просто проксирует трафик НА
ClusterIP сервиса, как любой внешний клиент. На самом деле это не так, и
вот почему:

1. Ingress Controller (Nginx, Traefik, HAProxy, Envoy) — это L7-прокси, а
   не ещё один потребитель Service.
2. Внутри контроллера работает управляющий демон, который через `watch`
   к API считывает объекты `Endpoints`/`EndpointSlice` сервиса напрямую.
3. Контроллер формирует собственный динамический upstream-список,
   содержащий непосредственные IP-адреса подов-реплик.
4. При поступлении запроса Ingress Controller сам выбирает целевой под,
   используя L7-алгоритмы (Least Conn, Round Robin, Consistent Hash,
   Sticky Sessions, Canary), и отправляет HTTP/gRPC-запрос НАПРЯМУЮ на
   IP пода через CNI-сеть, в обход ClusterIP и kube-proxy вообще.

Это исключает двойную балансировку (один раз в Ingress, второй раз в
iptables ClusterIP), убирает накладные расходы L4-слоя kube-proxy и
позволяет корректно поддерживать WebSockets, HTTP/2 multiplexing и gRPC
streaming — долгоживущие соединения, которые плохо проходят через
простую L4 DNAT-балансировку ClusterIP.

## 12. Исходящий трафик (Egress): SNAT/Masquerade

Под имеет приватный IP-адрес из кластерной сети (например,
`10.244.0.0/16`) — публичные маршрутизаторы интернета физически не могут
вернуть ответ на такой адрес (он не маршрутизируется глобально), поэтому
на границе кластера нужна подмена адреса:

1. Когда под шлёт запрос к внешнему ресурсу (например, `api.github.com`):
   пакет через veth выходит на хостовую ноду; ядро ноды видит, что IP
   назначения находится вне диапазона `podCIDR` и `serviceCIDR`; срабатывает
   правило iptables в цепочке `POSTROUTING` (обычно правило
   `KUBE-POSTROUTING` с действием `MASQUERADE`).
2. **SNAT**: ядро ноды заменяет приватный IP пода на свой собственный
   физический IP хостовой ноды, выделяя эфемерный порт из таблицы
   conntrack.
3. Внешний сервер видит запрос как пришедший от физической ноды кластера
   и возвращает ответ на её IP.
4. Ядро ноды через таблицу conntrack восстанавливает приватный IP пода и
   передаёт ответ обратно в сокет через veth.

Если в облаке нельзя выпускать поды через IP воркер-нод (например,
firewall-правила допускают только определённые выходные адреса),
используют утилиту `ip-masq-agent` для тонкой настройки исключений, либо
Egress Gateway (Cilium/Calico/Istio) со статическим выделенным публичным
IP.

## 13. Путь DNS-резолвинга и NodeLocal DNSCache

Когда приложение в поде выполняет `getaddrinfo("users-service")`:

1. Резолвер читает `/etc/resolv.conf` пода: `nameserver 10.96.0.10`
   (виртуальный ClusterIP сервиса CoreDNS), `search
   default.svc.cluster.local svc.cluster.local cluster.local`,
   `options ndots:5`.
2. Из-за `ndots:5` (если в имени меньше 5 точек) клиент сначала пытается
   разрешить полное имя: `users-service.default.svc.cluster.local.` —
   то есть на одно короткое имя сервиса может уйти несколько
   последовательных DNS-запросов с разными суффиксами, прежде чем один
   из них разрешится.
3. Запрос летит по UDP (порт 53) на ClusterIP `10.96.0.10`.
4. kube-proxy перенаправляет UDP-пакет на одну из реплик CoreDNS (тем же
   механизмом DNAT, что и §8).
5. CoreDNS проверяет свою внутреннюю базу (плагин `kubernetes`), находит
   соответствующий Service и возвращает его ClusterIP.

**Узкое место**: при тысячах одновременных DNS-запросов UDP-пакеты
вызывают гонки записи в таблице conntrack ядра Linux (несколько потоков
одновременно пытаются создать запись conntrack для похожих 5-tuple), что
проявляется как packet drops и таймауты ровно в 5 секунд (стандартный
таймаут UDP-резолвера при потере пакета). **Решение — NodeLocal
DNSCache**: на каждой ноде запускается DaemonSet, слушающий локальный
link-local IP (`169.254.20.10`). Поды обращаются к DNS-кешу на СВОЕЙ ноде
через loopback/dummy интерфейс (без похода в сеть и без конкуренции за
conntrack с другими нодами), локальный агент кэширует ответы, а к
центральному CoreDNS обращается уже по надёжному TCP вместо UDP.

## 14. Как CNI применяет NetworkPolicy на уровне ядра

Сам Kubernetes не фильтрует трафик — манифест `NetworkPolicy` является
лишь декларацией намерения в API; кто именно реально блокирует пакеты,
зависит от установленного CNI:

- **Calico**: CNI-агент Felix читает `NetworkPolicy` из etcd/k8s API. Для
  каждого пода на ноде Felix генерирует специализированные цепочки
  iptables (`cali-pi-*` для inbound и `cali-po-*` для outbound) на
  хостовом конце veth-пары пода, а также создаёт `ipset`-множества для
  селекторов подов/лейблов. Пакет фильтруется ядром на уровне хуков
  Netfilter ещё до того, как попадёт в стек приложения.
- **Cilium**: не использует iptables вообще. Cilium компилирует BPF-
  байткод на лету и загружает его в ядро на хуки `tc` (Traffic Control)
  или `XDP` сетевого интерфейса пода. Проверка правил `NetworkPolicy`
  происходит на уровне инструкций eBPF в памяти ядра за единицы
  наносекунд, обеспечивая практически нулевые накладные расходы даже при
  тысячах правил.

Практический вывод: если CNI в кластере не умеет применять
`NetworkPolicy` (например, Flannel в режиме "из коробки", без наложенного
Calico поверх), созданный манифест `NetworkPolicy` будет молча принят
API-сервером, но НИКАК не повлияет на реальный трафик — его просто
некому исполнять.

## 15. Типовые вопросы на собеседовании (Interview Q&A)

**1. Два контейнера внутри одного пода не могут слушать один и тот же TCP-порт, хотя физически это два разных процесса. Почему?**
*Ответ:* Все контейнеры одного пода разделяют ОДИН сетевой namespace (и
значит один и тот же набор сетевых интерфейсов и портов) — эту изоляцию
создаёт и удерживает Pause-контейнер, к netns которого присоединяются все
остальные контейнеры через `setns()`. Порт — это ресурс конкретного
сетевого стека, а не конкретного процесса/контейнера, поэтому попытка
второго контейнера забиндиться на уже занятый порт вернёт обычную ошибку
`bind: address already in use`, как было бы между двумя процессами на
одной машине без контейнеров вообще.

**2. Зачем вообще нужен отдельный Pause-контейнер — разве нельзя дать первому прикладному контейнеру создать netns и присоединить к нему остальные?**
*Ответ:* Если бы netns держал прикладной контейнер, перезапуск (crash,
OOM) этого контейнера уничтожил бы и сетевой namespace вместе с ним —
под потерял бы IP-адрес и все сетевые настройки, даже если остальные
контейнеры пода продолжают жить. Pause-контейнер ничего не делает (висит
в `pause()`) и почти никогда не падает — он существует именно для того,
чтобы быть стабильным "держателем" netns, не зависящим от жизненного
цикла прикладных контейнеров.

**3. Почему при использовании VXLAN-оверлея нужно вручную уменьшать MTU на интерфейсе пода, и что произойдёт, если этого не сделать?**
*Ответ:* VXLAN инкапсулирует оригинальный пакет пода в UDP-пакет,
добавляя примерно 50 байт служебных заголовков (VXLAN + внешние UDP/IP).
Если MTU пода равен физическому MTU хоста (обычно 1500), итоговый пакет
после инкапсуляции превысит физический MTU сети. Такой пакет либо
фрагментируется (если разрешено — лишние накладные расходы), либо
теряется с ошибкой "Fragmentation needed", если в TCP-сессии выставлен
флаг `DF` (Don't Fragment) — это проявляется как необъяснимые зависания
именно на крупных пакетах/запросах, при том что маленькие пакеты (ping)
проходят нормально.

**4. В чём принципиальная разница между Direct Routing (BGP, Calico) и Overlay (VXLAN) с точки зрения производительности?**
*Ответ:* Overlay инкапсулирует каждый пакет в дополнительный UDP-заголовок
и требует декапсуляции на другой стороне — это накладные расходы CPU на
каждый пакет и уменьшенный полезный MTU (см. вопрос 3). Direct Routing
передаёт пакет между нодами "как есть", без обёртки, полагаясь на то, что
физическая сеть дата-центра сама знает маршрут до `podCIDR` каждой ноды
(через анонсы BGP) — это даёт производительность line-rate и нулевой
оверхед по MTU/CPU, но требует, чтобы сетевое оборудование дата-центра
поддерживало BGP-пиринг с нодами кластера, что не всегда возможно в
облаке с управляемой провайдером сетью.

**5. Чем DNAT в iptables-режиме kube-proxy отличается от eBPF-подхода Cilium, и почему второй быстрее при больших масштабах?**
*Ответ:* В iptables-режиме пакет сначала полностью формируется
приложением, покидает пользовательское пространство, и только потом ядро
на хуках Netfilter переписывает его адрес назначения (DNAT), прогоняя
через последовательный список правил (`O(N)` от числа сервисов). Cilium
перехватывает сам системный вызов `connect()` приложения через BPF-
программу на cgroup-хуке `connect4` ещё ДО формирования пакета — сокет сразу
устанавливается на реальный IP пода, и трафику вообще не требуется
проходить через iptables/conntrack. Это убирает и сложность поиска
правила, и сам слой NAT-трансляции пакетов как таковой.

**6. Приложение в поде видит входящий трафик с IP ноды кластера вместо реального IP внешнего клиента. Какая настройка за это отвечает и какой у неё минус?**
*Ответ:* По умолчанию `externalTrafficPolicy: Cluster` допускает, что
запрос, пришедший на одну ноду, может быть переслан вторым хопом на
другую ноду, где реально работает под — а чтобы ответ вернулся по тому же
пути, первая нода выполняет SNAT, подменяя IP клиента на свой собственный.
Переключение на `externalTrafficPolicy: Local` убирает SNAT (трафик
принимается только нодами, где уже есть готовый под) и сохраняет
реальный IP клиента, но ценой возможного перекоса нагрузки между нодами
с разным числом реплик на борту.

**7. Почему Ingress Controller имеет право слать трафик напрямую на IP подов, минуя Service/ClusterIP, и что это даёт?**
*Ответ:* Ingress Controller — это L7-прокси с собственным управляющим
демоном, который сам читает объекты `Endpoints`/`EndpointSlice` через API
и формирует собственный upstream-список из реальных IP подов, применяя
свои L7-алгоритмы балансировки (Sticky Sessions, Consistent Hash, Canary).
Поход через ClusterIP означал бы ДВОЙНУЮ балансировку (сначала L7 в
Ingress, затем ещё раз L4 DNAT в iptables ClusterIP) и хуже бы работал с
долгоживущими соединениями (WebSocket, HTTP/2 multiplexing, gRPC
streaming), которые плохо переживают простую L4-балансировку по
отдельным TCP-соединениям.

**8. DNS-запросы из подов иногда зависают ровно на 5 секунд под нагрузкой. Какой механизм ядра виноват и как NodeLocal DNSCache решает проблему?**
*Ответ:* При большом числе одновременных DNS-запросов по UDP возникает
гонка записи в таблице conntrack ядра: несколько потоков одновременно
пытаются создать запись для похожих 5-tuple (источник/назначение/порты),
часть пакетов теряется, и клиент упирается в стандартный таймаут
UDP-резолвера — обычно ровно 5 секунд. NodeLocal DNSCache разворачивает
на каждой ноде DaemonSet-кеш, слушающий локальный link-local IP
(`169.254.20.10`); поды обращаются к нему через loopback/dummy интерфейс
без похода в сеть и без конкуренции за conntrack с другими нодами, а сам
кеш общается с центральным CoreDNS уже по надёжному TCP.

**9. Вы применили манифест NetworkPolicy, но трафик в кластере всё равно не блокируется. В чём может быть причина, не связанная с ошибкой в самом манифесте?**
*Ответ:* `NetworkPolicy` — это декларация намерения в API Kubernetes,
сама по себе она ничего не фильтрует. Реальную фильтрацию выполняет CNI
(Calico через iptables-цепочки `cali-pi-*`/`cali-po-*` и Felix, либо
Cilium через eBPF на хуках `tc`/`XDP`). Если в кластере установлен CNI,
не реализующий `NetworkPolicy` (например, Flannel в режиме "из коробки"
без наложенного Calico поверх), манифест будет принят API-сервером без
ошибок, но физически не повлияет на трафик — исполнять его просто некому.
