## 1. CRD: как k8s узнаёт про новый тип ресурса

`cert-manager` (см. [`../03_networking/`](../../03_networking/) §6) выдаёт сертификаты через объект `Certificate` — но такого ресурса нет в ванильном k8s. Как и большинство инструментов из этого репозитория (ArgoCD `Application`, ExternalSecret, Karpenter `NodePool`), он расширяет API кластера через **Custom Resource Definition (CRD)**.

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: websites.example.com
spec:
  group: example.com
  names:
    kind: Website
    plural: websites
  scope: Namespaced
  versions:
    - name: v1
      served: true
      storage: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                domain: {type: string}
                replicas: {type: integer}
```

После `kubectl apply -f` этого CRD команда `kubectl get websites` начинает работать так же, как `kubectl get pods` — со своим REST-эндпоинтом, валидацией схемы (OpenAPI v3) и хранением объектов в etcd. Но сам по себе CRD — это только описание **структуры данных** ("вот такие поля бывают у Website"), он ничего не *делает*.

## 2. Operator: reconcile loop на пальцах

**Operator** — то, что превращает декларацию в действие: обычный под с контроллером (написанным через `client-go`/`controller-runtime`, часто через Operator SDK или Kubebuilder), который работает по **reconcile loop**:

1. Подписывается (через **Informer**, кэширующий локальную копию через List+Watch к API-серверу — см. [`../01_architecture/`](../../01_architecture/) §5) на события создания/изменения/удаления CR своего типа.
2. При каждом событии вызывает функцию `Reconcile()`, которая сравнивает **желаемое состояние** (спецификация в CR, например `Website.spec.domain`) с **фактическим** (реальные ресурсы в кластере/во внешней системе).
3. Если есть расхождение — приводит фактическое состояние к желаемому (создаёт Deployment+Ingress+Certificate для сайта, или запрашивает сертификат у Let's Encrypt).

Это ровно тот же паттерн, по которому устроены **встроенные** контроллеры k8s — Deployment-controller делает reconcile между `Deployment.spec.replicas` и реальным числом Pod'ов (см. [`../01_architecture/`](../../01_architecture/) §1). Operators просто применяют его к прикладной логике, которую в vanilla k8s не заложили.

## 3. Idempotency: почему Reconcile можно звать бесконечно

`Reconcile()` — идемпотентная функция: она не "продолжает" прерванную операцию, а каждый раз **заново** сравнивает желаемое состояние с фактическим. Это критично: оператор может перезапуститься в середине обработки (OOM, деплой новой версии), потерять весь внутренний in-memory прогресс — и это не страшно. После рестарта он получает через Informer текущий список всех CR (List) и по каждому заново вызывает Reconcile. Если ресурс уже существует и соответствует спецификации — Reconcile увидит это и ничего не создаст повторно. Состояние в кластере — источник истины, а не память запущенного процесса.

## 4. Готовые Operators вокруг нас

Большинство инструментов, которые выглядят как "магия" в других разделах этой базы — на самом деле именно Operators:
- **cert-manager** — Operator для `Certificate`/`Issuer` (см. [`../03_networking/`](../../03_networking/)).
- **External Secrets Operator** — Operator для `ExternalSecret` (см. [`../06_security/`](../../06_security/) §6).
- **Karpenter** — Operator для `NodePool`/`NodeClaim` (см. [`../08_cluster_operations/02_node_autoscaling/`](../../08_cluster_operations/02_node_autoscaling/)).
- **Prometheus Operator** — Operator для `ServiceMonitor`/`PrometheusRule`.

Понимание reconcile loop — это ключ к тому, чтобы не считать каждый новый CRD отдельной "магией", а видеть один и тот же паттерн везде.

## 5. Типовые вопросы на собеседовании (Interview Q&A)

**1. Вы написали CRD `Website` и применили его через `kubectl apply`. Объект появился (`kubectl get websites` его видит), но реальный сайт не задеплоился. Что вы забыли?**
*Ответ:* CRD регистрирует только **схему** ресурса в API-сервере — структуру полей и способ их хранения в etcd. Он ничего не выполняет сам по себе. Чтобы CR превратился в реальное действие (создание Deployment/Ingress/Certificate), в кластере должен работать **Operator** — под с контроллером, который подписан на события этого типа ресурса и реализует reconcile loop. Без запущенного контроллера CRD `Website` — это просто мёртвая запись в etcd, за которой никто не следит.

**2. Оператор перезапустился (например, после OOM) в середине обработки ресурса. Почему это не приводит к дублированию созданных объектов?**
*Ответ:* Правильно написанный `Reconcile()` — идемпотентная функция: она не "продолжает" прерванную операцию, а каждый раз заново сравнивает желаемое состояние (спецификацию CR) с фактическим состоянием кластера. После перезапуска оператор получает через Informer текущий список всех CR (List) и по каждому заново вызывает Reconcile. Если ресурс уже существует и соответствует спецификации — Reconcile увидит это и ничего не создаст повторно. Это тот же принцип, по которому Deployment-controller не плодит лишние Pod'ы при своём перезапуске: состояние в кластере — источник истины, а не память запущенного процесса.

**3. Чем отличается `served: true` от `storage: true` в секции `versions` манифеста CRD, если у ресурса объявлено несколько API-версий (v1alpha1, v1beta1, v1)?**
*Ответ:* `served: true` означает, что API-сервер принимает запросы к этой версии через REST (`kubectl get websites.v1alpha1.example.com` сработает). `storage: true` означает, что именно в этом формате объект физически хранится в etcd — среди всех версий ровно одна обязана иметь `storage: true`. Когда приходит запрос на версию с `served: true`, но не `storage: true`, API-сервер на лету конвертирует объект из формата хранения в запрошенную версию (через встроенный или webhook-конвертер) — это позволяет постепенно мигрировать API ресурса, не ломая старых клиентов.
