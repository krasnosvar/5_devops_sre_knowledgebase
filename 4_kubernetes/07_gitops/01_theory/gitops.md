## 1. Push vs Pull модель деплоя

Традиционный CI/CD (GitLab CI, Jenkins) работает по **Push-модели**: пайплайн собирает образ, делает `kubeconfig` и запускает `helm upgrade`/`kubectl apply` прямо с раннера в кластер.
*Минусы:* Вы должны отдать CI/CD ключи (admin) от продакшен-кластера. Если CI взломают — взломают весь прод. Нет защиты от Configuration Drift (кто-то зашёл в кластер и руками удалил Deployment — CI/CD об этом не узнает).

**GitOps (Pull-модель)** решает это. В кластере работает внутренний агент (ArgoCD или Flux). Он имеет Read-Only доступ к Git-репозиторию с манифестами. Агент постоянно опрашивает (pull) Git. Если видит изменения — сам (изнутри кластера) применяет их к API. Ключи админа не покидают кластер. Входящие соединения снаружи в кластер не требуются вообще.

## 2. Configuration Drift и Reconciliation

**Configuration Drift** возникает, когда кто-то из инженеров руками меняет состояние кластера (`kubectl edit`, `kubectl scale` — например, ночью для тушения пожара), и это состояние расходится с тем, что написано в Git (Source of Truth).

GitOps-агент постоянно (обычно раз в 1-3 минуты) сверяет желаемое состояние (Git) с фактическим (кластер) — это тот же Reconciliation Loop, что лежит в основе встроенных контроллеров k8s (см. [`../11_operators_and_crds/`](../../11_operators_and_crds/)), просто применённый не к одному ресурсу, а ко всему набору манифестов из репозитория. Если он видит расхождение — приложение помечается как `OutOfSync`. Если включено самовосстановление (у ArgoCD — `selfHeal`, у Flux — аналогичный `prune`/reconcile у Kustomization CR), агент немедленно затирает ручные изменения, возвращая состояние кластера к тому, что описано в Git.

## 3. Автоматическое обновление образов (Image Updater)

Если манифесты лежат в Git, как выкатить новую версию приложения при `git push` в репозиторий с кодом (а не с манифестами)?

1. **CI Push**: CI-пайплайн собирает образ `app:v1.2`, пушит в registry, затем сам делает git-коммит (меняет `values.yaml`/тег образа с `v1.1` на `v1.2`) в репозиторий с манифестами. GitOps-агент видит коммит и деплоит. Частый паттерн, но засоряет Git техническими коммитами.
2. **Image Updater Controller** (у ArgoCD и Flux есть свои реализации): контроллер в кластере постоянно пингует registry, видит появление нового тега по regex-правилам, сам решает обновить манифесты и может сам сделать коммит обратно в Git (write-back) — без участия CI-пайплайна вообще.

## 4. Секреты в GitOps: Git требует всё, а пароли туда нельзя

Философия GitOps требует, чтобы Git был единственным источником истины — но хранить пароли от БД в открытом виде в Git нельзя. Индустриальный стандарт — секреты в Git хранятся **в зашифрованном виде**, а расшифровка происходит только внутри кластера:
- **SOPS / SealedSecrets** — шифруете файл публичным ключом локально, в Git лежит криптографический мусор; контроллер в кластере (с приватным ключом) расшифровывает манифест при синхронизации.
- **External Secrets Operator (ESO)** — секреты вообще не существуют в Git; контроллер в кластере сам обращается к Vault/AWS Secrets Manager и материализует k8s Secret напрямую в памяти кластера.

## 5. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему GitOps (Pull-модель) считается гораздо безопаснее классического пайплайна (Push-модели) с точки зрения информационной безопасности?**
*Ответ:* В классической Push-модели CI/CD-серверу требуется токен с админскими правами на Kubernetes кластер (чтобы сделать `kubectl apply`). Если хакер получает доступ к пайплайнам, он захватывает production-кластер. В GitOps агент находится *внутри* кластера за файрволом. Ему нужен только Read-Only доступ к Git-репозиторию. Входящие соединения снаружи в кластер не требуются. Компрометация CI/CD сервера не даёт прямого доступа к API k8s.

**2. Что такое Configuration Drift и как GitOps-агент его обнаруживает и лечит?**
*Ответ:* Дрейф возникает, когда инженер руками меняет состояние кластера (`kubectl edit`), и оно расходится с Git. GitOps-агент постоянно сверяет Git и Cluster через тот же Reconciliation Loop, что лежит в основе обычных k8s-контроллеров. Если он видит дрейф, приложение переходит в статус `OutOfSync`. Если включено самовосстановление, агент немедленно затирает ручные изменения и возвращает состояние кластера к описанному в Git.

**3. Разработчик удалил YAML манифест ConfigMap из Git-репозитория. GitOps-агент синхронизировался, но ConfigMap в кластере не удалился. Какая настройка пропущена?**
*Ответ:* Пропущена настройка авто-удаления (`prune`). По умолчанию GitOps-агенты только добавляют и обновляют ресурсы, чтобы избежать случайного катастрофического удаления данных в продакшене при ошибках парсинга Git. Чтобы агент физически удалял ресурсы, исчезнувшие из Git, опцию prune нужно включать явно.

**4. Как управлять секретами (паролями к БД) в GitOps-парадигме, если GitOps требует хранить всё в Git, а пароли в Git хранить нельзя?**
*Ответ:* Секреты хранятся в репозитории в зашифрованном виде. Индустриальный стандарт — `Sealed Secrets`, `SOPS` или `External Secrets Operator`. Например, с SealedSecrets вы шифруете пароль публичным ключом, кладёте манифест `SealedSecret` в Git. GitOps-агент синхронизирует его в кластер, где контроллер SealedSecrets (имея приватный ключ) расшифровывает его и создаёт настоящий k8s `Secret`. Исходный пароль остаётся в безопасности на всём пути через Git и CI.

**5. Если в GitOps-агенте выключить авто-синхронизацию, зачем вообще использовать GitOps?**
*Ответ:* Даже без авто-синка GitOps даёт огромную ценность в виде наблюдаемости и аудита. В UI (или через CLI) вы наглядно видите статус `OutOfSync`, показывающий diff между тем, что в Git, и тем, что в продакшене, и можете запустить синхронизацию вручную, одной командой. Это даёт жёсткий контроль над моментом релиза (например, для соблюдения Maintenance Windows), сохраняя все преимущества Git как единого источника истины.
