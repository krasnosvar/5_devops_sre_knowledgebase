## 1. Архитектура RBAC: Role и RoleBinding

В Kubernetes контроль доступа (RBAC — Role-Based Access Control) работает на принципе **Deny All by default**. Если у вас нет явного разрешения, вы получите HTTP 403 Forbidden.
- **Role**: Описывает "ЧТО можно делать" (список ресурсов и глаголов `get`, `list`, `create`). Привязана к конкретному Namespace.
- **ClusterRole**: То же самое, но действует на уровне всего кластера. Только через ClusterRole можно дать права на глобальные ресурсы (Nodes, PersistentVolumes).
- **RoleBinding**: Связывает `Role` (Что можно) с `Subject` (Кому можно — User, Group или ServiceAccount).
- **ClusterRoleBinding**: Дает права на ресурсы во *всех* неймспейсах кластера (опасно!).

Важный нюанс: `RoleBinding` может ссылаться на `ClusterRole` — в этом случае права из ClusterRole применяются **только в неймспейсе этого RoleBinding**, а не глобально (см. вопрос 1 в Q&A).

## 2. ServiceAccounts и Токены (Projected Volumes)

Люди (Users) в k8s аутентифицируются через внешние системы (OIDC, X.509 сертификаты). У k8s нет базы логинов и паролей.
А вот поды (приложения) аутентифицируются в API-сервере через **ServiceAccount** (SA).
Когда вы не указываете SA в манифесте пода, под получает SA `default`.

*Как под получает токен?*
Раньше k8s создавал Secret типа `kubernetes.io/service-account-token` и монтировал его в под навсегда. Это было небезопасно (токен не истекал).
Теперь (Bound Service Account Token Volume) Kubelet запрашивает у API-сервера **временный** OIDC/JWT токен с ограниченным сроком жизни (например, 1 час) и привязанный строго к имени Пода. Этот токен проецируется (Projected Volume) внутрь файловой системы контейнера по пути `/var/run/secrets/kubernetes.io/serviceaccount/token`. Kubelet автоматически обновляет его на лету.

Каждый микросервис должен иметь свой уникальный SA, а не использовать `default`. Автомонтирование токена (`automountServiceAccountToken: false`) нужно отключать для подов, которым не нужно общаться с k8s API — это снижает поверхность атаки (см. вопрос 2).

## 3. Как аутентифицируются пользователи (OIDC)

SRE и разработчики используют `kubeconfig`. Kubeconfig содержит либо клиентский X.509 сертификат (выпущенный внутренним CA кластера), либо OIDC-токен.
В production-средах всегда используется **OIDC (OpenID Connect)**:
1. Разработчик авторизуется в корпоративном Keycloak / Google Workspace / Azure AD.
2. Получает JWT-токен и кладет его в `kubeconfig`.
3. При выполнении `kubectl get pods`, токен отправляется в `kube-apiserver`.
4. API-сервер берет публичный ключ из Keycloak, валидирует подпись JWT-токена, читает из него поле `email` и поле `groups` (например, `devops-team`).
5. Передает эту группу в RBAC модуль, который проверяет наличие RoleBinding для группы `devops-team`.

В Kubernetes **нет** ресурса типа `User` или `Group` в etcd — это полностью делегировано внешнему IdP (см. вопрос 4).

## 4. Безопасность пода: SecurityContext и Pod Security Admission

По умолчанию Docker и k8s запускают процессы от имени пользователя `root` (UID 0).
**Best Practices (SecurityContext)**:
- `runAsNonRoot: true` — жесткий запрет запуска под root.
- `readOnlyRootFilesystem: true` — запрет записи в корень ФС (защита от скачивания зловредов).
- `allowPrivilegeEscalation: false` — запрет использования sudo (suid битов).
- Отбрасывание всех Linux Capabilities (`drop: ["ALL"]`).

**Pod Security Admission (PSA)**:
Встроенный контроллер допуска (пришел на замену устаревшему PodSecurityPolicy). Работает на уровне namespace через лейблы: `pod-security.kubernetes.io/enforce: restricted`. Если разработчик попытается задеплоить под от root в этот неймспейс, API-сервер мгновенно отвергнет YAML манифест.

## 5. NetworkPolicy как часть security-периметра

Механика NetworkPolicy (Default Deny, CNI enforcement, podSelector/namespaceSelector) разобрана в [`../../../03_networking/`](../../../03_networking/) §3 — не повторяем её здесь. С точки зрения безопасности важна одна частая ошибка (см. вопрос 10): секция `ingress: []` блокирует только входящий трафик, а исходящий по умолчанию остаётся разрешённым, если `egress` не объявлен явно — то есть "заблокировал NetworkPolicy" ещё не значит "изолировал под" в модели Zero Trust.

## 6. Управление Секретами (External Secrets, SOPS)

Встроенные `k8s Secrets` — это просто Base64 кодированные строки в базе `etcd` (не зашифрованные!).
Два правильных паттерна:
1. **External Secrets Operator (ESO)**: В кластере крутится контроллер. Вы создаете манифест `ExternalSecret`, контроллер идет в AWS Secrets Manager или HashiCorp Vault (через OIDC аутентификацию подов), берет пароль оттуда и генерирует нативный k8s Secret прямо в оперативной памяти кластера.
2. **SOPS / SealedSecrets**: Вы локально шифруете файл `secrets.yaml` публичным ключом. В Git лежит криптографический мусор. Контроллер в кластере (имеющий приватный ключ) расшифровывает манифест при деплое.

## 7. Runtime Security: Falco и Trivy

- **Trivy / Clair**: Сканеры уязвимостей. Ищут устаревшие версии библиотек (CVE) в Docker-образах до или во время деплоя.
- **Falco (Runtime Security)**: Глубокая инспекция на уровне ядра Linux (через eBPF). Когда приложение уже работает (Runtime), Falco слушает системные вызовы ядра. Если PHP-приложение вдруг попытается запустить команду `bash` (вызвать `execve`) или прочитать файл `/etc/shadow`, Falco немедленно заблокирует это и отправит Critical Алерт в Slack/OpsGenie. Это защита от 0-day уязвимостей и Remote Code Execution (RCE).

## 8. Аудит (Audit Logs)

Для расследования инцидентов ИБ в k8s используется Audit Log.
Он включается флагами на `kube-apiserver`. Политика аудита позволяет логировать:
- `RequestReceived`: Запрос только пришел.
- `ResponseComplete`: Запрос обработан (сохранен в etcd).
- `Metadata`: Логировать только факт запроса, кто и к какому ресурсу обращался.
- `RequestResponse`: Логировать полное содержимое YAML, которое передал пользователь. (Опасно: в логи попадет содержимое Secrets!).

## 9. Типовые вопросы на собеседовании (Interview Q&A)

**1. Вы написали `RoleBinding`, который связывает `ClusterRole` под названием `admin` (в ней полные права) с разработчиком Васей в неймспейсе `dev`. Получит ли Вася админские права на весь кластер?**
*Ответ:* Нет, не получит. Это очень частый паттерн в k8s. Привязка глобальной `ClusterRole` через локальный `RoleBinding` работает так: Вася получит права админа **только** внутри неймспейса `dev`. Он сможет удалить Deployment в `dev`, но не сможет удалить Node или посмотреть поды в неймспейсе `prod`. Чтобы дать глобальные права на весь кластер, нужно использовать `ClusterRoleBinding`.

**2. Разработчик оставил `automountServiceAccountToken: true` (по умолчанию) в поде веб-приложения, которое было взломано хакером (RCE). Что именно хакер сможет сделать внутри кластера?**
*Ответ:* В каждом поде k8s автоматически монтирует JWT-токен доступа к API-серверу по пути `/var/run/secrets/kubernetes.io/serviceaccount/token`. Хакер прочитает этот файл. Далее права зависят от ServiceAccount. Если это `default` SA без привязанных ролей (RoleBinding), хакер сможет делать лишь базовые вызовы. Но если к этому SA привязана роль с правами чтения секретов (`get secrets`), хакер выкачает пароли от всех баз данных в этом namespace. Именно поэтому автоматическое монтирование токена нужно отключать для подов, не общающихся с API k8s.

**3. Вы настраиваете аудит (Audit Policy) в API-сервере. Как сделать так, чтобы данные из ресурсов типа `Secret` не попадали в логи аудита в открытом виде?**
*Ответ:* В манифесте `AuditPolicy` необходимо явно создать правило, которое задает уровень `Metadata` для ресурсов типа `secrets`. Уровень `Metadata` означает, что API-сервер запишет в лог: "Пользователь Вася сделал GET-запрос к Secret X". Если оставить уровень `RequestResponse`, то API-сервер запишет в лог всё тело ответа, включая расшифрованные base64 пароли, что является грубейшим нарушением ИБ.

**4. Может ли в Kubernetes быть объект типа `User` (пользователь) и как его создать через `kubectl create user`?**
*Ответ:* В Kubernetes **не существует** ресурса типа `User` или `Group` в etcd (вы не можете сделать `kubectl get users`). K8s полностью делегирует управление пользователями внешним провайдерам (IdP), таким как OIDC (Keycloak), или полагается на сертификаты X.509. Если в поле Subject сертификата написано `CN=Alice, O=devs`, API-сервер просто поверит, что пришел пользователь Alice из группы devs. Создать пользователя командой `kubectl` невозможно.

**5. Зачем нужны `ClusterRole` (глобальные роли), если у нас всего один неймспейс в кластере?**
*Ответ:* Даже если у вас один неймспейс `default`, в Kubernetes существуют ресурсы, которые **не принадлежат никакому неймспейсу** (Nodes, PersistentVolumes, StorageClasses, CustomResourceDefinitions). Выдать права на них через обычную `Role` физически невозможно, так как `Role` всегда привязана к неймспейсу. Для них необходима `ClusterRole`.

**6. Как работает механизм "Имперсонации" (Impersonation) в Kubernetes?**
*Ответ:* Имперсонация позволяет пользователю выполнить запрос к API-серверу **от лица** другого пользователя или ServiceAccount'а (команда `kubectl get pods --as=system:serviceaccount:default:my-sa`). Это используется для дебага RBAC политик. Чтобы выполнить такой запрос, сам админ должен обладать правами на совершение глагола `impersonate` к ресурсу `users` или `serviceaccounts`.

**7. В вашем kubeconfig прописан токен OIDC. API-сервер потерял связь с провайдером OIDC (Keycloak). Сможете ли вы сделать `kubectl get pods`?**
*Ответ:* Сможете. OIDC использует **JWT (JSON Web Tokens)**, содержащий электронную цифровую подпись. API-серверу не нужно обращаться к Keycloak при каждом запросе — при старте он скачивает открытые ключи (JWKS) провайдера и кэширует их. Пока JWT токен не просрочен, API-сервер валидирует подпись математически, даже если сам Keycloak недоступен.

**8. Что такое `system:masters` в контексте сертификатов Kubernetes?**
*Ответ:* Жестко захардкоженная в исходном коде API-сервера "супер-группа" (Break-glass access). Любой пользователь, чей сертификат имеет в поле Organization (O) значение `system:masters`, обходит любые проверки RBAC и получает абсолютные права администратора на весь кластер. Эта группа не описана ни в одном RoleBinding, её нельзя удалить или ограничить. Поэтому утечка ключей пользователя `kubernetes-admin` — фатальный инцидент безопасности.

**9. Объясните процесс `SubjectAccessReview`. Зачем к этому API обращаются сторонние приложения (например, ArgoCD)?**
*Ответ:* `SubjectAccessReview` — специальный ресурс в Kubernetes API, позволяющий задать вопрос: "Сможет ли пользователь X сделать действие Y с ресурсом Z?". API-сервер прогоняет запрос через все цепочки RBAC и возвращает `allowed: true/false`. Сторонние приложения (ArgoCD, UI-дашборды) используют это, чтобы скрыть кнопку "Удалить Pod" в интерфейсе, если у пользователя нет на это прав в k8s.

**10. Вы добавили `NetworkPolicy`, которая запрещает весь входящий трафик к подам Backend'а. Но поды все равно могут ходить в интернет и в базу данных. Почему?**
*Ответ:* NetworkPolicy четко разделяет направления: `Ingress` (входящий) и `Egress` (исходящий). Если манифест содержит только секцию `ingress: []`, он блокирует весь входящий трафик, но **весь исходящий остается разрешенным** по умолчанию, если секция `egress` не задана. Для полной изоляции (Default Deny) нужно явно объявить пустую секцию `egress: []`, после чего точечно разрешать доступ к базе данных и к порту 53 (DNS кластера).

**11. В кластере включен Pod Security Admission (PSA) в режиме `restricted`. Разработчик деплоит под с базовым Nginx, но он отклоняется с ошибкой `Privilege escalation is not explicitly denied`. Почему?**
*Ответ:* Профиль `restricted` требует максимальной явности. По умолчанию контейнеры могут использовать SUID биты для повышения привилегий (например, утилита `ping`). Чтобы соответствовать строгому профилю, манифест **обязан** явно содержать `allowPrivilegeEscalation: false` и `drop: ["ALL"]` в `securityContext`. Без явного запрета API-сервер считает манифест небезопасным.

**12. Чем `External Secrets Operator` (ESO) архитектурно безопаснее, чем хранение секретов в Helm (values.yaml) через SOPS?**
*Ответ:* SOPS шифрует секреты в Git, но они все равно проходят через CI/CD контур — пайплайн должен расшифровать их и отправить в k8s API в открытом виде, где они могут осесть в логах или стейте Helm'а. В ESO секреты вообще **не существуют** в Git и пайплайнах: они лежат в защищенном Vault/AWS Secrets Manager, а контроллер ESO работает внутри кластера и материализует секреты напрямую в память Kubernetes.

**13. Как работает утилита `Falco` и почему она использует eBPF?**
*Ответ:* Falco — инструмент поведенческой безопасности в реальном времени (Runtime), в отличие от сканера образов (Trivy), который работает *до* запуска. Falco использует технологию ядра Linux **eBPF**, перехватывая системные вызовы ядра с минимальным оверхедом по CPU. Если Nginx внезапно делает сисколл `execve` для запуска `/bin/sh` (признак взлома), Falco перехватывает это и мгновенно отправляет алерт.

**14. В чем заключается опасность монтирования `hostPath` в поды и как это используют хакеры?**
*Ответ:* `hostPath` монтирует физическую директорию Worker-ноды внутрь файловой системы контейнера. Если хакеру удастся запустить под с `hostPath: /`, он получит доступ ко всей файловой системе сервера: сможет прочитать конфигурацию Kubelet, подменить бинарники, получить токены других подов на этом узле — и полностью скомпрометировать кластер. Использование `hostPath` должно быть запрещено через OPA Gatekeeper или PSA для непривилегированных подов.

**15. Как безопаснее всего разрешить доступ к базе данных Postgres (порт 5432) только из подов Backend?**
*Ответ:* Использовать `podSelector` с лейблами, а не IP-адреса (в k8s они динамические):
```yaml
ingress:
- from:
  - podSelector:
      matchLabels:
        app: backend
  ports:
  - port: 5432
```
Фильтрация по лейблам работает через внутренний CNI-плагин (Calico/Cilium) на уровне правил iptables/eBPF и не ломается при рестарте подов.
