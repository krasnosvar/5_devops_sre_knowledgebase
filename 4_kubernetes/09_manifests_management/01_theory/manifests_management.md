## 1. Анатомия манифеста: apiVersion/kind/metadata/spec

Любой ресурс k8s — это четыре обязательных поля:

```yaml
apiVersion: apps/v1      # группа API + версия (не просто "версия k8s")
kind: Deployment         # тип ресурса
metadata:                # имя, namespace, labels, annotations — "кто это"
  name: myapp
spec:                    # желаемое состояние — "что мы хотим получить"
  replicas: 3
```

`apiVersion` — это не версия Kubernetes, а версия конкретной API-группы. `apps/v1` (Deployment, StatefulSet) стабилизировалась в 1.9, `batch/v1` (Job) — своя ветка версионирования, `networking.k8s.io/v1` (Ingress) — своя. Ресурс без группы (`v1`) — это core API (Pod, Service, ConfigMap). Путаница здесь — частая причина ошибки `no matches for kind X in version Y`.

## 2. Labels vs Annotations — когда что

- **Labels** — индексируемые key-value поля для **выборки**. По ним работают Selectors (Service находит свои поды, Deployment — свои ReplicaSet). Стандартные ключи: `app.kubernetes.io/name`, `app.kubernetes.io/instance`, `app.kubernetes.io/version`.
- **Annotations** — тоже key-value, но НЕ индексируются и не участвуют в Selectors. Предназначены для метаданных, которые читают инструменты, а не k8s (checksum конфига для Helm, `external-dns.alpha.kubernetes.io/hostname`, произвольные заметки).

Практическое правило: если по полю нужно **фильтровать/находить** ресурсы (`kubectl get pods -l app=myapp`) — это label. Если поле нужно только **прочитать** конкретному контроллеру — это annotation.

## 3. Client-Side Apply vs Server-Side Apply

```bash
kubectl apply -f deploy.yaml
```
Классический (Client-Side Apply, CSA) `apply` хранит в самом объекте аннотацию `kubectl.kubernetes.io/last-applied-configuration` — сериализованный YAML предыдущего apply. При новом apply клиент **локально** сравнивает три состояния (last-applied, ваш новый YAML, live-объект) и решает, какие поля добавить/убрать. Проблема: это клиентская логика, разные версии `kubectl` считают diff по-разному, а сам YAML раздувает размер объекта в etcd.

```bash
kubectl apply -f deploy.yaml --server-side --field-manager=ci-pipeline
```
**Server-Side Apply (SSA)** переносит эту логику на API-сервер. Каждое поле объекта помечается владельцем (`fieldManager`) — кто его последним записал. Если два разных актора (человек через `kubectl edit` и CI через `apply`) правят одно и то же поле, сервер вернёт **conflict**, а не молча затрёт чужое изменение (в отличие от CSA, которая просто перезапишет). Это то, на чём в проде должны стоять GitOps-агенты (см. [`../../07_gitops/02_argocd/`](../../07_gitops/02_argocd/)) — иначе ручные правки и автоматический sync тихо конфликтуют.

## 4. dry-run и diff перед применением

```bash
# Проверить синтаксис и что примет API-сервер, ничего не применяя
kubectl apply -f deploy.yaml --dry-run=server

# Увидеть, ЧТО именно изменится в кластере (а не просто отрендерить YAML)
kubectl diff -f deploy.yaml
```
`--dry-run=client` рендерит и валидирует YAML только локально (не видит live-состояние). `--dry-run=server` прогоняет запрос через реальный API-сервер (включая admission-контроллеры и валидацию CRD-схем), но не сохраняет в etcd — ловит на порядок больше ошибок. `kubectl diff` — единственная команда, которая реально показывает дельту между live-объектом и вашим файлом, а не просто печатает итоговый YAML.

## 5. Multi-document YAML и порядок применения ресурсов

Один файл может содержать несколько ресурсов через разделитель `---`:
```yaml
apiVersion: v1
kind: ConfigMap
metadata: {name: cfg}
data: {key: value}
---
apiVersion: apps/v1
kind: Deployment
metadata: {name: myapp}
spec: { ... }
```
`kubectl apply -f file.yaml` применяет их в том порядке, в котором они записаны в файле, но **без ожидания готовности** предыдущего — Deployment из примера выше отправится на создание сразу вслед за ConfigMap, даже если ConfigMap ещё не полностью обработан API-сервером. Для зависимостей со строгим порядком (сначала CRD, потом CR, использующий эту CRD) обычному `apply` нельзя доверять — для этого в GitOps-инструментах существуют примитивы вроде SyncWaves (см. [`../../07_gitops/02_argocd/`](../../07_gitops/02_argocd/)).

## 6. Зачем вообще Helm/Kustomize, если есть kubectl apply

Сырой `kubectl apply` прекрасно работает для одного окружения. Проблема начинается при 3+ окружениях (dev/stage/prod) с похожими, но не идентичными манифестами: копипастить YAML и вручную править 5 строк в каждой копии — гарантированный дрейф и ошибки. Отсюда — две принципиально разные стратегии:
- **Шаблонизация** (Helm, → [`../02_helm/`](../02_helm/)) — один шаблон + разные `values.yaml` на окружение.
- **Патчинг без шаблонов** (Kustomize, → [`../03_kustomize/`](../03_kustomize/)) — один `base` + оверлеи с точечными патчами.

Обе темы разобраны в своих разделах — здесь достаточно понимать, что и то, и другое в конце концов превращается в сырой YAML и применяется тем же `kubectl apply`/SSA, который описан выше.

## 7. Типовые вопросы на собеседовании (Interview Q&A)

**1. В чём разница между `kubectl apply --dry-run=client` и `--dry-run=server`? Какие ошибки поймает второй, но не первый?**
*Ответ:* `--dry-run=client` — чисто локальная операция: `kubectl` валидирует синтаксис YAML и структуру ресурса по встроенной схеме, но не обращается к API-серверу вообще. `--dry-run=server` отправляет запрос на реальный API-сервер (через весь конвейер: аутентификация → авторизация → admission-webhooks → валидация CRD-схемы), но останавливается перед записью в etcd. Он поймает то, что не видно локально: нарушение политики Kyverno/OPA, конфликт с существующим ресурсом, ошибку в кастомной CRD-схеме, которой нет на вашей локальной машине.

**2. Два разных актора — CI-пайплайн (`kubectl apply`) и инженер (`kubectl edit`) — правят разные поля одного и того же Deployment. При Client-Side Apply второй `apply` из CI неожиданно стирает ручное изменение инженера. Как Server-Side Apply решает эту проблему?**
*Ответ:* При CSA у объекта в etcd есть только одна аннотация `last-applied-configuration`, которая знает лишь о том, что применял именно CI. Ручное изменение через `kubectl edit` в эту аннотацию не попадает, и следующий `apply` от CI, сравнивая только "свою" историю с новым YAML, считает ручное поле лишним и убирает его. При SSA каждое поле помечено `fieldManager`, который его последним записал. Если CI попытается изменить поле, которым сейчас владеет `kubectl edit` (ручной manager), сервер вернёт **conflict**, а не молча перезапишет — CI обязан либо уступить (`--force-conflicts` осознанно), либо оставить поле в покое.

**3. Почему `kubectl apply -f multi-doc.yaml`, где ConfigMap идёт раньше Deployment, не гарантирует, что ConfigMap будет полностью готов к моменту создания Deployment?**
*Ответ:* `kubectl apply` с multi-document файлом последовательно отправляет запросы на создание/обновление ресурсов в порядке их следования в файле, но не ждёт, пока предыдущий ресурс перейдёт в статус `Ready` — он лишь дожидается ответа API-сервера о том, что запрос принят (объект сохранён в etcd). Для ConfigMap это обычно не проблема (он не имеет состояния готовности), но для зависимостей вроде "сначала CRD, а не раньше — CR" порядка в файле недостаточно: нужен отдельный механизм ожидания (readiness gate, GitOps sync waves, Helm hooks).

**4. Чем annotation `external-dns.alpha.kubernetes.io/hostname` принципиально отличается от label с тем же значением, если оба варианта технически валидный YAML?**
*Ответ:* Формально можно записать хоть в label, хоть в annotation — k8s не проверяет семантику ключа. Но labels участвуют в Selectors и индексируются API-сервером для быстрого поиска (`kubectl get pods -l key=value`); их специально ограничивают короткими, "структурными" значениями. Annotations не индексируются и не участвуют в выборках — предназначены для метаданных, которые читает конкретный контроллер (в данном случае ExternalDNS) вне механизма Selector. Если бы это был label, ничего бы не сломалось технически, но так теряется сигнал для читающего код инженера: "это конфигурация для стороннего контроллера, а не критерий группировки ресурсов".
