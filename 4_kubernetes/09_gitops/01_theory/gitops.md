## 1. Что такое GitOps: четыре принципа

GitOps — способ доставки, при котором желаемое состояние системы целиком
описано в Git, а специальный агент постоянно приводит к нему реальное
состояние. Рабочая группа OpenGitOps (CNCF) формулирует четыре принципа:

1. **Декларативность** — описано *что* должно быть (манифесты, Helm-чарты,
   Kustomize-оверлеи), а не *как* туда прийти (скрипт из `kubectl` команд).
2. **Версионирование и неизменяемость** — желаемое состояние хранится в
   системе с историей (Git): каждое изменение — коммит с автором, ревью и
   возможностью `git revert`.
3. **Автоматическое получение (pull)** — агент сам забирает желаемое
   состояние из источника, а не ждёт, пока его "протолкнут" снаружи.
4. **Непрерывная сверка (reconciliation)** — агент не один раз применяет
   изменения, а постоянно сравнивает желаемое с фактическим и устраняет
   расхождения.

Важно: GitOps не заменяет Helm и Kustomize, а использует их. Агент берёт
из Git чарт или оверлей (см.
[`07_manifests_management`](../../07_manifests_management/)), рендерит
его в обычный YAML и применяет в кластер.

## 2. Push vs Pull модель деплоя

**Push-модель** (классический CI/CD: GitLab CI, Jenkins, GitHub Actions):

1. Пайплайн собирает образ и пушит его в registry.
2. Раннер получает `kubeconfig` с правами на запись в кластер.
3. Раннер сам выполняет `helm upgrade`/`kubectl apply` — изменения
   "проталкиваются" в API-сервер снаружи.

*Минусы:*
- CI/CD держит credentials с правами записи в прод-кластер. Взлом CI или
  утечка переменной пайплайна = доступ к проду.
- API-сервер должен быть сетево доступен раннеру (или раннер живёт внутри
  периметра).
- Деплой — разовое событие: после зелёного пайплайна никто не следит, что
  в кластере осталось то же самое. Ручной `kubectl edit` или удалённый
  Deployment CI не заметит до следующего запуска.
- Состояние кластера = сумма всех когда-либо выполненных пайплайнов, а не
  содержимое какого-то одного места.

**Pull-модель (GitOps):**

1. CI собирает образ и меняет тег в Git-репозитории с манифестами (или
   это делает Image Updater, §5). В кластер CI не ходит вообще.
2. Агент внутри кластера (Argo CD, Flux) периодически опрашивает Git
   (по умолчанию раз в несколько минут) или получает webhook о новом
   коммите — webhook лишь ускоряет опрос, источник истины всё равно Git.
3. Агент рендерит манифесты и применяет их к API своего кластера через
   in-cluster ServiceAccount.

*Что это даёт:*
- Credentials с правами записи не покидают кластер; агенту нужен только
  read-only доступ к Git (и к registry, если используется Image Updater).
- Входящие соединения в кластер не нужны: все соединения исходящие (агент
  → Git), что удобно для кластеров за NAT/файрволом.
- Git становится единственным источником истины и журналом аудита: кто,
  что и когда поменял — видно в истории коммитов и Pull Request'ах.
- Откат = `git revert`, а не поиск "какой пайплайн запускали в прошлый
  раз".

*Чего pull-модель не решает:* права записи в Git-репозиторий с
манифестами теперь равносильны правам деплоя в прод. Их защищают
обычными средствами Git: protected branches, обязательное ревью,
подписанные коммиты. Сам агент — тоже привилегированный компонент
(часто с `cluster-admin`), его права стоит сужать (у Argo CD — через
`AppProject`, у Flux — через `serviceAccountName` у `Kustomization`).

## 3. Reconciliation: как агент сверяет Git и кластер

Reconciliation loop — тот же паттерн, что лежит в основе встроенных
контроллеров k8s (см. [`11_operators_and_crds`](../../11_operators_and_crds/)):
"прочитать желаемое → прочитать фактическое → устранить разницу →
повторить". GitOps-агент применяет его не к одному объекту, а ко всему
набору манифестов из репозитория. Один цикл выглядит так:

1. **Fetch.** Забрать нужную ревизию из Git (ветку, тег, коммит).
   Ревизия фиксируется по SHA — агент применяет ровно то, что
   закоммичено.
2. **Render.** Отрендерить манифесты: сырой YAML как есть, `kustomize
   build` для оверлеев, `helm template` для чартов.
3. **Diff.** Сравнить отрендеренные объекты с live-объектами в кластере.
   Сравниваются только поля, заданные в Git: поля, которые проставляют
   API-сервер и контроллеры (`status`, `metadata.uid`, defaulting),
   игнорируются — иначе всё было бы вечно "не синхронизировано".
4. **Apply.** Если есть разница и включена автосинхронизация — применить
   изменения (Argo CD — `kubectl apply` или Server-Side Apply, Flux —
   Server-Side Apply). Объекты, удалённые из Git, удаляются из кластера
   только при включённом `prune`.
5. **Health.** Оценить здоровье применённых ресурсов (Deployment
   раскатился, Pod'ы Ready) и записать статус.

Два независимых статуса, которые нельзя путать:
- **Sync status** (`Synced`/`OutOfSync`) — совпадает ли кластер с Git.
- **Health status** (`Healthy`/`Progressing`/`Degraded`) — работает ли
  то, что применено.

Приложение может быть `Synced` и `Degraded` одновременно: в Git записан
образ с опечаткой в теге, агент честно его применил, Pod'ы висят в
`ImagePullBackOff`. GitOps гарантирует соответствие Git, а не
работоспособность того, что в Git записано.

## 4. Configuration Drift: обнаружение и самовосстановление

**Configuration Drift** возникает, когда кто-то меняет состояние кластера
в обход Git (`kubectl edit`, `kubectl scale` — например, ночью при
тушении пожара), и оно расходится с Source of Truth.

На шаге Diff агент видит расхождение и помечает приложение как
`OutOfSync`. Дальше поведение зависит от настроек:
- **Только обнаружение** — агент показывает diff, но ничего не делает;
  человек решает, что правильно: вернуть кластер к Git или закоммитить
  ручное изменение в Git.
- **Самовосстановление** — агент сам затирает ручное изменение и
  возвращает состояние из Git. У Argo CD это отдельный флаг `selfHeal`
  (без него автосинхронизация срабатывает только на новые коммиты, а не
  на дрейф в кластере). У Flux `Kustomization` заново применяет
  манифесты на каждом `interval`, поэтому ручные правки управляемых полей
  откатываются по умолчанию.

Ловушка: если какое-то поле законно меняет другой контроллер (HPA меняет
`replicas`), агент будет бесконечно "чинить" это поле, сражаясь с HPA.
Решение — не указывать `replicas` в манифесте при наличии HPA или
явно исключить поле из сравнения (у Argo CD — `ignoreDifferences`).

## 5. Автоматическое обновление образов (Image Updater)

Если манифесты лежат в Git, как выкатить новую версию приложения при
`git push` в репозиторий с кодом (а не с манифестами)?

1. **CI Push в Git**: CI-пайплайн собирает образ `app:v1.2`, пушит в
   registry, затем сам делает коммит (меняет тег в `values.yaml` или
   `kustomization.yaml` с `v1.1` на `v1.2`) в репозиторий с манифестами.
   GitOps-агент видит коммит и деплоит. Частый паттерн, но засоряет Git
   техническими коммитами. Подробно — в
   [`6_cicd/05_gitops_cd`](../../../6_cicd/05_gitops_cd/).
2. **Image Updater Controller** (Argo CD Image Updater; у Flux —
   `ImageRepository`/`ImagePolicy`/`ImageUpdateAutomation`): контроллер
   в кластере периодически опрашивает registry, находит новый тег по
   правилу (semver-диапазон, regex) и сам делает коммит обратно в Git
   (write-back) — без участия CI-пайплайна.

## 6. Секреты в GitOps: Git требует всё, а пароли туда нельзя

Философия GitOps требует, чтобы Git был единственным источником истины —
но хранить пароли от БД в открытом виде в Git нельзя. Стандартные
решения — секреты в Git хранятся **в зашифрованном виде** (или не
хранятся вовсе), а расшифровка происходит только внутри кластера:
- **SOPS / SealedSecrets** — шифруете файл публичным ключом локально, в
  Git лежит шифротекст; контроллер в кластере (с приватным ключом)
  расшифровывает манифест при синхронизации.
- **External Secrets Operator (ESO)** — секреты вообще не существуют в
  Git; в Git лежит только `ExternalSecret` со ссылкой, а контроллер в
  кластере сам обращается к Vault/AWS Secrets Manager и создаёт k8s
  Secret.

## 7. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему GitOps (Pull-модель) считается гораздо безопаснее
классического пайплайна (Push-модели) с точки зрения информационной
безопасности?**
*Ответ:* В классической Push-модели CI/CD-серверу требуется токен с
правами записи в Kubernetes-кластер (чтобы сделать `kubectl apply`). Если
атакующий получает доступ к пайплайнам, он захватывает production-кластер.
В GitOps агент находится *внутри* кластера. Ему нужен только read-only
доступ к Git-репозиторию, входящие соединения в кластер не требуются.
Компрометация CI/CD сервера не даёт прямого доступа к API k8s. Подвох:
права записи в Git-репозиторий с манифестами теперь равносильны правам
деплоя, поэтому защита смещается в Git (protected branches, ревью).

**2. Что такое Configuration Drift и как GitOps-агент его обнаруживает и
лечит?**
*Ответ:* Дрейф возникает, когда инженер руками меняет состояние кластера
(`kubectl edit`), и оно расходится с Git. GitOps-агент постоянно сверяет
отрендеренные из Git объекты с live-объектами через Reconciliation Loop.
Если он видит дрейф, приложение переходит в статус `OutOfSync`. Если
включено самовосстановление (`selfHeal` у Argo CD; у Flux — по умолчанию
на каждом `interval`), агент затирает ручные изменения и возвращает
состояние кластера к описанному в Git.

**3. Разработчик удалил YAML манифест ConfigMap из Git-репозитория.
GitOps-агент синхронизировался, но ConfigMap в кластере не удалился.
Какая настройка пропущена?**
*Ответ:* Пропущена настройка авто-удаления (`prune`). По умолчанию
GitOps-агенты только добавляют и обновляют ресурсы, чтобы избежать
случайного катастрофического удаления в продакшене (например, при ошибке
в пути к директории, из-за которой агент "увидел" пустой репозиторий).
Чтобы агент удалял ресурсы, исчезнувшие из Git, prune включают явно.

**4. Как управлять секретами (паролями к БД) в GitOps-парадигме, если
GitOps требует хранить всё в Git, а пароли в Git хранить нельзя?**
*Ответ:* Секреты хранятся в репозитории в зашифрованном виде
(`Sealed Secrets`, `SOPS`) или не хранятся вовсе (`External Secrets
Operator`). Например, с SealedSecrets вы шифруете пароль публичным ключом,
кладёте манифест `SealedSecret` в Git. GitOps-агент синхронизирует его в
кластер, где контроллер SealedSecrets (имея приватный ключ) расшифровывает
его и создаёт настоящий k8s `Secret`. Исходный пароль не появляется в Git
и в CI в открытом виде.

**5. Если в GitOps-агенте выключить авто-синхронизацию, зачем вообще
использовать GitOps?**
*Ответ:* Даже без авто-синка GitOps даёт наблюдаемость и аудит: статус
`OutOfSync` и diff между Git и продакшеном видны в UI/CLI, синхронизацию
можно запустить вручную одной командой. Это даёт контроль над моментом
релиза (например, для Maintenance Windows), сохраняя Git как единый
источник истины и журнал изменений.

**6. Приложение в Argo CD одновременно `Synced` и `Degraded`. Как такое
возможно и что делать?**
*Ответ:* Sync status и Health status независимы. `Synced` значит, что
кластер совпадает с Git; `Degraded` — что применённые ресурсы не работают
(например, Pod'ы в `CrashLoopBackOff` или `ImagePullBackOff` из-за
неверного тега в Git). Агент честно применил то, что записано. Чинить
нужно Git: исправить тег или откатить коммит (`git revert`), а не
кластер руками — ручная правка будет либо затёрта, либо станет дрейфом.

**7. В кластере работают HPA и Argo CD с `selfHeal: true`. В Deployment в
Git указано `replicas: 3`. Что произойдёт под нагрузкой?**
*Ответ:* HPA поднимет `replicas` до, скажем, 8, Argo CD увидит дрейф
(`8 != 3`) и вернёт 3, HPA снова поднимет — два контроллера будут
бесконечно бороться за одно поле. Решение: убрать `replicas` из
манифеста в Git (тогда поле принадлежит HPA) или добавить
`ignoreDifferences` для `/spec/replicas`.

**8. Чем webhook от Git-хостинга отличается от периодического опроса в
pull-модели? Не превращает ли webhook GitOps обратно в push?**
*Ответ:* Нет. Webhook — лишь сигнал "проверь Git сейчас", он не несёт
манифестов и не даёт прав в кластер. Агент всё равно сам забирает
состояние из Git и сам применяет его. Webhook только сокращает задержку
между коммитом и синхронизацией; периодический опрос остаётся
страховкой на случай потерянного webhook.
