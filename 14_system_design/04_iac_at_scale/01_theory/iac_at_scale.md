## 1. Чем "много команд" отличается от "много ресурсов"

Terraform одинаково легко описывает и 10, и 10 000 ресурсов — технически
масштаб состояния (state) решается разделением на слои (см.
[`../../../5_iac/07_iac_patterns/`](../../../5_iac/07_iac_patterns/) §5). Настоящая сложность
системного дизайна IaC на масштабе **организации** — не объём кода, а то, что
десятки команд одновременно вносят изменения в общую инфраструктуру и должны
при этом не блокировать друг друга, не иметь возможности случайно сломать
чужой сервис, и проходить единые проверки безопасности и cost control.
Вопрос переходит из "как описать инфраструктуру" в "как организовать
репозитории, модули, state и гейты так, чтобы сотня инженеров могла менять
общую инфраструктуру безопасно и независимо".

## 2. Монорепо vs полирепо для IaC

- **Монорепо** (весь `.tf`-код организации в одном репозитории): единая
  история изменений, легко делать cross-cutting рефакторинг (переименовать
  общий модуль и сразу поправить всех потребителей одним PR), единый набор
  CI-проверок. Минус — PR от одной команды в одной "папке" репозитория всё
  равно технически может затронуть права CI на весь репозиторий, и при росте
  репозитория `terraform plan` на весь монорепо становится медленным, если не
  разбит на независимые слои/stack (см. State Decomposition).
- **Полирепо** (отдельный репозиторий на команду/домен): чёткие границы
  владения и прав доступа CI (репозиторий команды A физически не может
  тронуть ресурсы команды B), независимые циклы ревью. Минус — общие модули
  приходится версионировать и публиковать отдельно (см. §3), а
  cross-cutting изменения (обновить версию общего модуля у всех потребителей)
  превращаются в N отдельных PR вместо одного.
- Частый компромисс на практике: монорепо для **общих модулей/платформенного
  кода** (поддерживается платформенной командой), полирепо (или отдельные
  "stack"-директории с независимым state) для **конечных окружений
  приложений**, которые эти модули потребляют.

## 3. Модули как внутренний продукт

На масштабе организации переиспользуемые Terraform-модули перестают быть
просто "общим кодом" и становятся внутренним продуктом со своим контрактом:

- **Приватный registry модулей** (Terraform Cloud/Enterprise private registry,
  либо просто Git-теги + `source = "git::...?ref=vX.Y.Z"`) — команды-
  потребители явно указывают версию модуля, которую используют, вместо
  постоянного чтения `main`/`HEAD`.
- **SemVer-контракт**: platform-команда, владеющая модулем, обязана
  соблюдать семантику версий (patch — безопасно, minor — новые необязательные
  возможности, major — breaking changes в интерфейсе модуля/переменных).
  Без этой дисциплины потребители модуля боятся обновляться, и организация
  накапливает разъехавшиеся версии одного и того же модуля в проде.
- **Тестирование модулей перед публикацией** (`terraform test`, Terratest) —
  обязательная часть пайплайна релиза модуля, а не опция: ломающееся
  изменение в общем модуле на масштабе задевает все команды-потребители
  одновременно.

## 4. Разделение state на масштабе организации

На уровне одной команды выбор "один workspace на окружение" vs "отдельный
backend на окружение" — вопрос удобства (см. механику в
[`../../../5_iac/03_terraform_state/`](../../../5_iac/03_terraform_state/)). На уровне организации это
ещё и вопрос **блокировок и blast radius**:

- Общий state на много команд означает, что `terraform apply` одной команды
  блокирует (через state lock) `apply` всех остальных, работающих с тем же
  state — на масштабе это превращается в постоянную очередь и фактический
  bottleneck для параллельной работы множества команд.
- Разделение state по team/env/region (каждая единица владения — свой
  backend) убирает конкуренцию за блокировку и ограничивает blast radius
  ошибочного `apply` только зоной ответственности одной команды — тот же
  принцип изоляции, что у разделения кластеров Kubernetes
  (см. [`../02_single_vs_multi_cluster/`](../../02_single_vs_multi_cluster/)).
  Цена — явные "мосты" между слоями (data sources/remote state чтение
  значений из state другой команды), которые нужно поддерживать как
  публичный интерфейс.
- Инструменты вроде `Terragrunt` (см. [`../../../5_iac/05_terragrunt/`](../../../5_iac/05_terragrunt/))
  решают здесь DRY-проблему: конфигурация backend/provider не копируется
  вручную в каждый из сотен разделённых state, а генерируется из общего
  шаблона.

## 5. Policy as Code как организационный гейт

На масштабе ручной код-ревью каждого `terraform plan` силами security-команды
не масштабируется — число PR в день растёт быстрее, чем пропускная
способность ревьюеров. Policy as Code переносит часть проверок из "человек
читает diff" в "машина проверяет план по правилам до merge":

- `Sentinel` (Terraform Cloud/Enterprise) или `OPA/Rego`/`conftest` (open
  source, инструмент-агностичный) проверяют сгенерированный `plan` против
  правил организации: запрет публичных S3-бакетов, обязательные теги
  (`cost-center`, `owner`), запрет создания ресурсов вне разрешённого региона.
- Это тот же принцип, что Admission Controllers в Kubernetes (см.
  [`../../../4_kubernetes/06_security/`](../../../4_kubernetes/06_security/)) — централизованная,
  не обходимая команда-потребителем проверка на границе применения
  изменения, а не полагание на дисциплину каждого инженера.
- Гейт должен быть частью CI до `apply`, а не постфактум-аудитом: отклонённый
  `plan` не должен иметь физической возможности попасть в прод.

## 6. Дрифт-детект на масштабе тысяч ресурсов

Configuration Drift (ресурс в облаке изменили в обход Terraform — через
консоль или другой инструмент) описан механически в
[`../../../5_iac/07_iac_patterns/`](../../../5_iac/07_iac_patterns/) §4. На масштабе тысяч
ресурсов и десятков отдельных state (§4) проверка дрифта вручную
(`terraform plan` в каждом репозитории по очереди) нереалистична:

- Нужен **плановый автоматический прогон** `plan` (не `apply`!) по расписанию
  для каждого выделенного слоя state, с агрегацией результатов в единый
  дашборд/алерт ("в этих 12 stack обнаружен дрифт") вместо ручного обхода.
- Дрифт, обнаруженный автоматически, не должен автоматически же
  "чиниться" через `apply` без ревью — внешние изменения иногда вносятся
  намеренно (экстренный ручной фикс инцидента), и слепой авто-apply поверх
  них может откатить легитимную экстренную правку.
- На масштабе организации дрифт-дашборд становится метрикой здоровья
  платформенной команды — процент "state без дрифта" так же измерим и
  репортится, как error budget в SRE-практиках
  (см. [`../../../9_sre/01_slo_sli_sla/`](../../../9_sre/01_slo_sli_sla/)).

## 7. Типовые вопросы на собеседовании (Interview Q&A)

**1. В организации 40 команд, и каждая вносит изменения в общую инфраструктуру. Что именно в этой ситуации является "проблемой масштаба" — объём Terraform-кода или что-то другое?**
*Ответ:* Объём кода сам по себе Terraform обрабатывает одинаково что на 10,
что на 10 000 ресурсов. Настоящая проблема масштаба — координация: как 40
команд одновременно меняют общую инфраструктуру, не блокируя друг друга
(конкуренция за state lock), не имея возможности случайно задеть чужой
сервис (blast radius общего state), и как единообразно применить
security/cost-гейты ко всем 40 командам без ручного ревью каждого PR
силами одной центральной команды.

**2. Почему общий Terraform state на несколько независимых команд считается анти-паттерном на масштабе, даже если технически он помещается в один backend?**
*Ответ:* Общий state означает общую блокировку: `apply` одной команды
блокирует `apply` всех остальных, работающих с тем же state, превращая
параллельную работу множества команд в последовательную очередь. Кроме
того, общий state означает общий blast radius — ошибка в `apply` одной
команды технически способна затронуть ресурсы, которыми управляет другая
команда. Решение — разделение state по владению (team/env/region) с
явными "мостами" между слоями через remote state data sources.

**3. Чем модуль в приватном Terraform registry с семантическим версионированием лучше, чем просто `source = "git::...//modules/vpc"` без указания версии?**
*Ответ:* Без фиксированной версии (`ref`) потребитель модуля неявно читает
последнее состояние ветки `main` на каждый `init` — любое изменение модуля,
даже breaking, мгновенно и незаметно долетает до всех потребителей при
следующем прогоне. Версионирование с SemVer-контрактом (patch/minor/major)
даёт потребителю явный контроль над моментом обновления и явный сигнал,
безопасно ли обновление (patch) или требует проверки интерфейса (major) —
без этого организация либо боится обновлять модули вообще, либо получает
непредсказуемые breaking changes в проде.

**4. Зачем на масштабе организации нужен Policy as Code (Sentinel/OPA), если у организации и так есть обязательный ревью Pull Request security-командой?**
*Ответ:* Ручной ревью security-командой не масштабируется линейно с ростом
числа PR в день — на определённом масштабе пропускная способность
ревьюеров становится бутылочным горлышком всей разработки, либо качество
ревью падает под нагрузкой. Policy as Code переносит проверку базовых,
формализуемых правил (запрет публичных бакетов, обязательные теги, разрешённые
регионы) из ручного человеческого ревью в автоматическую, не обходимую
проверку сгенерированного `plan` до `apply` — человеческий ревью остаётся
для содержательных, неформализуемых решений, а не для проверки чек-листа
правил.

**5. Почему автоматически обнаруженный configuration drift не стоит чинить автоматическим `terraform apply` без участия человека?**
*Ответ:* Изменение в обход Terraform иногда вносится намеренно — например,
экстренный ручной фикс прод-инцидента в консоли облака, когда времени на
PR и ревью не было. Слепой автоматический `apply` поверх такого изменения
откатит легитимную экстренную правку обратно к "правильному" по коду, но
устаревшему состоянию, потенциально воспроизводя инцидент. Поэтому дрифт
должен попадать в дашборд/алерт для осознанного решения человека (внести
правку в код задним числом или откатить вручную), а не исправляться
автоматически.

**6. В чём разница между монорепо и полирепо подходом к хранению IaC-кода с точки зрения прав доступа CI, и какой компромисс используют чаще всего?**
*Ответ:* В монорепо CI, технически работающий с одной "папкой" репозитория,
часто имеет права на весь репозиторий целиком, что усложняет строгое
разграничение "команда A не может тронуть ресурсы команды B" только
структурой директорий. Полирепо даёт естественную границу прав доступа —
репозиторий команды физически не содержит ресурсов других команд. На
практике часто комбинируют: монорепо для общих платформенных модулей
(поддерживает одна команда), и полирепо/отдельные state-слои для
конечных окружений приложений, которые эти модули используют.
