## 1. Фундаментальная физика кэширования: зачем и какой ценой

Кэширование — самый мощный рычаг снижения задержки (Latency) и разгрузки
баз данных в System Design. Оно опирается на **принцип локальности ссылок
(Locality of Reference)** и распределение Парето / Ципфа: в реальных системах
80–95% чтений приходится на 5–20% самых популярных данных («горячие» товары,
свежие новости, профили активных пользователей).

### 1.1 Ключевые метрики эффективности кэша
- **Hit Ratio (Доля попаданий)**:
  $\text{Hit Ratio} = \frac{\text{Cache Hits}}{\text{Cache Hits} + \text{Cache
  Misses}}$.
  Для зрелого продуктового кэша целевой показатель — **90–99%**.
- **Средняя эффективная задержка чтения ($T_{\text{eff}}$)**:

$$T_{\text{eff}} = \text{Hit Ratio} \times T_{\text{cache}} + (1 - \text{Hit
Ratio}) \times (T_{\text{cache}} + T_{\text{db}})$$

**Наглядный расчёт**: пусть ответ из Redis занимает $T_{\text{cache}} =
1\text{ мс}$,
а тяжёлый запрос в БД — $T_{\text{db}} = 50\text{ мс}$.
- При $\text{Hit Ratio} = 90\%$ на базу данных идёт $10\%$ трафика, а средняя
  задержка равна $0.9 \times 1 + 0.1 \times 51 = 6.0\text{ мс}$.
- Если поднять $\text{Hit Ratio}$ с $95\%$ до $99\%$, доля промахов (`Miss
  Ratio`)
  упадёт с $5\%$ до $1\%$ — то есть **нагрузка на базу данных снизится в 5
  раз!**
  Именно за `Miss Ratio` (промахи в секунду) должен следить SRE в первую
  очередь.

## 2. Полная топология кэширования на пути запроса (L0–L5)

В высоконагруженной архитектуре кэш — это не «просто поставить Redis перед
Postgres». Каждый уровень отсекает свою долю трафика ещё до того, как пакет
дойдёт до вашего дата-центра:

```text
[ L0: Браузер / Мобильный клиент ]   (0 мс сети — HTTP Cache-Control, ETag)
               |
               v
[ L1: CDN / Edge Network ]           (5-20 мс — статика, медиа, публичный JSON)
               |
               v
[ L2: Reverse Proxy / API Gateway ]  (1-2 мс — nginx proxy_cache, Varnish)
               |
               v
[ L3: In-Process L1 Cache сервиса ]  (~50-200 нс — локальная RAM процесса, 0 сети!)
               |
               v
[ L4: Distributed L2 Cache ]         (0.5-2 мс — Redis, KeyDB, Dragonfly, Memcached)
               |
               v
[ L5: Кэши СУБД и Ядра ОС ]          (Page Cache Linux, PostgreSQL shared_buffers)
```

### 2.1 Краткая характеристика уровней
1. **L0 (Клиентский HTTP-кэш)**: самый быстрый запрос — тот, который вообще
   не был отправлен по сети. Управляется заголовками:
   - `Cache-Control: public, max-age=31536000, immutable` (для версионированной
     статики с хэшем в имени файла `app.8f3a1.js`);
   - `ETag` + `If-None-Match` (условный запрос: если данные не изменились,
     сервер возвращает пустой ответ `304 Not Modified`, экономя полосу).
2. **L1 (CDN — Content Delivery Network)**: гео-распределённые узлы (PoP)
   близко к пользователю. Принимают на себя раздачу картинок, видео,
   JS/CSS-бандлов и публичных каталог-страниц (`stale-while-revalidate`),
   защищая ваш Origin-сервер.
3. **L2 (Reverse Proxy — nginx / Varnish / Envoy)**: кэширует готовые
   HTTP-ответы целиком на входе в кластер (`proxy_cache_use_stale updating`
   в nginx позволяет отдавать чуть устаревший ответ тысячам клиентов, пока
   ровно один фоновый запрос обновляет кэш с бэкенда).
4. **L3 (In-Process / Local Cache)**: хэш-таблица прямо в оперативной памяти
   процесса приложения. Быстрее Redis в **10 000 раз** (`~100 нс` против
   `~1 мс`, так как нет системного вызова `sendto`/`recvfrom`, TCP-стека и
   десериализации). **Минус**: тратит память каждого воркера/пода и требует
   очень короткого TTL (1–10 с) или шины инвалидации (Redis Pub/Sub /
   Client-side
   caching), чтобы разные реплики не отдавали противоречивые данные.
5. **L4 (Distributed Cache — Redis / Memcached)**: единый разделяемый кэш
   для всех реплик микросервиса. Переживает рестарты подов приложения.
6. **L5 (СУБД и ОС)**: `shared_buffers` в PostgreSQL / `InnoDB Buffer Pool`
   в MySQL и системный `Page Cache` ядра Linux. Если рабочее множество
   индексов и горячих таблиц целиком помещается в RAM сервера БД, чтение с
   физического NVMe-диска почти не происходит.

## 3. Архитектурные паттерны чтения и записи в кэш

Как приложение координирует состояние между кэшем (Redis) и первичным
источником истины (БД)?

### 3.1 Паттерны чтения: Cache-Aside vs Read-Through

```text
Cache-Aside (Ленивая загрузка — самый частый паттерн в микросервисах):
1. Приложение -> Кэш: GET key (Miss!)
2. Приложение -> БД:  SELECT ...
3. Приложение -> Кэш: SET key value EX 300
```

- **Cache-Aside (Lazy Loading)**: само приложение знает и про кэш, и про БД.
  При записи в БД приложение **удаляет ключ из кэша (`DEL key`)**, а не
  обновляет его!
  > **Почему при записи в БД нужно делать `DEL`, а не `SET` в кэш?**
  > Представьте два параллельных потока $A$ и $B$, обновляющих одну запись:
  > 1) Поток $A$ записывает в БД `price = 100`.
  > 2) Поток $B$ записывает в БД `price = 200`.
  > 3) Из-за сетевой паузы поток $B$ первым пишет в Redis `SET price 200`.
  > 4) Следом просыпается поток $A$ и перезаписывает в Redis старое значение
  >    `SET price 100`! Теперь в БД лежит `200`, а в кэше до конца TTL
  >    навсегда застряло неверное значение `100`. Инвалидация через `DEL`
  >    решает эту проблему (при следующем чтении подтянется актуальное `200`).
- **Read-Through**: приложение обращается только к прослойке кэша, а сам
  провайдер кэша при промахе прозрачно загружает данные из БД.

### 3.2 Паттерны записи: Write-Through, Write-Behind и Write-Around

| Паттерн | Как работает | Плюсы | Минусы и риски |
| :--- | :--- | :--- | :--- |
| **Write-Through** | Запись идёт синхронно в кэш и сразу в БД | Кэш всегда актуален для чтений | Высокая задержка записи (ждём две системы); кэш забивается данными, которые никто не прочитает |
| **Write-Behind (Write-Back)** | Запись мгновенно кладётся в кэш, а в БД сбрасывается **асинхронно батчами** | Колоссальная скорость записи (сглаживает пики в 100x: счётчики лайков, просмотров) | ⚠️ **Риск потери данных**, если узел кэша умрёт до сброса батча на диск БД |
| **Write-Around** | Запись идёт напрямую в БД в обход кэша (с `DEL` старого ключа) | Кэш не засоряется одноразовыми холодными записями | Первое чтение после записи всегда даёт Cache Miss |

## 4. Инвалидация кэша, TTL и алгоритмы вытеснения (Eviction Policies)

Память в кэше конечна. Когда достигается лимит (`maxmemory` в Redis), кэш
обязан решить, какие ключи вытеснить:

1. **TTL (Time-To-Live)**: обязательный предохранитель для любого кэшируемого
   ключа. Даже если логика инвалидации по событиям дала сбой, через время
   TTL система сама придёт в консистентное состояние.
2. **LRU (Least Recently Used)**: вытесняет ключ, к которому **дольше всего
   не обращались**. Прост, но уязвим к полному сканированию (один фоновый
   проход по редким данным вымывает из кэша действительно популярные ключи).
3. **LFU (Least Frequently Used)** и **W-TinyLFU**: учитывает **частоту**
   обращений за период времени (использует вероятностный счётчик Count-Min
   Sketch и затухание со временем). Значительно эффективнее удерживает
   реально популярные ключи при шумном трафике (в Redis политика
   `allkeys-lfu` или `volatile-lfu`).

## 5. Четыре катастрофические аномалии кэша на высоких нагрузках

На собеседованиях Senior-уровня и в реальных посмертных отчётах (Postmortems)
падение высоконагруженных систем почти всегда связано с одной из четырёх
аномалий кэша:

```text
1. Cache Stampede (Thundering Herd) : 1 горячий ключ истёк -> 10 000 потоков бьют в БД за ним
2. Cache Avalanche (Лавина кэша)    : 100 000 ключей истекли в одну секунду (или упал узел Redis)
3. Cache Penetration (Пробивание)   : Запросы за НЕСУЩЕСТВУЮЩИМ id=-1 обходят и кэш, и БД
4. Hot Key (Горячий ключ)           : 1 ключ (пост звезды) даёт 500 000 RPS и кладёт 1 шард Redis
```

### 5.1 Cache Stampede (Thundering Herd / Dogpiling)
- **Суть**: у очень популярного ключа (главная страница, курс валют) при
  нагрузке 5 000 RPS истекает TTL. В ту же миллисекунду все 5 000 параллельных
  запросов получают `Cache Miss` и одновременно отправляют тяжёлый SQL-запрос
  в базу данных, мгновенно кладя её по CPU и соединениям.
- **Как лечить**:
  1. **Request Coalescing / Singleflight** (внутри процесса) или
     **Распределённый лок с перепроверкой кэша** (между подами): только один
     запрос берёт право пойти в БД и пересчитать кэш, а остальные 4 999
     запросов ждут его результат (или получают слегка устаревшее значение
     — `stale-while-revalidate`).
  2. **Logical Expiration / Фоновый прогрев**: физический TTL ключа в Redis
     ставится большим (например, 1 час), но внутри JSON хранится поле
     `logical_expire_at` (5 минут). Когда воркер видит, что логическое время
     вышло, он мгновенно отдаёт пользователю старые данные, а в фоне запускает
     одну асинхронную задачу на обновление.
  3. **Probabilistic Early Expiration (Алгоритм XFetch)**: по мере
     приближения времени к концу TTL с небольшой вероятностью один из запросов
     пересчитывает ключ заранее, до того как он физически исчезнет.

### 5.2 Cache Avalanche (Лавина кэша)
- **Суть**: при старте системы или ночной джобе в кэш загрузили 1 миллион
  товаров с одинаковым `TTL = 3600` секунд. Ровно через час все 1 миллион
  ключей протухают в одну и ту же секунду (либо падает целиком узел Redis),
  и вся нагрузка обрушивается на БД.
- **Как лечить**:
  1. **TTL Jitter (Случайный разброс TTL)**: никогда не используйте константный
     TTL! Всегда добавляйте случайную дельту:
     $\text{TTL} = 3600 + \text{random}(-300, +300)$ секунд.
  2. Высокая доступность самого кэша (Redis Sentinel / Redis Cluster с
     репликами) и Circuit Breaker + Rate Limiter перед базой данных для
     graceful degradation.

### 5.3 Cache Penetration (Пробивание кэша несуществующими ключами)
- **Суть**: злоумышленник (или баг на клиенте) шлёт десятки тысяч запросов
  за заведомо несуществующими `user_id` или `product_id`. В кэше их нет
  (`Miss`), запрос идёт в БД, БД ничего не находит (`NULL`), приложение ничего
  не кладёт в кэш, и каждый следующий запрос снова бьёт напрямую в диск БД.
- **Как лечить**:
  1. **Negative Caching (Кэширование пустого результата)**: если БД вернула
     «не найдено», записать в кэш специальный маркер `NOT_FOUND` с коротким
     TTL (например, 30–60 секунд).
  2. **Фильтр Блума (Bloom Filter)**: компактная битовая вероятностная
     структура данных в памяти перед кэшем. Она со 100% точностью отвечает,
     что ключа **точно не существует в природе**, отсекая мусорные запросы
     за наносекунды без обращения к Redis и БД.

### 5.4 Hot Key Problem (Проблема сверхгорячего ключа)
- **Суть**: даже если у вас Redis Cluster из 20 шардов, один конкретный ключ
  (`promo:iphone_sale`) хэшируется ровно в один конкретный слот и попадает на
  **один физический узел Redis**. Так как основной цикл команд Redis
  однопоточный, нагрузка в 300 000 RPS на этот один ключ выжигает 100% одного
  ядра CPU на этом шарде, тормозя и все остальные ключи на нём.
- **Как лечить**:
  1. Вынести горячие ключи на уровень **L3 (In-Process кэш в памяти самих
     подов приложения)** с коротким TTL в 1–5 секунд (или через Redis
     Client-Side Tracking) — тогда чтение масштабируется на сотни подов.
  2. **Key Splitting (Размножение ключа по суффиксам)**: записать копию
     горячего ключа под $N$ именами `promo:iphone_sale:1` ..
     `promo:iphone_sale:20`,
     чтобы они разъехались по всем шардам Redis Cluster, а при чтении
     выбирать случайный суффикс `1..N`.

## 6. Эксплуатация распределённого кэша (Redis / Memcached) глазами SRE

1. **Однопоточное ядро выполнения команд в Redis**: команды типа `KEYS *`,
   `SMEMBERS` на миллион элементов или `DEL` гигантского хэша на 5 млн полей
   блокируют весь инстанс Redis для всех остальных клиентов!
   - Вместо `KEYS *` используйте итератор `SCAN`.
   - Вместо `DEL` для больших структур используйте асинхронное удаление в
     фоновом потоке `UNLINK` (и настройку `lazyfree-lazy-eviction yes`).
2. **Подводный камень персистентности (`RDB` / `fork()` и Copy-on-Write)**:
   когда Redis делает фоновый снепшот `BGSAVE`, он вызывает системный вызов
   `fork()`. Ядро Linux использует механизм Copy-on-Write (CoW): при интенсивной
   записи в Redis во время снятия снепшота модифицируемые страницы памяти
   дублируются, и потребление RAM процессом Redis может мгновенно вырасти в
   **1.5–2 раза**, вызывая `OOM Killer`! Обязательно оставляйте запас памяти и
   включайте `vm.overcommit_memory = 1`.

```bash
# Диагностика задержек, фрагментации памяти и больших ключей в Redis
redis-cli --intrinsic-latency 5
redis-cli --latency-history
redis-cli info memory | grep -E "used_memory_human|mem_fragmentation_ratio|maxmemory_policy"
redis-cli --bigkeys
```

## 7. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему в паттерне Cache-Aside при обновлении данных в базе правильнее
удалить ключ из кэша (`DEL`), а не перезаписать его новым значением (`SET`)?**
*Ответ:* При параллельных обновлениях перезапись кэша (`SET`) подвержена гонке
(race condition) из-за разного порядка выполнения сетевых запросов к БД и
кэшу. Если поток А записал в БД значение `1`, затем поток Б записал в БД
значение `2` и обновил кэш на `2`, а задержавшийся по сети поток А после этого
выполнил `SET 1` в кэш, то в базе данных останется актуальное значение `2`,
а в кэше до истечения TTL застрянет устаревшее `1`. Кроме того, ленивое
удаление (`DEL`) экономит ресурсы, если ключ часто меняется, но редко читается.

**2. Даже при использовании `Write DB -> DEL Cache` существует редкая гонка
между параллельным чтением и записью. Опишите этот сценарий и способ его
устранения.**
*Ответ:* Сценарий гонки: (1) Кэш пуст; поток чтения А видит `Cache Miss` и
читает из БД старое значение `v1`, после чего засыпает (например, на паузе GC
или планировщика). (2) В этот момент поток записи Б обновляет БД на `v2` и
делает `DEL` в кэше (который и так пуст). (3) Просыпается поток чтения А и
записывает прочитанное им ранее старое значение `v1` в кэш через `SET`!
Способы защиты: (а) использование CAS / версий (`version` или `updated_at`),
чтобы не перезаписывать кэш более старой версией; (б) паттерн **Delayed Double
Delete** (повторный `DEL` через 200–500 мс или асинхронная инвалидация кэша
строго по потоку CDC из транзакционного лога БД — Debezium).

**3. В чём разница между аномалиями Cache Stampede, Cache Avalanche и Cache
Penetration, и какой специфичный механизм лечит каждую из них?**
*Ответ:*
- **Cache Stampede (Thundering Herd)** — одновременный промах тысяч потоков по
  *одному* горячему ключу в момент истечения его TTL; лечится схлопыванием
  запросов (`singleflight` / распределённый mutex) или фоновым обновлением до
  истечения физического TTL.
- **Cache Avalanche (Лавина)** — одновременное истечение *миллионов разных*
  ключей, загруженных с одинаковым TTL (или падение узла кэша); лечится
  добавлением случайного разброса к времени жизни (**TTL Jitter**).
- **Cache Penetration (Пробивание)** — запросы за *несуществующими* в БД
  ключами, которые всегда проходят сквозь кэш в базу; лечится кэшированием
  `NULL`-ответов с коротким TTL (Negative Caching) и **фильтром Блума (Bloom
  Filter)** перед кэшем.

**4. Как работает фильтр Блума (Bloom Filter) для защиты от Cache Penetration,
и почему из классического фильтра Блума нельзя просто удалить элемент?**
*Ответ:* Фильтр Блума — это битовый массив из $m$ бит и $k$ независимых
хэш-функций. При добавлении существующего в БД ключа вычисляются $k$ хэшей,
и соответствующие им биты в массиве выставляются в `1`. При проверке входящего
запроса, если хотя бы один из $k$ битов равен `0`, ключа со 100% гарантией
нет в БД (запрос мгновенно отклоняется). Возможны редкие ложноположительные
срабатывания (`False Positive`), но невозможны ложноотрицательные (`False
Negative`). Обнулить биты при удалении ключа нельзя, так как эти же биты могут
быть выставлены в `1` другими ключами (коллизия), и их сброс сломает фильтр
для других существующих записей (для удалений нужен Counting Bloom Filter или
Cuckoo Filter).

**5. У вас развёрнут Redis Cluster на 16 шардов, общая загрузка CPU кластера —
15%, но клиенты массово получают таймауты от кэша. Что произошло и как это
исправить?**
*Ответ:* Это классическая проблема **Hot Key (Горячего ключа)** или **Big Key**.
В Redis Cluster каждый ключ по алгоритму `CRC16(key) mod 16384` привязан ровно
к одному хэш-слоту и одному физическому мастер-узлу. Если на один ключ
приходится 200 000 RPS, один узел кластера упирается в 100% своего единственного
рабочего потока (при этом остальные 15 узлов простаивают, давая среднюю
загрузку 15%). Решение: кэшировать горячие ключи в локальной памяти самих
подов бэкенда (L1 In-Process Cache) на 1–5 секунд, либо размножить ключ на $N$
копий с суффиксами (`key:1`..`key:16`), чтобы размазать чтения по всем шардам.

**6. Почему выполнение команды `DEL` для удаления устаревшего ключа в Redis
иногда вызывает скачок латентности (`p99`) для всех остальных запросов на
десятки миллисекунд?**
*Ответ:* Если удаляемый ключ представляет собой крупную коллекцию (Big Key —
например, `Hash`, `Set` или `Sorted Set` с миллионами элементов), синхронная
команда `DEL` освобождает память всех этих элементов прямо в основном рабочем
потоке цикла событий Redis (`main event loop`). Пока `free()` обходит миллион
указателей, Redis полностью заблокирован и не отвечает ни на один другой
запрос. Чтобы избежать блокировки, нужно использовать команду **`UNLINK`**,
которая за `O(1)` отвязывает ключ из основного словаря, а реальное освобождение
памяти передаёт фоновому потоку (`bio_lazy_free`).

**7. Почему инстанс Redis с `maxmemory = 40GB` на виртуальной машине с `48GB
RAM` может внезапно быть убит `OOM Killer` ядра Linux ровно в 03:00 ночи?**
*Ответ:* В 03:00 ночи срабатывает создание фонового дампа на диск (`BGSAVE`
для RDB или `BGREWRITEAOF`). Для этого Redis делает системный вызов `fork()`.
Дочерний процесс разделяет страницы памяти с родительским в режиме
**Copy-on-Write (CoW)**. Если в этот момент на Redis идёт интенсивный поток
записи (`SET`/`HSET`), каждая изменяемая родительским процессом страница
памяти (4 КБ или 2 МБ при Transparent Huge Pages!) копируется ядром ОС. При
высокой доле модификаций память удваивается, превышает физические 48 ГБ хоста,
и `OOM Killer` убивает Redis. Решается отключением Transparent Huge Pages
(`never`), запасом RAM минимум 40–50% от `maxmemory` на узлах с персистентностью
и переносом `BGSAVE` на реплики.

**8. В каких случаях локальный In-Process кэш внутри памяти микросервиса (L1)
может навредить архитектуре сильнее, чем его отсутствие?**
*Ответ:* Во-первых, при строгих требованиях к консистентности: если у сервиса
50 реплик в Kubernetes и каждая кэширует данные в своей памяти без общей шины
инвалидации, то после изменения данных пользователь при каждом обновлении
страницы (попадая через балансировщик на разные поды) будет видеть то старое,
то новое состояние («флаппинг данных»). Во-вторых, в языках со сборщиком
мусора (Go, Java) хранение десятков миллионов объектов с указателями в
локальном кэше заставляет GC постоянно сканировать этот гигантский граф во
время фазы `Mark`, раздувая CPU и паузы сборщика мусора.

**9. Чем политика вытеснения `LFU` (`allkeys-lfu`) превосходит классическую
`LRU` (`allkeys-lru`) на реальном продакшен-трафике?**
*Ответ:* Классический `LRU` смотрит только на время *последнего* обращения.
Если аналитический скрипт, поисковый бот или пользователь разово запросил
пачку из 100 000 архивных записей за 2019 год, эти одноразовые ключи получат
самую свежую метку времени и вытеснят из `LRU`-кэша действительно популярные
ключи, к которым обращаются каждые 5 секунд (эффект **Cache Pollution**).
Политика `LFU` (и её модификация `W-TinyLFU`) отслеживает *частоту* обращений
и не позволяет однократно прочитанным ключам вымыть горячее ядро кэша.

**10. Как спроектировать систему подсчёта просмотров видео или лайков под
нагрузкой 500 000 инкрементов в секунду, чтобы не убить реляционную базу
данных?**
*Ответ:* Прямой `UPDATE videos SET views = views + 1 WHERE id = X` на 500k RPS
положит любую реляционную БД из-за блокировок строк (`Row Lock Contention`) и
записи WAL. Применяется паттерн **Write-Behind (Write-Back) с агрегацией**:
1) На уровне воркеров приложения инкременты сначала суммируются в локальной
   памяти процесса в течение 1–2 секунд.
2) Раз в пару секунд воркер сбрасывает накопленную дельту в Redis командой
   `HINCRBY video_views <id> <delta>` и добавляет `id` во множество изменённых
   видео `SADD dirty_videos <id>`.
3) Фоновый воркер раз в 30–60 секунд забирает пачку из `dirty_videos` и одним
   батчевым SQL-запросом (`INSERT ... ON CONFLICT DO UPDATE`) сбрасывает
   итоговые значения в постоянную БД.
