## 1. Что меняется, когда хостов/сервисов тысячи

Пайплайн, который прекрасно работает для одного сервиса на десяти серверах,
ломается на масштабе не из-за багов, а из-за **других узких мест**:

- Сборка "в лоб" на каждый деплой становится дороже, чем сама раскатка —
  если 50 микросервисов собираются по 3 минуты каждый при каждом пуше,
  суммарное время CI превращается в основной бутылочное горлышко разработки.
- Раскатка последовательно на N хостов/подов по одному — операция `O(N)` по
  времени: то, что было незаметно на 10 хостах, превращается в час простоя
  при деплое на 2000.
- Централизованная точка (один раннер, один control-узел конфигурации) сама
  становится узким местом и единой точкой отказа для всего флота.
- "Откатить один сервис" и "откатить весь флот" — разные по стоимости
  операции, и дизайн пайплайна должен явно отвечать, какая из них нужна чаще.

## 2. Build once, deploy many: неизменяемые артефакты

Фундаментальный принцип CI/CD на масштабе — собрать артефакт **один раз** и
затем продвигать **тот же самый** бинарный артефакт через окружения
(dev → stage → prod), а не пересобирать код на каждом окружении:

- Пересборка на каждом окружении рискует получить разные артефакты из
  "одного и того же" кода (разные версии зависимостей, разный таймстамп) —
  это ломает воспроизводимость и усложняет диагностику "в stage работает, в
  prod — нет".
- Артефакт (Docker-образ, собранный бинарник) помечается неизменяемым тегом
  (digest, а не `latest`) и складывается в registry с кэшированием слоёв.
  Промотирование между окружениями — это смена значения тега/digest в
  манифесте окружения, а не новый `docker build`.
- Это напрямую стыкуется с GitOps-паттерном "App Repo vs Ops Repo" (см.
  [`../../../6_cicd/05_gitops_cd/`](../../../6_cicd/05_gitops_cd/)): CI пишет
  только новый digest в Ops Repo нужного окружения, сама раскатка — задача CD.

## 3. Флот раннеров: самохостинг, кэширование, автомасштабирование

При тысячах пайплайн-запусков в день managed-раннеры (общие shared runners
провайдера CI) становятся либо дорогими, либо медленными из-за очередей.
Стандартный ответ — **флот самохостинг раннеров**:

- Раннеры разворачиваются как пул (часто сами в Kubernetes — `GitLab Runner`
  в режиме Kubernetes executor, `actions-runner-controller` для GitHub
  Actions), с автомасштабированием числа раннеров по длине очереди джобов —
  похоже на KEDA-паттерн для воркеров (см. [`../01_scaling_high_load_systems/`](../../01_scaling_high_load_systems/)).
- Кэширование — главный рычаг против роста времени сборки на масштабе:
  кэш слоёв Docker (`BuildKit` cache mounts, registry cache), кэш зависимостей
  пакетных менеджеров между джобами. Без распределённого кэша каждый раннер
  в автомасштабируемом пуле начинает "с нуля", обнуляя выгоду от кэширования.
- Изоляция раннеров друг от друга (отдельные поды/VM на джобу, а не общий
  shared-хост) — требование безопасности: один скомпрометированный пайплайн
  не должен читать секреты/кэш другого пайплайна того же флота раннеров.

## 4. Конфигурация флота: push vs pull на масштабе

Когда артефакт собран, его ещё нужно довести до конфигурации множества
хостов — и здесь push- и pull-модели ведут себя принципиально по-разному на
масштабе (глубокий разбор Ansible — [`../../../5_iac/06_ansible/`](../../../5_iac/06_ansible/)):

- **Push (Ansible по SSH)** — control-нода сама инициирует подключение к
  каждому хосту. На сотнях хостов упирается в накладные расходы: fork
  процессов на control-ноде, SSH handshake на каждое подключение. Лечится
  батчами (`serial:` — применять не ко всем сразу, а волнами), ускоренным
  транспортом (`Mitogen`), либо `Ansible Pull` (хост сам тянет конфигурацию
  по расписанию, снимая нагрузку с центральной ноды).
- **Pull (агент-based: Puppet/Chef/SaltStack)** — каждый хост сам периодически
  опрашивает центральный сервер за желаемым состоянием. Это нативно
  масштабируется горизонтально (сервер конфигурации просто отдаёт готовые
  манифесты, вся "работа" выполняется децентрализованно на самих хостах), но
  требует постоянно работающего агента на каждом хосте и усложняет
  "применить прямо сейчас и только на этот один хост" сценарии.
- На практике большие флоты часто комбинируют: `Ansible` для первоначального
  bootstrap/редких операций, и более "тяжёлый" pull-механизм (или просто
  Kubernetes как единый pull-based control loop, если нагрузка уже в
  контейнерах) для постоянного дрейф-контроля.

## 5. Progressive delivery на флоте: canary/blue-green для тысяч инстансов

Раскатка новой версии сразу на весь флот — это максимальный blast radius
деплоя. На масштабе прогрессивная раскатка перестаёт быть "best practice" и
становится необходимостью чисто из соображений вероятности:

- **Canary**: новая версия сначала раскатывается на малую долю флота (1-5%)
  с автоматическим сравнением метрик ошибок/latency против baseline; при
  регрессии — автоматический откат до того, как задета основная масса.
  На масштабе тысяч инстансов ручное сравнение метрик нереалистично — нужен
  автоматизированный анализ (`Argo Rollouts` с `AnalysisTemplate`, см.
  [`../../../4_kubernetes/07_gitops/04_argo_rollouts/`](../../../4_kubernetes/07_gitops/04_argo_rollouts/)).
- **Blue-green на уровне флота** — требует двойной ёмкости (держать старую и
  новую версию полностью одновременно), что на масштабе тысяч хостов может
  быть экономически неприемлемо; чаще применяется посервисно/по зонам, а не
  ко всему флоту разом.
- **Волновая раскатка (rolling по батчам)** — компромисс между скоростью
  и риском: флот делится на волны (например, по availability zone или по
  региону), каждая следующая волна стартует только после здоровья
  предыдущей — тот же принцип, что в §6 статьи про [`../02_single_vs_multi_cluster/`](../../02_single_vs_multi_cluster/)
  для раскатки на несколько кластеров.

## 6. GitOps как ответ на масштаб

GitOps — не просто стилистический выбор, а прямой ответ на проблему
масштаба: вместо того чтобы CI-системе доверять **push**-доступ к тысячам
продакшн-целей (что требует широчайших прав у CI и делает его точкой
компрометации всего флота), каждая цель (кластер, группа хостов) сама
**pull**-ит желаемое состояние из Git и применяет его локально:

- `Argo CD` / `Flux` работают как постоянный pull-based контроллер
  сверки (reconciliation loop) для каждого окружения независимо —
  на масштабе N окружений это N независимых циклов, а не одна центральная
  точка, которая должна дотянуться до всех N.
- `ApplicationSets` (Argo CD) генерируют приложения на лету из шаблона +
  список целей (кластеров/окружений), что убирает ручное дублирование
  манифестов при росте числа целей — одно изменение шаблона раскатывается
  на все цели по тому же волновому принципу из §5.
- Git остаётся единым источником истины и единой точкой аудита: "что сейчас
  должно быть развёрнуто на флоте" — это просто состояние репозитория,
  проверяемое `git log`, а не разрозненные логи тысяч push-деплоев.

## 7. Типовые вопросы на собеседовании (Interview Q&A)

**1. У компании 50 микросервисов, каждый собирается 3 минуты при каждом пуше, и разработчики жалуются, что CI стал главным бутылочным горлышком. В чём, скорее всего, системная причина, и как её устранить не "ускоряя железо"?**
*Ответ:* Скорее всего каждый сервис пересобирается с нуля без переиспользуемого
кэша слоёв/зависимостей, и/или сборки идут последовательно на ограниченном
пуле раннеров вместо параллельного горизонтально масштабируемого пула.
Системное решение — распределённый кэш сборки (кэш слоёв Docker/BuildKit,
кэш зависимостей между джобами) плюс автомасштабируемый флот самохостинг
раннеров, параллельно обрабатывающий независимые сборки, а не просто более
мощный единственный раннер.

**2. Почему "собрать один артефакт и продвигать его через окружения" считается более безопасным подходом, чем пересобирать код отдельно для dev/stage/prod?**
*Ответ:* Пересборка на каждом окружении рискует дать технически разные
артефакты из "одного и того же" коммита (другие версии транзитивных
зависимостей на момент сборки, другой таймстамп), что ломает
воспроизводимость и усложняет диагностику расхождений между окружениями.
Сборка один раз и продвижение неизменяемого артефакта (по digest, а не по
мутабельному тегу вроде `latest`) гарантирует, что в prod оказывается
буквально то же самое, что было протестировано на предыдущих окружениях.

**3. В чём принципиальная разница между push-моделью (Ansible по SSH) и pull-моделью (Puppet/агент) при масштабировании конфигурации с 50 до 5000 хостов?**
*Ответ:* Push-модель упирается в накладные расходы центральной control-ноды:
fork процессов и SSH handshake на каждый хост линейно растут с числом
хостов, и единственная control-нода становится узким местом. Pull-модель
нативно масштабируется горизонтально — каждый хост сам периодически
опрашивает центральный сервер, и вся "работа" применения конфигурации
распределена по самим хостам; цена — необходимость постоянно работающего
агента на каждом хосте и меньшая мгновенность "применить прямо сейчас".

**4. Почему GitOps снижает риск компрометации CI-системы по сравнению с классическим push-деплоем из CI напрямую в прод?**
*Ответ:* При push-деплое CI-система должна обладать широкими правами записи
во все продакшн-цели, что делает саму CI-систему крайне привлекательной
точкой атаки — компрометация CI даёт прямой путь во весь флот. При GitOps
каждая цель сама забирает (pull) желаемое состояние из Git и применяет его
локально — CI/CD-пайплайну достаточно прав только на запись в Git-репозиторий,
а не прямого доступа к продакшн-инфраструктуре, что резко уменьшает blast
radius компрометации пайплайна.

**5. Что произойдёт при раскатке новой версии canary-деплоем на флот из 2000 инстансов, если сравнение метрик canary vs baseline делается вручную человеком?**
*Ответ:* На таком масштабе ручное сравнение метрик физически не успевает за
скоростью, с которой canary либо подтверждается, либо должен откатываться —
регрессия может незаметно расползтись на весь флот, пока человек анализирует
дашборды. Решение — автоматизированный анализ метрик (например, Argo
Rollouts с `AnalysisTemplate`, сравнивающий error rate/latency canary против
baseline по заданным порогам) с автоматическим промотированием или
автоматическим откатом без участия человека в каждом цикле.

**6. Почему blue-green деплой, который отлично работает для одного сервиса, часто экономически неприемлем при применении ко всему флоту из тысяч инстансов сразу?**
*Ответ:* Blue-green требует держать полную дублирующую ёмкость (старую и
новую версию одновременно) на время переключения. На масштабе одного
сервиса это приемлемая цена; умноженное на тысячи инстансов всего флота
это означает фактическое удвоение всей инфраструктуры разом — обычно
экономически неоправданно. Поэтому на масштабе флота чаще применяют
волновую (батчевую) раскатку по зонам/регионам вместо полного blue-green
по всему флоту одновременно.

**7. В чём разница между ApplicationSets в Argo CD и просто копированием одного и того же манифеста Application в N файлов для N кластеров?**
*Ответ:* Копирование N файлов означает, что любое изменение шаблона
(например, общей политики или версии образа) нужно вручную вносить в
каждую из N копий — источник рассинхронизации и человеческих ошибок на
масштабе. ApplicationSet генерирует N объектов Application динамически из
одного шаблона и списка целей (генератора — список кластеров, Git-директорий
и т.д.), так что одно изменение шаблона автоматически раскатывается на все
цели по единому волновому принципу, без ручного дублирования файлов.
