## 1. Как разбирать сквозные архитектурные кейсы

Четыре классических кейса ниже покрывают 90% паттернов, встречающихся в
реальных системах и на собеседованиях:
1. **Денежные переводы** — эталон **CP / ACID-системы** со строжайшей
   согласованностью, борьбой с гонками, дедлоками и двойными списаниями.
2. **Медиа-хостинг (Галерея картинок/видео)** — эталон работы с **тяжёлым
   бинарным трафиком**, объектными хранилищами (S3), асинхронными конвейерами
   обработки и CDN.
3. **Сокращатель ссылок (URL Shortener)** — эталон **Read-Heavy системы**
   (`100 : 1`) с генерацией уникальных коротких идентификаторов (Base62) и
   агрессивным кэшированием.
4. **Лента новостей (News Feed)** — эталон **масштабирования графовых
   связей** (Fan-out on Write vs Fan-out on Read) и решения проблемы
   знаменитостей (Hot Key / Celebrity Problem).

## 2. Кейс 1: Система денежных переводов и платежей (Payment / Ledger System)

### 2.1 Требования и главные инварианты
- **Функционал**: перевод денег со счёта $A$ на счёт $B$, проверка баланса,
  выписка по истории операций, отправка уведомлений после перевода.
- **Главные NFR**:
  - **CP и строгий ACID**: ни одна копейка не может исчезнуть из воздуха или
    удвоиться (`RPO = 0`).
  - **Никаких `float`!** Деньги хранятся и считаются исключительно в целых
    минимальных единицах валюты (`BIGINT` копеек / центов: `15050` = `150.50 ₽`)
    или типах точной десятичной арифметики (`NUMERIC(19, 4)` / `Decimal`),
    так как в IEEE 754 `0.1 + 0.2 = 0.30000000000000004`.
  - **Идемпотентность**: при плохом интернете мобильное приложение повторит
    запрос на перевод 5 раз — списание должно произойти **ровно один раз**.

### 2.2 Схема базы данных: Double-Entry Bookkeeping (Двойная запись)
В настоящих финансовых системах баланс счёта никогда не меняется «просто
перезаписью числа без следа». Используется бухгалтерская книга двойной записи
(**Double-Entry Ledger**):

```sql
-- 1. Таблица счетов (текущий проекционный баланс для быстрой проверки)
CREATE TABLE accounts (
    account_id BIGINT PRIMARY KEY,
    currency   CHAR(3) NOT NULL,
    balance    BIGINT  NOT NULL CHECK (balance >= 0), -- В копейках!
    version    BIGINT  NOT NULL DEFAULT 1
);

-- 2. Таблица транзакций перевода (обеспечивает идемпотентность по idempotency_key)
CREATE TABLE transfers (
    transfer_id     UUID PRIMARY KEY,
    idempotency_key UUID UNIQUE NOT NULL,
    from_account_id BIGINT NOT NULL REFERENCES accounts(account_id),
    to_account_id   BIGINT NOT NULL REFERENCES accounts(account_id),
    amount          BIGINT NOT NULL CHECK (amount > 0),
    status          VARCHAR(20) NOT NULL -- 'COMPLETED', 'FAILED'
);

-- 3. Неизменяемый журнал проводок (Append-Only Ledger): сумма всех строк всегда = 0!
CREATE TABLE ledger_entries (
    entry_id    BIGSERIAL PRIMARY KEY,
    transfer_id UUID NOT NULL REFERENCES transfers(transfer_id),
    account_id  BIGINT NOT NULL REFERENCES accounts(account_id),
    amount      BIGINT NOT NULL -- Отрицательное (-1000) для дебета, положительное (+1000) для кредита
);
```

### 2.3 Защита от гонок (Lost Update) и взаимных блокировок (Deadlocks)

Представьте, что у пользователя на счету `1000 ₽`, и он одновременно с двух
устройств отправляет два запроса на вывод `800 ₽`. Если оба потока сначала
сделают обычный `SELECT balance` (оба увидят `1000 >= 800`), а затем спишут
деньги, со счёта уйдёт `1600 ₽`, и баланс уйдёт в минус (**аномалия Lost
Update / Write Skew**)!

#### Два правильных способа синхронизации в БД:
1. **Пессимистичная блокировка (`SELECT ... FOR UPDATE`)**:
   Внутри транзакции `BEGIN ... COMMIT` мы берём эксклюзивную блокировку строк
   обоих счетов перед проверкой баланса.
   > **Критическая ловушка Deadlock (Взаимная блокировка)**:
   > Пусть Поток 1 переводит деньги со счёта `10` на счёт `20`, а Поток 2 в
   > ту же миллисекунду переводит обратно со счёта `20` на счёт `10`.
   > Если Поток 1 заблокирует счёт `10` и ждёт `20`, а Поток 2 заблокирует
   > счёт `20` и ждёт `10` — возникнет классический **Deadlock**!
   > **Золотое правило предотвращения Deadlock**: всегда захватывайте
   > блокировки ресурсов в **строго детерминированном порядке (например, по
   > возрастанию `account_id`)**:
   ```sql
   SELECT account_id, balance FROM accounts
   WHERE account_id IN (10, 20)
   ORDER BY account_id ASC
   FOR UPDATE;
   ```
2. **Оптимистичная блокировка / Атомарный `UPDATE` с версией**:
   ```sql
   UPDATE accounts
   SET balance = balance - 800, version = version + 1
   WHERE account_id = 10 AND balance >= 800 AND version = :expected_version;
   ```
   Если `rows_affected == 0` — значит, параллельный поток изменил счёт или
   денег не хватило; транзакция откатывается и при необходимости повторяется.

### 2.4 Полный цикл атомарного перевода с Transactional Outbox

```text
[Client] --(POST /transfers + Idempotency-Key)--> [Payment Service]
                                                         |
          +----------------------------------------------+
          | Единая ACID-транзакция в PostgreSQL:
          |   1. INSERT INTO transfers (idempotency_key...) -> Если дубль, вернуть старый ответ!
          |   2. SELECT ... WHERE account_id IN (min, max) ORDER BY account_id FOR UPDATE;
          |   3. Проверить balance >= amount, вставить 2 строки в ledger_entries (-X и +X);
          |   4. UPDATE accounts SET balance ... для отправителя и получателя;
          |   5. INSERT INTO outbox_events ('TransferCompleted') для пуш-уведомлений.
          +----------------------------------------------+
```

### 2.5 Что делать, когда счета лежат на разных шардах (Distributed Transfers)?
Когда система вырастает до сотен миллионов счетов и база данных шардируется
по `account_id`, счёт отправителя `A` (Шард 1) и счёт получателя `B` (Шард 2)
оказываются на разных физических серверах. Локальный `SELECT ... FOR UPDATE`
больше невозможен. Применяется **паттерн Saga с оркестратором и двухэтапным
резервированием (Hold / Two-Step Transfer)**:
1. **Шаг 1 (Debit / Hold на Шарде 1)**: списать деньги со счёта `A` (или
   перевести в `reserved_balance`) в локальной транзакции Шарда 1 + записать
   событие в Outbox Шарда 1.
2. **Шаг 2 (Credit на Шарде 2)**: воркер саги с уникальным `transfer_id`
   (идемпотентно!) зачисляет сумму на счёт `B` на Шарде 2.
3. **Компенсация (Refund)**: если счёт `B` на Шарде 2 оказался закрыт или
   заблокирован, оркестратор саги выполняет компенсирующую транзакцию на
   Шарде 1 — возвращает средства на счёт `A`.

## 3. Кейс 2: Галерея изображений и медиа-хостинг (Image / Media Hosting)

### 3.1 Требования и главные узкие места
- **Функционал**: пользователь загружает оригинальное фото/видео (до 50 МБ),
  система генерирует 3 превью разных разрешений (`thumbnail`, `medium`,
  `webp`), проверяет контент (антивирус / NSFW-модерация) и быстро раздаёт
  галерею миллионам зрителей по всему миру.
- **Главная ошибка новичков**: прогонять загрузку и раздачу 50-мегабайтных
  файлов прямо через память воркеров своего веб-фреймворка (FastAPI / Go) и
  синхронно жать картинки прямо внутри HTTP-запроса `POST /upload`! При
  100 одновременных загрузках память подов переполнится (`OOM`), а CPU
  ляжет на кодировании JPEG/WebP.

### 3.2 Архитектура загрузки и обработки (Presigned URLs + Async Pipeline)

```text
1. [Клиент] --(POST /media/init {filename, sha256, size})--> [Media API]
2. [Клиент] <--(Возвращает Presigned S3 PUT URL)------------ [Media API] (пишет статус PENDING в БД)
3. [Клиент] =====(Прямой PUT 50 МБ файла напрямую в S3!)===> [S3 / Object Storage]
                                                                    |
4. [S3 Event Notification] ---> [Kafka / RabbitMQ] -----------------+
                                        |
5.                             [Resize Workers (CPU Pool)]
                                 |-- Скачивает потоком из S3
                                 |-- Генерирует sm/md/lg WebP
                                 |-- Кладёт превью в S3
                                 +-- Обновляет статус в БД -> READY
                                        |
6. [Зрители по миру] ---> [CDN (Cloudflare / CloudFront)] ---> [Origin S3]
```

### 3.3 Ключевые архитектурные решения медиа-конвейера
1. **Обход бэкенда при загрузке (Presigned URLs + Multipart Upload)**:
   Бэкенд только проверяет права пользователя, создаёт запись в БД со
   статусом `UPLOADING` и за `1 мс` генерирует криптографически подписанную
   временную ссылку **S3 Presigned PUT URL** (с ограничением максимального
   размера `Content-Length` и типа файла). Клиент заливает тяжелые мегабайты
   **напрямую в S3** (для больших файлов — кусками по 5 МБ через `Multipart
   Upload`, чтобы при обрыве связи в лифте докачать только один кусок!).
2. **Дедупликация контента по хэшу (Content-Addressable Storage)**:
   Перед загрузкой клиент считает `SHA-256` файла. Если файл с таким
   `sha256` уже есть в таблице блобов нашего хранилища, физическая загрузка
   и повторный ресайз вообще не нужны — мы просто создаём новую ссылку в
   галерее пользователя на уже существующий S3-объект!
3. **Разделение пулов (Bulkhead: I/O API vs CPU Workers)**:
   API-серверы остаются на лёгких сетевых нодах, а воркеры обработки
   изображений (`libvips` / `Pillow` / `FFmpeg`) выделяются в отдельный
   Kubernetes Node Pool на вычислительных CPU-инстансах и масштабируются
   через **KEDA** по длине очереди в Kafka/RabbitMQ.
4. **Раздача через CDN и защита от кэш-промахов (Origin Shield)**:
   Зрители никогда не читают картинки из S3 напрямую — ссылки ведут на домен
   **CDN** (`cdn.example.com/img/8f3a1_md.webp`) с заголовком
   `Cache-Control: public, max-age=31536000, immutable` (так как имя файла
   содержит хэш контента, файл никогда не меняется — инвалидация кэша не
   нужна!).

## 4. Кейс 3: Сокращатель ссылок (URL Shortener — Bitly / TinyURL)

### 4.1 Требования и математика
- **Функционал**:
  - `POST /api/v1/shorten { "long_url": "https://..." }` → возвращает
    короткую ссылку `https://sho.rt/aB9xYz1` (длина кода 7 символов).
  - `GET /aB9xYz1` → возвращает редирект на длинный URL + считает статистику
    переходов.
- **Профиль нагрузки**: экстремальный перекос в сторону чтения (`Read : Write
  = 100 : 1`, например `1 000 RPS` на создание и `100 000 RPS` на редиректы).
- **Почему именно 7 символов алфавита Base62 (`[a-z, A-Z, 0-9]`)?**
  - В Base62 ровно $26 + 26 + 10 = 62$ безопасных для URL символа.
  - Длина 6 символов даёт $62^6 \approx 56.8\text{ млрд}$ комбинаций.
  - Длина **7 символов** даёт $62^7 \approx \mathbf{3.52\text{ триллиона}}$
    уникальных ссылок (при скорости 1 000 ссылок в секунду этого хватит на
    **110 лет**!).

### 4.2 Как генерировать короткий код без коллизий (Hash vs Counter/Snowflake)

| Подход | Как работает | Плюсы и минусы |
| :--- | :--- | :--- |
| **1. Обрезка MD5 / SHA-256** | Взять первые 7 символов Base62 от `MD5(long_url)` | ⚠️ **Коллизии неизбежны** (по парадоксу дней рождения)! Требует проверки в БД `INSERT ... ON CONFLICT` и добавления соли при совпадении |
| **2. Центральный автоинкремент / Диапазоны (Range Allocator)** | Воркер берёт у координатора (Redis / БД / ZooKeeper) блок из $10\,000$ чисел (например, `1000000..1010000`) в память и переводит число в Base62 | **0% коллизий**, не нужно проверять уникальность в БД перед выдачей! Чтобы коды не были угадываемыми по порядку, биты числа перемешивают (Feistel cipher) |
| **3. Twitter Snowflake (64-bit ID)** | `41 бит timestamp + 10 бит worker_id + 12 бит локальный счётчик` → перевод в Base62 | Полностью автономная генерация на каждом поде без походов по сети к координатору, 0% коллизий |

### 4.3 Тонкость HTTP-кода редиректа: `301 Moved Permanently` vs `302 Found`
Классический вопрос с подвохом на интервью:
- **`HTTP 301 Moved Permanently`**: браузер пользователя **навсегда кэширует**
  длинный URL у себя локально. При повторных кликах браузер переходит на
  целевой сайт напрямую, вообще не обращаясь к нашему серверу!
  - *Плюс*: минимальная нагрузка на наши серверы.
  - *Минус*: мы **теряем аналитику кликов** и возможность изменить целевой
    URL у короткой ссылки в будущем.
- **`HTTP 302 Found` (или `307 Temporary Redirect`)**: браузер каждый раз
  обращается к нашему серверу `sho.rt`.
  - *Плюс*: точная статистика каждого перехода (User-Agent, GeoIP, Referer
    отправляются асинхронно в Kafka → ClickHouse) и динамическая подмена ссылки.
  - *Защита нашей БД при `302`*: все `100 000 RPS` чтений обслуживаются из
    кластера **Redis** (Cache-Aside с политикой `allkeys-lfu`) + локального
    L1-кэша для самых вирусных ссылок + фильтра Блума от несуществующих кодов.

## 5. Кейс 4: Лента новостей соцсети (News Feed — Twitter / VK / Instagram)

### 5.1 Суть задачи и два противоположных подхода к формированию ленты
Пользователь открывает приложение и должен за `< 100 мс` увидеть ленту из
последних постов тех людей, на которых он подписан.

```text
ПОДХОД 1: Fan-out on Write (Push Model — Предрасчёт ленты при публикации)
[Обычный автор (300 подписчиков)] --(Пишет пост)--> [Fan-out Worker]
                                                           |
      +----------------------------------------------------+
      | Раскладывает post_id в готовые персональные списки в Redis:
      +--> LPUSH feed:user_1 <post_id>
      +--> LPUSH feed:user_2 <post_id> ... (для всех 300 подписчиков)
  * Чтение ленты зрителем: МГНОВЕННОЕ за O(1) (просто LRANGE feed:user_1 0 50 из Redis!).
  * Где ломается: Если пост опубликовала ЗВЕЗДА с 50 000 000 подписчиков ->
    сделать 50 млн записей в Redis на один твит невозможно (Write Amplification / Lag)!

ПОДХОД 2: Fan-out on Read (Pull Model — Сборка ленты на лету при чтении)
[Автор] --(Пишет пост)--> Просто сохраняет 1 запись в свою таблицу posts (O(1) запись!)
[Зритель открывает ленту] --> Сервис берёт список подписок зрителя (500 авторов),
                              идёт во все их списки постов и делает Merge Sort на лету.
  * Где ломается: Тяжёлое и медленное чтение на каждый вход пользователя!
```

### 5.2 Промышленное решение: Гибридный подход (Hybrid Fan-out)
Во всех крупных социальных сетях применяется **гибридная модель**, разделяющая
авторов на две категории по порогу подписчиков (например, `10 000` подписчиков):
1. **Для обычных пользователей (`< 10 000` подписчиков) — используется
   Fan-out on Write (Push)**: когда обычный человек публикует пост, воркеры
   из Kafka асинхронно дописывают `post_id` в предрассчитанные списки лент
   его подписчиков в кэше (`Redis ZSET / List`, хранящий только последние
   500–800 `post_id` для активных за последние 30 дней пользователей).
2. **Для знаменитостей / блогеров-миллионников (`> 10 000` подписчиков) —
   используется Fan-out on Read (Pull)**: когда звезда публикует пост, он
   записывается **только в один собственный список постов этой звезды**
   (никакого размножения на 50 миллионов списков!).
3. **Когда зритель открывает приложение**: сервис за `1 мс` берёт из Redis
   уже готовую предрассчитанную ленту зрителя от его обычных друзей и на
   лету подмешивает к ней (`Merge`) свежие посты тех 3–5 знаменитостей, на
   которых подписан этот зритель (кэшированные в L1/L2 памяти), после чего
   обогащает `post_id` текстами и авторами из кэша сущностей.

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему в системе денежных переводов нельзя просто выполнить `SELECT
balance FROM accounts WHERE id = 1` в коде приложения, проверить `if balance
>= amount` и сделать `UPDATE accounts SET balance = balance - amount`?**
*Ответ:* Между чтением `SELECT` и записью `UPDATE` без блокировки строки
возникает классическое состояние гонки **Time-of-Check to Time-of-Use (TOCTOU)
/ Lost Update**. Если пользователь параллельно отправит 5 запросов на перевод
всей суммы счёта, все 5 потоков одновременно прочитают старый положительный
баланс, все 5 пройдут проверку `if` в коде приложения и все 5 перезапишут
баланс, позволив вывести деньги 5 раз. Проверка и изменение должны выполняться
либо под пессимистичной блокировкой строки `SELECT ... FOR UPDATE` внутри
транзакции, либо одним атомарным условным запросом `UPDATE accounts SET
balance = balance - :amt WHERE id = 1 AND balance >= :amt`.

**2. Как именно возникает взаимная блокировка (Deadlock) при параллельных
переводах между двумя счетами под `SELECT ... FOR UPDATE`, и какое правило на
100% исключает этот Deadlock?**
*Ответ:* Deadlock возникает при встречном (перекрёстном) порядке захвата
блокировок: Транзакция 1 переводит со счёта А на счёт Б (блокирует сначала А,
затем пытается заблокировать Б), а параллельная Транзакция 2 переводит со
счёта Б на счёт А (блокирует сначала Б, затем ждёт освобождения А). Образуется
замкнутый цикл ожидания, который СУБД вынуждена разорвать аварийным убийством
одной из транзакций. Чтобы исключить этот Deadlock математически, все
транзакции в системе обязаны блокировать участвующие счета в **едином
глобально отсортированном порядке** (например, всегда сначала счёт с меньшим
числовым `account_id`, а затем с бо́льшим: `ORDER BY account_id ASC FOR
UPDATE`).

**3. Клиент отправил запрос `POST /transfers` с ключом идемпотентности
`key_123`. Что должен вернуть сервер, если второй параллельный запрос с тем же
самым `key_123` пришёл через 50 мс, когда первый запрос ещё выполняется и
транзакция ещё не завершена?**
*Ответ:* Если первый запрос ещё находится в процессе выполнения (`IN_PROGRESS`),
сервер ни в коем случае не должен запускать параллельное выполнение операции!
Если ключ идемпотентности фиксируется на входе (например, через атомарный
`SET key_123 IN_PROGRESS NX EX 60` в Redis или отдельную быструю фиксацию в
БД), то конкурирующий дублирующий запрос при обнаружении статуса `IN_PROGRESS`
должен либо получить ответ **`HTTP 409 Conflict` / `425 Too Early`** (с
просьбой повторить запрос через пару секунд, когда результат будет готов),
либо подождать освобождения лока и вернуть готовый сохранённый ответ первого
запроса.

**4. Зачем в схеме финансовой базы данных кроме колонки `balance` в таблице
`accounts` обязательно ведут неизменяемую таблицу проводок `ledger_entries`
(Double-Entry Bookkeeping)?**
*Ответ:* Простая перезапись ячейки `balance` не оставляет аудируемого следа:
при любой ошибке в коде или сбое невозможно доказать, откуда взялась текущая
сумма и куда делись деньги. В системе двойной записи (**Double-Entry Ledger**)
каждая операция порождает минимум две неизменяемые строки в `ledger_entries`:
списание со счёта-источника (`-1000`) и зачисление на счёт-получатель (`+1000`).
Алгебраическая сумма всех записей во всей таблице `ledger_entries` в любой
момент времени строго равна **нулю** ($\sum \text{amount} = 0$). Ежедневная
сверка (**Reconciliation**) проверяет этот инвариант и соответствие суммы
проводок текущему полю `balance`, мгновенно выявляя любую аномалию.

**5. Почему в кейсе Медиа-хостинга загрузка файлов напрямую в S3 по Presigned
URL может привести к накоплению миллионов «осиротевших» (Orphaned) файлов в
бакете, и как это решается?**
*Ответ:* Сценарий: клиент запросил у бэкенда `Presigned URL` (бэкенд создал
запись в БД со статусом `PENDING`), клиент успешно залил 50 МБ в S3, но перед
отправкой финального подтверждения на бэкенд у клиента пропал интернет (либо
клиент вообще бросил загрузку на полпути). Чтобы не полагаться на честное
уведомление от клиента и не копить мусор: (1) переход файла из `PENDING` в
`UPLOADED` триггерится **напрямую событием от самого S3 (`s3:ObjectCreated:*`
→ очередь)**, а не запросом с телефона клиента; (2) для незавершённых
`Multipart Uploads` и неподтверждённых временных префиксов в самом S3
настраивается политика жизненного цикла (**S3 Lifecycle Rule**), автоматически
удаляющая брошенные части через 24 часа, а фоновая джоба в БД чистит старые
записи `PENDING`.

**6. На ваш медиа-хостинг залили вирусное изображение, и в одну секунду его
запросили 100 000 пользователей из разных городов. В кэше CDN этого файла ещё
нет (Cold Cache). Как защитить Origin-сервер / S3 от пробоя 100 000
запросами?**
*Ответ:* Если у CDN 200 периферийных узлов (Edge PoP) по всему миру, то при
холодном кэше на каждом PoP сработает локальный `Request Coalescing`
(схлопывание
параллельных запросов к одному URL на одном узле), но все 200 PoP всё равно
одновременно отправят 200 тяжёлых запросов на ваш Origin. Чтобы свести их к
**ровно одному** запросу на Origin, включают архитектуру иерархического
кэширования — **Origin Shield (Экранирующий прокси-слой CDN)** с настройкой
`proxy_cache_lock on` (в nginx/Varnish): все 200 периферийных PoP идут за
промахом не напрямую в Origin, а через единый центральный узел Origin Shield,
который пропускает к вашему бэкенду ровно 1 запрос.

**7. В сервисе сокращения ссылок (URL Shortener) вы решили выдавать воркерам
блоки по 10 000 номеров из центрального координатора для кодирования в Base62.
Какие две проблемы есть у этого решения и как их устранить?**
*Ответ:*
- *Проблема 1 (Безопасность / Предсказуемость)*: если переводить
  последовательные
  числа `100001, 100002, 100003` напрямую в Base62, короткие ссылки будут
  отличаться ровно на последнюю букву. Конкурент или злоумышленник сможет
  простым перебором (`+1`) скачать все созданные в системе приватные ссылки!
  *Решение*: перед переводом в Base62 прогонять 64-битное число через быструю
  обратимую битовую перестановку (например, **Сеть Фейстеля / Feistel Cipher**
  или `XOR` с секретным ключом) — тогда соседние числа дают внешне абсолютно
  случайные 7-символьные коды, сохраняя 100% уникальность без коллизий.
- *Проблема 2 (Потеря остатка блока при рестарте пода)*: если воркер взял
  блок из 10 000 номеров в память и перезапустился через минуту,
  неиспользованные
  9 500 номеров просто сгорают. При 3.5 триллионах комбинаций ($62^7$) потеря
  нескольких тысяч номеров при редких деплоях абсолютно бесплатна и не требует
  усложнения системы!

**8. Как в сервисе сокращения ссылок с нагрузкой 100 000 RPS на чтение (`302
Redirect`) собирать детальную аналитику каждого клика (время, страна,
браузер), не замедляя сам редирект и не нагружая основную БД?**
*Ответ:* Записывать клики синхронно в реляционную БД внутри обработчика
`GET /{code}` категорически нельзя — это увеличит задержку редиректа и убьёт
БД потоком в `100 000 INSERT/sec`. Обработчик редиректа только достаёт
длинный URL из памяти (L1/Redis) за `1 мс`, мгновенно отдаёт клиенту `302
Found`, а событие клика **асинхронно (неблокирующе)** кидает в локальный
кольцевой буфер в памяти процесса. Фоновая горутина/поток раз в 100 мс
сбрасывает пачки событий в **Apache Kafka**, откуда стриминговый консьюмер
вставляет их крупными батчами (по 10 000–50 000 строк за раз) в колоночную
аналитическую СУБД **ClickHouse**.

**9. Почему в кейсе Ленты новостей (News Feed) в предрассчитанных списках
пользователей в Redis (`feed:user_id`) хранят только массив идентификаторов
(`post_id`), а не полные JSON-объекты постов с текстом, лайками и именем
автора?**
*Ответ:* Две фундаментальные причины:
1) **Экономия дорогой оперативной памяти (RAM)**: если один пост весит `2 КБ`,
   то при размножении (Fan-out on Write) поста на 1 000 подписчиков один пост
   займёт `2 МБ` в Redis, а лента из 500 постов для 50 млн пользователей
   потребует терабайты RAM. Хранение только 8-байтного `int64 post_id`
   уменьшает объём списка ленты в сотни раз!
2) **Изменяемость метаданных поста (Mutable State)**: у поста каждую секунду
   растёт счётчик лайков/комментариев, а автор может отредактировать текст
   или сменить аватарку. Если бы полный JSON поста был скопирован в 10 000
   персональных списков подписчиков, при каждом лайке пришлось бы обновлять
   10 000 копий в Redis! При хранении только `post_id` сам объект поста лежит
   в кэше сущностей (`post_cache:post_id`) в единственном экземпляре, и при
   чтении ленты приложение за один батч-запрос `MGET` собирает актуальные
   данные.

**10. Как в гибридной архитектуре Ленты новостей формируется единая
отсортированная по времени лента с пагинацией, когда часть постов берётся из
предрассчитанного Push-кэша (обычные друзья), а часть подтягивается на лету по
Pull-модели (знаменитости)?**
*Ответ:* При запросе страницы ленты с курсором `before_timestamp` (или
`max_post_id`, если используется Snowflake ID, где старшие 41 бит — это
точное время создания!) сервис формирования ленты (`Feed Aggregator`) делает
два быстрых параллельных чтения из кэша:
1) Читает $K = 20$ записей до курсора из предрассчитанного `ZSET` пользователя
   (`ZREVRANGEBYSCORE feed:user_id :cursor -inf LIMIT 0 20`).
2) Смотрит в закэшированный список знаменитостей, на которых подписан этот
   пользователь (обычно это 5–20 аккаунтов), и берёт последние посты до
   курсора из их персональных кэшированных списков `celebrity_posts:celeb_id`.
3) В памяти процесса за микросекунды выполняет слияние отсортированных списков
   (**K-way Merge с помощью Min/Max-Heap** по убыванию `post_id` / времени),
   отрезает верхние 20 элементов, обогащает их через `MGET` из кэша постов и
   возвращает клиенту вместе с новым курсором 20-го элемента.
