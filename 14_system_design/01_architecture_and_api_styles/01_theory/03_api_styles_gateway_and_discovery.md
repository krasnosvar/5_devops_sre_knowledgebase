## 1. Роль контрактов взаимодействия в распределённой системе

В распределённой архитектуре сетевой интерфейс сервиса — это граница между
независимо разворачиваемыми компонентами. Ошибка в выборе протокола или
проектировании контракта бьёт сразу по трём фронтам:
1. **Производительность (CPU и Сеть)**: текстовая сериализация JSON и
   отсутствие мультиплексирования соединений на масштабе десятков тысяч RPS
   превращают до 30–50% ядер CPU в «обогреватель» для парсинга строк.
2. **Эволюция без даунтайма (Backward / Forward Compatibility)**: если
   изменение поля в ответе требует одновременного обновления клиента и
   сервера, система превращается в распределённый монолит.
3. **Управляемость и наблюдаемость на уровне L7**: способность балансировщика,
   CDN и Service Mesh маршрутизировать, кэшировать и лимитировать запросы
   напрямую зависит от семантики протокола.

## 2. REST: ресурсный подход, идемпотентность и HTTP-семантика

**REST (Representational State Transfer, Рой Филдинг)** моделирует систему
как набор **ресурсов** (существительных с уникальными URI: `/v1/orders/42`),
над которыми выполняются стандартные операции протокола HTTP.

### 2.1 Безопасность и идемпотентность HTTP-методов
Для инженера SRE и разработчика отказоустойчивых систем ключевое свойство
HTTP-метода — **идемпотентность** (повторный вызов с теми же параметрами
приводит систему в то же состояние и не создаёт дублирующих побочных
эффектов):

| Метод | Безопасный (Safe) | Идемпотентный | Архитектурный смысл для ретраев и кэша |
| :--- | :--- | :--- | :--- |
| `GET`, `HEAD` | Да | Да | Можно кэшировать на CDN/прокси и безопасно ретраить при сбое |
| `PUT` | Нет | **Да** | Полная замена ресурса: безопасен для автоматического ретрая |
| `DELETE` | Нет | **Да** | Удаление ресурса: повторный вызов вернёт `404`/`204`, но состояние то же |
| `PATCH` | Нет | Зависит | Идемпотентен, если задаёт значение (`{"status": "paid"}`), но НЕ идемпотентен при инкременте (`{"add": 10}`) |
| `POST` | Нет | **Нет!** | Создание/действие: авто-ретрай на уровне прокси **опасен** без `Idempotency-Key` |

> **Золотое правило для платёжных и мутирующих `POST`-запросов**: клиент
> обязан генерировать уникальный UUID в заголовке `Idempotency-Key`. Сервер
> атомарно сохраняет результат обработки по этому ключу (в БД или Redis) и
> при повторном получении того же ключа после сетевого обрыва возвращает
> сохранённый ответ без повторного списания средств.

### 2.2 Пагинация (Offset vs Cursor/Keyset)
При возврате больших списков (`GET /v1/events`) выбор способа пагинации
определяет выживаемость базы данных:
- **Offset-пагинация (`?limit=50&offset=100000`)**: заставляет СУБД
  вычитывать с диска и отбрасывать первые 100 000 строк (`O(N)` на запрос)
  и даёт дубли/пропуски элементов при вставке новых записей в начало списка.
- **Cursor / Keyset-пагинация (`?limit=50&after_id=984120`)**: использует
  индекс `WHERE id < 984120 ORDER BY id DESC LIMIT 50`, работая за
  стабильное время `O(log N)` на любой глубине истории.

## 3. gRPC и Protocol Buffers: бинарный RPC поверх HTTP/2

**gRPC** — стандарт де-факто для синхронного **межсервисного взаимодействия
(East-West traffic)** внутри дата-центра. Вместо ресурсов он опирается на
вызов удалённых процедур (`OrderService.CreateOrder`), строгую кодогенерацию
из `.proto`-файлов и бинарную сериализацию **Protocol Buffers (Protobuf)**.

### 3.1 Почему Protobuf и HTTP/2 в разы эффективнее JSON over HTTP/1.1
1. **Бинарное кодирование по номерам тегов**: вместо передачи строкового
   ключа `"transaction_amount_cents": 1500` в каждом сообщении, Protobuf
   передаёт только компактный номер поля (`field tag = 1`), тип (`varint`)
   и само значение — экономия трафика и CPU на парсинге в 3–10 раз.
2. **Мультиплексирование HTTP/2**: десятки параллельных RPC-вызовов между
   двумя сервисами идут по **одному долгоживущему TCP-соединению** в виде
   независимых потоков (`streams`) с бинарными фреймами и сжатием заголовков
   `HPACK`. Нет проблемы Head-of-Line blocking уровня HTTP/1.1 и нет
   исчерпания эфемерных портов.
3. **Четыре режима стриминга**: Unary (обычный запрос-ответ), Server
   Streaming, Client Streaming и **Bidirectional Streaming** (полнодуплексный
   поток сообщений).
4. **Встроенное распространение дедлайнов (`grpc-timeout`)**: клиент задаёт
   общий дедлайн, который автоматически передаётся по цепочке вызовов.

### 3.2 Обратная совместимость в Protobuf и ловушка L4-балансировки
- **Правило эволюции `.proto`**: никогда не меняйте номера (`= 1`, `= 2`)
  у существующих полей и не переиспользуйте номера удалённых полей
  (помечайте их ключевым словом `reserved`). Тогда старый и новый сервисы
  смогут прозрачно общаться друг с другом, просто игнорируя неизвестные им
  номера тегов.
- **Критическая ловушка для SRE (L4 vs L7 Load Balancing для gRPC)**:
  так как gRPC мультиплексирует все запросы внутри **одного долгоживущего
  TCP-соединения**, обычный L4-балансировщик (например, стандартный
  Kubernetes `Service` типа `ClusterIP` на базе `iptables`/`IPVS`)
  балансирует **только в момент установки TCP-соединения**! Если под-клиент
  открыл одно соединение к сервису, а затем HPA поднял ещё 9 реплик
  сервера, все 100% gRPC-запросов продолжат лететь в одну старую реплику.
  **Решение**: L7-балансировка осведомлённым прокси (Envoy / Istio / Linkerd)
  или client-side load balancing в самом gRPC-клиенте (через Headless
  Service `clusterIP: None`).

## 4. GraphQL: гибкие выборки для клиентов и их инфраструктурная цена

**GraphQL** позволяет клиенту (мобильному приложению, SPA-фронтенду) в
одном запросе к единому эндпоинту `POST /graphql` точно указать, какие
именно вложенные поля из разных сущностей ему нужны.

### 4.1 Какие проблемы решает GraphQL
- **Избавляет от Over-fetching**: мобильный клиент с медленным 3G-интернетом
  запрашивает только `id` и `title` товара, а не гигантский JSON на 50 полей.
- **Избавляет от Under-fetching (проблемы множества RTT)**: вместо 5
  последовательных запросов с телефона (`/user`, `/orders`, `/items`,
  `/reviews`) клиент забирает граф данных за один сетевой раундтрип.

### 4.2 Инфраструктурные и архитектурные проблемы GraphQL
1. **Проблема $N+1$ запросов на сервере**: наивный резолвер для списка из
   50 заказов сделает 1 запрос за заказами и 50 отдельных запросов к
   сервису пользователей. Требует обязательного использования паттерна
   **DataLoader** (склейка и батчинг однотипных подзапросов в рамках одного
   тика цикла событий).
2. **Сложность HTTP-кэширования и мониторинга**: все запросы идут методом
   `POST /graphql` и часто возвращают `HTTP 200 OK`, даже если внутри JSON
   лежит массив `"errors": [...]`. Стандартный CDN или nginx не может
   закэшировать ответ по URL, а стандартные метрики веб-сервера не видят
   5xx-ошибок без парсинга тела ответа.
3. **Уязвимость к DoS через глубоко вложенные запросы**: злоумышленник может
   прислать рекурсивный запрос `user { friends { friends { friends ... } } }`,
   который экспоненциально положит бэкенд. Обязательны лимиты глубины
   (`Max Query Depth`), сложности (`Query Cost Analysis`) и **Persisted
   Queries** (разрешение только заранее зарегистрированных хэшей запросов).

## 5. Сравнительная матрица: когда выбирать REST, gRPC или GraphQL

| Критерий | REST (JSON / OpenAPI) | gRPC (Protobuf / HTTP/2) | GraphQL |
| :--- | :--- | :--- | :--- |
| Лучшая ниша | Публичные API, внешние интеграции, простые веб-сервисы | Внутреннее межсервисное общение (East-West), микросервисы, стриминг | Мобильные и сложные Web-клиенты со множеством экранов (BFF-слой) |
| Формат и скорость | Текстовый JSON (медленнее парсинг, больше трафик) | Бинарный Protobuf (минимальный CPU и размер пакета) | Текстовый JSON (накладные расходы на парсинг AST запроса) |
| Строгость контракта | Опционально (OpenAPI / JSON Schema) | Обязательно на уровне компиляции (`.proto`) | Обязательно (строгая схема графа типов) |
| Кэширование на L7/CDN | Тривиально (стандартные HTTP `GET` + `Cache-Control` / `ETag`) | Сложно (требует специализированных прокси) | Сложно (`POST`-запросы, нужен Persisted Queries / нормализованный кэш) |
| Поддержка в браузере | Нативная (`fetch`) | Требует `gRPC-Web` и прокси-транслятора (Envoy) | Нативная (поверх HTTP `POST`) |

## 6. API Gateway и паттерн BFF (Backend for Frontend)

В микросервисной архитектуре внешние клиенты никогда не должны обращаться к
десяткам внутренних сервисов напрямую. На входе в периметр (**North-South
traffic**) ставится **API Gateway** (Kong, Envoy Gateway, Apache APISIX,
AWS API Gateway, собственной разработки BFF).

```text
[ Mobile App ] --\                      /--> [ Auth Service ]
                  +--> [ API Gateway ]--+--> [ Order Service (gRPC) ]
[ Web Browser ]--/     (TLS, Auth, RL)  \--> [ Catalog Service ]
```

### 6.1 Зона ответственности API Gateway (Cross-Cutting Concerns)
- **Терминация TLS и защита периметра** (WAF, защита от DDoS, валидация
  размеров заголовков и тела).
- **Аутентификация и первичная авторизация**: проверка подписи JWT/OAuth2
  токенов (по `JWKS`), сессионных кук и API-ключей, проброс проверенного
  `X-User-ID` внутрь контура.
- **Rate Limiting и квотирование** по IP, пользователю или тарифному плану.
- **Маршрутизация, версионирование и трансляция протоколов**: внешний клиент
  шлёт `REST/JSON`, а API Gateway транслирует его во внутренний `gRPC`.
- **Наблюдаемость на входе**: генерация корневого `trace_id` (`traceparent`),
  структурное логирование доступа и снятие RED-метрик периметра.

> **Антипаттерн «Умный шлюз (Smart Gateway / ESB)»**: никогда не помещайте
> внутрь API Gateway бизнес-логику предметной области, сложные оркестрации
> или прямые походы в базы данных! Иначе шлюз превращается в монолитное
> бутылочное горлышко, за деплой которого конкурируют все продуктовые команды.

### 6.2 Паттерн BFF (Backend for Frontend)
Когда у продукта сильно различаются клиенты (например, тяжёлый Desktop Web,
мобильное приложение iOS/Android и приложение для умных часов), единый
универсальный API становится неудобным для всех. В паттерне **BFF** для
каждого типа клиента создаётся свой легковесный фасадный сервис (часто
поддерживаемый самой фронтенд/мобильной командой), который агрегирует вызовы
к внутренним gRPC-микросервисам и отдаёт данные ровно в том формате (REST
или GraphQL), который нужен конкретному экрану.

## 7. Service Discovery, Ingress, Gateway API и Service Mesh

Как один сервис находит IP-адрес и порт другого сервиса в динамической
среде, где поды и виртуальные машины постоянно пересоздаются?

### 7.1 Client-Side vs Server-Side Service Discovery
1. **Client-Side Discovery**: сервис-клиент сам опрашивает реестр сервисов
   (**Service Registry** — `Consul`, `etcd`, `Eureka`), получает список живых
   IP:Port инстансов целевого сервиса и сам выбирает, куда слать запрос (по
   Round Robin или Least Connections).
   - *Плюс*: нет лишнего сетевого хопа через прокси-балансировщик.
   - *Минус*: логику дискавери и балансировки нужно вшивать в библиотеки для
     каждого языка программирования в компании.
2. **Server-Side Discovery**: клиент просто шлёт запрос на стабильное имя
   или виртуальный IP (VIP), а маршрутизацией на живые бэкенды занимается
   инфраструктурный балансировщик (ALB, nginx, либо связка `CoreDNS` +
   `kube-proxy` / `cilium` в Kubernetes).

### 7.2 Маршрутизация в k8s: Service → Ingress → Gateway API → Service Mesh
- **Kubernetes `Service` (`ClusterIP`)**: базовая абстракция L4 для
  внутрикластерного трафика. `CoreDNS` резолвит имя
  `orders.prod.svc.cluster.local`
  в виртуальный `ClusterIP`, а `kube-proxy` (через таблицы `nftables`/`IPVS`)
  или eBPF-датаплейн (`Cilium`) перенаправляет пакеты на `Pod IP` из объекта
  `EndpointSlice`.
- **`Ingress` и `Gateway API` (North-South)**: отвечают за вход внешнего
  L7-трафика в кластер. Современный стандарт **Kubernetes Gateway API**
  пришёл на смену ограниченному `Ingress`, разделив роли между платформенной
  командой (`GatewayClass`, `Gateway` — порты, TLS-сертификаты) и командами
  разработки (`HTTPRoute`, `GRPCRoute` — маршруты, веса для canary,
  зеркалирование).
- **Service Mesh (Istio, Linkerd, Cilium Service Mesh — East-West)**: когда
  микросервисов становятся десятки и сотни, управлять ретраями, таймаутами,
  L7-балансировкой gRPC и взаимным шифрованием (**mTLS** с автоматической
  ротацией сертификатов SPIFFE/SPIRE) в коде каждого сервиса становится
  невозможно. Service Mesh выносит эту логику на уровень инфраструктуры
  (через sidecar-прокси Envoy в каждом поде или ambient/node-level прокси).

```bash
# Диагностика Service Discovery и EndpointSlice в Kubernetes
kubectl get endpointslices -l kubernetes.io/service-name=orders-svc
kubectl run -it --rm debug --image=busybox:1.36 -- nslookup orders-svc.default.svc.cluster.local
```

## 8. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему при переходе межсервисного взаимодействия с REST (HTTP/1.1) на
gRPC (HTTP/2) в Kubernetes стандартный Service (`ClusterIP`) перестаёт
равномерно распределять нагрузку по подам?**
*Ответ:* HTTP/2 мультиплексирует все параллельные gRPC-вызовы внутри одного
долгоживущего TCP-соединения. Стандартный Kubernetes `Service` (`kube-proxy`
в режиме `iptables` или `IPVS`) работает на уровне L4 и принимает решение о
балансировке только один раз — в момент установки нового TCP-соединения
(пакет `SYN`). В результате все последующие gRPC-запросы по установленному
соединению идут в один и тот же под, а новые реплики после масштабирования
простаивают. Решается либо переходом на L7-прокси (Service Mesh Envoy/Linkerd),
либо использованием Headless Service (`clusterIP: None`) с client-side
балансировкой `round_robin` внутри самого gRPC-клиента.

**2. Сетевой прокси (Envoy / nginx) получил таймаут при чтении ответа от
бэкенда на запрос `POST /v1/payments` и автоматически повторил запрос на
другую реплику. Почему это опасно и как спроектировать систему правильно?**
*Ответ:* Метод `POST` по спецификации HTTP не является идемпотентным. Таймаут
чтения ответа не означает, что первый бэкенд не выполнил операцию: он мог
успешно списать деньги в БД и зависнуть перед самой отправкой ответа в сокет.
Слепой ретрай на уровне прокси приведёт к двойному списанию средств. Чтобы
сделать ретраи безопасными, клиент должен передавать уникальный заголовок
`Idempotency-Key`, а сервер — фиксировать этот ключ в одной ACID-транзакции
с бизнес-операцией (либо через атомарную блокировку) и возвращать кэшированный
результат при повторе.

**3. Что произойдёт, если в `.proto`-файле gRPC-сервиса удалить устаревшее
поле `string legacy_code = 3;`, а через месяц другой разработчик добавит новое
поле `int64 discount_id = 3;` с тем же номером тега?**
*Ответ:* В бинарном формате Protocol Buffers имена полей по сети вообще не
передаются — передаются только числовые номера тегов (`field number = 3`) и
тип кодирования (wire type). Если старый клиент или сообщение из очереди
пришлёт данные со старым полем №3 (`string`), новый сервер попытается
распарсить эти байты как `int64 discount_id`, что приведёт к повреждению
данных или ошибке десериализации. При удалении поля из `.proto` его номер и
имя необходимо навсегда блокировать директивой `reserved 3; reserved
"legacy_code";`.

**4. Почему для бесконечной ленты событий или истории транзакций пагинация
через `LIMIT 50 OFFSET 500000` положит базу данных, и как работает
альтернатива?**
*Ответ:* При `OFFSET 500000` движок СУБД вынужден реально просканировать по
индексу или таблице все 500 050 записей, отбросить первые 500 000 и вернуть
только 50. Сложность такого запроса растёт линейно `O(Offset)`, нагружая
CPU и вымывая буферный пул БД. Кроме того, если между запросами первой и
второй страницы в начало таблицы вставили новую запись, все строки сдвинутся,
и клиент увидит дубликат. Альтернатива — **Keyset (Cursor) пагинация**, где
клиент передаёт значение последнего увиденного ключа (`WHERE created_at <
:cursor_ts AND id < :cursor_id ORDER BY created_at DESC, id DESC LIMIT 50`),
что выполняется по B-Tree индексу за `O(log N)` независимо от глубины.

**5. Какие специфичные риски безопасности и отказоустойчивости приносит
вынесение GraphQL-сервера на внешний периметр по сравнению с REST API?**
*Ответ:* В REST структура и стоимость каждого эндпоинта фиксированы на
сервере. В GraphQL клиент сам конструирует произвольное дерево запроса, что
открывает вектор для ресурсного DoS: один сложный запрос с глубокой
вложенностью или циклическими связями способен породить тысячи запросов к БД
(проблема $N+1$). Кроме того, так как все запросы идут на один URL `POST
/graphql`, стандартные правила WAF и L7 Rate Limiting по URL-путям перестают
различать дешёвые и тяжёлые запросы. Защита требует внедрения `DataLoader`,
ограничения максимальной глубины (`maxDepth`), расчёта стоимости запроса
(`Query Complexity`) до его выполнения и перехода на `Persisted Queries`.

**6. В чём разница между использованием DNS с коротким TTL для Service
Discovery и использованием специализированного реестра вроде Consul/etcd или
Kubernetes EndpointSlice?**
*Ответ:* DNS работает по pull-модели с агрессивным многоуровневым
кэшированием: резолверы ОС, локальные кэши библиотек (JVM, glibc) и
промежуточные DNS-серверы часто игнорируют слишком малый TTL (например,
1–2 секунды), а уже открытые keep-alive TCP-соединения вообще не делают
повторный DNS-запрос. Поэтому при падении инстанса клиенты будут ещё долго
слать трафик на мёртвый IP. В Kubernetes (`EndpointSlice` watch) и Consul
используется реактивная подписка на изменения: как только под не проходит
readiness probe, контроллер мгновенно пушит обновление на все
узлы/sidecar-прокси.

**7. Почему перенос бизнес-логики (например, расчёта скидок или сложной
агрегации данных из БД) внутрь центрального API Gateway считается опасным
архитектурным антипаттерном?**
*Ответ:* Центральный API Gateway — это общая инфраструктурная точка входа
для всей компании. Если поместить туда продуктовый код, шлюз превращается в
монолитную точку синхронизации всех команд: любая правка бизнес-логики одной
команды требует релиза и тестирования общего шлюза, а ошибка или утечка
памяти в кастомном плагине кладёт доступ ко всем микросервисам компании
разом (максимальный blast radius). Шлюз должен решать только инфраструктурные
задачи (TLS, Auth, Rate Limit, роутинг), а агрегация данных под конкретный
интерфейс должна жить в отдельных сервисах BFF.

**8. Чем архитектура Kubernetes Gateway API концептуально превосходит
классический ресурс `Ingress`?**
*Ответ:* Классический `Ingress` был спроектирован как один плоский объект,
куда вперемешку складывались и инфраструктурные настройки (TLS-сертификаты,
классы балансировщиков), и маршруты приложений, а для любых продвинутых фич
(canary-веса, таймауты, ретраи, gRPC) приходилось писать десятки
несовместимых вендорских `annotations`. **Gateway API** разделяет ресурсы по
ролям в организации: администратор инфраструктуры управляет `GatewayClass` и
`Gateway` (слушающие порты, сертификаты, квоты), а разработчики в своих
namespace независимо управляют `HTTPRoute` и `GRPCRoute` со стандартной,
строго типизированной поддержкой весов трафика, заголовков и зеркалирования.

**9. В каком случае внедрение Service Mesh (Istio / Linkerd) оправдано, а
когда оно лишь создаёт лишнюю нагрузку и сложность?**
*Ответ:* Внедрение Service Mesh оправдано, когда в системе десятки
микросервисов на разных языках программирования, и бизнесу или регуляторам
требуются: обязательный **mTLS** между всеми подами с автоматической ротацией
сертификатов, единая политика авторизации L7 (`AuthorizationPolicy`),
корректная L7-балансировка gRPC, единые метрики RED и распределённые ретраи
без переписывания кода всех сервисов. В небольшом кластере из 5–10 сервисов
на одном языке sidecar-прокси в каждом поде лишь удвоят потребление памяти,
добавят `~1–2 мс` латентности на каждый сетевой хоп и резко усложнят отладку
сети.

**10. Как организовать проверку JWT-токенов между API Gateway и внутренними
микросервисами, чтобы не превратить центральный сервис авторизации (Auth
Service) в узкое место на каждый запрос?**
*Ответ:* Вместо того чтобы на каждый входящий запрос синхронно ходить по сети
из API Gateway в Auth Service за проверкой токена (Introspection), используют
асимметрично подписанные JWT (`RS256` / `EdDSA`). Auth Service подписывает
токен приватным ключом и публикует открытые ключи по стандартному эндпоинту
`/.well-known/jwks.json`. API Gateway (и внутренние сервисы при необходимости
Zero Trust) кэширует публичный `JWKS` в памяти и проверяет криптографическую
подпись и срок действия (`exp`) локально за микросекунды без единого сетевого
запроса к Auth Service.
