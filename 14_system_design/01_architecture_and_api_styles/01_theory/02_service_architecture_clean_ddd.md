## 1. Зачем внутренняя архитектура кода нужна в System Design

На первый взгляд может показаться, что внутренняя структура папок и классов
внутри одного сервиса — дело исключительно прикладных разработчиков. Однако
на уровне System Design ошибки внутрисервисной архитектуры напрямую приводят
к системным отказам:
- **Неправильное разбиение на домены** порождает распределённый монолит
  (см.
[`01_system_architecture_monolith_microservices.md`](./01_system_architecture_monolith_microservices.md)).
- **Протекание инфраструктуры (ORM, HTTP, брокеров) в бизнес-логику** не
  позволяет безболезненно сменить базу данных, вынести чтение в кэш,
  перевести синхронный HTTP-вызов на асинхронную очередь Kafka или покрыть
  критичный расчёт быстрыми unit-тестами без поднятия тяжёлого стенда.
- **Слишком крупные транзакционные границы (Aggregates)** вызывают
  конкуренцию за блокировки строк в БД (`Lock Contention`) и обрушивают
  пропускную способность под высокой нагрузкой.

> Прикладную реализацию этих паттернов с учётом особенностей рантайма и
> типизации конкретных языков см. в связанных репозиториях:

## 2. Организация бизнес-логики: Transaction Script vs Domain Model

Мартин Фаулер выделил два базовых подхода к организации логики обработки
запроса:

### 2.1 Transaction Script (Сценарий транзакции)
Вся логика одного действия пользователя записана как последовательная
процедура: «прочитать входной JSON → сделать `SELECT` из БД → проверить
`if/else` → сделать `UPDATE` → отправить сообщение».
- **Где уместно**: простые CRUD-сервисы, ETL-скрипты, тонкие адаптеры и
  прокси-сервисы с минимальной ветвистостью бизнес-правил.
- **Где ломается**: как только правил становится много (скидки, налоги,
  лимиты, статусные переходы заказа), одни и те же проверки `if` начинают
  копироваться между десятками процедур. При изменении бизнес-правила
  одно из мест забывают обновить, и в базе появляются невалидные состояния.

### 2.2 Domain Model (Доменная модель)
Бизнес-данные и правила их изменения объединяются в объекты домена, которые
сами защищают свои **инварианты** (условия, которые должны быть истинны
всегда). Перевести заказ в статус `PAID` нельзя простым присваиванием поля
`order.status = "PAID"` — вызывается метод `order.mark_as_paid(payment_id)`,
который внутри проверяет, что заказ не был отменён и сумма сходится.

> **Антипаттерн Anemic Domain Model (Анемичная модель)**: когда в проекте
> формально есть классы сущностей (`Order`, `Account`), но в них лежат
> только геттеры и сеттеры данных (как в структурах БД), а вся логика
> размазана по гигантским процедурным классам `OrderService` / `OrderManager`.
> Это тот же Transaction Script, замаскированный под ООП.

## 3. Слоистая архитектура (Layered / N-Tier Architecture)

Классический способ разделения ответственности внутри приложения —
горизонтальные слои, где каждый верхний слой обращается только к
нижележащему:

```text
+-------------------------------------------------------+
| 1. Presentation / Transport Layer (HTTP, gRPC, CLI)   |
+-------------------------------------------------------+
                           |
                           v
+-------------------------------------------------------+
| 2. Application / Service Layer (Оркестрация сценария) |
+-------------------------------------------------------+
                           |
                           v
+-------------------------------------------------------+
| 3. Domain / Business Logic Layer (Бизнес-правила)     |
+-------------------------------------------------------+
                           |
                           v
+-------------------------------------------------------+
| 4. Data Access / Infrastructure Layer (SQL, Redis, S3)|
+-------------------------------------------------------+
```

### 3.1 Главный изъян классической слоистой архитектуры
В традиционной N-tier схеме поток зависимостей направлен **сверху вниз**:
`Domain Layer` напрямую зависит от `Data Access Layer` (импортирует пакеты
ORM, драйверы БД, модели таблиц). В результате:
- Доменная логика оказывается намертво прибита к структуре реляционных
  таблиц и конкретной СУБД (**Database-Driven Design**).
- Невозможно протестировать бизнес-правила в изоляции без поднятия реальной
  базы данных или тяжёлого мокирования внутренностей ORM.

## 4. Hexagonal (Ports & Adapters), Onion и Clean Architecture

Все три подхода — **Гексагональная архитектура** (Алистер Кокберн),
**Луковая архитектура (Onion)** (Джеффри Палермо) и **Чистая архитектура
(Clean Architecture)** (Роберт Мартин) — решают проблему зависимости домена
от инфраструктуры с помощью одного фундаментального принципа:
**Инверсии зависимостей (Dependency Inversion Principle, буква D в SOLID)**.

### 4.1 Главное правило зависимостей (The Dependency Rule)

```text
+-------------------------------------------------------------------+
| Infrastructure & Frameworks (HTTP, gRPC, Postgres, Kafka, Redis)  |
|   +-----------------------------------------------------------+   |
|   | Interface Adapters (Controllers, Presenters, Gateways,    |   |
|   |                     Repository Implementations)           |   |
|   |   +---------------------------------------------------+   |   |
|   |   | Application / Use Cases (Оркестрация сценариев,   |   |   |
|   |   |                          Порты / Интерфейсы)      |   |   |
|   |   |   +-------------------------------------------+   |   |   |
|   |   |   | Domain / Entities (Чистые бизнес-правила  |   |   |   |
|   |   |   |                    и инварианты, 0 импорт)|   |   |   |
|   |   |   +-------------------------------------------+   |   |   |
|   |   +---------------------------------------------------+   |   |
|   +-----------------------------------------------------------+   |
+-------------------------------------------------------------------+
     Направление зависимостей в исходном коде: ТОЛЬКО ВНУТРЬ!
```

**Правило направления зависимостей**: исходный код может зависеть (`import`)
только от более внутренних концентрических слоёв. Внутренний слой ничего не
знает о существовании внешнего:
1. **Domain (Entities & Value Objects)**: самый центр. Содержит чистые
   бизнес-сущности и правила. Не импортирует ни веб-фреймворк, ни ORM, ни
   библиотеку работы с Kafka.
2. **Application (Use Cases / Interactors)**: содержит сценарии использования
   системы (например, `TransferMoneyUseCase`). Здесь же объявляются
   **Порты (Ports)** — абстрактные интерфейсы того, что нужно сценарию для
   работы (`AccountRepository`, `PaymentGateway`).
3. **Adapters (Interface Adapters)**: переводят данные из формата внешних
   систем во внутренний формат Use Case и наоборот.
   - **Первичные / Входящие адаптеры (Driving / Primary Adapters)**:
     HTTP-контроллеры, gRPC-хендлеры, консьюмеры Kafka, CLI-команды — они
     *вызывают* Use Case.
   - **Вторичные / Исходящие адаптеры (Driven / Secondary Adapters)**:
     Postgres-репозиторий, клиент Redis, продюсер в брокер — они
     *реализуют* интерфейс (Порт), объявленный внутри Application/Domain.
4. **Infrastructure (Frameworks & Drivers)**: самая внешняя оболочка —
   конфигурация веб-сервера, пулы соединений к СУБД, инициализация и сборка
   зависимостей в точке входа (`main`).

### 4.2 Практическая выгода для надежности и эволюции системы
- **Заменяемость инфраструктуры**: переход с REST на gRPC или замена
  синхронного HTTP-клиента на публикацию в Kafka затрагивает только тонкий
  внешний слой адаптеров — ядро бизнес-логики не меняется ни на строчку.
- **Мгновенные тесты**: 90% сложных бизнес-сценариев проверяются за
  миллисекунды в памяти с простейшим in-memory фейком репозитория.

## 5. Стратегический DDD: как резать систему на сервисы

**Domain-Driven Design (DDD, Эрик Эванс)** делится на две части:
**стратегическую** (как проектировать границы подсистем и команд) и
**тактическую** (как писать код внутри одного домена). В System Design
стратегический DDD — главный инструмент против создания распределённого
монолита.

### 5.1 Единый язык (Ubiquitous Language)
Разработчики, SRE и бизнес-эксперты используют одни и те же термины и в
разговорах, и в названиях сервисов/классов/таблиц/метрик. Если бизнес
говорит «Полис заблокирован по невыплате премии», в коде не должно быть
абстрактного `update_record_flag(id, type=3)`.

### 5.2 Ограниченный контекст (Bounded Context)
В большой компании одно и то же слово означает совершенно разные вещи для
разных отделов. Возьмём сущность «Товар (`Product`)»:
- В контексте **Каталога (`Catalog Context`)** важны название, фотографии,
  описание, характеристики для поиска и отзывы.
- В контексте **Склада и Логистики (`Inventory / Shipping Context`)**
  описание и фото не нужны — важны только габариты, вес, хрупкость и номер
  ячейки на складе.
- В контексте **Биллинга (`Billing Context`)** важны только цена, ставка
  НДС и код по налоговому классификатору.

Попытка создать единую «универсальную» таблицу/класс `Product` на всю
компанию порождает монстра из 200 колонок, за которого конкурируют все
команды. **Bounded Context** проводит чёткую границу: внутри каждого
контекста своя собственная модель `Product` со своими полями и своей базой
данных. **Хороший микросервис (или модуль монолита) всегда выравнивается по
границе Bounded Context.**

### 5.3 Карта контекстов (Context Map) и интеграционные паттерны
Как разные Bounded Contexts общаются между собой:
- **Customer / Supplier (Заказчик / Поставщик)**: вышестоящая команда
  (Upstream) учитывает нужды нижестоящей (Downstream) при планировании API.
- **Open Host Service (OHS) + Published Language**: сервис предоставляет
  стандартизированный публичный протокол (например, версионированный
  Protobuf/OpenAPI контракт) для всех потребителей.
- **Anti-Corruption Layer (ACL, Предохранительный слой)**: если ваш новый
  чистый сервис вынужден интегрироваться со старой запутанной легаси-системой
  или внешним API со странной моделью данных, вы ставите на своей границе
  адаптер-переводчик (ACL). Он не пускает уродливые структуры и термины
  внешней системы внутрь вашего доменного ядра.

## 6. Тактический DDD: строительные блоки внутри сервиса

Когда границы контекста определены, внутри него применяются тактические
паттерны DDD:

### 6.1 Сущность (Entity) против Объекта-значения (Value Object)

| Характеристика | Entity (Сущность) | Value Object (Объект-значение) |
| :--- | :--- | :--- |
| Идентичность | Определяется уникальным `ID` (`user_id`, `order_id`) | Определяется **только значениями своих полей** (нет `ID`) |
| Изменяемость | Состояние меняется во времени (жизненный цикл) | Строго **неизменяем (Immutable)** — при изменении создаётся новый |
| Примеры | `User`, `Order`, `BankAccount`, `SupportTicket` | `Money(100, "RUB")`, `EmailAddress`, `GeoCoordinates`, `DateRange` |

Использование `Value Object` вместо примитивов (передача `Money(amount,
currency)` вместо голого `float`/`int`, или `Email` с валидацией в
конструкторе вместо простого `str`) избавляет от ошибки **Primitive
Obsession** — например, невозможно случайно сложить рубли с долларами или
передать невалидный email вглубь бизнес-логики.

### 6.2 Агрегат (Aggregate) и Корень агрегата (Aggregate Root)
**Агрегат** — это кластер доменных объектов (`Entity` и `Value Objects`),
который рассматривается как **единое целое для изменения данных и проверки
инвариантов** (например, `Order` + список его `OrderLine`).
- **Aggregate Root (Корень агрегата)** — главная сущность (`Order`), через
  которую внешний мир взаимодействует с агрегатом. Внешний код не может
  напрямую изменить `OrderLine` в обход методов `Order` (иначе `Order` не
  сможет проверить инвариант «сумма позиций не превышает кредитный лимит»).
- **Граница транзакции**: **одна транзакция БД должна изменять ровно один
  агрегат**. Если вам кажется, что в одной транзакции нужно заблокировать и
  изменить сразу 5 разных агрегатов — либо границы агрегатов выбраны неверно,
  либо связь между ними должна быть асинхронной (через доменные события).
- **Правило для высоких нагрузок**: делайте агрегаты **маленькими**! Гигантский
  агрегат, подгружающий из БД тысячи дочерних строк при каждом изменении,
  убивает память и создаёт жесточайший `Lock Contention` в СУБД.

### 6.3 Repository, Domain Service, Domain Events и Unit of Work
- **Repository (Репозиторий)**: абстракция коллекции агрегатов, скрывающая
  детали хранения. Имеет методы уровня домена (`get_by_id`, `save`),
  принимающие и возвращающие целиком `Aggregate Root`, а не отдельные
  колонки таблицы.
- **Domain Service (Доменный сервис)**: содержит доменную бизнес-логику,
  которая неестественна для размещения внутри одной сущности (например,
  расчёт курса конвертации или проверка правил перевода между двумя счетами).
- **Domain Events (Доменные события)**: фиксируют свершившийся факт в
  прошедшем времени (`OrderPaid`, `InventoryReserved`), позволяя развязать
  побочные эффекты внутри монолита или опубликовать событие во внешний
  брокер через Transactional Outbox.
- **Unit of Work (Единица работы)**: паттерн, управляющий атомарностью
  бизнес-операции — отслеживает все изменения агрегатов в рамках сценария и
  фиксирует их в БД одной транзакцией (`commit` / `rollback`), гарантируя,
  что сам `Use Case` не завязан на конкретный драйвер транзакций СУБД.

## 7. CQRS и Event Sourcing: мощный инструмент или ловушка сложности

### 7.1 CQRS (Command Query Responsibility Segregation)
В обычной системе одна и та же модель (и одна БД) используется и для
записи (Commands), и для чтения (Queries). **CQRS** разделяет их на два
независимых пути:
- **Write Model (Команды)**: оптимизирована под строгую валидацию
  инвариантов, транзакции и нормализованную запись (например, PostgreSQL +
  Tactical DDD агрегаты).
- **Read Model (Запросы)**: оптимизирована под быстрые выборки и сложные
  проекции для UI без тяжёлых `JOIN` (например, денормализованные таблицы
  в PostgreSQL, индекс в Elasticsearch/OpenSearch или кэш в Redis,
  обновляемые асинхронно по событиям из Write Model).

**Цена CQRS с раздельными хранилищами**: между записью и обновлением Read
Model возникает **репликационный лаг (Eventual Consistency)** — пользователь
создал заказ, обновил страницу через 20 мс и ещё не увидел его в списке,
если интерфейс не учитывает это явно.

### 7.2 Event Sourcing (Хранение событий)
Вместо хранения только *текущего состояния* сущности (`UPDATE accounts SET
balance = 150`), система хранит в неизменяемом журнале (**Append-Only Event
Store**) всю последовательность *событий*, которые привели к этому состоянию:
`AccountCreated(0)` → `MoneyDeposited(+200)` → `MoneyWithdrawn(-50)`.
Текущее состояние восстанавливается проигрыванием (replay) событий, а для
ускорения периодически сохраняются слепки (**Snapshots**).

### 7.3 Когда это нужно, а когда это оверинжиниринг
- **Когда оправдано**: финансовые книги (ledger), биллинг, системы с
  железным регуляторным требованием полного аудита и воспроизведения
  состояния на любую секунду в прошлом, сложные коллаборативные системы.
- **Когда это ловушка**: в 90% обычных продуктовых сервисов полный Event
  Sourcing создаёт колоссальную сложность при эволюции версий схемы событий
  (upcasting старых событий за 5 лет), удалении персональных данных по
  закону (GDPR «право на забвение» в неизменяемом логе) и отладке.

## 8. Типовые вопросы на собеседовании (Interview Q&A)

**1. В чём фундаментальная разница между классической слоистой архитектурой
(N-tier) и Чистой / Гексагональной архитектурой?**
*Ответ:* Разница в направлении зависимостей исходного кода относительно слоя
доступа к данным. В классической N-tier архитектуре зависимости идут сверху
вниз: слой бизнес-логики (Domain) напрямую зависит от слоя данных (Data
Access / ORM). В Чистой и Гексагональной архитектуре применяется принцип
инверсии зависимостей (DIP): все стрелки зависимостей направлены внутрь к
ядру домена. Внутри домена/приложения объявляется абстрактный интерфейс
(Порт, например `OrderRepository`), а конкретная реализация работы с
PostgreSQL/Redis (Адаптер) живёт во внешнем инфраструктурном слое и зависит
от домена, а не наоборот.

**2. Почему протекание ORM-моделей базы данных (например, моделей SQLAlchemy
или GORM) в слой бизнес-логики и HTTP-ответов считается опасным на
дистанции?**
*Ответ:* Во-первых, это связывает внешние API-контракты и доменную логику
со схемой таблиц: переименование колонки или разбиение таблицы в БД ломает
сериализацию JSON для клиентов. Во-вторых, ORM-модели часто содержат скрытое
поведение (ленивая подгрузка связей — Lazy Loading): обращение к полю в
шаблоне или сериализаторе внезапно генерирует $N+1$ синхронных SQL-запросов
к БД прямо во время формирования ответа (или падает в асинхронном коде).
В-третьих, становится невозможно протестировать сложные бизнес-правила без
инициализации инфраструктуры ORM.

**3. Что такое Bounded Context в стратегическом DDD и как он помогает избежать
создания распределённого монолита?**
*Ответ:* Bounded Context (Ограниченный контекст) — это смысловая и языковая
граница, внутри которой каждый термин домена имеет строго одно однозначное
определение и свою специализированную модель данных. Например, «Пользователь»
в контексте Авторизации (логин, хэш пароля, MFA) и «Покупатель» в контексте
Доставки (адрес, телефон, история вручений) — это разные модели в разных
контекстах, связанные только по `user_id`. Если резать микросервисы строго
по границам Bounded Contexts, сервисы обладают высокой внутренней связностью
(high cohesion) и слабым внешним зацеплением (low coupling), не требуя общих
таблиц и синхронных распределённых транзакций.

**4. Зачем нужен Anti-Corruption Layer (ACL) при интеграции микросервиса со
старым монолитом или внешним легаси-провайдером?**
*Ответ:* Внешние и легаси-системы часто имеют запутанную схему данных,
неудачные имена полей, числовые коды вместо статусов и специфичные ошибки.
Если использовать их DTO и понятия напрямую внутри вашего сервиса, чужая
модель «заразит» ваш домен: при любом изменении внешнего API или при смене
провайдера придётся переписывать всю бизнес-логику. ACL (Предохранительный
слой) выступает изолирующим адаптером-переводчиком на границе: он принимает
внешний формат и маппит его в чистые объекты вашего собственного домена.

**5. Как на практике определить правильный размер Агрегата (Aggregate) в DDD,
и к каким проблемам производительности приводит слишком крупный агрегат?**
*Ответ:* Граница агрегата определяется только **истинными бизнес-инвариантами**,
которые обязаны проверяться синхронно в одной транзакции (ACID). Всё, что
может быть согласовано асинхронно (eventual consistency), должно быть
вынесено в отдельные агрегаты и связываться только по `ID`. Если сделать
агрегат слишком большим (например, включить в агрегат `Merchant` все его
100 000 товаров `Product`), то любая загрузка агрегата в память выгребет
мегабайты данных из БД, а параллельные попытки обновить разные товары одного
продавца будут сериализоваться на блокировке одного и того же корня агрегата
(`Lock Contention` / оптимистичные конфликты версий).

**6. Почему правило «одна транзакция — один агрегат» так важно при
проектировании систем, рассчитанных на последующее шардирование БД?**
*Ответ:* При горизонтальном шардировании базы данных разные агрегаты (или
агрегаты разных пользователей/тенант-ключей) физически оказываются на разных
серверах (шардах). Локальная ACID-транзакция работает только в пределах
одного шарда; транзакция, охватывающая несколько агрегатов на разных шардах,
потребует медленного и блокирующего двухфазного коммита (2PC). Если система
изначально спроектирована так, что одна транзакция меняет ровно один агрегат,
а остальные уведомляются асинхронно через доменные события, она шардируется
по ID корня агрегата без переписывания бизнес-логики.

**7. В чём разница между применением CQRS внутри одной базы данных и CQRS с
разделением хранилищ записи и чтения?**
*Ответ:* В простейшем (и часто самом практичном) варианте CQRS разделяется
только код: команды записи идут через богатую доменную модель и ORM с
проверкой всех инвариантов, а запросы на чтение выполняют прямые быстрые
SQL-запросы (`SELECT` нужных колонок сразу в DTO) к той же самой БД — здесь
нет ни лага репликации, ни лишней инфраструктуры. При разделении хранилищ
(например, запись в PostgreSQL, а чтение из Elasticsearch через Kafka) мы
получаем огромную масштабируемость чтения, но платим за это появлением
Eventual Consistency (задержкой обновления Read Model) и необходимостью
поддерживать конвейер синхронизации проекций.

**8. Какие скрытые операционные проблемы приносит Event Sourcing через 2–3
года эксплуатации в продакшене?**
*Ответ:* Три главные проблемы: (1) **Эволюция схем событий (Schema Evolution
/ Upcasting)** — события в Event Store неизменяемы, поэтому при изменении
бизнес-логики код должен уметь читать и конвертировать на лету все исторические
версии событий (`OrderCreated_v1`..`v5`). (2) **Деградация времени загрузки**
длинных цепочек событий без механизма регулярных Snapshots. (3) **Удаление
персональных данных (GDPR / 152-ФЗ)** — нельзя просто сделать `DELETE` из
append-only лога; приходится применять крипто-шреддинг (Crypto-Shredding):
шифровать персональные данные в событиях индивидуальным ключом пользователя
и при запросе на удаление уничтожать сам ключ шифрования.

**9. Когда паттерн Clean Architecture с четырьмя слоями, мапперами и
интерфейсами превращается во вредный оверинжиниринг?**
*Ответ:* Когда сервис представляет собой простой CRUD-прокси над базой данных
без сложной бизнес-логики и инвариантов. В таком сервисе создание четырёх
идентичных структур (`UserHTTPRequest` → `UserUseCaseInput` → `DomainUser` →
`UserDBModel`) и трёх слоёв перекладывания полей из одной структуры в другую
не даёт никакой архитектурной выгоды, но увеличивает объём бойлерплейт-кода,
нагрузку на сборщик мусора (аллокации при копировании) и время разработки
простых фич в разы. Для простого CRUD достаточно Transaction Script или
простой двухслойной структуры (Handler → Storage).

**10. Зачем нужен паттерн Unit of Work, если у каждого репозитория можно
просто вызвать метод `.save()` с автокоммитом внутри?**
*Ответ:* Если каждый метод репозитория делает `COMMIT` самостоятельно,
невозможно атомарно выполнить бизнес-операцию, которая в рамках одного
сценария сохраняет агрегат И записывает доменное событие в таблицу
Transactional Outbox (или обновляет связанные таблицы в пределах одной
границы согласованности). Если второй вызов упадёт, первый уже не откатится.
Unit of Work инкапсулирует транзакцию БД: сценарий (`Use Case`) выполняет
все операции внутри контекста UoW и вызывает единый `uow.commit()` в самом
конце, не протекая объектом `db.Session`/`sql.Tx` в сигнатуры всех методов.
