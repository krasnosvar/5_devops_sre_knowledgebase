## 1. Эволюция макроархитектуры: какую проблему мы решаем

Выбор между монолитом и микросервисами — это прежде всего решение о том,
**где проходят границы развёртывания (deployment boundaries), изоляции
отказов (fault boundaries) и владения кодом (team boundaries)**. Всякая
макроархитектура ищет баланс между двумя фундаментальными силами:
- **Когнитивная и организационная сложность внутри одного артефакта**:
  когда над единой кодовой базой работают 100+ разработчиков, очереди
  на слияние (merge queue), время прогона тестов и риск сломать чужой
  модуль при релизе начинают парализовать поставку фич.
- **Операционная и сетевая сложность распределённой системы**: как только
  вызов функции в памяти (`~1–10 нс`) заменяется сетевым вызовом по TCP/IP
  (`~0.5–5 мс`), появляются частичные отказы (partial failures), сетевые
  таймауты, сериализация, рассинхронизация данных и необходимость в
  оркестрации, распределённом трейсинге и сложной инфраструктуре CI/CD.

### 1.1 Три измерения границ

```text
+-------------------------------------------------------------------+
| 1. Классический монолит:                                          |
|    [ Единый процесс / Единый пайплайн / Общая БД (единая схема) ] |
+-------------------------------------------------------------------+
| 2. Модульный монолит:                                             |
|    [ Единый процесс: Модуль A | Модуль B | Модуль C ]             |
|    [ Внутри БД: Схема A      | Схема B  | Схема C  (без JOIN!) ]  |
+-------------------------------------------------------------------+
| 3. Микросервисы:                                                  |
|    [ Сервис A ] --(сеть/брокер)--> [ Сервис B ]                   |
|    [ Своя БД A]                    [ Своя БД B]                   |
+-------------------------------------------------------------------+
```

Для инженера DevOps/SRE этот выбор определяет всю архитектуру платформы:
от топологии сетей и пайплайнов (см.
[`../../05_cicd_at_scale/`](../../05_cicd_at_scale/))
до кардинальности метрик и стоимости трафика между зонами доступности (AZ).

## 2. Классический монолит: сильные стороны и точка отказа

**Монолит** — это система, собираемая, тестируемая и разворачиваемая как
единая неделимая единица (один бинарный файл, один контейнерный образ,
один процесс ОС).

### 2.1 Архитектурные преимущества монолита
- **Атомарные транзакции (ACID)**: все бизнес-сущности живут в одной
  реляционной БД. Перевод денег, списание товара со склада и начисление
  бонусов выполняются в одной локальной транзакции `BEGIN ... COMMIT` без
  двухфазных коммитов и паттерна Saga.
- **Нулевая сетевая нагрузка между модулями**: вызов соседней подсистемы
  — это переход по указателю в адресном пространстве процесса (Virtual
  Address Space), без аллокации сокетов, TLS handshake и парсинга JSON/Protobuf.
- **Простота траблшутинга и профилирования**: один стектрейс, один `perf`
  или `eBPF`-профиль, единый лог-поток, отсутствие проблем с потерей
  контекста трассировки (`traceparent`) между десятком сетевых хопов.
- **Простой деплой и откат**: один артефакт, один `Deployment`, атомарный
  rollback одной версии.

### 2.2 Почему монолит перестаёт масштабироваться
1. **Единый домен отказа (Blast Radius)**: утечка памяти (memory leak),
   исчерпание пула потоков или `OOM Killer` из-за тяжёлого генератора
   PDF-отчётов убивает весь процесс — вместе с приёмом платежей и
   авторизацией.
2. **Несовместимые профили ресурсов**: модуль поиска требует много RAM
   (Page Cache / in-memory индексы), модуль обработки видео — CPU/GPU,
   а веб-API — быстрых сетевых воркеров. В монолите приходится
   масштабировать весь «комбайн» целиком на дорогих универсальных нодах.
3. **Деградация CI/CD и связность БД**: когда все таблицы связаны внешними
   ключами (`FOREIGN KEY`) и запросами с `JOIN` на 15 таблиц, любая
   миграция схемы (`ALTER TABLE` с `AccessExclusiveLock` в PostgreSQL)
   рискует заблокировать всю систему.

## 3. Модульный монолит: золотая середина для 80% систем

**Модульный монолит (Modular Monolith)** сохраняет единый артефакт
развёртывания (один процесс в продакшене), но внутри кода и базы данных
вводит жёсткие границы доменов, аналогичные микросервисным:

### 3.1 Правила изоляции в модульном монолите
- **Запрет прямого доступа к чужим данным**: модуль `Billing` не имеет
  права делать `SELECT` или `JOIN` к таблицам модуля `Catalog`. У каждого
  модуля — свой логический набор таблиц (или отдельная PostgreSQL-схема
  `billing.*`, `catalog.*` с проверкой в линтере/CI).
- **Взаимодействие только через публичные контракты (In-process API)**:
  модули общаются через явно определённые интерфейсы (фасады) или
  внутрипроцессную шину событий, передавая неизменяемые DTO (Data Transfer
  Objects), а не внутренние ORM-сущности.
- **Готовность к выделению (Extractability)**: если один модуль (`Media
  Processing`) начинает упираться в CPU, его можно вырезать в отдельный
  микросервис за пару дней, просто заменив in-process реализацию интерфейса
  на gRPC/HTTP-клиент.

## 4. Микросервисная архитектура и её реальная цена для SRE

**Микросервисы** — это архитектурный стиль, при котором система строится
как набор небольших сервисов, каждый из которых:
1. Владеет своим бизнес-доменом (Bounded Context в терминах DDD);
2. **Может быть развёрнут независимо (Independent Deployability)** без
   координации релиза с другими командами;
3. **Владеет собственным хранилищем данных (Database-per-Service)** —
   никакой другой сервис не ходит в его БД напрямую.

### 4.1 Инфраструктурный «налог» на микросервисы (Microservices Tax)

Переход к микросервисам перекладывает сложность из кода приложения на
платформу и SRE-команду:

| Область | В монолите | В микросервисах |
| :--- | :--- | :--- |
| Вызов соседа | Вызов функции (~10 нс) | Сетевой RPC (0.5–10 мс), сериализация, ретраи |
| Согласованность | Локальная ACID-транзакция | Eventual Consistency, Outbox, Saga |
| Наблюдаемость | Логи + метрики 1 сервиса | Distributed Tracing (OTel), высокая кардинальность |
| Сеть и облако | Внутри процесса (бесплатно) | Cross-AZ трафик (в облаках стоит больших денег!) |
| Секреты и сеть | 1 набор кредов, 1 порт | mTLS, Service Discovery, тысячи NetworkPolicy |
| CI/CD | 1 пайплайн | Сотни пайплайнов, матрица совместимости контрактов |

### 4.2 Сетевая математика и хвосты латентности (Tail Latency Amplification)

Если один пользовательский запрос проходит последовательно через $N = 10$
микросервисов, и каждый сервис имеет надёжность $99.9\%$ и $p99 = 50\text{ мс}$:
- Итоговая доступность цепочки падает до $0.999^{10} \approx 99.0\%$
  (в 10 раз больше простоев, чем у одного сервиса!).
- Вероятность того, что хотя бы один из 10 сервисов попадёт в свой
  99-й перцентиль задержки: $1 - 0.99^{10} \approx 9.56\%$. То есть
  почти **каждый десятый** пользовательский запрос будет медленным.

Проверить реальную стоимость сетевых хопов и cross-AZ трафика на Linux-ноде
инженер SRE может с помощью `ss` и счётчиков ядра:

```bash
# Оценка числа активных TCP-соединений между микросервисами на ноде
ss -tan state established | wc -l

# Проверка ретрансмитов и таймаутов TCP, раздувающих p99 в цепочке вызовов
nstat -az TcpRetransSegs TcpExtTCPTimeouts TcpExtListenDrops
```

## 5. Антипаттерн «Распределённый монолит» (Distributed Monolith)

**Распределённый монолит** — худший из возможных сценариев: система
разрезана на десятки сетевых сервисов (платим полный инфраструктурный
налог микросервисов), но при этом сервисы **не могут деплоиться и работать
независимо** (теряем все плюсы микросервисов).

### 5.1 Главные симптомы распределённого монолита
1. **Синхронные каскадные релизы (Lockstep Deployment)**: чтобы выкатить
   фичу, нужно обновить Сервис А, Сервис Б и Сервис В строго одновременно
   или в жёстком порядке, иначе продакшен падает с ошибками сериализации.
2. **Общая база данных (Shared Database Integration)**: несколько
   микросервисов читают и пишут в одни и те же таблицы PostgreSQL/MySQL.
   Любая миграция схемы в одном сервисе ломает запросы в трёх других.
3. **Длинные цепочки синхронных RPC-вызовов**: для ответа на один запрос
   Сервис А синхронно вызывает Б → В → Г → Д. Падение сервиса Д на краю
   графа вешает пулы потоков/горутин во всех вышестоящих сервисах.
4. **Общая библиотека с бизнес-логикой («God Library»)**: вся доменная
   логика вынесена в общий пакет `common-core`, обновление которого
   требует принудительной пересборки и редеплоя всех 40 сервисов.

## 6. Закон Конвея и критерии выбора архитектуры

> **Закон Конвея (Melvin Conway, 1967):** «Организации, проектирующие
> системы, ограничены дизайном, который повторяет структуру коммуникаций
> внутри этих организаций».

Если в компании 3 кросс-функциональные продуктовые команды (Checkout,
Catalog, Logistics), система естественно распадётся на 3 домена. Если же
разделить команду из 5 человек на 25 микросервисов, каждый разработчик
будет тратить 80% времени на поддержание Helm-чартов, Protobuf-контрактов
и пайплайнов вместо продукта.

**Обратный манёвр Конвея (Inverse Conway Maneuver)**: сознательное
переформатирование команд под целевую архитектуру (выделение автономных
Stream-aligned команд и Platform-команды), чтобы границы команд совпадали
с границами сервисов (Bounded Contexts).

### 6.1 Матрица принятия решения

| Критерий | Выбирайте Модульный Монолит | Выбирайте Микросервисы |
| :--- | :--- | :--- |
| Размер инженерного штата | До 15–30 разработчиков (1–3 команды) | 40+ разработчиков, много автономных команд |
| Понятность границ домена | Стартап / новый продукт, границы меняются | Домен зрелый, границы Bounded Contexts ясны |
| Зрелость DevOps/SRE | Базовый CI/CD, малая платформенная команда | Автоматизированный k8s, GitOps, OTel, IaC |
| Профиль нагрузки | Однородный по всей системе | Сильно перекошен (1 модуль держит 95% RPS) |
| Требования к изоляции | Одинаковые требования ко всему коду | Разный compliance (PCI DSS для биллинга) |

## 7. Методология 12-Factor App как фундамент облачных сервисов

Независимо от того, строите ли вы модульный монолит или микросервис, для
работы в современной облачной среде и Kubernetes приложение должно
следовать принципам **The Twelve-Factor App**:

1. **Codebase (Кодовая база)**: отслеживается в системе контроля версий,
   один код — много развёртываний (dev/stage/prod).
2. **Dependencies (Зависимости)**: явно объявлены и изолированы (`uv.lock`,
   `poetry.lock`, `go.mod`/`go.sum`), никакой надежды на системные пакеты.
3. **Config (Конфигурация)**: хранится в окружении (Environment Variables,
   `ConfigMap`/`Secret`), а не зашита в код или константы.
4. **Backing services (Сторонние сервисы)**: БД, Redis, Kafka, S3
   рассматриваются как подключаемые ресурсы (замена локального Postgres на
   облачный RDS меняется только сменой URL в конфиге).
5. **Build, release, run (Сборка, релиз, запуск)**: строгое разделение
   этапов (неизменяемый Docker-образ + конфигурация = релиз; см.
   [`../../05_cicd_at_scale/`](../../05_cicd_at_scale/)).
6. **Processes (Процессы)**: приложение исполняется как один или несколько
   **stateless-процессов** (share-nothing); любое долгоживущее состояние
   выносится во внешние хранилища.
7. **Port binding (Привязка к портам)**: сервис самодостаточен и сам
   слушает сокет/порт, не требуя внешнего веб-сервера-контейнера.
8. **Concurrency (Параллелизм)**: масштабирование через модель процессов
   (горизонтальное добавление реплик по типу нагрузки: web, worker).
9. **Disposability (Утилизируемость)**: быстрый старт и **корректное
   завершение (Graceful Shutdown)** по сигналу `SIGTERM` (закрытие
   слушающего сокета, доработка активных запросов, сброс буферов).
10. **Dev/prod parity (Идентичность окружений)**: минимальный разрыв во
    времени, персонале и версиях инструментов между разработкой и продом.
11. **Logs (Логи)**: рассматриваются как поток событий; приложение пишет
    в `stdout`/`stderr` (обычно в JSON), а сбор и маршрутизацию берёт на
    себя инфраструктура (kubelet → FluentBit/Vector → Loki/ELK).
12. **Admin processes (Админ-задачи)**: миграции БД и разовые скрипты
    запускаются как одноразовые процессы (Kubernetes `Job`) в том же
    окружении и из того же образа, что и основное приложение.

## 8. Стратегии миграции: Strangler Fig и Branch by Abstraction

Переписывание монолита «с нуля» (Big Bang Rewrite) почти всегда кончается
провалом: пока 2 года пишется «новая система», бизнес-требования уходят
вперёд. На практике применяют эволюционные паттерны:

### 8.1 Паттерн Strangler Fig («Душитель»)
Перед монолитом ставится маршрутизирующий прокси (API Gateway / Ingress /
Envoy). Выделяемый модуль (например, `/api/v2/payments`) разворачивается
рядом как новый сервис:
1. **Transform (Создание)**: новый сервис реализует целевую функциональность.
2. **Coexist (Сосуществование)**: API Gateway направляет запросы к
   `/api/v2/payments` в новый сервис (можно через canary 1% → 10% → 100%
   или теневое зеркалирование трафика — **Traffic Shadowing / Mirroring**),
   а все остальные пути по-прежнему идут в монолит.
3. **Eliminate (Удаление)**: когда 100% трафика домена переведено на новый
   сервис и старый код молчит по метрикам, мёртвый код и таблицы удаляются
   из монолита.

### 8.2 Миграция данных при распиле монолита
Самая сложная часть Strangler Fig — расцепить общую базу данных:
- **Шаг 1**: Внутри монолита запретить прямые `JOIN` к таблицам выделяемого
  домена, переведя чтение/запись на уровень кода через интерфейс.
- **Шаг 2**: Настроить **Dual Write** или потоковую репликацию изменений
  **CDC (Change Data Capture, например Debezium из WAL PostgreSQL)** из
  старой таблицы монолита в новую БД микросервиса.
- **Шаг 3**: Переключить чтение на новую БД (с верификацией расхождений в
  фоновом режиме), затем переключить запись и удалить старую таблицу.

## 9. Типовые вопросы на собеседовании (Interview Q&A)

**1. Команда решила распилить монолит на 15 микросервисов, но оставила им
общую базу данных PostgreSQL «чтобы не терять транзакции». Какие проблемы это
создаст в продакшене?**
*Ответ:* Это классический антипаттерн интеграции через общую БД, создающий
распределённый монолит. Во-первых, пропадает независимость деплоя (Independent
Deployability): любая миграция схемы (`ALTER TABLE`), берущая блокировку или
меняющая структуру колонки для одного сервиса, может сломать или повесить
остальные 14 сервисов. Во-вторых, пулы соединений всех 15 сервисов (умноженные
на число их реплик в HPA) быстро исчерпают `max_connections` единой БД.
В-третьих, невозможно изолировать отказы: тяжёлый аналитический запрос одного
сервиса вымоет буферный кэш (shared_buffers) и положит IOPS для всех остальных.

**2. Как математически объяснить бизнесу, почему цепочка из 8 синхронно
вызывающих друг друга микросервисов ухудшает и SLA доступности, и p99
латентности?**
*Ответ:* При последовательном синхронном вызове вероятности успешного ответа
перемножаются: если каждый из 8 сервисов имеет SLA $99.9\%$, итоговая
доступность цепочки равна $0.999^8 \approx 99.2\%$, то есть допустимое время
простоя вырастает в 8 раз (с 43 минут до ~5.8 часов в месяц). Для латентности
работает эффект усиления хвостов (Tail Latency Amplification): вероятность
того, что ни один из 8 независимых сервисов не попадёт в свой 1% худших
задержек (p99), равна $0.99^8 \approx 92.27\%$. Значит, почти $7.7\%$ всех
пользовательских запросов испытают задержку уровня p99 или хуже.

**3. По каким техническим признакам (метрикам в мониторинге и процессу в
Git/CI) вы поймёте, что в компании построен распределённый монолит, а не
микросервисы?**
*Ответ:* В CI/CD это видно по связанным релизам: невозможно выкатить сервис А
без одновременного обновления сервисов Б и В (общее релизное окно, падение
интеграционных тестов при раздельном деплое). В трассировке (Jaeger/Tempo)
видна глубокая синхронная вложенность спанов (веер или лесенка из 5–10+
синхронных RPC на один входящий запрос). В мониторинге инцидентов падение
одного некритичного второстепенного сервиса вызывает каскадный отказ (5xx)
по всей системе из-за отсутствия фолбэков и асинхронного разделения.

**4. Почему в методологии 12-Factor App категорически запрещено хранить
состояние в локальной памяти/на диске процесса и писать логи напрямую в файлы
на ноде?**
*Ответ:* Контейнеры и поды в облачной оркестрации эфемерны: в любой момент
HPA может убить реплику при спаде нагрузки, kube-scheduler — перенести под
на другую ноду, или сама нода может быть заменена (Spot/Preemptible VM).
Локальное состояние на диске контейнера при этом безвозвратно теряется
(включая не отправленные локальные лог-файлы), а привязка сессии пользователя
к памяти конкретного процесса ломает горизонтальное масштабирование и
балансировку нагрузки. Запись в `stdout`/`stderr` позволяет рантайму контейнера
надежно перехватывать поток без риска переполнить диск внутри контейнера.

**5. В чём преимущество модульного монолита перед микросервисами на старте
нового продукта, и как технически не дать модульному монолиту превратиться в
спагетти-монолит?**
*Ответ:* На старте продукта предметная область ещё плохо изучена, и границы
доменов (Bounded Contexts) постоянно двигаются. Рефакторинг границ между
пакетами внутри одного репозитория делается средствами IDE и компилятора за
минуты, тогда как перенос логики и данных между микросервисами и их БД занимает
недели. Чтобы модульный монолит не выродился в спагетти, границы модулей
защищают архитектурными тестами в CI (например, запрет прямого импорта
внутренних пакетов чужого модуля) и разделением таблиц БД по схемам с полным
запретом кросс-модульных `JOIN` и внешних ключей.

**6. Как безопасно переключить трафик со старого монолита на новый микросервис
по паттерну Strangler Fig, чтобы убедиться в корректности ответов до реального
переключения пользователей?**
*Ответ:* Используется техника **Traffic Shadowing (Mirroring)** на уровне
API Gateway или Service Mesh (например, Envoy / Istio `VirtualService` с
блоком `mirror`). Прокси отправляет основной запрос в монолит (и именно его
ответ возвращается клиенту), а асинхронную копию запроса параллельно шлёт
в новый микросервис в режиме «fire-and-forget». Это позволяет проверить новый
сервис под реальной продакшен-нагрузкой, сравнить его ответы и профиль
латентности с монолитом, не рискуя затронуть пользователей при ошибках.

**7. Почему при распиле базы данных монолита опасен наивный паттерн Dual Write
(когда код приложения сам пишет сначала в старую БД, а затем в новую), и чем
CDC (Debezium) лучше?**
*Ответ:* При наивном Dual Write без распределённой транзакции неизбежны гонки
(race conditions) и частичные отказы: запись в первую БД может пройти успешно,
а во вторую — упасть по сети (или два параллельных потока запишут обновления
в две БД в разном порядке), что приведёт к тихому разъезду данных. Подход с
CDC (Change Data Capture) оставляет одну точку записи (первичную БД), а
инструмент вроде Debezium вычитывает уже зафиксированный транзакционный лог
(WAL в PostgreSQL / binlog в MySQL) строго в порядке коммитов и гарантированно
доставляет изменения во вторую БД через Kafka.

**8. Как микросервисная архитектура влияет на облачный счёт (FinOps) в части
сетевого трафика, о чём часто забывают при расчётах?**
*Ответ:* В облачных провайдерах (AWS, GCP, Azure) трафик между разными зонами
доступности (Cross-AZ traffic) внутри одного региона тарифицируется в обе
стороны. В монолите вызовы между модулями происходили в оперативной памяти
бесплатно. В микросервисах, размазанных по 3 AZ для отказоустойчивости, один
входящий запрос порождает десятки межсервисных вызовов, которые при стандартной
балансировке случайно пересекают границы AZ. На высоких RPS счёта за Cross-AZ
Data Transfer нередко превышают стоимость самого вычислительного железа (EC2),
что требует внедрения Topology Aware Routing в Kubernetes.

**9. Что именно должен сделать процесс микросервиса в промежутке между
получением сигнала `SIGTERM` от kubelet и принудительным `SIGKILL`?**
*Ответ:* Во-первых, перевести свой readiness-эндпоинт в состояние неготового
(или положиться на параллельное удаление Pod IP из `EndpointSlice` с учётом
задержки распространения правил `kube-proxy`/Envoy, для чего часто ставят
`preStop` hook с небольшой паузой). Во-вторых, прекратить принимать новые
соединения на слушающем сокете, но не обрывать уже принятые запросы (дать
им завершиться в пределах `terminationGracePeriodSeconds`). В-третьих,
дообработать взятые из брокера сообщения, закоммитить смещения (offsets),
сбросить буферы метрик/логов/трейсов и корректно закрыть пулы соединений к БД.

**10. В каком случае выделение одного модуля из монолита в отдельный
микросервис оправдано даже в маленькой команде из 5 человек?**
*Ответ:* Когда этот модуль имеет кардинально иной профиль потребления ресурсов,
изоляции безопасности или надёжности. Классические примеры: (1) тяжёлая
CPU/GPU-обработка (генерация видео, ML-инференс, парсинг больших файлов),
которая иначе забивает CPU/память и вызывает `OOM Killer` для основного веб-API;
(2) модуль работы с данными банковских карт, выделение которого в отдельный
изолированный контур выводит остальной монолит из-под жёсткого аудита PCI DSS.
