## 1. Архитектура и Data Sources

Grafana — это только frontend (визуализатор). Она не хранит временные ряды.
Вся магия происходит через абстракцию **Data Sources (Источники данных)**.
Когда вы открываете график, браузер (через сервер Grafana) делает API-запрос к базе данных (Prometheus, PostgreSQL, CloudWatch).
*Важно:* Если база данных (Prometheus) "тормозит", график в Grafana не загрузится (будет спиннер). Графана не кэширует гигабайты метрик, она полностью полагается на производительность backend-базы.

## 2. Dashboards: Переменные (Templating) и Chaining

Хардкодить имена серверов в запросах — плохая практика. Grafana использует **Variables (Переменные)**.
Вы создаете переменную `$cluster`, которая делает скрытый запрос в Prometheus: `label_values(up, cluster)`. Вверху дашборда появляется выпадающий список.
В коде графиков вы пишете `node_cpu_seconds_total{cluster="$cluster"}`.
**Chained Variables (Связанные переменные)**: Мощный паттерн. Переменная `$namespace` зависит от `$cluster`. Если юзер выбрал кластер `prod`, в списке неймспейсов отобразятся только те, которые реально существуют в проде.

## 3. Unified Alerting (Встроенные алерты)

Исторически алерты создавались прямо в файлах Prometheus (`prometheus.rules`).
С выходом Grafana 8/9 появился **Unified Alerting**.
Вы можете накликать алерт мышкой прямо из графика (например, "Оповестить, если эта линия CPU будет выше 90% в течение 5 минут").
Grafana сама периодически опрашивает базу и управляет роутингом (отправляет уведомления в Slack/Telegram). Идеально для бизнес-метрик (например, график из MySQL "Количество неоплаченных заказов").

## 4. Аутентификация и RBAC

В Enterprise-среде локальные пароли не используются.
- **SSO/OIDC**: Интеграция с Google Workspace, GitHub или Keycloak. Юзеры логинятся в Графану без паролей.
- **Service Accounts (Ранее API Keys)**: Токены для скриптов (например, для пайплайна, который автоматически создает дашборды при деплое сервиса).
- **RBAC (Role-Based Access Control)**: Разделение прав. Папка `Dev` доступна для редактирования (Editor) разработчикам, а папка `Prod` доступна им только для чтения (Viewer), чтобы они не сломали критичные графики.

## 5. Provisioning (Дашборды как код)

В SRE все дашборды хранятся в Git в формате JSON (Dashboards as Code).
Если сервер Grafana сгорит, SRE просто поднимает новый пустой контейнер.
В контейнер через Volume прокидываются два YAML-файла (Provisioning):
1. Конфиг Data Sources (где лежит Prometheus).
2. Конфиг Dashboards (путь к папке с JSON-файлами).
Графана на старте автоматически читает их и воссоздает всю инфраструктуру мониторинга за 2 секунды. Никаких кликов мышкой при восстановлении после аварии.

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Вы открываете дашборд Grafana с графиком CPU за последние 30 дней. Почему график загружается мгновенно, хотя в Prometheus за месяц накоплены миллионы точек данных? Как Grafana оптимизирует отрисовку?**
*Ответ:* Grafana не запрашивает миллионы точек. Она использует внутреннюю переменную `$__interval` (или `$__rate_interval`). Когда вы смотрите на 30 дней, на вашем экране всего около 1000 пикселей по ширине. Grafana динамически вычисляет `$__interval` (например, 1 час). В PromQL запрос подставляется `rate(metric[$__interval])`. База данных (Prometheus) группирует (схлопывает) точки по 1 часу и возвращает Графане ровно 720 точек, которые моментально рендерятся в браузере.

**2. В чем разница между архитектурным подходом `Grafana Alerting` и классическим `Prometheus Alertmanager`? Что лучше использовать в Kubernetes?**
*Ответ:* `Grafana Alerting` вычисляется сервером Grafana. Это удобно для не-инженеров (можно накликать мышкой) и позволяет делать алерты на SQL-базы данных. Но если сервер Grafana упадет, вы ослепнете.
`Prometheus + Alertmanager` вычисляется самим движком метрик (максимально близко к данным). В k8s это стандарт де-факто, так как он описывается декларативно (через `PrometheusRule` CRD в GitOps). SRE всегда предпочитают хранить инфраструктурные алерты (упал сервер, нет памяти) на уровне Prometheus/Alertmanager для максимальной надежности.

**3. У вас есть график с 50 линиями (каждая линия — под в микросервисе). Легенда под графиком занимает половину экрана и нечитаема. Как это исправить средствами Grafana?**
*Ответ:* Нужно использовать настройки формата легенды (Legend Format). В запросе Prometheus (в настройках панели) поле Legend заполняется переменной-плейсхолдером `{{pod}}`. Тогда вместо длинного мусора (вроде `http_requests_total{pod="myapp-1234-abcd", namespace="prod"}`) под графиком будет отображаться аккуратное и короткое имя `myapp-1234-abcd`. Также можно переключить легенду в режим Table (таблица) с сортировкой по максимуму/текущему значению.

**4. Разработчик скопировал JSON-код дашборда из интернета (Grafana.com) и импортировал в свой кластер. Графики показывают ошибку "Data source not found". В чем проблема и как ее исправить?**
*Ответ:* При экспорте дашбордов из Grafana в них зашивается уникальный внутренний ID (uid) источника данных автора. При импорте в ваш кластер, вашего источника данных с таким ID не существует. Чтобы дашборд был переносимым, в настройках экспорта (в JSON) Data Source должен быть задан как **Variable (Переменная)**, например `${DS_PROMETHEUS}`. Тогда при импорте Grafana сама покажет выпадающий список и попросит вас выбрать, какой из ваших Data Sources подставить в этот дашборд.

**5. Объясните концепцию `Annotations` (Аннотаций) в Grafana и как они помогают при расследовании инцидентов (Post-mortems)?**
*Ответ:* Аннотации — это вертикальные линии-маркеры на графиках с текстовым описанием события. Например, CI/CD пайплайн (GitLab) при успешном деплое делает API-вызов в Grafana и создает аннотацию "Деплой версии v1.5.0". Если на графике Latency в 15:00 виден скачок, и прямо на этой же секунде стоит вертикальная линия аннотации "Деплой", SRE мгновенно понимает причину деградации (Root Cause) без необходимости лезть в логи и сверять время. Корреляция происходит визуально.

**6. Зачем в Grafana используются трансформации (Transformations), если агрегацию можно сделать прямо в запросе к базе данных (SQL/PromQL)?**
*Ответ:* Не все источники данных умеют делать сложную математику (особенно простые API, логи или базовые SQL). Трансформации (вкладка Transform) выполняются **в браузере пользователя (или на сервере Графаны)** уже после того, как данные получены из базы. Например, вы можете сделать два независимых запроса (один к Prometheus, другой к MySQL), а затем через трансформацию `Outer Join` или `Merge` объединить эти данные в одну таблицу. Также трансформации (например, `Filter data by values`) разгружают базу от лишних вычислений.

**7. У вас есть переменная `$namespace` со списком неймспейсов. Вы хотите вывести на один график сразу 3 неймспейса. Вы выбираете их галочками в выпадающем списке (Multi-value), но график ломается (ошибка синтаксиса). Как это починить в PromQL?**
*Ответ:* Если переменная Multi-value включена, Grafana подставляет ее в код как строку с разделителями (например, `dev|stage|prod`). В PromQL знак равенства `=` ожидает точного совпадения строки. Чтобы PromQL понял регулярное выражение, нужно изменить оператор в коде графика с `=` на `=~`. Код должен выглядеть так: `kube_pod_info{namespace=~"$namespace"}`. Тогда база данных корректно распарсит regex и вернет ряды из всех трех неймспейсов.

**8. Чем отличается `Server-side rendering` (создание PNG картинок графиков) в старых версиях Grafana от нового плагина Image Renderer? Почему это сложный процесс?**
*Ответ:* Создание скриншотов графиков необходимо для рассылки алертов в Slack/Telegram (чтобы дежурный сразу видел график в мессенджере). Раньше это делалось костылями (PhantomJS). Сейчас используется Grafana Image Renderer (основан на Headless Chrome/Puppeteer). Проблема в том, что рендеринг реального браузера требует **огромных затрат RAM и CPU**. В Kubernetes это обычно выносят в отдельный микросервис (pod), чтобы тяжелая генерация PNG скриншотов не завалила по OOM (Out Of Memory) основной сервер Grafana.

**9. Что такое `Grafana Explore` и чем оно отличается от обычных дашбордов?**
*Ответ:* Дашборды предназначены для мониторинга (Monitoring) — пассивного наблюдения за известными метриками. Графики там зафиксированы. `Explore` — это песочница для расследований (Troubleshooting/Observability). Инженер заходит туда, чтобы писать произвольные запросы (Ad-hoc queries) к метрикам, логам (Loki) или трейсам (Tempo) "на лету", не сохраняя их. Это интерфейс для поиска причины инцидента, который позволяет легко переключаться между метриками и логами с сохранением выбранного диапазона времени.

**10. Почему при настройке SSO (OIDC) интеграции с Keycloak или Google Workspace, Grafana использует механизм `Role Sync` (Синхронизация ролей)?**
*Ответ:* Без `Role Sync` все новые пользователи, заходящие через Google SSO, будут получать дефолтную роль (например, Viewer). Если вам нужно дать админские права 50 SRE-инженерам, вам придется заходить в Графану и раздавать их руками. `Role Sync` маппит (сопоставляет) группы из Identity Provider'а на роли в Grafana. Например, если юзер состоит в группе `sre-team` в Keycloak, Grafana при входе прочитает этот JWT-токен и автоматически выдаст юзеру роль `Admin` или `Editor` без ручного вмешательства.
