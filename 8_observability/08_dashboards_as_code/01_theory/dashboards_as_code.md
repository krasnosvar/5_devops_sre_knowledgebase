## 1. Почему "Кликать мышкой" — это антипаттерн?

Создание графиков руками в веб-интерфейсе Grafana работает только для пет-проектов.
**Проблемы в Production:**
- Отсутствие версионирования. Кто-то случайно удалил график, и вы не знаете кто и когда (нет `git blame`). Нет возможности сделать `git revert`.
- Невоспроизводимость (Disaster Recovery). Если диск сервера Grafana сгорит, вы потеряете сотни человеко-часов работы.
- Отсутствие ревью (Pull Requests). Изменения графиков идут в прод без проверок.
**Dashboards as Code (DaC)** решает эти проблемы, переводя дашборды в формат файлов в Git. Grafana становится полностью Stateless.

## 2. Подход 1: Grafana Provisioning (JSON + ConfigMaps)

Самый базовый нативный подход.
Вы создаете дашборд руками, нажимаете `Export -> Save as JSON`. Кладете этот огромный JSON-файл в Git.
Grafana поддерживает `Provisioning` из коробки. Вы создаете YAML-файл, в котором указываете путь к папке (например, `/etc/grafana/dashboards`).
В Kubernetes вы просто запаковываете все эти JSON-файлы в один большой `ConfigMap` и монтируете (Volume Mount) в контейнер Графаны. При рестарте пода Графана прочитает их и автоматически создаст.
*Минус:* JSON-файлы графаны огромны (по 3000 строк). Делать Code Review такого JSON в GitHub PR невозможно (глаза сломаются).

## 3. Подход 2: Kube-prometheus-stack (GrafanaDashboard CRD)

Эволюция первого подхода для Kubernetes. Оператор Prometheus вводит Custom Resource Definition — `GrafanaDashboard`.
Разработчику больше не нужно монтировать ConfigMaps в чужую Графану. Разработчик в своем неймспейсе пишет YAML:
```yaml
apiVersion: integreatly.org/v1alpha1
kind: GrafanaDashboard
metadata:
  name: my-app-dashboard
spec:
  json: >
    { ... тут вставлен сжатый JSON Графаны ... }
```
Специальный контроллер (K8s Sidecar) автоматически находит все такие манифесты по кластеру и по API загружает их в центральную Grafana. Это позволяет деплоить дашборд вместе с микросервисом (через один Helm чарт).

## 4. Подход 3: Генерация из кода (Jsonnet / Grafonnet / Cuelang)

Поскольку читать сырой JSON невозможно, инженеры решили **генерировать** его.
**Jsonnet** (и библиотека Grafonnet) — это язык программирования конфигураций от Google. Вы пишете логику:
```jsonnet
local grafana = import 'grafonnet/grafana.libsonnet';
grafana.dashboard.new('My App')
.addPanel(
  grafana.graphPanel.new('CPU Usage').addTarget('rate(cpu[5m])')
)
```
*Плюсы:* Код становится крошечным (20 строк вместо 3000). Поддерживаются циклы (for) и функции. Идеально для Code Review. В пайплайне CI/CD этот Jsonnet компилируется в грязный JSON и скармливается Графане.

## 5. Подход 4: Инфраструктура как код (Terraform Grafana Provider)

Если ваша инфраструктура управляется через Terraform, вы можете деплоить дашборды, папки и права доступа (RBAC) через официальный провайдер.
```hcl
resource "grafana_dashboard" "metrics" {
  config_json = file("dashboard.json")
  folder      = grafana_folder.prod.id
}
```
*Плюсы:* Вся инфраструктура (создание баз данных RDS, IAM ролей и Дашбордов) находится в одном state-файле и разворачивается одной командой `terraform apply`.

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Вы настроили Provisioning дашбордов через файлы (JSON). Инженер заходит в веб-интерфейс Grafana, нажимает кнопку "Edit" на графике, вносит изменения и хочет сохранить. Что произойдет?**
*Ответ:* Кнопка "Save" в веб-интерфейсе Grafana будет **заблокирована** (Read-Only). Архитектура Provisioning подразумевает строгий однонаправленный поток (Single Source of Truth). Дашборды, загруженные с диска, нельзя изменять через UI (и сохранять в базу SQLite графаны), чтобы не создавать конфликт состояний (Configuration Drift). Если инженеру нужно изменить график, он обязан внести изменения в код в Git и прогнать пайплайн.

**2. Зачем разработчики используют `Sidecar` контейнер (grafana-sc-dashboard) при деплое Grafana в Kubernetes (например, в официальном Helm-чарте)?**
*Ответ:* Sidecar-контейнер решает проблему динамического обнаружения ConfigMaps. Вместо того чтобы привязывать все ConfigMaps жестко через Volume Mounts (что требует перезапуска пода Графаны каждый раз при добавлении нового дашборда), Sidecar делает API Watch на сервер Kubernetes. Он ищет любые ConfigMap с лейблом `grafana_dashboard: "1"`. Как только разработчик создает такой ConfigMap, Sidecar ловит это событие, скачивает JSON и отправляет его в Grafana по HTTP API (Hot Reload). Без даунтайма.

**3. В чем фундаментальный недостаток хранения сырых JSON-файлов Grafana (экспортированных из UI) в Git-репозитории?**
*Ответ:* JSON-модель Grafana невероятно избыточна (Verbose). Один график из 2 линий может занимать 500 строк JSON-кода (включая цвета осей, толщину линий, отступы).
- **Нечитаемость PR**: Во время Code Review инспектор не может понять, что именно изменилось.
- **Обслуживаемость**: Если вам нужно изменить цвет линии ошибки с красного на бордовый в 50 дашбордах, вам придется писать сложный скрипт парсинга.
Поэтому продвинутые SRE команды переходят на языки-генераторы (Jsonnet, Cuelang).

**4. Вы используете Terraform для управления дашбордами. В какой момент происходит рендеринг графиков? Знает ли Terraform, работает ли ваш PromQL запрос?**
*Ответ:* Нет, не знает. Terraform — это чисто транспортный механизм доставки конфигурации (Infrastructure as Code). Terraform Provider для Grafana берет текстовый JSON и отправляет его через HTTP POST запрос в Grafana API. Terraform понятия не имеет о структуре PromQL или правильности метрик. Валидацией запросов и рендерингом занимается исключительно сама Grafana в браузере.

**5. Объясните концепцию `Mixins` (например, Kubernetes Mixin) в экосистеме Prometheus/Grafana.**
*Ответ:* Mixin — это готовый, переиспользуемый пакет Observability как кода (обычно написанный на Jsonnet). Вместо того чтобы самому изобретать графики для мониторинга Nginx или Kubernetes, вы импортируете готовый `Nginx Mixin`. Он содержит в себе сразу 3 вещи:
1. Идеальные дашборды для Grafana.
2. Проверенные алерты (Alerting Rules) для Prometheus.
3. Recording Rules для оптимизации.
Вы компилируете этот Mixin и получаете стандартизированный SRE-мониторинг "из коробки" для любого сервиса.

**6. Как в подходе `Dashboards as Code` решить проблему переноса дашборда между средами (Dev, Stage, Prod), где источники данных (Data Sources) называются по-разному?**
*Ответ:* В JSON-коде дашборда категорически нельзя хардкодить имена `datasource: "prometheus-prod"`. При экспорте/написании кода нужно использовать **шаблонизацию Data Source**. Поле DataSource заменяется на переменную (например, `"${DS_PROMETHEUS}"`). При развертывании в Dev-среде пайплайн (или настройки Provisioning в Графане) автоматически заменят эту переменную на `prometheus-dev`, а в Prod-среде — на `prometheus-prod`, используя один и тот же исходный код дашборда.

**7. Разработчик прислал Pull Request с JSON дашборда. Вы мержите его. На утро выясняется, что дашборд не открывается в Grafana (ошибка парсинга). Как этого избежать в CI/CD пайплайнах?**
*Ответ:* Сырой JSON легко сломать (забыть запятую или скобку). В CI/CD пайплайне обязательно должен быть шаг **Linting & Validation**. Для дашбордов используются инструменты типа `grafana-dashboard-linter` или простая валидация схемы JSON (JSON Schema validator). Пайплайн проверит синтаксис файла до того, как он попадет в главную ветку и заблокирует (Fail) сломанный Pull Request.

**8. У вас мульти-тенантная (Multi-tenant) Графана (несколько команд). Как при подходе Provisioning (ConfigMaps) разложить дашборды разных команд по разным папкам (Folders) с разными правами доступа?**
*Ответ:* В конфигурационном файле Provisioning (yaml) можно объявить несколько блоков `providers`.
```yaml
providers:
- name: 'team-a-dashboards'
  folder: 'Team A'
  options:
    path: /var/lib/grafana/dashboards/team-a
- name: 'team-b-dashboards'
  folder: 'Team B'
```
Каждый провайдер сканирует свою директорию (свой ConfigMap) и автоматически складывает графики в нужную папку в UI. Права доступа (RBAC) к этим папкам можно настроить либо руками, либо через тот же Terraform, выдав Команде А права Editor только на папку `Team A`.

**9. Что такое `Grafana API` и какую роль оно играет в автоматизации мониторинга (помимо использования Terraform)?**
*Ответ:* Grafana имеет мощное REST API. Это позволяет интегрировать ее с любыми внешними инструментами. Например:
1. Backstage (Developer Portal) может дергать API, чтобы вытаскивать скриншоты дашбордов и показывать их на странице сервиса.
2. В пайплайне при создании нового микросервиса, скрипт на Python может дернуть API Grafana, чтобы создать новую папку и положить туда базовый дашборд.
3. Динамическое управление юзерами (раздача API ключей машинам).

**10. В чем отличие декларативного деплоя дашбордов (GitOps/ArgoCD + CRD) от императивного (через CI скрипт и `curl` к API Графаны)?**
*Ответ:* 
- **Императивный (CI pipeline + curl)**: Скрипт выполняется один раз при слиянии в `main`. Если после этого кто-то зайдет в Grafana (если там не отключено редактирование) и изменит дашборд руками, система этого не заметит. Возникает рассинхрон (Configuration Drift).
- **Декларативный (ArgoCD + CRD)**: Контроллер (GitOps) постоянно работает в цикле синхронизации (Reconciliation loop). Он следит за Git. Если кто-то изменит или удалит дашборд в базе Графаны (напрямую), контроллер заметит отклонение от Git-репозитория и немедленно принудительно перезапишет (Heal) дашборд, восстановив идеальное состояние. Это гарантия надежности.
