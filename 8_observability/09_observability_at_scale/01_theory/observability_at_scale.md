## 1. Что ломается первым: cardinality, а не объём

Интуитивно кажется, что мониторинг "ломается на масштабе" из-за объёма данных
(больше хостов → больше метрик → больше дискового места). На практике первым
узким местом почти всегда оказывается **cardinality** — число уникальных
комбинаций label'ов временного ряда, а не абсолютное количество данных:

```
http_requests_total{method="GET", path="/users/12345", status="200"}
http_requests_total{method="GET", path="/users/12346", status="200"}
http_requests_total{method="GET", path="/users/12347", status="200"}
...
```

Если `path` содержит ID пользователя (вместо нормализованного шаблона
`/users/:id`), каждый новый пользователь создаёт **новый уникальный
временной ряд** — метрика, которая должна была быть одной, превращается в
миллионы. Prometheus хранит каждый уникальный ряд отдельно в памяти (индекс
label'ов), и high-cardinality метрика может обрушить потребление памяти
сервера на порядки быстрее, чем просто "много хостов" — один
неудачно спроектированный counter способен убить single-node Prometheus
быстрее, чем рост всего остального флота.

## 2. Federation и remote_write: от одного Prometheus к кластеру

Single-node Prometheus (см. [`../02_metrics_prometheus/`](../../02_metrics_prometheus/))
принципиально не распределён — он хранит всё на локальном диске одного
процесса. На масштабе множества кластеров/дата-центров это решается одним
из двух способов:

- **Federation** — верхнеуровневый Prometheus скрейпит агрегированные
  метрики с нижнеуровневых Prometheus (через их `/federate` endpoint).
  Подходит для небольшого числа уже агрегированных (recording rules)
  метрик, но не предназначен для перетаскивания сырых high-cardinality
  данных наверх — federation легко перегружается тем же способом, что и
  обычный scrape.
- **remote_write в централизованное хранилище** — каждый локальный
  Prometheus/vmagent отправляет (push) сырые метрики в горизонтально
  масштабируемое хранилище (`Thanos`, `VictoriaMetrics cluster`, `Mimir`),
  которое само разделяет данные между множеством узлов хранения и даёт
  единую точку запроса поверх них. Это стандартный путь для организаций
  с десятками Kubernetes-кластеров: в каждом кластере свой маленький
  Prometheus/vmagent только для локального скрейпа, вся долгосрочная
  история и кросс-кластерные запросы — в центральном кластерном хранилище.
- `VictoriaMetrics` в кластерном режиме (vminsert/vmstorage/vmselect — см.
  [`../03_victoriametrics/`](../../03_victoriametrics/)) и `Thanos` (Sidecar + Store
  Gateway + Querier) решают одну и ту же задачу разными архитектурами:
  VictoriaMetrics ближе к "изначально кластерная БД", Thanos — "надстройка
  над существующими Prometheus для дедупликации и общего query layer".

## 3. Управление cardinality на источнике

Централизованное хранилище не решает проблему cardinality — оно просто
переносит её с одного сервера на распределённый кластер, который сломается
точно так же, просто позже и дороже. Настоящее решение — не пускать
high-cardinality данные в систему вообще:

- **Relabeling на этапе scrape** — явный `drop`/`keep` лейблов до того, как
  метрика попала в TSDB; например, дропнуть лейбл с ID пользователя/сессии,
  если он случайно просочился в метрику приложения.
- **Recording rules** — предвычисление агрегатов (`sum by (service)
  (rate(http_requests_total[5m]))`) заранее, а не на каждый dashboard-запрос;
  это и ускоряет чтение, и снижает нагрузку, если сырые данные всё равно
  приходится хранить для детального дебага отдельно.
- **Лимиты cardinality** (`VictoriaMetrics` поддерживает `-storage.maxHourlySeries`/
  `-storage.maxDailySeries`) — явный предохранитель, превращающий "весь
  кластер лёг от одной плохой метрики" в "одно приложение потеряло часть
  своих метрик, остальная observability жива".
- Дисциплина на уровне приложения: метки вроде `path`/`user_id`/`request_id`
  в метриках — почти всегда архитектурная ошибка; такая гранулярность
  принадлежит трейсингу/логам (см. §4 и [`../06_tracing/`](../../06_tracing/)), а не
  метрикам.

## 4. Логи на масштабе: sampling и tiered retention

Логи растут в объёме гораздо быстрее метрик (одна строка на каждый запрос
вместо одного числа на агрегат), и на масштабе тысяч инстансов простое
"храним всё одинаково долго" становится экономически неприемлемым:

- **Sampling** — для высокообъёмных, низкоценных логов (debug-уровень,
  успешные health-check запросы) сохраняется не 100%, а фиксированная доля
  (например, 1 из 100 success-логов), тогда как ошибки/аномалии сохраняются
  всегда полностью (biased sampling: важное — всегда, шум — выборочно).
- **Tiered retention** — горячий слой (последние часы/дни, быстрый поиск,
  дорогое хранилище) и холодный слой (архив в объектном хранилище, дешёвое,
  медленный поиск по запросу) вместо единой политики хранения для всего.
  `Loki` нативно спроектирован под эту модель (индексируются только лейблы,
  не полный текст, что и так снижает cardinality-подобную проблему для
  логов — см. [`../05_logs_loki/`](../../05_logs_loki/)).
- **Структурированное логирование** (JSON вместо произвольного текста) —
  предпосылка для дешёвой фильтрации на масштабе: парсинг неструктурированного
  текста на query-time над петабайтами логов на порядки дороже, чем
  фильтрация по уже распарсенным полям.

## 5. Дашборды и алертинг поверх множества кластеров

Когда данные уже агрегированы в централизованном хранилище (§2), остаётся
архитектурный вопрос самого слоя визуализации/алертинга:

- Один `Grafana`, подключенный к центральному `Thanos`/`VictoriaMetrics
  cluster` datasource — даёт глобальный вид ("сколько ошибок во всех
  кластерах сразу"), но локальный дашборд одного кластера всё ещё удобнее
  держать через локальный datasource для низкой задержки при дебаге
  конкретного инцидента в конкретном кластере.
- Алертинг должен различать **глобальные** SLO (агрегат по всему флоту,
  считается централизованно) и **локальные** пороги (специфичные для одного
  кластера/региона аномалии, которые теряются при агрегации — отдельный
  кластер на 2% ошибок "теряется" на фоне здорового флота на 99 кластеров,
  если смотреть только на агрегированный глобальный error rate).
- Централизация не должна создавать единую точку отказа самого мониторинга:
  деградация центрального Thanos/VictoriaMetrics кластера не должна лишать
  локальные команды возможности видеть хотя бы локальные метрики своего
  кластера (отсюда и принцип "маленький локальный Prometheus всегда жив
  сам по себе, центральное хранилище — для истории и кросс-кластерных
  запросов", а не единственный источник данных).

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Один сервис добавил в метрику label с ID пользователя, и через несколько дней весь Prometheus в кластере стал потреблять в разы больше памяти и начал падать по OOM. Разработчик утверждает, что "метрик стало не так уж много". В чём реальная причина?**
*Ответ:* Проблема не в количестве метрик, а в **cardinality** — числе
уникальных комбинаций значений label'ов одного и того же имени метрики.
Label с ID пользователя создаёт отдельный уникальный временной ряд на
каждого пользователя, и Prometheus держит индекс каждого уникального ряда
в памяти — тысячи/миллионы пользователей превращают одну метрику в
миллионы рядов, взрывая потребление памяти непропорционально росту трафика.
Решение — убрать высококардинальные label'ы из метрик (дропнуть через
relabeling) и переносить такую гранулярность в трейсинг/логи.

**2. В чём разница между Federation и remote_write как способами собрать метрики с нескольких Prometheus в одно место, и почему federation не подходит для переноса сырых данных?**
*Ответ:* Federation — верхнеуровневый Prometheus периодически скрейпит
агрегированные (обычно уже через recording rules) метрики с нижнеуровневых
Prometheus через их `/federate` endpoint; это, по сути, ещё один scrape
поверх scrape, и он так же уязвим к перегрузке высококардинальными данными,
как и обычный Prometheus. remote_write — push сырых метрик из каждого
локального источника в горизонтально масштабируемое распределённое
хранилище (Thanos/VictoriaMetrics cluster/Mimir), спроектированное изначально
для распределённого хранения и запроса больших объёмов данных, а не для
скрейпа поверх скрейпа.

**3. Почему централизованное кластерное хранилище метрик (Thanos/VictoriaMetrics cluster) само по себе не решает проблему cardinality explosion?**
*Ответ:* Распределённое хранилище решает проблему объёма и доступности
(данные размазаны по множеству узлов, можно хранить дольше и запрашивать
по всему флоту), но если источник продолжает присылать
высококардинальные метрики, распределённая система столкнётся с той же
проблемой индексации огромного числа уникальных рядов — просто на большем
масштабе и позже по времени. Настоящее решение — не пускать
высококардинальные данные в систему вообще, через relabeling на источнике
и явные лимиты cardinality (например, `-storage.maxHourlySeries` в
VictoriaMetrics) как предохранитель.

**4. Почему для логов имеет смысл sampling для debug-уровня, но не для логов с ошибками, и что такое biased sampling в этом контексте?**
*Ответ:* Debug-логи успешных операций и health-check запросов создают
огромный объём с низкой информационной ценностью — потеря части из них
не мешает диагностике. Логи с ошибками/аномалиями, напротив, малочисленны,
но критичны для диагностики конкретного инцидента — потеря даже части из
них может скрыть единственное вхождение важной ошибки. Biased sampling —
стратегия, при которой "шумные" низкоценные события сэмплируются
(сохраняется фиксированная малая доля), а важные события (ошибки, аномалии)
сохраняются полностью всегда, вместо единой политики для всех логов.

**5. Компания держит один центральный Grafana/Thanos для всех 50 кластеров и в момент его деградации все команды теряют возможность смотреть даже метрики своего собственного кластера во время инцидента. Что спроектировано неправильно?**
*Ответ:* Централизация мониторинга не должна превращать единую точку
агрегации в единую точку отказа для базовой наблюдаемости каждого
отдельного кластера. Правильная архитектура держит маленький локальный
Prometheus/vmagent в каждом кластере, который самодостаточен для локальных
дашбордов и алертов этого кластера независимо от состояния центрального
хранилища; центральное хранилище (Thanos/VictoriaMetrics cluster) нужно
для долгосрочной истории и кросс-кластерных запросов, но не должно быть
единственным путём увидеть состояние одного конкретного кластера.

**6. Почему агрегированный глобальный error rate по 100 кластерам может скрыть серьёзную проблему в одном из них, и как с этим бороться на уровне алертинга?**
*Ответ:* Если 99 кластеров полностью здоровы, а один деградировал до
высокого error rate, агрегированный по всему флоту показатель "размывает"
проблему одного кластера почти до незаметного значения на фоне общего
здорового трафика. Алертинг должен работать на двух уровнях одновременно:
глобальные SLO-алерты по агрегату всего флота (для капасити/бизнес-метрик)
и локальные пороговые алерты по каждому отдельному кластеру/региону (для
обнаружения именно точечных деградаций) — полагаться только на
агрегированный глобальный показатель недостаточно.
