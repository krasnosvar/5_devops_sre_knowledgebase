## 1. Зачем нужны модули (DRY)

Модули в Terraform — это аналог функций в языках программирования.
Если вам нужно развернуть базу данных, вам потребуется создать 5 разных ресурсов: саму БД, Security Group, Subnet Group, KMS ключ для шифрования, и IAM роль.
Вместо того чтобы 10 раз копировать эти 5 блоков в разные папки (нарушение принципа DRY - Don't Repeat Yourself), вы выносите их в отдельную папку `db-module`.
В основном коде вы просто вызываете модуль, передавая ему на вход параметры:
```hcl
module "my_database" {
  source = "./modules/db-module"
  db_name = "prod-db"
  disk_size = 100
}
```

## 2. Структура стандартного модуля

Хороший модуль должен иметь стандартную структуру файлов:
- `main.tf`: Основной код (создание ресурсов).
- `variables.tf`: Описание входных параметров (Input Variables). Они выступают в роли аргументов функции. Обязательно писать `description` и задавать `type`.
- `outputs.tf`: Возвращаемые значения (Return values). Модуль базы данных должен вернуть `db_endpoint`, чтобы другие модули (бэкенд) могли к ней подключиться.
- `README.md`: Документация (авто-генерируется утилитой `terraform-docs`).

## 3. Источники модулей (Local, Git, Registry)

В аргументе `source` можно указать откуда качать модуль:
1. **Local**: `source = "./modules/vpc"` — загружает с локального диска.
2. **Git**: `source = "git::https://github.com/org/vpc.git?ref=v1.2.0"` — качает прямо из гитхаба. Параметр `?ref=` **критически важен**, он фиксирует (pin) версию по тегу. Если его не указать, скачается `master` ветка, и чужой коммит может сломать ваш прод.
3. **Terraform Registry**: `source = "terraform-aws-modules/vpc/aws"` — загружает официальный проверенный модуль из публичного реестра HashiCorp (или вашего приватного GitLab Terraform Registry).

## 4. Передача Провайдеров в модули (Providers passing)

Раньше провайдеры (например, `provider "aws"`) часто писали прямо внутри кода самого модуля. Это огромный антипаттерн!
Если модуль сам создает провайдера, вы не сможете его переиспользовать в Multi-Region архитектуре.
**Правило**: Модуль никогда не должен содержать блок `provider`.
Родительский (Root) код объявляет провайдеры и неявно (или явно через атрибут `providers = { aws = aws.eu-west-1 }`) передает их внутрь модуля. Модуль просто использует то, что ему дали.

## 5. Типовые вопросы на собеседовании (Interview Q&A)

**1. Вы написали модуль, и внутри него есть ресурс `aws_instance`. В корневом модуле вы вызываете этот модуль с параметром `count = 3`. Сколько машин создастся и как они будут отражены в файле состояния (state)?**
*Ответ:* Создастся 3 виртуальные машины. В файле состояния Terraform сохранит их адреса по индексу модуля. Это будет выглядеть так: `module.my_module[0].aws_instance.main`, `module.my_module[1].aws_instance.main`, `module.my_module[2].aws_instance.main`. Мета-аргументы `count` и `for_each` можно применять прямо к блоку `module` (начиная с Terraform 0.13), что позволяет размножать весь модуль целиком.

**2. Разработчик обновил код в репозитории модуля в ветке `main` на GitHub. Однако при запуске `terraform apply` в основном проекте никаких изменений не происходит (старый код). Почему?**
*Ответ:* Потому что Terraform скачивает модули один раз и кэширует их в скрытой локальной папке `.terraform/modules`. Обычные команды `plan` или `apply` не лезут в интернет для проверки обновлений в Git (особенно если не изменен `ref` тег). Чтобы принудительно обновить кэш и скачать свежий код из ветки `main`, разработчик должен явно выполнить команду `terraform get -update` или `terraform init -upgrade`.

**3. Что такое "Root Module" (Корневой модуль)?**
*Ответ:* В терминологии Terraform любая директория с файлами `.tf` является модулем. "Корневой модуль" (Root Module) — это та самая папка, в которой вы находитесь в терминале и запускаете команду `terraform apply`. Все остальные модули, которые вызываются из корневого через блок `module { ... }`, называются дочерними модулями (Child Modules).

**4. Зачем внутри `variables.tf` модуля строго определять `type = map(string)` или `type = list(object({...}))`? Разве Terraform не умеет выводить типы сам (Type Inference)?**
*Ответ:* Terraform умеет выводить типы (`type = any` по умолчанию). Но строгое определение типов — это защита "от дурака" (Contract Validation). Если модуль ожидает список IP-адресов, а пользователь модуля передаст просто строку, Terraform упадет с непонятной ошибкой глубоко внутри логики модуля на этапе `apply`. Строгая типизация позволяет Terraform немедленно отвергнуть неправильный ввод еще на этапе парсинга (validation phase) с четкой ошибкой.

**5. Как передать данные ИЗ дочернего модуля обратно в родительский?**
*Ответ:* Исключительно через блок `output` в дочернем модуле. Если дочерний модуль создает базу данных, он должен описать `output "db_ip" { value = aws_instance.db.private_ip }`. В родительском (корневом) модуле к этому значению можно будет обратиться через синтаксис `module.<ИМЯ_МОДУЛЯ>.<ИМЯ_OUTPUT>`, например: `module.database.db_ip`.

**6. В чем опасность использования блоков `provider` (например, для настройки региона AWS) непосредственно внутри дочернего модуля?**
*Ответ:* Это фундаментальный антипаттерн, который ломает `terraform destroy`. Если модуль сам инициализирует провайдера, и вы удаляете вызов этого модуля из корневого кода, Terraform сначала удаляет конфигурацию модуля, а вместе с ней — и информацию о провайдере! При попытке удалить ресурсы в облаке Terraform не сможет подключиться к AWS, потому что провайдер исчез. Провайдеры всегда должны передаваться сверху вниз (из Root модуля).

**7. Как в Terraform написать модуль, который создает ресурс условно (только если передан флаг `create_db = true`)?**
*Ответ:* В Terraform HCL нет императивного оператора `if`. Для условного создания ресурсов внутри модуля используется хак с мета-аргументом `count`. 
Вы пишете: `count = var.create_db ? 1 : 0`. Тернарный оператор вернет `1`, если флаг `true` (создастся 1 ресурс), и вернет `0`, если `false` (создастся 0 ресурсов, то есть ресурс будет пропущен).

**8. Вы скачали отличный модуль из Terraform Registry, но вам нужно добавить всего один дополнительный лейбл (Tag) к ресурсу внутри него. Можете ли вы переопределить ресурс чужого модуля снаружи?**
*Ответ:* Нет. Terraform модули — это жесткие, инкапсулированные "черные ящики". Вы не можете снаружи влезть в код дочернего модуля и изменить там атрибуты ресурсов (в отличие от Kustomize в Kubernetes, который умеет делать patch). Вы можете изменять только то, что автор модуля явно вывел в качестве входных параметров (`variables`). Если нужной переменной нет — вам придется форкнуть модуль и написать ее самому.

**9. Разработчик хочет, чтобы при вызове модуля атрибут `instance_type` можно было не указывать, и он бы сам принимал значение `t3.micro`. Как это сделать?**
*Ответ:* В файле `variables.tf` модуля для переменной `instance_type` нужно задать значение `default = "t3.micro"`. Любая переменная, у которой есть блок `default` (даже пустая строка или `null`), считается **опциональной**. Если блок `default` отсутствует, переменная считается **обязательной** (Required), и Terraform выдаст ошибку, если пользователь не передаст её при вызове модуля.

**10. Можно ли вызывать один дочерний модуль изнутри другого дочернего модуля (Вложенность модулей)? Каковы Best Practices?**
*Ответ:* Технически Terraform не ограничивает вложенность модулей (Nested Modules). Однако Best Practices (от самой HashiCorp) настоятельно рекомендуют избегать глубокой вложенности (не больше 1 уровня). Если Модуль А вызывает Модуль B, который вызывает Модуль С, то для передачи одной переменной из корня в Модуль С вам придется прописывать эту переменную 3 раза во всех промежуточных модулях (Boilerplate). Это делает код нечитаемым и невероятно трудным для рефакторинга. Лучше использовать плоскую архитектуру (Composition) в корневом модуле.
