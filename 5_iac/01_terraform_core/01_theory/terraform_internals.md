## 1. Декларативность и Граф зависимостей

Terraform (написан на Go) использует язык **HCL (HashiCorp Configuration Language)**.
Главная архитектурная особенность Terraform — он строит **Направленный ациклический граф (DAG)** перед тем, как что-либо сделать.
Когда вы пишете манифесты, порядок их написания в файле `.tf` не имеет значения. Если `aws_instance` ссылается на ID `aws_vpc`, Terraform понимает эту неявную зависимость (Implicit Dependency). Во время `terraform apply` он скомпилирует граф, поймет, что VPC нужно создать первым, а независимые ресурсы (например, разные EC2-инстансы) создаст **параллельно** (по умолчанию до 10 потоков).

## 2. Циклы: count vs for_each

Для создания нескольких одинаковых ресурсов есть два мета-аргумента:
- **`count = 3`**: Создает ресурсы как массив (список). Обращение к ресурсу идет по индексу: `aws_instance.web[0]`, `aws_instance.web[1]`.
  *Минус:* Если вы удалите 1-й элемент, индексы сдвинутся. Terraform удалит ресурсы `[1]` и `[2]` и пересоздаст их заново, что приведет к даунтайму.
- **`for_each = toset(["web1", "web2"])`**: Создает ресурсы как словарь (Map). Обращение идет по ключу: `aws_instance.web["web1"]`.
  *Плюс:* Удаление любого элемента из середины никак не влияет на остальные ресурсы. Это Best Practice.

## 3. Продвинутый синтаксис: dynamic blocks

В ресурсах AWS часто бывают вложенные блоки (например, список разрешенных портов `ingress` в Security Group). Вы не можете использовать `for_each` на самом ресурсе, если вам нужно сгенерировать только вложенные блоки.
Для этого используется конструкция **`dynamic "ingress" { ... }`**.
Она пробегается по переданному списку портов и на лету генерирует множество вложенных блоков внутри одного большого ресурса.

## 4. Data Sources и Lifecycles

- **Data Sources (`data "aws_ami" "ubuntu" {}`)**: В отличие от блоков `resource` (создание), блоки `data` делают API-вызовы в облако только на **чтение**. Позволяют получить ID существующих ресурсов (сетей, образов), созданных кем-то другим, чтобы не хардкодить их.
- **Lifecycle rules**: Мета-аргументы для изменения дефолтного поведения Terraform.
  - `create_before_destroy = true`: При замене ресурса Terraform сначала создаст новый, и только потом удалит старый (Zero Downtime).
  - `prevent_destroy = true`: Жестко заблокирует `terraform destroy` для этого ресурса (идеально для баз данных).
  - `ignore_changes = [tags]`: Если кто-то руками меняет теги в облаке, Terraform не будет пытаться откатить их обратно.

## 5. Типовые вопросы на собеседовании (Interview Q&A)

**1. В чем архитектурная разница между неявными (Implicit) и явными (Explicit) зависимостями в Terraform?**
*Ответ:* Неявная зависимость создается автоматически, когда один ресурс обращается к атрибутам другого (например, `subnet_id = aws_subnet.main.id`). Terraform сам понимает, что VPC нужно создать до инстанса. Явная зависимость задается руками через мета-аргумент `depends_on = [aws_s3_bucket.main]`. Она нужна только тогда, когда ресурсы логически зависят друг от друга, но в коде HCL не передают друг другу никаких атрибутов (например, инстансу нужна готовая роль IAM для старта приложения, хотя в самом ресурсе инстанса ссылка на роль не прописана).

**2. Разработчик использовал `count = 3` для создания трех виртуальных машин. Затем он изменил код на `count = 2`. Что произойдет при `terraform apply`? А если использовать `for_each`?**
*Ответ:* При использовании `count` ресурсы хранятся как массив (0, 1, 2). При изменении `count = 2`, Terraform удалит элемент с индексом `[2]` (последний в списке), даже если разработчик логически хотел удалить первую машину. При использовании `for_each` с картой (Map) имен (например, "web-a", "web-b", "web-c"), удаление "web-a" из исходной Map приведет к тому, что Terraform удалит строго `aws_instance.web["web-a"]`, не трогая и не пересоздавая остальные машины.

**3. Что такое `local` переменные и чем они отличаются от `variable`?**
*Ответ:* Блок `variable` — это *входные* параметры модуля (Input Variables). Их значения задает пользователь при запуске через командную строку, файлы `terraform.tfvars` или переменные окружения. Блок `locals` — это локальные константы и вычисляемые значения, доступные *только внутри* текущего модуля. Главное отличие: внутри `locals` можно использовать функции и обращаться к другим ресурсам (например, сложить две строки), а в блоке `variable` значение должно быть строгим статичным литералом.

**4. Вы написали блок `data` для получения ID VPC по его имени. Если этого VPC в облаке не существует, на каком этапе Terraform выдаст ошибку: при `plan` или при `apply`?**
*Ответ:* Terraform выдаст ошибку на этапе `terraform plan`. По умолчанию, при построении плана Terraform делает реальные API-вызовы ко всем Data Sources, чтобы подставить их значения в граф. Если ресурс не найден, планирование немедленно обрывается. (Исключение: если аргументы Data Source зависят от ресурсов, которые *еще не созданы* (Computed), чтение переносится на этап `apply`).

**5. Зачем нужен мета-аргумент `lifecycle { ignore_changes = [...] }` и как это связано с Configuration Drift?**
*Ответ:* Configuration Drift (дрейф конфигурации) — это ситуация, когда реальное состояние инфраструктуры в облаке отличается от описанного в коде Terraform (например, автоскейлер изменил `desired_capacity` у ASG). При `terraform apply` Terraform попытается откатить (затереть) эти изменения. Использование `ignore_changes = [desired_capacity]` приказывает Terraform игнорировать расхождения по этому конкретному атрибуту, позволяя внешним системам управлять им безопасно.

**6. Можно ли использовать `count` и `for_each` внутри одного и того же ресурса одновременно?**
*Ответ:* Нет. Это взаимоисключающие мета-аргументы. Terraform выдаст синтаксическую ошибку, если попытаться определить оба аргумента в одном блоке `resource` или `module`. Нужно выбрать что-то одно (в современных реалиях почти всегда выбирают `for_each`).

**7. Объясните назначение блока `dynamic`. Почему нельзя просто написать цикл `for` внутри ресурса?**
*Ответ:* Блоки `resource` в HCL имеют строгую структуру. Вы не можете использовать императивные циклы (`for`) для генерации вложенных конфигурационных блоков (например, правил `ingress` внутри `aws_security_group`). Обычный цикл `for` в Terraform может генерировать только списки или мапы (выражения), но не структурные блоки HCL. Блок `dynamic` был специально добавлен для итерации по переменной и динамической вставки вложенных блоков конфигурации.

**8. В чем разница между операторами `!=` и `!==` в Terraform HCL?**
*Ответ:* Это вопрос с подвохом. В Terraform HCL **не существует** оператора строгого неравенства `!==` (или строгого равенства `===`), как в JavaScript. Terraform строго типизирован (String, Number, Bool). Существуют только операторы `==` и `!=`. Если вы попытаетесь сравнить строку и число, Terraform попытается автоматически привести типы (Type Conversion), либо выдаст ошибку компиляции.

**9. Разработчик хочет передать пароль к базе данных в Terraform. Если он передаст его через `export TF_VAR_db_password=secret`, безопасно ли это? Где пароль может "засветиться"?**
*Ответ:* Это небезопасно с точки зрения долговременного хранения. Terraform поймает переменную из окружения и успешно отрендерит манифест. Однако, после выполнения `terraform apply`, это значение (в абсолютно открытом виде, plain-text) будет сохранено в файле состояния `terraform.tfstate`. Любой, кто имеет доступ к бакету S3 (или где хранится стейт), сможет прочитать пароль базы данных.

**10. Как Terraform понимает, сколько потоков использовать при создании инфраструктуры? Можно ли заставить его создавать 100 ВМ одновременно?**
*Ответ:* Terraform строит DAG (направленный граф) и может создавать независимые ветви графа параллельно. По умолчанию Terraform использует **10 потоков** (concurrency). Если вам нужно создать 100 независимых ВМ быстрее, вы можете увеличить этот лимит, передав флаг при запуске: `terraform apply -parallelism=100`. Главное ограничение здесь — Rate Limits (защита от DDoS) самого облачного провайдера (AWS/GCP), который может заблокировать вас за слишком частые API-запросы.
