## 1. Что такое State и зачем он нужен?

Terraform — это декларативный инструмент. Ему нужен "мост" между тем, что написано в вашем `.tf` файле, и тем, что реально создано в AWS/GCP.
Этот мост — файл **`terraform.tfstate`** (большой JSON файл).
Каждый раз, когда вы делаете `apply`, Terraform записывает туда `ID` ресурсов. Например, если в коде написано `aws_instance.web`, в стейте будет сохранено, что этому логическому ресурсу соответствует реальная виртуалка с `i-0abcd1234567890`.
При следующем `plan` Terraform сделает API-запрос к облаку по этому `ID`, проверит, жива ли виртуалка, и сравнит ее с вашим кодом.

## 2. Remote Backend: S3 + DynamoDB (Блокировки)

По умолчанию стейт хранится локально на ноутбуке разработчика. Это фатально для командной работы:
- Кто-то забудет закоммитить стейт (или нельзя коммитить стейт в Git из-за паролей).
- Два инженера одновременно сделают `terraform apply`, что приведет к конфликтам и порче инфраструктуры (Race Condition).

Для этого настраивают **Remote Backend** (например, бакет S3).
Чтобы решить проблему Race Condition, добавляют **State Locking** (Блокировку). В AWS это делается через таблицу в DynamoDB. Когда Инженер 1 делает `apply`, Terraform создает запись `LockID` в DynamoDB. Если в эту же секунду Инженер 2 запустит `apply`, Terraform проверит таблицу, увидит блокировку и сразу завершится с ошибкой: "Error acquiring the state lock".

## 3. Безопасность: Секреты в стейте

**Terraform хранит стейт в незашифрованном виде (Plain-Text JSON).**
Если вы генерируете пароль для базы данных RDS или скачиваете TLS-сертификат через Terraform, этот пароль будет лежать в файле `terraform.tfstate` совершенно открыто.
*Best Practices:*
- **Никогда** не коммитить `terraform.tfstate` в Git.
- Хранить стейт в облачном S3-бакете с обязательным шифрованием (KMS / SSE-S3).
- Доступ к S3-бакету стейта должен быть ограничен строгими IAM политиками (только для CI/CD пайплайнов и Lead-инженеров).

## 4. Управление State: import, mv, rm, taint

Иногда в стейт нужно вмешаться руками:
- `terraform import aws_vpc.main vpc-123456`: Позволяет взять существующий ресурс в облаке (который кто-то создал мышкой) и "подчинить" его Терраформу, записав его ID в стейт.
- `terraform state mv`: Переименовывает ресурс в стейте (например, если вы вынесли ресурс из корня внутрь модуля). Без `mv` Terraform бы удалил ресурс и создал его заново.
- `terraform state rm`: "Забыть" ресурс. Terraform удаляет запись из стейта, но **не удаляет** ресурс из облака. Теперь это сирота.
- `terraform taint` (устарело, сейчас `apply -replace`): Принудительно помечает ресурс как "испорченный". При следующем `apply` Terraform обязательно убьет его и создаст с нуля (используется для ребута ВМ или ре-запуска provisioners).

## 5. Типовые вопросы на собеседовании (Interview Q&A)

**1. Вы сделали `terraform apply`, процесс пошел, но у вас отключился интернет. Вы перезапустили команду, и она выдает ошибку "Error acquiring the state lock". Как это исправить?**
*Ответ:* При обрыве соединения Terraform не смог удалить блокировку (Lock) из DynamoDB (или другого бекенда) по завершении работы. Стейт остался в статусе "заблокирован". Чтобы снять блокировку, администратор должен выполнить команду `terraform force-unlock <LOCK_ID>`. (Перед этим критически важно убедиться, что ни один другой CI/CD пайплайн или коллега в этот момент реально не выполняет `apply`!).

**2. Зачем Terraform делает Refresh состояния перед выполнением `terraform plan`? Можно ли это отключить?**
*Ответ:* Операция Refresh опрашивает облачный API (делает `GET` запросы по всем ID из стейта), чтобы узнать **текущее (реальное)** состояние ресурсов. Вдруг кто-то зашел в веб-консоль AWS и руками удалил виртуалку? Refresh обновит стейт в памяти, и `plan` покажет, что машину нужно воссоздать. Отключить это можно флагом `terraform plan -refresh=false`. Это значительно ускоряет планирование для огромных стейтов (на тысячи ресурсов), но вы теряете защиту от Drift Configuration (ручных изменений).

**3. Коллега создал RDS базу данных через AWS Console (мышкой). Вы написали для нее код в Terraform. Выполняете `terraform apply`, но получаете ошибку "Resource already exists". Почему так вышло и как решить?**
*Ответ:* Код в Terraform есть, база в AWS есть, но в файле `terraform.tfstate` пусто (Terraform о ней не знает). При `apply` он пытается создать базу с таким же именем, но облако отклоняет запрос из-за конфликта имен. Чтобы "подружить" их, нужно сделать `terraform import <resource_path> <resource_id>`. Это скачает реальную конфигурацию базы из AWS и запишет ее в ваш стейт. После этого `apply` пройдет успешно.

**4. В чем разница между `terraform destroy` и `terraform state rm`?**
*Ответ:* `terraform destroy` читает ваш стейт, делает API-вызовы в облако и **физически удаляет** реальные ресурсы (виртуалки, диски), после чего очищает стейт. Операция `terraform state rm <resource>` работает ТОЛЬКО с файлом стейта. Она просто стирает строчку JSON-файла. В облаке сервер продолжит работать как ни в чем не бывало. Вы просто "отвязали" (unmanaged) ресурс от Terraform.

**5. Почему нельзя просто переименовать ресурс в коде HCL (например, с `aws_instance.web` на `aws_instance.nginx`)?**
*Ответ:* Если вы просто переименуете блок в файле `.tf`, Terraform воспримет это как две операции: 1) Ресурс `web` исчез из кода -> надо физически удалить его в облаке. 2) Появился новый ресурс `nginx` -> надо создать новую виртуалку с нуля. Если на виртуалке крутится база данных, вы потеряете данные (downtime + data loss). Чтобы просто переименовать логическое имя без пересоздания, нужно выполнить `terraform state mv aws_instance.web aws_instance.nginx`.

**6. Как работает Terraform Backend конфигурация (блок `backend "s3"`)? Почему нельзя использовать переменные (variables) внутри этого блока?**
*Ответ:* Блок инициализации бекенда читается и выполняется в самом начале (на этапе `terraform init`), задолго до того, как Terraform начинает строить граф ресурсов или парсить файлы с переменными (variables/tfvars). Поэтому использование `var.bucket_name` внутри блока `backend` невозможно архитектурно. Если вам нужно передавать динамические параметры для бекенда (например, разные бакеты для prod и dev), нужно использовать флаги командной строки `terraform init -backend-config="bucket=my-prod-bucket"`.

**7. У вас есть огромный стейт на 5000 ресурсов. `terraform plan` работает 15 минут. Как SRE должен архитектурно решить эту проблему производительности?**
*Ответ:* Большой стейт (Монолит) — это антипаттерн. Единственный правильный выход: **Декомпозиция (Дробление стейта)**. Инфраструктуру нужно разбить на логические слои (например: 1. Network/VPC, 2. Database, 3. EKS Cluster, 4. Apps). У каждого слоя будет свой независимый Remote Backend (свой `.tfstate` файл) и свой пайплайн в CI/CD. Если слою Apps нужны ID от слоя Network, используется механизм `terraform_remote_state` (data source, читающий чужой стейт в режиме read-only).

**8. Вы закоммитили в Git файл `.tf`, где создается `aws_iam_user` и к нему `aws_iam_access_key`. С точки зрения ИБ, где таится критическая уязвимость?**
*Ответ:* Уязвимость находится в файле стейта. Terraform успешно создаст пользователя и ключ в AWS. Сам `Secret Access Key` не показывается в выводе консоли. Однако Terraform обязан сохранить его в файл `terraform.tfstate`, чтобы знать его на будущее. Ключ будет лежать в стейте в **Plain-Text** (в открытом виде без шифрования). Любой сотрудник или система (например, скомпрометированный CI-раннер), имеющая права на чтение S3-бакета со стейтом, сможет похитить AWS Secret Key. 

**9. Что делает флаг `terraform apply -replace=aws_instance.web` (ранее `terraform taint`)? Зачем он нужен, если сервер и так управляется Terraform?**
*Ответ:* Если сервер работает (Terraform видит, что конфигурация в облаке совпадает с кодом), он не будет ничего трогать. Но что если кто-то зашел по SSH и удалил системные библиотеки, сломав сервер? В коде все окей, в облаке ВМ жива, но приложение не работает. Флаг `-replace` принудительно говорит Терраформу: "Да, дифф равен нулю, но я приказываю тебе физически удалить эту ВМ и создать ее абсолютно с нуля при следующем apply". Это быстрый способ пересоздать сбойный ресурс.

**10. Как Terraform понимает, что в DynamoDB таблице блокировок находится устаревшая "мертвая" блокировка от упавшего CI/CD раннера, а не живой процесс?**
*Ответ:* Никак. Terraform не имеет механизмов отслеживания жизнеспособности (Heartbeat) процесса, который поставил блокировку. В записи блокировки DynamoDB просто сохраняется время создания, ID процесса (PID) и кто запустил (например, Jenkins-Worker-42). Если Jenkins-worker упал по Out-Of-Memory, запись блокировки останется в таблице навсегда. Terraform будет вечно выдавать ошибку `State is locked`, пока человек не проанализирует ситуацию и не удалит блокировку вручную через `force-unlock`.
