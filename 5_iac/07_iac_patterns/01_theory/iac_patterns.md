## 1. Иммутабельная (Immutable) vs Мутабельная Инфраструктура

**Мутабельная инфраструктура (Mutable)**:
Вы создаете ВМ (через Terraform), а затем годами обновляете ее (ставите новые версии nginx, патчите ядро) через Ansible или Puppet.
*Минусы*: На сервере накапливается "мусор", файлы конфигурации расходятся, появляются уникальные серверы-снежинки (Snowflakes). Откатиться к версии 3-месячной давности почти невозможно.

**Иммутабельная инфраструктура (Immutable)**:
Сервер никогда не обновляется. Если нужна новая версия Nginx, вы используете **Packer** для сборки нового образа ВМ (AMI) со всем готовым ПО. Затем Terraform (или AWS ASG) разворачивает новые ВМ из этого образа, а старые ВМ полностью уничтожаются (Terminate).
*Плюсы*: Абсолютная повторяемость. Откат — это просто деплой старого AMI. Никаких серверов-снежинок. Контейнеры (Docker/Kubernetes) — это вершина развития иммутабельного паттерна.

## 2. GitOps для Инфраструктуры (Atlantis, Terraform Cloud)

Локальный запуск `terraform apply` с ноутбука инженера — это нарушение ИБ и нулевой аудит (кто и когда сломал прод?).
SRE-стандарт — это автоматизация через Git (Pull Request Driven Ops).
- Инженер пишет код и делает Pull Request.
- Инструмент типа **Atlantis** (или GitHub Actions) перехватывает вебхук от PR, делает `terraform plan` и пишет результат прямо в комментарии к PR.
- Команда ревьюеров проверяет план (какие ресурсы будут удалены).
- После аппрува (Approve) и слияния (Merge) в `main`, пайплайн автоматически делает `terraform apply`.
Ключи от AWS находятся только у раннера в CI/CD, у инженеров их нет.

## 3. Управление секретами (Secret Injection)

Никогда не храните пароли, токены и TLS ключи в открытом виде в Git-репозиториях IaC.
Архитектурные паттерны:
- **SSM Parameter Store / AWS Secrets Manager**: Секрет создается в облаке вручную (или безопасным скриптом). Terraform использует Data Sources (`data "aws_ssm_parameter" "db_pass"`) для чтения секрета в момент применения.
- **HashiCorp Vault**: Провайдер Terraform напрямую ходит в Vault, вытаскивает динамические пароли (которые живут пару часов) и создает инфраструктуру с ними.
- В любом случае, секрет **осядет в `terraform.tfstate`**. Это фундаментальная проблема, решаемая только строгим шифрованием бакета со стейтом и запретом на его чтение.

## 4. Проблема Configuration Drift (Дрифт конфигурации)

Вы развернули инфраструктуру через IaC. Месяц спустя junior-админ зашел в консоль облака и руками открыл порт 22 (SSH) для всего мира (0.0.0.0/0) в Security Group.
Код в Git идеален, но реальность скомпрометирована. Это Дрифт.
**Решения**:
1. **Забрать права**: У людей должен быть доступ Read-Only к консоли AWS. Любые изменения только через CI/CD (Atlantis).
2. **Drift Detection**: Ежедневный запуск `terraform plan` в CI по крону. Если скрипт возвращает Exit Code не равный нулю (найден дифф между кодом и облаком) — шлется алерт в Slack (OpsGenie).
3. **Облачные защиты**: Инструменты вроде AWS Config, которые блокируют несанкционированные ручные изменения на уровне облачного API.

## 5. Разделение на слои (State Decomposition)

Класть все 10,000 ресурсов компании в один огромный репозиторий и один `.tfstate` файл (Монолитный стейт) — фатально. 
- `plan` будет длиться 30 минут.
- Опечатка может привести к случайному удалению Production базы данных при обновлении dev-фронтенда.

**Паттерн Слоев (Layering / Blast Radius reduction)**:
Разбиваем на папки, каждая со своим `backend` стейтом:
1. `01-network`: VPC, Subnets, Transit Gateways. (Меняется редко, очень опасно).
2. `02-data`: RDS, Redis, S3 бакеты с данными. (Меняется редко).
3. `03-apps`: EKS кластер, ASG, Load Balancers. (Меняется часто).
Связь между ними обеспечивается через Data Sources (`terraform_remote_state` или вытаскиванием ID из SSM Parameter Store).

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему связка "Terraform (для инфраструктуры) + Ansible (для настройки ВМ)" считается классическим паттерном, но постепенно уступает место связке "Packer + Terraform"?**
*Ответ:* Связка Terraform + Ansible реализует **Мутабельную инфраструктуру**. Terraform поднимает "голую" ВМ, а Ansible затем настраивает ее. Это медленно (старт ВМ + прогон плейбука занимает минуты, что ужасно для автоскейлинга) и склонно к поломкам (если внешний apt-репозиторий упадет, Ansible не настроит ВМ). Связка Packer + Terraform (или ASG) реализует **Иммутабельную инфраструктуру**. Packer заранее печет "золотой образ" (Golden AMI) с готовым софтом. Terraform просто запускает этот образ за секунды. Это надежно и предсказуемо.

**2. Объясните концепцию "Blast Radius" (Радиус поражения) в контексте Infrastructure as Code.**
*Ответ:* Blast Radius — это максимальный размер ущерба (количество сломанных систем), который может причинить одна неудачная команда `terraform apply` (или опечатка в коде). Если у вас монолитный стейт (все от сети до баз данных в одной папке), Blast Radius равен всей компании (100%). Если вы разбили код на микро-стейты по проектам и слоям (Network стейт отдельно, Frontend стейт отдельно), то опечатка во фронтенд-репозитории сломает только фронтенд. Радиус поражения изолирован.

**3. Что такое `terraform_remote_state` и какую архитектурную проблему он решает?**
*Ответ:* Когда инфраструктура разбита на независимые слои (декомпозиция стейта), возникает проблема передачи данных. Например, слою `Apps` нужен ID подсети, которая была создана в слое `Network`. В Terraform Data Source `terraform_remote_state` позволяет одному слою (Apps) в режиме Read-Only прочитать файл состояния (например, из S3 бакета) другого слоя (Network) и вытащить оттуда значения из секции `outputs`. Это позволяет связывать разрозненные IaC-проекты.

**4. Коллега предлагает запустить скрипт миграции базы данных прямо из Terraform, используя `provisioner "local-exec"`. Почему с точки зрения SRE это ужасная идея (антипаттерн)?**
*Ответ:* Terraform не предназначен для оркестрации прикладных задач (как Ansible или CI-скрипты). Провижинеры в Terraform не отслеживают статус (нет идемпотентности). Если скрипт миграции базы упадет посередине, Terraform пометит ресурс базы данных как "tainted" (испорченный) в стейте. При следующем `apply` Terraform попытается **физически удалить (destroy) базу данных** и создать её заново, что приведет к катастрофической потере данных в Production.

**5. Как автоматизировать выявление Дрифта Конфигурации (Configuration Drift) с помощью GitLab CI или GitHub Actions?**
*Ответ:* Настраивается отдельный Scheduled Pipeline (крон), который запускается, например, каждый час или ночью. В пайплайне выполняется только `terraform plan -detailed-exitcode`. Этот флаг заставляет Terraform вернуть `Exit Code 2`, если найдены расхождения (дифф) между кодом в Git и облаком. CI/CD пайплайн перехватывает этот код ошибки, окрашивается в красный (Failed) и отправляет Webhook (алерт) в Slack команды DevOps для ручного разбирательства.

**6. В чем суть инструмента "Atlantis" для Terraform и зачем он нужен, если есть GitLab CI?**
*Ответ:* GitLab CI работает поверх коммитов (Push-driven). Для IaC часто нужен Pull Request-driven flow. Atlantis — это специализированный веб-сервер для Terraform, который слушает вебхуки от GitHub/GitLab. Прямо в комментариях к Pull Request разработчик может написать `atlantis plan` или `atlantis apply`. Atlantis исполнит это, покажет результат прямо в комментариях и поставит глобальную блокировку (Lock) на директорию проекта, чтобы два разработчика не смогли делать изменения в один и тот же стейт из разных веток одновременно (чего GitLab CI из коробки не умеет).

**7. Разработчик добавил пароль (plain-text) в файл `terraform.tfvars` и случайно закоммитил его в публичный репозиторий. Как правильно отозвать (Rotate) пароль? Достаточно ли удалить его из коммита и сделать force push?**
*Ответ:* Нет, не достаточно. Если пароль попал в открытый Git (особенно публичный), он **считается скомпрометированным навсегда**. Боты парсят GitHub за миллисекунды. Удаление из истории Git (force push) не поможет — кто-то уже мог его склонировать. Единственно правильный путь — немедленно зайти в AWS (или БД) и **физически сменить (сбросить) пароль** или удалить утекший Access Key, выпустив новый. Только после этого заливать новый пароль в секретницу (Vault/SSM).

**8. В чем идеологическая разница между Terraform и AWS CloudFormation (или ARM Templates для Azure)?**
*Ответ:* CloudFormation (CFN) — это Managed сервис самого облака AWS. Вы отправляете YAML-файл в AWS, и облако само разбирается (движок внутри AWS строит граф и деплоит). CFN привязан только к AWS.
Terraform — это независимый, Client-Side инструмент. Движок Terraform (Go-бинарник) крутится на вашем CI-раннере. Он строит граф локально и делает сотни REST API вызовов в AWS. Плюс Терраформа — это мультиоблачность (провайдеры). Вы можете одним инструментом настроить и AWS, и Datadog, и Cloudflare.

**9. Объясните паттерн "ClickOps" и почему он презирается в SRE-культуре.**
*Ответ:* ClickOps (или ConsoleOps) — это пренебрежительный термин для управления инфраструктурой путем "кликанья мышкой" в веб-консоли (AWS Management Console, vSphere UI) без использования кода (IaC). ClickOps не оставляет следов (нет истории коммитов), его невозможно отревьюить, сложно повторить для второго окружения (Dev/Stage), и он непредсказуем при масштабировании. Задача SRE — полностью запретить ClickOps (выдав права Read-Only) и перевести 100% изменений в Git (IaC).

**10. Почему при создании инфраструктуры часто используют "Terragrunt" как надстройку над Terraform? Какую главную боль он решает?**
*Ответ:* Главная боль Terraform — это дублирование кода конфигурации (DRY). Если у вас 3 окружения (dev, stage, prod) и 5 регионов, вам придется 15 раз копипастить один и тот же блок `backend "s3" {}` и вызовы модулей в разные папки. Terragrunt — это обертка (wrapper). Он позволяет вынести логику backend-стейта и переменные в один мастер-файл `terragrunt.hcl` на уровне корня репозитория, и дочерние папки будут динамически наследовать эти настройки, уменьшая количество бойлерплейт-кода на тысячи строк.
