## 1. Зачем нужен оркестратор в ML и отличие от CI/CD

GitLab CI или GitHub Actions отлично подходят для сборки образов и
быстрых тестов, но плохо справляются со сложными пайплайнами данных и
обучения (DAG — Directed Acyclic Graph), где нужны:
- запуск по расписанию (cron) или по событию появления новых данных;
- перезапуск (retry) только упавшего шага без пересчета предыдущих
  3 часов подготовки датасета;
- backfill (пересчет пайплайна за прошлые даты);
- динамическое выделение разных ресурсов под разные шаги (шаг парсинга
  текста — 2 ядра CPU, шаг обучения — 6 P-ядер или GPU-узел).

Типовой DAG обучения в нашем проекте Личной базы документов:
```text
[S3 / Local Vault: новые документы]
         │
         ▼
[1. OCR & Parsing] ──► [2. Pandera Validation]
                                │
         ┌──────────────────────┴──────────────────────┐
         ▼                                             ▼
[3a. Train Router (TF-IDF/BERT)]              [3b. Chunking & BGE-M3]
         │                                             │
         ▼                                             ▼
[4a. Export ONNX + Quality Gate]              [4b. Upsert в Qdrant]
         │
         ▼
[5. Promote @champion в MLflow]
```

## 2. Сравнение оркестраторов: Airflow, Prefect, Kubeflow, Argo

| Критерий | Apache Airflow | Prefect / Dagster | Kubeflow Pipelines / Argo |
| :--- | :--- | :--- | :--- |
| **Изначальная ниша** | Data Engineering (ETL по расписанию) | Python-native Data & ML workflows | Kubernetes-native контейнеры и ML |
| **Изоляция шагов** | Общий Python-окружение (если не `KubernetesPodOperator`) | Python-процессы, Docker или K8s-воркеры | Каждый шаг — отдельный Pod со своим Docker-образом |
| **Передача артефактов** | Вручную через S3 (XCom только для метаданных) | Встроенные Result Stores / Asset-модель (Dagster) | Встроенная передача артефактов через S3/MinIO |
| **Порог входа и вес** | Средний/высокий (Scheduler, Webserver, DB) | **Низкий** (Prefect запускается локально за 1 минуту) | **Высокий** (требует K8s, Istio/Dex в полном Kubeflow) |
| **Когда выбирать** | В компании уже есть Airflow у Data-инженеров | **Лучший выбор для локального стенда** и небольших команд | Крупный K8s-кластер с десятками разных ML-окружений |

## 3. Антипаттерны оркестрации: XCom и локальный диск

### 3.1 Главная ошибка с Airflow XCom
В Airflow механизм `XCom` (Cross-Communication) сохраняет возвращаемое
значение функции шага в **таблицу метаданных PostgreSQL** самого
Airflow.
- Если Data Scientist возвращает из Task 1 `pandas.DataFrame` на
  500 МБ или веса модели, база данных Airflow зависает или падает по
  лимиту размера строки/памяти.
- **Правильный паттерн:** Task 1 сохраняет датасет в S3 (`s3://bucket/
  runs/{{ run_id }}/features.parquet`) и передает через XCom только
  **строку с S3 URI** и SHA256-хэш файла (~100 байт).

### 3.2 Ошибка с локальным `/tmp` между шагами
В распределенном Airflow (`CeleryExecutor` или `KubernetesPodOperator`)
и в Argo Workflows Task 1 и Task 2 могут запуститься **на разных
физических нодах** (или в разных контейнерах с изолированным `emptyDir`).
Запись в `/tmp/data.csv` на первом шаге приведет к `FileNotFoundError`
на втором. Всегда используйте объектное хранилище (S3) для передачи
данных между шагами.

## 4. LoRA SFT пайплайн для LLM на CPU (Intel 155H)

Если кроме классического роутера (`ONNX`) нужно дообучить (Supervised
Fine-Tuning, SFT) малую языковую модель (`Qwen2.5-0.5B` или
`SmolLM2-360M`) извлекать строгий JSON из текста справок и чеков, на
процессоре **Intel Core Ultra 7 155H (64 ГБ ОЗУ)** это реально сделать
в учебном пайплайне без дискретной GPU:

1. **Выбор базовой модели:** `Qwen2.5-0.5B-Instruct` (~1 ГБ в `fp32`/
   `bf16`).
2. **Метод PEFT (`LoRA`):** замораживаем базовые веса, обучаем только
   адаптеры ранга `r=8` на модулях `q_proj, v_proj` (< 1% параметров).
3. **Ограничение потоков CPU:** привязываем процесс к 6 производительным
   P-ядрам (`taskset -c 0-11`), чтобы планировщик не ждал медленные
   E-ядра на барьерах синхронизации градиентов.
4. **Пост-обработка в пайплайне:**
   - слияние адаптера с базой (`merge_and_unload()`);
   - конвертация в `GGUF` (`Q4_K_M`) через `llama.cpp`;
   - автоматическая проверка на контрольных примерах (валидный ли JSON
     возвращает модель).

## 5. Распределенное обучение в Kubernetes (Kubeflow Training Operator)

Когда модель не помещается на один узел или обучение идет слишком
долго, используют **Data Parallelism (DDP / FSDP)** в Kubernetes с
помощью **Kubeflow Training Operator** (CRD `PyTorchJob`):

```yaml
apiVersion: kubeflow.org/v1
kind: PyTorchJob
metadata:
  name: doc-classifier-ddp
spec:
  pytorchReplicaSpecs:
    Master:
      replicas: 1
      template:
        spec:
          containers:
            - name: pytorch
              image: registry.local/mlops/trainer:v1.2
              env:
                - name: OMP_NUM_THREADS
                  value: "6"
    Worker:
      replicas: 2
      template:
        spec:
          containers:
            - name: pytorch
              image: registry.local/mlops/trainer:v1.2
```

Что делает `Training Operator` за инженера:
1. Создает поды `Master` (ранг 0) и `Worker` (ранги 1..N) и Headless
   Service для их взаимного обнаружения по DNS.
2. Автоматически прокидывает в контейнеры переменные окружения, которые
   ждет `torch.distributed`:
   - `MASTER_ADDR` — DNS-имя пода Master;
   - `MASTER_PORT` — порт рандеву (например, `23456`);
   - `WORLD_SIZE` — общее число процессов (`1 + 2 = 3`);
   - `RANK` — глобальный номер текущего воркера (`0`, `1`, `2`).
3. Отслеживает статус: если `Master` завершился с кодом `0`, помечает
   всю задачу `Succeeded` и гасит воркеры.

## 6. Идемпотентность, ретраи и чекпоинты (Spot / Preemptible)

Обучение в облаке часто запускают на **Spot / Preemptible ВМ** (скидка
60–80%), которые облако может забрать в любой момент с предупреждением
за 30–120 секунд (сигнал `SIGTERM` в Pod).

Чтобы ретрай оркестратора (`retries=3`) не начинал 5-часовое обучение
с нуля:
1. Скрипт обучения сохраняет **чекпоинт** (веса модели + состояние
   оптимизатора + номер шага/эпохи) в S3 каждые $N$ шагов и перехватывает
   `SIGTERM` для внеочередного сохранения.
2. При старте (и после рестарта пода) скрипт проверяет, есть ли в
   папке текущего `RUN_ID` в S3 последний чекпоинт, и вызывает
   `trainer.train(resume_from_checkpoint=last_ckpt)`.
3. Шаг записи результатов делаем **идемпотентным**: пишем по ключу
   `s3://mlops/runs/{dag_run_id}/model.onnx` (перезапись при ретрае
   безопасна и не плодит дубликаты).

## 7. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему для запуска каждого шага ML-пайплайна в Airflow лучше
использовать `KubernetesPodOperator` (или `DockerOperator`), а не
обычный `PythonOperator`?**
*Ответ:* `PythonOperator` выполняет код внутри процесса воркера самого
Airflow. Если одному ML-пайплайну нужен `scikit-learn 1.2` и `numpy 1.26`,
а другому — `pytorch 2.5` и `numpy 2.1`, возникает неразрешимый конфликт
зависимостей (`Dependency Hell`), плюс тяжелый ML-код может вызвать OOM
и убить воркер Airflow вместе с десятком чужих задач.
`KubernetesPodOperator` запускает каждый шаг в отдельном Pod со своим
собственным Docker-образом и собственными лимитами CPU/RAM/GPU.

**2. Что произойдет, если передать `pandas.DataFrame` на 2 ГБ между
двумя задачами Airflow через стандартный `XCom`?**
*Ответ:* Стандартный `XCom` сериализует объект и записывает его в
таблицу `xcom` в базе метаданных Airflow (PostgreSQL). Передача 2 ГБ
вызовет OOM на воркере при сериализации/десериализации или положит базу
данных Airflow. Через `XCom` передают только ссылки (S3 URI) и небольшие
метаданные (метрики, `run_id`), либо настраивают кастомный
`XCom Backend` поверх S3.

**3. Что такое идемпотентность шага пайплайна и почему `INSERT INTO
features VALUES (...)` при `retries=3` — это опасный баг?**
*Ответ:* Идемпотентный шаг при повторном запуске с теми же входными
параметрами дает точно такое же состояние системы, как и после одного
запуска. Если шаг упал в конце по таймауту сети после `INSERT`, Airflow
перезапустит его, и в таблице появятся дубликаты строк (на которых
модель переобучится). Правильное решение: перед вставкой делать
`DELETE FROM features WHERE partition_date = '{{ ds }}'` в одной
транзакции, использовать `UPSERT` (`ON CONFLICT DO UPDATE`) или
перезаписывать партицию файла в S3 целиком.

**4. Какие переменные окружения нужны PyTorch (`torch.distributed`) для
объединения нескольких контейнеров в единый кластер обучения?**
*Ответ:* Четыре базовые переменные:
1. `MASTER_ADDR` — IP или DNS-имя главного узла (`rank 0`);
2. `MASTER_PORT` — открытый TCP-порт на `rank 0` для rendezvous;
3. `WORLD_SIZE` — общее число процессов, участвующих в обучении;
4. `RANK` — глобальный индекс текущего процесса (от `0` до
   `WORLD_SIZE - 1`), плюс `LOCAL_RANK` (индекс внутри одной ноды).

**5. Почему при распределенном или многопоточном обучении один
медленный воркер (straggler) тормозит весь кластер?**
*Ответ:* В синхронном Data Parallelism (`DDP`) на каждом шаге обратного
распространения ошибки (`backward pass`) выполняется коллективная
операция `AllReduce` — усреднение градиентов со всех воркеров. Это
жесткий барьер синхронизации: быстрые узлы (или быстрые P-ядра CPU)
простаивают в ожидании самого медленного узла (или медленного E-ядра),
прежде чем сделать шаг оптимизатора `optimizer.step()`.

**6. Как безопасно обучать модели на дешевых Spot / Preemptible
узлах в Kubernetes?**
*Ответ:*
1. Настроить обработчик сигнала `SIGTERM` в тренировочном скрипте (при
   отзыве Spot-ноды Kubelet шлет `SIGTERM` за `terminationGracePeriodSeconds`),
   который сбрасывает внеочередной чекпоинт в S3.
2. Сохранять регулярные чекпоинты (веса + состояние `AdamW` + шаг
   обучения + состояние генератора случайных чисел) в S3 каждые $N$
   минут.
3. Включить автоматический перезапуск пода/шага и при старте всегда
   проверять наличие чекпоинта для текущего `RUN_ID`.

**7. В чем разница между Airflow и Argo Workflows с точки зрения
архитектуры и Kubernetes?**
*Ответ:* Airflow — это монолитная платформа со своим собственным
планировщиком, базой данных (Postgres) и очередью (Redis/Celery), которая
существует отдельно от Kubernetes (даже если задеплоена в него). Argo
Workflows — это Kubernetes-native контроллер (CRD `Workflow`), где
каждый шаг пайплайна изначально является Kubernetes Pod'ом, а состояние
хранится в Kubernetes API / etcd и архивируется в Postgres/S3.

**8. Почему нельзя запускать переобучение модели в продакшене по
расписанию и сразу выкатывать новую модель без шага `Evaluation /
Quality Gate`?**
*Ответ:* Даже если данные прошли проверку схемы (Pandera), в них мог
произойти сдвиг распределения, появиться битая разметка или аномальный
период (праздники, сбой источника). Без автоматического шага `Quality
Gate`, который сравнивает метрики новой модели с текущей `@champion`
на неизменном `Golden Dataset`, сломанная модель автоматически попадет
в продакшен и заменит рабочую.

**9. Что такое `Backfill` в пайплайнах подготовки признаков и какую
ошибку (`Data Leakage`) легко допустить при его написании?**
*Ответ:* `Backfill` — это ретроспективный запуск пайплайна за прошлые
периоды (например, пересчитать витрину признаков за последние 6 месяцев).
Главная ошибка — использовать в SQL-запросе текущее состояние таблиц
(`NOW()` или таблицы без версионирования по времени), из-за чего в
признаки за январь попадают данные, ставшие известными только в марте
(утечка будущего, `Time-Travel Leakage`).

**10. Зачем после дообучения LoRA-адаптера в тренировочном пайплайне
часто делают шаг `merge_and_unload()` перед экспортом?**
*Ответ:* Хранить LoRA-адаптер отдельно удобно, если на одном сервере
крутится 20 разных адаптеров поверх одной базовой модели. Но если в
продакшене используется одна конкретная дообученная модель (или её нужно
сконвертировать в `GGUF` / `ONNX`), вычисление базовой матрицы $W_0 x$ и
отдельной поправки $\Delta W x = B A x$ на каждом слое добавляет накладные
расходы. Слияние $W_{\text{merged}} = W_0 + B \cdot A$ на этапе пайплайна
дает единую модель с **нулевым оверхедом** на инференсе.
