## Когда какой оркестратор использовать

| Оркестратор | Как описывается шаг | Изоляция шага | Когда выбирать |
| :--- | :--- | :--- | :--- |
| **`Prefect`** | Обычная Python-функция с декоратором `@task` | Процесс / контейнер / K8s Job | Лучший старт для ML-команды: минимум бойлерплейта, работает локально из коробки |
| **`Apache Airflow`** | Оператор в DAG (`KubernetesPodOperator`, `@task`) | Воркер Celery или отдельный Pod в K8s | Когда в компании уже есть Airflow у дата-инженеров и нужно связать SQL/S3 ETL с обучением |
| **`Kubeflow Pipelines` (KFP)** | `@dsl.component(base_image=...)` → компиляция в YAML | Каждый шаг — отдельный Pod в Kubernetes | Крупные ML-платформы на K8s с жёсткой изоляцией зависимостей и GPU-квотами |
| **`Argo Workflows`** | Kubernetes CRD (`kind: Workflow`) на YAML | Каждый шаг — отдельный контейнер в K8s | Инфраструктурно чистый K8s-native движок без тяжёлой обвязки всего Kubeflow |
| ⚠️ Ловушка в `Airflow`: передача `DataFrame` или весов через `XCom` | `XCom` сериализует возвращаемое значение функции прямо в таблицу метаданных `PostgreSQL` (лимит ~48 КБ / десятки МБ) | Между шагами передавайте **только строковый URI** (`s3://bucket/run_123/train.parquet`), а сами данные кладите в S3 |

## Пайплайн дообучения малой LLM через LoRA (`peft` + `trl`) на CPU

| Шаг пайплайна | Что происходит | Инструмент / Артефакт |
| :--- | :--- | :--- |
| **1. Форматирование SFT** | Документы и ответы приводятся к списку сообщений `[{"role": "user", ...}, {"role": "assistant", ...}]` | `datasets` (JSONL) |
| **2. Инициализация LoRA** | Базовая модель (`Qwen2.5-0.5B`) замораживается; добавляются матрицы ранга `r=8..16` к слоям `q_proj, v_proj` | `peft.LoraConfig` (~0.5% обучаемых весов) |
| **3. Обучение (`SFTTrainer`)** | 1–3 эпохи на CPU (`use_cpu=True`, `fp32`/`bf16`), сохранение только весов адаптера | `adapter_model.safetensors` (~15 МБ) |
| **4. Слияние (`Merge`)** | Матрицы адаптера прибавляются к базовым весам: $W_{\text{new}} = W_0 + \frac{\alpha}{r} B \cdot A$ | `model.merge_and_unload()` |
| **5. Конвертация в `GGUF`** | Слитая модель конвертируется и квантуется в `Q4_K_M` для быстрого запуска в `llama.cpp` / `Ollama` | `convert_hf_to_gguf.py` → `model-q4_k_m.gguf` |

## Проверка симптомов пайплайна

| Симптом | Причина и решение |
| :--- | :--- |
| База данных `Airflow` распухла и планировщик (`scheduler`) завис | Таски возвращают массивы данных через `return df` (`XCom`) либо тяжёлый код импортируется на верхнем уровне файла DAG |
| Шаг обучения в `Airflow` упал с конфликтом версий `numpy`/`pydantic` самого Airflow | Не запускайте ML-код в `PythonOperator` внутри процесса воркера Airflow — используйте `KubernetesPodOperator` или `DockerOperator` |
| Распределённое обучение `PyTorch DDP` зависает на старте по таймауту `NCCL`/`Gloo` | Не открыты порты между подами воркеров или не заданы переменные `MASTER_ADDR`, `MASTER_PORT`, `WORLD_SIZE`, `RANK` (используйте `PyTorchJob` из Kubeflow Training Operator) |

> Проверка: `python3 -m py_compile 02_examples/prefect_flow.py`; не проверено: `PyTorchJob` в многоузловом GPU-кластере.
