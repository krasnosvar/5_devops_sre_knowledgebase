## 1. Проблема воспроизводимости Python-окружения в ML

В отличие от обычных веб-сервисов на чистом Python, стек машинного
обучения (`torch`, `onnxruntime`, `scipy`, `pyarrow`, `tokenizers`,
`llama-cpp-python`) на 90% состоит из скомпилированного C++, Rust и
Fortran кода, обёрнутого в Python C-API.

### 1.1 Почему системный Python 3.14 на хосте ломает установку ML-библиотек
Каждая минорная версия CPython (`3.12`, `3.13`, `3.14`) меняет внутренний
Application Binary Interface (ABI). Бинарные колёса на PyPI именуются по
стандарту PEP 425, например:
`onnxruntime-1.20.0-cp312-cp312-manylinux_2_27_x86_64.whl`.

Если в современном дистрибутиве Linux (Fedora, Arch) системный
интерпретатор обновился до `Python 3.14`, а мейнтейнеры `onnxruntime` или
`torch` ещё не выпустили колесо с тегом `cp314`:
1. Пакетный менеджер не находит готовый бинарник (`wheel`).
2. Он скачивает исходный архив (`sdist` `.tar.gz`) и запускает локальную
   сборку через `cmake`, `ninja` и `gcc`.
3. Сборка падает из-за отсутствия системных заголовочных файлов или
   длится 40 минут со 100% загрузкой всех ядер.

### 1.2 Фиксация Python 3.12 и детерминизм через `uv`
Инструмент `uv` (написанный на Rust) решает проблему сразу на двух
уровнях:
- **Управление самим интерпретатором:** `uv python install 3.12` скачивает
  автономную сборку CPython (`python-build-standalone`) в домашний каталог
  пользователя без прав `root` и без конфликта с системным `dnf`/`apt`.
- **Глобальный кэш с жёсткими ссылками (`hardlinks`):** если у вас 5
  разных виртуальных окружений используют `torch` (весом 800 МБ), `uv`
  хранит файлы пакета на диске в одном экземпляре в `~/.cache/uv` и
  прокидывает их в `.venv` через системный вызов `link(2)` (inodes те же,
  расход диска — 0 байт, создание окружения — 0.5 секунды).

```bash
# Зафиксировать стабильную для ML версию Python 3.12
uv python install 3.12
uv python pin 3.12

# Создать окружение и установить пакеты строго по lock-файлу
uv sync --frozen
```

## 2. Анатомия гибридного процессора (Intel 155H) и барьеры синхронизации

Современные мобильные и десктопные процессоры (включая **Intel Core Ultra
7 155H**) имеют гетерогенную (гибридную) архитектуру:
- **6 P-cores (Performance / Redwood Cove):** поддерживают Hyper-Threading
  (12 логических потоков, обычно `CPU 0..11`), имеют высокий IPC, большие
  кэши L2 и максимальную частоту до 4.8 ГГц.
- **8 E-cores (Efficient / Crestmont):** без Hyper-Threading (8 потоков,
  обычно `CPU 12..19`), меньшая частота и пропускная способность векторных
  регистров AVX2/VNNI.
- **2 LP E-cores (Low Power Island):** 2 сверхэкономичных ядра в отдельном
  домене (`CPU 20..21`), предназначенных для фонового простоя.

### 2.1 Что происходит под капотом при матричном умножении (GEMM)
Инференс любой модели (как классического бустинга/трансформера в `ONNX
Runtime`, так и LLM в `llama.cpp`) состоит из последовательного вычисления
слоёв. Внутри каждого слоя матрица весов делится поровну между рабочими
потоками (`OpenMP` / `pthread`).

Между слоями `N` и `N+1` стоит **барьер синхронизации (`pthread_barrier` /
futex)**: слой `N+1` не может начаться, пока **все** потоки не закончат
свою часть слоя `N`.

Если запустить `llama.cpp` с дефолтным числом потоков по числу логических
CPU (`22`):
1. Планировщик раскидывает одинаковые куски матрицы и на быстрые P-ядра,
   и на медленные E-ядра / LP-ядра, и на виртуальные HT-потоки.
2. Поток на P-ядре считает свой кусок за `1 мс`, а поток на LP E-ядре —
   за `4 мс`.
3. Быстрые P-ядра **75% времени ждут** в цикле активного ожидания
   (spin-wait) на барьере, пока отстающее ядро досчитает свой кусок!
4. Кроме того, два потока Hyper-Threading на одном физическом P-ядре
   делят один и тот же блок векторных регистров FMA/AVX2, мешая друг другу
   и вытесняя данные из L1d-кэша.

### 2.2 Практическое правило тюнинга CPU для ML
Для максимальной скорости инференса на CPU число потоков вычислений должно
равняться числу **физических P-ядер** (для Intel 155H это **6 потоков**),
а маска ядер процесса (`sched_setaffinity(2)`) должна запрещать миграцию
на E-ядра:

```bash
# 1. Проверить раскладку ядер своего процессора
lscpu -e=CPU,CORE,SOCKET,MAXMHZ

# 2. Запустить процесс строго на P-ядрах (CPU 0-11) в 6 рабочих потоков
OMP_NUM_THREADS=6 taskset -c 0-11 python3 inference.py
```

В `docker-compose.yml` это закрепляется на уровне `cpuset` контроллера
cgroups v2:

```yaml
services:
  llm-engine:
    image: ghcr.io/ggerganov/llama.cpp:server
    cpuset: "0-11"
    environment:
      OMP_NUM_THREADS: "6"
    command: ["-m", "/models/qwen3-8b-q4_k_m.gguf", "-t", "6", "--host", "0.0.0.0"]
```

## 3. Память (64 ГБ RAM), `mmap` и единый кэш весов моделей

### 3.1 Как ядро Linux загружает модели через `mmap(2)`
Современные форматы весов (`safetensors`, `GGUF`) выровнены на диске так,
чтобы движок инференса не читал их через `read(2)` в выделенный буфер кучи
(`malloc`), а вызывал системный вызов `mmap(2)`:
- Файл весов отображается напрямую в виртуальное адресное пространство
  процесса через **Page Cache** ядра Linux.
- Если вы перезапустите контейнер или поднимете второй воркер, читающий
  тот же файл `.gguf` с того же inode на хосте, ядро **не будет читать
  диск заново** и не потратит лишние 6 ГБ RAM — оба процесса будут читать
  одни и те же физические страницы памяти (Shared Page Cache)!

### 3.2 Единая директория кэша на хосте
Чтобы `mmap` и переиспользование кэша работали между запусками скриптов на
хосте, контейнерами Docker Compose и подами в Kubernetes (`k3d`), создаём
единое дерево каталогов:

```bash
mkdir -p ~/.cache/mlops-models/{hf,gguf,ollama,onnx,torch}
```

И прописываем переменные в `~/.bashrc` (или в `.env` проекта):

```bash
export MLOPS_CACHE_DIR="$HOME/.cache/mlops-models"
export HF_HOME="$MLOPS_CACHE_DIR/hf"
export TORCH_HOME="$MLOPS_CACHE_DIR/torch"
export OLLAMA_MODELS="$MLOPS_CACHE_DIR/ollama"
```

## 4. Локальный Kubernetes (`k3d`) с пробросом моделей и профили Compose

При 64 ГБ RAM можно держать включёнными сразу все сервисы, но для
экономии заряда батареи и тишины кулеров инфраструктуру удобно делить на
слои:

1. **Профили в Docker Compose (`profiles`):**
   - Базовый профиль (`storage`): `SeaweedFS (S3)`, `PostgreSQL`, `Qdrant`.
   - Профиль `tracking`: `MLflow`.
   - Профиль `llm`: `Ollama` / `llama.cpp` + `LiteLLM`.
   - Профиль `monitoring`: `Prometheus`, `Grafana`, `Evidently`, `Langfuse`.
2. **Проброс кэша моделей в кластер `k3d`:**
   Узлы `k3d` — это контейнеры Docker, внутри которых крутится `k3s`.
   Если при создании кластера пробросить папку `~/.cache/mlops-models` в
   контейнеры нод (`/var/lib/ml-cache`), любой Pod в Kubernetes сможет
   подключить её через `hostPath` (или `local-path` PVC) за 0 секунд без
   скачивания гигабайтов по сети!

## 5. Структура репозитория и изоляция личных документов (Privacy-first)

В нашем сквозном пет-проекте используются **личные документы** (выписки
врачей, результаты анализов, справки из госструктур, заметки и фото).

Золотое правило безопасности при работе в публичном Git-репозитории:
- **Реальные личные документы никогда не лежат внутри папки Git-проекта.**
  Они хранятся во внешнем каталоге хоста, например:
  `~/personal_docs_vault/{inbox,archive,exports}` и подключаются в сервис
  только через переменную окружения `DOCS_VAULT_PATH` или Docker bind-mount.
- Внутри самого Git-репозитория в папке `data/sample_docs/` хранятся
  **только синтетические обезличенные шаблоны** (на вымышленного пациента
  Иванова И.И.) для прогона автотестов в CI/CD и демонстрации проекта.
- В `.gitignore` жёстко блокируются как бинарные форматы весов (`.gguf`,
  `.safetensors`, `.onnx`, `.pt`, `.pkl`), так и любые офисные/медиа
  расширения вне папки `sample_docs/`.

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему при установке `torch` или `onnxruntime` на самый свежий
Python пакетный менеджер иногда начинает часовую компиляцию из C++?**
*Ответ:* Потому что бинарные пакеты (`wheels`) привязаны к тегу версии
CPython ABI (например, `cp312`). Если для новой версии Python (например,
`3.14`) авторы библиотеки ещё не опубликовали готовое колесо `manylinux`,
менеджер пакетов откатывается к скачиванию архива исходного кода (`sdist`)
и пытается собрать C++/CUDA-расширения локально. Решение — фиксировать
поддерживаемую версию Python (например, `3.12`) через `uv python pin`.

**2. Как `uv` умудряется создавать виртуальное окружение с тяжёлыми
ML-зависимостями за доли секунды и не дублировать гигабайты на диске?**
*Ответ:* `uv` держит распакованные колёса в централизованном кэше
пользователя (`~/.cache/uv`) и при создании `.venv` на той же файловой
системе создаёт **жёсткие ссылки (`hardlinks`, сисколл `link(2)`)** или
использует `reflink` (Copy-on-Write на Btrfs/XFS). В результате файлы
указывают на те же самые `inode` диска без физического копирования байтов.

**3. Почему на процессоре с 22 логическими потоками (6 P-ядер + 8 E-ядер +
2 LP-ядра) запуск инференса LLM в 22 потока работает медленнее, чем в 6?**
*Ответ:* На каждом слое нейросети матричное умножение синхронизируется
барьером (`pthread_barrier`). Если работа поделена поровну между быстрыми
P-ядрами и медленными E-ядрами, быстрые ядра заканчивают свой блок раньше
и простаивают в ожидании самого медленного потока (эффект «отстающего
воркера» — straggler problem). Плюс Hyper-Threading потоки конкурируют за
одни и те же SIMD/AVX2-блоки внутри одного физического ядра.

**4. Каким системным вызовом утилита `taskset` и параметр Docker `cpuset`
ограничивают выполнение процесса только выбранными ядрами CPU?**
*Ответ:* `taskset` использует системный вызов `sched_setaffinity(2)`,
устанавливающий битовую маску разрешённых ядер для потока. Параметр
`cpuset` в Docker/Kubernetes работает ещё жёстче — через подсистему ядра
`cgroups v2` (`cpuset.cpus`), которую процесс внутри контейнера не может
обойти самостоятельно.

**5. В чём преимущество загрузки весов модели через `mmap(2)` по сравнению
с обычным чтением файла через `read(2)` в буфер `malloc`?**
*Ответ:* При `read(2)` данные сначала копируются с диска в Page Cache
ядра, а затем второй раз копируются в пользовательскую память (Heap)
процесса — расход RAM удваивается. При `mmap(2)` (используется в
`safetensors` и `GGUF`) страницы Page Cache отображаются напрямую в
адресное пространство процесса (zero-copy). При рестарте пода модель
стартует мгновенно из памяти ОС, а несколько процессов могут разделять
одни и те же физические страницы весов.

**6. Как в локальном кластере Kubernetes (`k3d` или `kind`) избежать
повторного скачивания 10-гигабайтной модели при каждом пересоздании пода?**
*Ответ:* При создании кластера пробросить директорию кэша с хоста внутрь
контейнеров нод (`k3d cluster create --volume ~/.cache/mlops-models:/var/lib/ml-cache@all`),
а в манифесте пода подключить этот путь через `PersistentVolume` / `hostPath`
и указать переменную `HF_HOME=/var/lib/ml-cache/hf`.

**7. Зачем нужна переменная `HF_HUB_OFFLINE=1` в продакшн-подах?**
*Ответ:* По умолчанию библиотеки `transformers` и `huggingface_hub` при
каждом вызове `from_pretrained()` делают HTTP-запрос к `huggingface.co`
для проверки актуальности метаданных. Если внешний интернет в кластере
закрыт или у Hugging Face сбой, под упадёт по таймауту даже при наличии
модели на диске. `HF_HUB_OFFLINE=1` отключает сеть и заставляет читать
строго из локального кэша.

**8. Что произойдёт, если случайно закоммитить файл весов `.gguf` на 5 ГБ
в Git, а в следующем коммите удалить его через `git rm`?**
*Ответ:* Файл исчезнет только из рабочего дерева последнего коммита
(`HEAD`), но его блоб на 5 ГБ навсегда останется внутри истории `.git/objects/pack/`,
и репозиторий не пушнется в GitHub (лимит 100 МБ на файл). Потребуется
переписывать историю через `git filter-repo` или `git reset`.

**9. Как правильно организовать работу с реальными чувствительными
документами (медицина, паспорта) при разработке пет-проекта в публичном
репозитории?**
*Ответ:* Физически вынести каталог реальных данных за пределы папки
Git-репозитория (например, в `~/personal_docs_vault`) и передавать путь к
нему через переменную окружения. Внутри самого репозитория хранить только
синтетические тестовые фикстуры на вымышленных лиц для проверки пайплайна
в CI.

**10. Почему при запуске нескольких Python-воркеров (например, в Gunicorn
или Celery) важно следить за переменной `OMP_NUM_THREADS`?**
*Ответ:* Если поднять 8 воркеров `gunicorn`, и каждый из них внутри
`onnxruntime` или `numpy`/`OpenBLAS` по умолчанию породит пул из 16
OpenMP-потоков, в системе возникнет `8 × 16 = 128` конкурирующих потоков
вычислений (thread oversubscription). Процессор потратит всё время на
переключение контекста (`context switches`). При масштабировании числом
процессов ставят `OMP_NUM_THREADS=1` или `2`.
