## 1. Зачем нужен трекинг экспериментов и что обязано логироваться

Когда команда подбирает архитектуру классификатора документов или настраивает
гибридный RAG, за неделю выполняются десятки запусков (`runs`). Без
автоматического трекинга возникает классическая ситуация:
- модель `router_v3_final_new.onnx` показывает отличную точность, но никто
  не помнит, при каком коэффициенте регуляризации `C`, на каком сплите
  датасета и из какого Git-коммита она была обучена.

Каждый воспроизводимый запуск эксперимента (`Run`) должен фиксировать 5
обязательных компонентов:
1. **Версия кода:** `git commit SHA` (и предупреждение, если в рабочей
   директории есть незакоммиченные изменения).
2. **Версия данных:** `MD5`/`SHA256` хэш обучающего датасета (из `DVC`)
   или номер ревизии на Hugging Face.
3. **Гиперпараметры (`Params`):** скалярные настройки запуска (`learning_rate`,
   `max_depth`, `chunk_size`, `top_k`, имя базовой LLM).
4. **Метрики (`Metrics`):** численные показатели качества (`f1_macro`,
   `roc_auc`, `hit_at_5`, `latency_p99_ms`) — в том числе в динамике по
   эпохам (`step`).
5. **Артефакты (`Artifacts`):** сам файл весов модели (`.onnx`,
   `.safetensors`), матрица ошибок (`confusion_matrix.png`), схема входных
   и выходных типов (`MLmodel` signature) и список зависимостей.

## 2. Архитектура `MLflow`: Backend Store, Artifact Store и Model Registry

Главное архитектурное решение **`MLflow`** — жёсткое разделение хранения
**лёгких метаданных** и **тяжёлых бинарных файлов**:

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                    Python-скрипт обучения (MLflow SDK)                  │
└──────────────────┬───────────────────────────────────┬──────────────────┘
                   │ 1. REST API (параметры, метрики)  │ 2. S3 API (файлы весов)
                   ▼                                   ▼
     ┌───────────────────────────┐       ┌───────────────────────────┐
     │  MLflow Tracking Server   │       │      Artifact Store       │
     │      (порт :5000)         │       │  SeaweedFS / MinIO / S3   │
     └─────────────┬─────────────┘       │      (порт :8333)         │
                   │ SQL                 │  s3://mlflow/<run_id>/    │
                   ▼                     │    └── model.onnx         │
     ┌───────────────────────────┐       └───────────────────────────┘
     │       Backend Store       │
     │   PostgreSQL / SQLite     │
     │ (runs, metrics, registry) │
     └───────────────────────────┘
```

### 2.1 Backend Store vs Artifact Store
- **Backend Store (`PostgreSQL` или `SQLite`):** реляционная СУБД, где в
  таблицах `experiments`, `runs`, `params`, `metrics`, `model_versions`
  лежат только строки, числа и ссылки на пути в S3. Благодаря этому поиск
  и сортировка тысяч запусков в веб-интерфейсе выполняются за миллисекунды.
- **Artifact Store (`S3` / `SeaweedFS` / `GCS`):** объектное хранилище для
  бинарных файлов весов и графиков.
- **Режим `--serve-artifacts` (Proxied Artifact Access):** в базовом режиме
  Python-клиент сам загружает файлы в S3, а значит каждому разработчику на
  ноутбуке нужны ключи `AWS_ACCESS_KEY_ID` от продакшн-бакета. Если запустить
  сервер с флагом `--serve-artifacts` и `--artifacts-destination s3://mlflow`,
  клиент отправляет файлы по HTTP на сам `MLflow Server`, и только сервер
  имеет ключи доступа к S3!

### 2.2 Model Registry: почему вместо Stages теперь используют Model Aliases
Раньше в `MLflow Model Registry` использовались 4 фиксированные стадии
(`None`, `Staging`, `Production`, `Archived`). Начиная с **MLflow 2.9+**,
жёсткие стадии объявлены **устаревшими (deprecated)** и заменены на
гибкий механизм **Model Aliases (алиасы) и Tags**:

- Вы назначаете конкретной версии модели именованный указатель, например
  `@champion` (основная прод-модель, получающая 90% трафика) и
  `@challenger` (кандидат в Canary / A/B-тесте, получающий 10% трафика).
- Сервис инференса в Kubernetes вообще не знает номеров версий — он всегда
  запрашивает URI `models:/doc-router@champion`.
- Чтобы выкатить новую версию или сделать мгновенный **rollback**, инженеру
  не нужно пересобирать контейнер — достаточно переключить алиас `@champion`
  с версии `4` обратно на версию `3`!

```python
import mlflow
from mlflow import MlflowClient

mlflow.set_tracking_uri("http://localhost:5000")
client = MlflowClient()

# Переключаем прод-алиас @champion на проверенную версию 3:
client.set_registered_model_alias(
    name="personal-docs-router",
    alias="champion",
    version="3",
)
```

## 3. Архитектура `ClearML`: `Task.init`, `ClearML Agent` и очереди задач

Во многих компаниях и обучающих программах наряду с `MLflow` используется
платформа **`ClearML`**. Важно понимать её фундаментальное отличие: если
`MLflow` — это лёгкий модульный трекер, то `ClearML` объединяет в себе
**трекер экспериментов, систему управления данными и оркестратор воркеров**.

### 3.1 Подход «двух строчек кода» (`Task.init`)
В `MLflow` вы явно пишете, какие параметры и метрики залогировать. В
`ClearML` в начало скрипта добавляется вызов:

```python
from clearml import Task

task = Task.init(project_name="PersonalDocs", task_name="train_router")
```

В момент вызова `Task.init()` библиотека выполняет **monkey-patching**
окружения:
- автоматически считывает URL Git-репозитория, ветку, `commit SHA` и даже
  сохраняет незакоммиченный `git diff`;
- перехватывает все аргументы командной строки из `argparse`;
- перехватывает вызовы `torch.save` / `joblib.dump`, графики `matplotlib` /
  `tensorboard` и весь поток `stdout`/`stderr`.

### 3.2 Как работают `ClearML Agent` и очереди (`Queues`)
Главный козырь `ClearML` — встроенная удалённая оркестрация без необходимости
поднимать `Airflow` или `Kubeflow` на старте:
1. На вычислительных узлах (например, серверах с GPU или мощным CPU)
   запускается демон **`clearml-agent daemon --queue default --docker`**.
2. В веб-интерфейсе ClearML инженер берёт любой ранее выполненный
   эксперимент, нажимает **Clone**, меняет прямо в браузере гиперпараметр
   (например, `learning_rate = 0.0005`) и ставит задачу в очередь `default`
   (`Enqueue`).
3. Свободный `ClearML Agent` забирает задачу из очереди, поднимает нужный
   Docker-контейнер, клонирует точный Git-коммит, накатывает поверх него
   сохранённый `git diff`, подставляет новые гиперпараметры из UI и
   запускает обучение!

### 3.3 Почему для нашей практики мы выбираем `MLflow`, а не `ClearML`
- Стек `ClearML Server` требует одновременного запуска `MongoDB`,
  `Elasticsearch`, `Redis` и трёх сервисов API/Web/Files (съедает 4–6 ГБ
  RAM впустую).
- Подход `Task.init()` с автоматическим перехватом всего подряд удобен для
  исследователей в ноутбуках, но в строгом продакшне DevOps/SRE предпочитают
  прозрачный и предсказуемый `MLflow` (1 лёгкий контейнер + S3), а
  оркестрацию делегируют штатному Kubernetes или `Prefect`/`Airflow`.

## 4. Как отслеживать эксперименты в LLMOps и RAG

В классическом ML мы сравниваем алгоритмы и гиперпараметры. В LLMOps и RAG
экспериментом является **комбинация параметров поисково-генеративного
конвейера**:
- какая модель эмбеддингов использовалась (`bge-m3` vs `multilingual-e5`);
- стратегия разбиения документов (`chunk_size = 512` vs `1024`,
  `chunk_overlap = 64`);
- шаблон системного промпта и его версия;
- квантование и модель генерации (`Qwen3-8B Q4_K_M` vs `Gemma-3-4B`).

Все эти параметры точно так же логируются в `MLflow` через `mlflow.log_params()`,
а в качестве метрик записываются результаты прогона на **Golden Dataset**:
`retrieval_hit_at_3`, `answer_keyword_match`, `avg_latency_ms` и
сохраняется таблица ответов модели в `.json` / `.csv` артефакт для
визуального сравнения двух промптов!

## 5. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему в продакшн-инсталляции `MLflow` нельзя хранить и метаданные, и
артефакты моделей на локальном диске внутри контейнера (`./mlruns`)?**
*Ответ:* Во-первых, локальная файловая система не позволяет горизонтально
масштабировать `MLflow Server` в нескольких репликах за балансировщиком.
Во-вторых, без реляционного Backend Store (`PostgreSQL`) не работают
транзакции, конкурентная запись и функции `Model Registry`. В-третьих,
хранение гигабайтных весов требует дешёвого и безлимитного объектного
хранилища (`S3`), а не блочного диска БД.

**2. Зачем в `MLflow Server` нужен режим `--serve-artifacts` (Proxied
Artifact Storage)?**
*Ответ:* Без этого флага `MLflow Server` лишь возвращает клиенту `s3://`
URI, а загрузку и скачивание файлов весов выполняет сам Python-скрипт на
машине пользователя или в CI-раннере — значит, всем клиентам нужно выдавать
IAM-ключи от S3-бакета. В режиме `--serve-artifacts` все файлы передаются
через HTTP API самого `MLflow Server`, и ключи от S3 хранятся только на
сервере.

**3. Почему в современных версиях `MLflow` отказались от фиксированных
стадий (`Staging`, `Production`) в пользу `Model Aliases` (`@champion`,
`@challenger`)?**
*Ответ:* Фиксированный набор из двух рабочих стадий не позволял удобно
описывать реальные продакшн-сценарии: например, когда в проде одновременно
работают 3 версии модели (основная `@champion`, канареечная `@canary` и
региональная `@eu-prod`) или нужно атомарно переключать трафик в A/B-тесте
простым переназначением указателя.

**4. В чём ключевое архитектурное отличие `ClearML` от `MLflow`?**
*Ответ:* `MLflow` следует философии UNIX: он отвечает только за трекинг
экспериментов и реестр моделей, не вмешиваясь в управление серверами и
очередями. `ClearML` — это сквозная платформа с собственным демоном
оркестрации (`ClearML Agent`) и очередями задач (`Queues`), позволяющая
клонировать эксперимент в веб-интерфейсе и отправить его на выполнение на
удалённый GPU/CPU-узел.

**5. Как `ClearML` воспроизводит эксперимент на удалённом `ClearML Agent`,
если разработчик запустил скрипт локально, не сделав `git commit` своих
правок?**
*Ответ:* В момент вызова `Task.init()` SDK сохраняет на сервер не только
базовый `git commit SHA` и адрес репозитория, но и полный текстовый патч
незакоммиченных изменений (`git diff`). При запуске задачи на удалённом
узле `ClearML Agent` делает `git checkout <sha>`, а затем накатывает
сохранённый патч поверх кода.

**6. Что такое `MLmodel` и `Model Signature` внутри сохранённого артефакта
MLflow?**
*Ответ:* `MLmodel` — это главный YAML-манифест внутри папки модели,
описывающий поддерживаемые форматы загрузки (`flavors`: `onnx`,
`python_function`, `sklearn`), версию Python и `signature` — строгую схему
типов и размерностей входных и выходных тензоров/колонок. Если на вход
модели в продакшне подать не те типы колонок, `MLflow` отклонит запрос до
вызова математического ядра.

**7. Как связать конкретный запуск обучения в `MLflow` с точной версией
датасета из `DVC`?**
*Ответ:* Перед стартом обучения считать `md5`-хэш датасета из файла
`dataset.dvc` (или `dvc.lock`) и записать его в теги или параметры запуска:
`mlflow.set_tag("dvc.dataset.md5", dataset_hash)` и `mlflow.set_tag("git.commit",
commit_sha)`. Тогда по любой модели в `Model Registry` можно однозначно
восстановить данные, на которых она училась.

**8. Какие известные уязвимости безопасности встречаются у стандартного
`MLflow Tracking Server` и как его защищать в инфраструктуре?**
*Ответ:* По умолчанию базовый `MLflow` не имеет включённой аутентификации
и ролевой модели, а в старых версиях неоднократно находили критические CVE
(Path Traversal / LFI при чтении артефактов и RCE при десериализации
моделей). В продакшне `MLflow` закрывают внутренним Ingress с OAuth2-Proxy /
OIDC, включают встроенный `--app-name basic-auth`, обновляют версию и
запрещают деплой непроверенных `pickle`-моделей.

**9. Что такое `Parent Run` и `Child Runs` (`nested=True`) в `MLflow` и
когда они применяются?**
*Ответ:* Вложенные запуски (`mlflow.start_run(nested=True)`) применяются
при кросс-валидации (`K-Fold`) или подборе гиперпараметров (`Optuna`):
родительский `Run` хранит общую конфигурацию поиска и лучшие итоговые
метрики, а дочерние `Runs` — результаты каждой отдельной попытки или фолда,
не захламляя главный список эксперимента.

**10. Чем трекинг экспериментов в `MLflow` отличается от трейсинга LLM в
`Langfuse` (почему в LLMOps часто нужны оба)?**
*Ответ:* `MLflow` ориентирован на **итерации разработки и оценки** (прогон
всего датасета при смене промпта/эмбеддера, сравнение агрегированных метрик
`Hit@K` и версионирование весов роутера). `Langfuse` ориентирован на
**позапросный продакшн-трейсинг** многошаговых цепочек и агентов LLM
(дерево спанов каждого запроса пользователя, стоимость в токенах, задержка
каждого шага ретривера и фидбек пользователя).
