## 1. Две главные проблемы: Training-Serving Skew и Time-Travel Leakage

1. **Training-Serving Skew (расхождение между обучением и продакшеном):**
   Data Scientist вычисляет признак `avg_medical_spend_90d` на Python/SQL
   в ноутбуке при обучении, а Backend-разработчик переписывает эту
   формулу на Go для микросервиса (например, делит на 90 дней вместо
   реального числа чеков или по-другому обрабатывает `NULL`). В итоге на
   инференсе модель получает распределение чисел, которого никогда не
   видела при обучении.
2. **Time-Travel Data Leakage (утечка из будущего):**
   При сборке обучающего датасета за прошлый год инженер делает обычный
   `LEFT JOIN user_features USING (user_id)`. В таблицу попадают
   **сегодняшние** значения признаков пользователя (включая события,
   произошедшие *после* целевого события). На кросс-валидации модель
   показывает `ROC-AUC = 0.99`, а в реальном времени оказывается
   бесполезной.

## 2. Архитектура Dual Store: Offline Store + Online Store

Feature Store разделяет хранение признаков на два физически разных
движка с единым каталогом определений (`Registry`):

```text
                    Batch / Streaming Pipeline
                                │
Raw Data ──────────────────────►│ Расчет признаков
                                │
                                ▼
                  ┌───────────────────────────┐
                  │       Offline Store       │ ◄── get_historical_features()
                  │ (Parquet/S3, ClickHouse,  │     (Обучение, миллионы строк,
                  │  BigQuery, PostgreSQL)    │      Point-in-Time ASOF JOIN)
                  └───────────────────────────┘
                                │
                  feast materialize-incremental
                                │
                                ▼
                  ┌───────────────────────────┐
                  │       Online Store        │ ◄── get_online_features()
                  │ (Redis, DynamoDB, SQLite) │     (Онлайн-инференс, 1–5 мс,
                  │ Только последнее значение │      чтение по ключу entity_id)
                  └───────────────────────────┘
```

- **Offline Store** хранит **всю историю** изменения каждого признака с
  таймстемпами (`event_timestamp`) за месяцы и годы. Оптимизирован под
  колоночное сканирование больших объемов при генерации обучающих выборок.
- **Online Store** хранит **только самое свежее (последнее) значение**
  признака для каждого `entity_id` в быстрой Key-Value базе в памяти
  (например, `Redis`), обеспечивая чтение за `1–3 мс` во время
  HTTP-запроса к модели.

## 3. Point-in-Time Correctness (`ASOF JOIN`) под капотом

Когда вызывается `store.get_historical_features(entity_df, features)`,
Feature Store выполняет не обычный `JOIN`, а **Point-in-Time Join
(`ASOF JOIN`)**:

Для каждой строки обучающего события $(u_i, t_{\text{event}})$ из
`entity_df` система ищет в `Offline Store` запись признака того же
пользователя $u_i$ с максимальным временем $t_{\text{feature}}$, которое:
1. **не позже** момента события: $t_{\text{feature}} \le t_{\text{event}}$
   (защита от заглядывания в будущее);
2. **не старее** допустимого времени жизни признака (`TTL`):
   $t_{\text{event}} - t_{\text{feature}} \le \text{TTL}$ (защита от
   протухших данных).

## 4. Практическая конфигурация Feast (`feature_store.yaml` и `features.py`)

```yaml
# feature_store.yaml
project: personal_docs_vault
registry: data/registry.db
provider: local

offline_store:
  type: file

online_store:
  type: sqlite  # для локальной разработки; в продакшене: type: redis
entity_key_serialization_version: 2
```

```python
# features.py
from datetime import timedelta
from feast import Entity, FeatureService, FeatureView, Field, FileSource
from feast.types import Float32, Int64, String

owner = Entity(name="owner_id", join_keys=["owner_id"])

doc_stats_source = FileSource(
    path="data/owner_doc_stats.parquet",
    timestamp_field="event_timestamp",
)

doc_stats_fv = FeatureView(
    name="owner_doc_stats",
    entities=[owner],
    ttl=timedelta(days=30),
    schema=[
        Field(name="medical_docs_90d", dtype=Int64),
        Field(name="tax_debt_rub", dtype=Float32),
        Field(name="last_active_category", dtype=String),
    ],
    online=True,
    source=doc_stats_source,
)

assistant_features = FeatureService(
    name="doc_router_context_v1",
    features=[doc_stats_fv],
)
```

## 5. Когда Feature Store нужен, а когда это оверинжиниринг

| Ситуация | Нужен ли Feature Store? |
| :--- | :--- |
| Табличный антифрод / скоринг / рекомендации, где на инференсе приходит только `user_id`, а модели нужно за `5 мс` подтянуть 50 исторических агрегатов | **Да, критически нужен** |
| 3+ разных моделей в компании переиспользуют одни и те же витрины признаков | **Да, окупает поддержку** |
| Текстовый классификатор документов или RAG, где все входные данные (текст документа/вопроса) приходят прямо в теле HTTP-запроса (`Stateless Inference`) | **Не нужен** (достаточно векторной БД `Qdrant` для чанков и обычной БД метаданных) |

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Что такое `Training-Serving Skew` и по каким трем причинам он чаще
всего возникает в продакшене?**
*Ответ:* Это расхождение между распределением или логикой расчета
признаков на этапе обучения и на этапе онлайн-инференса. Три главные
причины:
1. Разный код расчета признака (SQL/Spark в офлайне против Python/Go в
   онлайне).
2. Утечка данных из будущего (`Time-Travel Leakage`) при неаккуратном
   `JOIN` исторических таблиц на обучении.
3. Отставание конвейера доставки данных в `Online Store` (модель обучена
   на свежих агрегатах, а в Redis лежат вчерашние данные).

**2. Зачем в Feature Store два хранилища (`Offline Store` и `Online
Store`), почему нельзя использовать одну базу данных для обоих контуров?**
*Ответ:* У обучения и онлайн-сервинга противоположные профили нагрузки:
- Обучению нужно прочитать **сотни миллионов исторических строк** по всем
  пользователям за год с выполнением тяжелых `ASOF JOIN` — для этого
  нужны колоночные хранилища (Parquet/S3, ClickHouse, BigQuery), где
  запрос идет секунды или минуты.
- Онлайн-инференсу нужно прочитать **одну строку** последних признаков
  по конкретному `user_id` за **`1–3 мс`** при тысячах RPS — колоночные
  базы на точечных чтениях (`point lookups`) дают десятки или сотни
  миллисекунд, поэтому для онлайна используют In-Memory Key-Value (Redis,
  DynamoDB).

**3. Как работает `Point-in-Time Join` (`ASOF JOIN`) в `get_historical_features`
и какую ошибку он предотвращает?**
*Ответ:* Для каждого исторического таргета с отметкой времени
$t_{\text{label}}$ он подбирает состояние признака на момент
$t_{\text{feature}} \le t_{\text{label}}$ (но не старше `TTL`). Это
гарантирует, что модель при обучении на событии из прошлого видит ровно
те значения признаков, которые реально были известны системе в ту
секунду, предотвращая `Data Leakage` из будущего.

**4. Что делает процесс `Materialization` (`feast materialize-incremental`)
и что случится с онлайн-моделью, если этот джоб упадет на выходные?**
*Ответ:* Материализация выгружает свежие рассчитанные значения признаков
из `Offline Store` и записывает их в `Online Store` (Redis). Если джоб
упадет на выходные, онлайн-сервис продолжит работать без ошибок HTTP 500,
но будет подавать в модель устаревшие (пятничные) значения признаков
либо `NULL` (если истечет `TTL`), что вызовет скрытую деградацию качества
предсказаний. Поэтому лаг материализации обязательно мониторят в
Prometheus.

**5. Какую роль играет параметр `ttl` (Time-To-Live) в `FeatureView` как
на этапе обучения, так и на этапе онлайн-инференса?**
*Ответ:* На этапе обучения (`ASOF JOIN`) `ttl` ограничивает, насколько
старое значение признака можно приклеить к событию: если последнее
обновление признака было за 45 дней до события, а `ttl=30d`, вместо
протухшего числа подставится `NULL`. В `Online Store` (Redis) `ttl`
позволяет автоматически удалять из дорогой оперативной памяти ключи
неактивных пользователей, которые давно не заходили в сервис.

**6. Чем обычный `Feast` отличается от полнофункциональных платформ
вроде `Tecton` или `Hopsworks`?**
*Ответ:* Обычный open-source `Feast` **не вычисляет** сами трансформации
(агрегации по окнам в Spark/Flink) — он ожидает, что внешний пайплайн
(Airflow/dbt/Spark) уже положил готовые таблицы в `Offline Store`, и
берет на себя только единый каталог, `Point-in-Time Join` и
материализацию в `Online Store`. Платформы вроде `Tecton` сами управляют
запуском потоковых и батчевых пайплайнов трансформации данных.

**7. Как обновлять признаки в `Online Store`, если бизнесу нужна
свежесть не раз в сутки (batch), а в течение 2 секунд после действия
пользователя (например, в антифроде)?**
*Ответ:* Для таких признаков батчевой материализации через
`Offline Store` недостаточно. Используют **Streaming / Push Source**:
потоковый движок (Kafka + Flink / Faust) считает скользящее окно в
реальном времени и пушит обновленное значение одновременно и в
`Online Store` (`store.push(...)` в Redis), и в `Offline Store` (для
будущих переобучений).

**8. Что такое `On-Demand Feature View` в Feast и для каких признаков он
используется?**
*Ответ:* Это признаки, которые невозможно предрассчитать заранее в батче,
так как они зависят от параметров самого текущего запроса в момент
вызова (например: «отношение суммы текущей транзакции из запроса к
среднему чеку пользователя за 30 дней из Redis» или расстояние от
текущих GPS-координат пользователя до магазина). Они вычисляются на лету
в момент вызова инференса.

**9. Как версионировать изменения логики расчета признака в Feature
Store, чтобы не сломать уже работающую в продакшене модель `v1`?**
*Ответ:* Изменять формулу существующего признака «на месте» (`in-place`)
нельзя — для старой модели `v1` это мгновенно создаст `Training-Serving
Skew`. Правильный паттерн (как с миграциями API): добавить новый признак
с версией в имени (`avg_spend_30d_v2`) или новую `FeatureService`
(`fraud_features_v2`), обучить на ней модель `v2`, переключить трафик и
только после вывода модели `v1` из эксплуатации удалить `v1`-признак.

**10. Нужен ли Feature Store для нашего классификатора документов или
RAG-ассистента, и почему?**
*Ответ:* Если классификатор принимает только текст самого документа, он
является **stateless** — все данные уже есть в запросе, и Feature Store
будет лишним усложнением инфраструктуры. Feature Store понадобится только
тогда, когда модели наряду с текстом запроса нужно за миллисекунды
подать исторический профиль пользователя (например, счетчики категорий
его прошлых документов, активные медицинские назначения или налоговый
статус), который регулярно пересчитывается в фоне.
