## 1. Главная физика инференса: Memory Bandwidth против FLOPS и трюк MoE

При авторегрессионной генерации текста (`batch_size = 1`, фаза `Decode`)
процессор или видеокарта на каждый новый токен обязаны прочитать из
оперативной/видеопамяти **все активные веса модели**. Поэтому скорость
генерации определяется не гигагерцами ядра, а **пропускной способностью
памяти (Memory Bandwidth)**:

$$\text{Tokens/sec} \approx \frac{\text{Memory Bandwidth (GB/s)}}{\text{Active Weights Size (GB)}} \times \eta \quad (\eta \approx 0.65)$$

### Почему MoE (`Mixture-of-Experts`) — чит-код для машины с 64 ГБ ОЗУ
Обычная плотная (`Dense`) модель на `30B` параметров в квантовании `Q4`
занимает `~18 ГБ` ОЗУ. При пропускной способности двухканальной DDR5
`~90 ГБ/с` чтение всех 18 ГБ на каждый токен даст всего `~3–3.5 ток/с`
(слишком медленно для комфортного чата).

Архитектура **MoE** (например, `Qwen3-30B-A3B`) хранит в ОЗУ все `30B`
параметров (`~18 ГБ` — легко помещается в ваши **64 ГБ ОЗУ**!), но для
каждого конкретного токена роутер внутри слоев активирует только **малую
долю экспертов (`~3B` активных параметров $\approx 2$ ГБ весов)**.
В результате:
- из памяти на каждый токен читается всего `~2 ГБ` вместо `18 ГБ`;
- скорость на CPU возрастает до **`20–30 токенов/с`** (быстрее плотной
  8B-модели!), а эрудиция и качество рассуждений соответствуют крупной
  30B-модели.

## 2. Анатомия гибридного процессора Intel Core Ultra 7 155H (P/E ядра, Arc iGPU, NPU)

На рабочей машине с процессором **Intel Core Ultra 7 155H (Meteor Lake)**
внутри одного чипа находятся сразу **три разных вычислителя** и
неоднородные ядра CPU:

```text
┌──────────────────────────────────────────────────────────────────────┐
│                   Intel Core Ultra 7 155H (64 GB RAM)                │
├──────────────────────┬───────────────────────┬───────────────────────┤
│ 1. Гибридный CPU     │ 2. Intel Arc iGPU     │ 3. Intel AI Boost NPU │
│ - 6 P-ядер (CPU 0-11)│ - 8 Xe-cores          │ - Энергоэффективный   │
│   AVX2 / VNNI, 4.8ГГц│ - /dev/dri/renderD128 │   нейроускоритель     │
│ - 8 E-ядер + 2 LP-E  │ - Доступ к общей RAM! │ - /dev/accel/accel0   │
│   (CPU 12-21), 3.8ГГц│ - Vulkan / SYCL /     │ - Фоновый OCR /       │
│                      │   OpenVINO            │   эмбеддинги (OpenVINO)│
└──────────────────────┴───────────────────────┴───────────────────────┘
```

### 2.1 Почему для `llama.cpp` и `ONNX Runtime` на CPU нужно ровно 6 потоков на P-ядрах
Движки `ggml` (`llama.cpp`) и `OpenMP` делят матрицу на $T$ равных кусков
по числу потоков и в конце каждого слоя ждут завершения всех потоков на
барьере синхронизации (`pthread_barrier` / spin-wait).
- Если поставить `--threads 16` или `22`, часть кусков попадет на
  медленные энергоэффективные `E-ядра` (`CPU 12..19`), у которых ниже
  частота и пропускная способность кэша L2, и на `Hyper-Threading`
  сиблинги.
- В итоге 6 быстрых `P-ядер` выполнят свою работу и будут впустую жечь
  такты в ожидании отстающих `E-ядер`.
- **Золотое правило для Intel 155H:** ограничивать пул потоков инференса
  числом физических `P-ядер` (`--threads 6`, `OMP_NUM_THREADS=6`) и
  привязывать контейнер к `cpuset: "0-11"`.

### 2.2 Использование встроенной графики Intel Arc iGPU (`/dev/dri/renderD128`)
Огромный плюс встроенного **Intel Arc iGPU** на ноутбуке с **64 ГБ ОЗУ**
— **общая память (Unified Memory Architecture)**: в отличие от бюджетных
дискретных видеокарт с 8 ГБ VRAM, встроенный Arc iGPU может адресовать
десятки гигабайт вашей системной оперативной памяти без пересылки по
шине PCIe!

Как пробросить Intel Arc iGPU в Docker / Kubernetes:
```yaml
# В docker-compose.yml:
services:
  llm-vulkan:
    image: ghcr.io/ggerganov/llama.cpp:server-vulkan
    devices:
      - /dev/dri:/dev/dri
    group_add:
      - video
      - render
```
На фазе **Prefill** (обработка длинного документа из RAG) запуск через
бэкенд **Vulkan**, **SYCL (`ipex-llm`)** или **OpenVINO GenAI** на
Intel Arc iGPU дает ускорение в **2–3.5 раза** по сравнению с чистым CPU.

## 3. Классификация дискретных GPU: Consumer, Workstation и Datacenter

| Класс | Примеры карт | Объем памяти и ПСП | Сетевая связность и особенности |
| :--- | :--- | :--- | :--- |
| **Consumer (игровые)** | `RTX 4090` (24 ГБ), `RX 7900 XTX` (24 ГБ), `Arc B580` (12 ГБ) | `500–1008 ГБ/с` (GDDR6/X) | Только PCIe (`~64 ГБ/с`), нет аппаратного `MIG`, высокое тепловыделение |
| **Workstation (проф.)** | `RTX 6000 Ada` (48 ГБ), `Radeon Pro W7900` (48 ГБ) | `860–960 ГБ/с` (GDDR6 с ECC) | Память с коррекцией ошибок **ECC**, турбинное охлаждение для стоек |
| **Datacenter (серверные)** | `NVIDIA H100` (80 ГБ), `H200` (141 ГБ), `AMD MI300X` (192 ГБ) | **`2000–5300 ГБ/с` (HBM2e / HBM3e)** | **NVLink** (`900 ГБ/с` между GPU), аппаратный **MIG**, `InfiniBand / RoCE RDMA` |

### Почему для распределенного обучения (`Tensor Parallelism`) критичен NVLink
При разрезании одного слоя трансформера между 4 видеокартами (`--tensor-parallel-size 4`)
картам нужно обмениваться активациями (`AllReduce`) **после каждого
слоя** (32–80 раз за генерацию одного токена!). По обычной шине PCIe 4.0
(`64 ГБ/с`) накладные расходы на пересылку съедают всю выгоду, тогда как
высокоскоростная шина **NVLink (`600–900 ГБ/с`)** делает обмен почти
мгновенным.

## 4. GPU и ускорители в Kubernetes: Device Plugins и NVIDIA GPU Operator

Сам по себе планировщик Kubernetes (`kube-scheduler`) знает только про
`cpu`, `memory` и `ephemeral-storage`. Чтобы он увидел видеокарты, на
каждом узле должен работать **Device Plugin** (`DaemonSet`), который
общается с `kubelet` по локальному gRPC-сокету в
`/var/lib/kubelet/device-plugins/`:

- Для **NVIDIA**: ресурс `nvidia.com/gpu: 1` (устанавливается
  автоматически через Helm-чарт **NVIDIA GPU Operator**, который сам
  ставит драйвер на хост, `nvidia-container-toolkit`, `Device Plugin`,
  `DCGM Exporter` и менеджер `MIG`).
- Для **AMD ROCm**: ресурс `amd.com/gpu: 1`.
- Для **Intel GPU (Arc / Flex / Max)**: `Intel Device Plugin for
  Kubernetes` регистрирует ресурс `gpu.intel.com/i915` или
  `gpu.intel.com/xe` (пробрасывая `/dev/dri/renderD128` в поды без
  опасного `privileged: true`).

## 5. Разделение GPU между контейнерами: MIG против Time-Slicing

По умолчанию запрос `nvidia.com/gpu: 1` отдает поду **всю видеокарту
целиком** (даже если там крутится маленькая модель роутера на 1 ГБ VRAM).
Чтобы разделить одну дорогую карту между несколькими подами, используют
два принципиально разных механизма:

1. **MIG (Multi-Instance GPU — только на `A30`, `A100`, `H100`, `H200`):**
   аппаратное разделение кристалла GPU, кэша L2, контроллеров памяти
   HBM и вычислительных блоков (`SM`) на независимые физические партиции
   (например, одну `A100 80GB` можно разбить на семь инстансов
   `nvidia.com/mig-1g.10gb` или два `3g.40gb`).
   - **Полная изоляция отказов и QoS:** если в одном поде произойдет
     `CUDA Out Of Memory` или тяжелый цикл, соседние поды на других
     MIG-партициях этого даже не заметят.
2. **Time-Slicing (доступно на любых картах NVIDIA, включая `RTX` и `T4`):**
   Device Plugin объявляет в K8s, что на ноде якобы есть `4` виртуальных
   ресурса `nvidia.com/gpu`, которые указывают на одну физическую карту.
   - Поды по очереди получают кванты времени GPU, но **память VRAM у них
     общая и никак не изолирована**: один жадный под может занять все
     24 ГБ VRAM и уронить все соседние поды с ошибкой `CUDA OOM`.

## 6. Мониторинг ускорителей: NVIDIA DCGM Exporter, `rocm-smi` и `intel_gpu_top`

В Kubernetes стандарт сбора метрик с карт NVIDIA — DaemonSet
**DCGM Exporter**, отдающий метрики в Prometheus:

```promql
# 1. Процент занятости вычислительных ядер GPU
DCGM_FI_DEV_GPU_UTIL

# 2. Процент загрузки контроллера памяти (главное узкое место LLM!)
DCGM_FI_DEV_MEM_COPY_UTIL

# 3. Занятая видеопамять в МБ
DCGM_FI_DEV_FB_USED

# 4. Аппаратные ошибки памяти ECC (ненулевое значение Double-Bit Error = замена карты)
DCGM_FI_DEV_ECC_DBE_VOL_TOTAL
```

На машинах с графикой **Intel Arc** (как наш стенд) загрузку движков
`Render/3D` и `Compute` в реальном времени смотрят утилитой
`intel_gpu_top` (из пакета `igt-gpu-tools`), а список устройств
проверяют через `ls -la /dev/dri/` (см. `./02_examples/gpu_monitor.sh`).

## 7. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему при генерации ответа LLM для одного пользователя (`batch_size = 1`)
скорость в токенах в секунду упирается в пропускную способность памяти
(`Memory Bandwidth`), а не в терафлопсы (`TFLOPS`) ядра?**
*Ответ:* На фазе авторегрессионного декодирования (`Decode`) каждый
следующий токен вычисляется строго последовательно. Чтобы умножить вектор
одного токена на матрицы всех слоев модели, вычислителю приходится
прочитать из памяти все гигабайты весов (например, 5 ГБ для 8B Q4) ради
выполнения всего одного векторно-матричного умножения (`GEMV`). Поэтому
ядра процессора или GPU простаивают в ожидании подгрузки весов по шине
памяти (`Memory-bandwidth-bound`).

**2. Посчитайте на собеседовании: с какой максимальной скоростью (ток/с)
будет генерировать текст модель `8B` в формате `FP16` на карте с
пропускной способностью памяти `800 ГБ/с`, и что изменится при
квантовании в `INT4`?**
*Ответ:*
- В `FP16` (2 байта на параметр) веса модели `8B` занимают
  $8 \times 2 = 16\text{ ГБ}$. Теоретический потолок:
  $800\text{ ГБ/с} / 16\text{ ГБ} = 50\text{ ток/с}$ (на практике с учетом
  КПД шины $\approx 35\text{–}40\text{ ток/с}$).
- При квантовании весов в `INT4` (0.5 байта на параметр) объем весов
  падает в 4 раза — до $\approx 4\text{–}4.5\text{ ГБ}$. Поскольку с шины
  памяти на каждый токен нужно прочитать в 4 раза меньше байт, скорость
  генерации вырастет почти в 3–4 раза (до $\approx 110\text{–}140\text{ ток/с}$).

**3. Почему архитектура `MoE (Mixture-of-Experts)` идеально подходит для
локальных машин с большим объемом оперативной памяти (например, 64 ГБ
RAM), но ограниченной пропускной способностью CPU?**
*Ответ:* В MoE-модели (например, `30B-A3B`) общий объем параметров велик
(`30B`, ~18 ГБ в Q4 — он спокойно лежит в 64 ГБ RAM), но при генерации
каждого конкретного токена активируется только подмножество экспертов
(`3B` параметров, ~2 ГБ). Поскольку процессор читает из оперативной
памяти на каждый токен только активные 2 ГБ весов, а не все 18 ГБ,
скорость генерации оказывается такой же высокой, как у крошечной
3B-модели, при качестве большой 30B-модели.

**4. Почему на гибридных процессорах (Intel Core Ultra / 12th–15th Gen с
P-ядрами и E-ядрами) запуск `llama.cpp` или `ONNX Runtime` на всех
логических потоках работает медленнее, чем только на физических P-ядрах?**
*Ответ:* Параллельные циклы матричного умножения (`OpenMP` / `ggml`)
делят работу поровну между потоками и синхронизируются на барьере в
конце каждого слоя трансформера. Медленные энергоэффективные `E-ядра`
выполняют свою порцию вычислений дольше производительных `P-ядер`,
заставляя все быстрые ядра простаивать на каждом барьере синхронизации,
плюс потоки начинают конкурировать за кэш и шину памяти.

**5. Из каких основных компонентов состоит `NVIDIA GPU Operator` в
Kubernetes и какую задачу решает каждый из них?**
*Ответ:* `GPU Operator` автоматизирует управление жизненным циклом GPU-нод
через контейнеры (без ручной настройки хост-ОС):
1. **NVIDIA Driver DaemonSet** — собирает и загружает модули ядра драйвера;
2. **NVIDIA Container Toolkit** — настраивает `containerd` (хук проброса
   устройств `/dev/nvidia*` и библиотек CUDA в контейнеры);
3. **Kubernetes Device Plugin** — сообщает `kubelet`'у о наличии ресурса
   `nvidia.com/gpu`;
4. **Node Feature Discovery (NFD)** и **GPU Feature Discovery (GFD)** —
   вешают на ноды лейблы с моделью карты, объемом VRAM и версией CUDA;
5. **DCGM Exporter** — отдает телеметрию GPU в Prometheus;
6. **MIG Manager** — управляет нарезкой профилей `MIG`.

**6. В чем фундаментальная разница между `MIG (Multi-Instance GPU)` и
`Time-Slicing` в Kubernetes?**
*Ответ:* `MIG` — это **аппаратное** разделение датацентровых карт
(`A100`/`H100`) на уровне кремния: каждый инстанс получает выделенный
кусок памяти HBM, свои контроллеры памяти и свои вычислительные блоки
`SM`, обеспечивая 100% изоляцию по памяти, пропускной способности и
сбоям. `Time-Slicing` — это **программное** переключение контекста по
времени на одной общей карте: изоляции видеопамяти (VRAM) нет, и если
один контейнер выделит слишком большой тензор, от `CUDA OOM` упадут
соседние контейнеры на этой же карте.

**7. Почему `kubectl top pod` не показывает загрузку GPU и видеопамяти
(VRAM), и какие метрики `DCGM` нужно вывести на дашборд в Grafana?**
*Ответ:* Стандартный `metrics-server` в Kubernetes собирает через `cgroups`
только метрики процессора (`cpu`) и системной оперативной памяти (`memory`)
хоста, ничего не зная о драйвере видеокарты. Для мониторинга GPU ставят
`DCGM Exporter` и выводят:
- `DCGM_FI_DEV_FB_USED` (потребление VRAM);
- `DCGM_FI_DEV_GPU_UTIL` (активность ядер);
- `DCGM_FI_DEV_MEM_COPY_UTIL` (утилизация шины памяти);
- `DCGM_FI_DEV_SM_ACTIVE` и `DCGM_FI_DEV_PIPE_TENSOR_ACTIVE` (реальная
  загрузка тензорных ядер — гораздо точнее обычного `GPU_UTIL`).

**8. В чем подвох метрики `GPU-Util` в `nvidia-smi` (`DCGM_FI_DEV_GPU_UTIL`),
когда она показывает `99%`, но обучение идет медленно?**
*Ответ:* Метрика `GPU_UTIL` показывает лишь долю времени, в течение
которого на видеокарте было запущено **хотя бы одно любое ядро CUDA**
(даже если это крошечная операция на 1 из 132 потоковых мультипроцессоров
`SM` или ожидание чтения из памяти). Чтобы понять, реально ли нагружены
вычислительные блоки, смотрят на энергопотребление (`Power Usage` близко
к TDP) и профильные метрики `DCGM_FI_DEV_SM_OCCUPANCY` и
`DCGM_FI_DEV_PIPE_TENSOR_ACTIVE`.

**9. Зачем датацентровым и профессиональным GPU нужна память с `ECC
(Error Correction Code)`, и что делает `DCGM` при росте ошибок `DBE`?**
*Ответ:* При многодневном распределенном обучении на сотнях гигабайт
памяти космическое излучение и тепловой шум неизбежно вызывают инверсию
отдельных битов (`bit flips`). Если перевернется бит экспоненты в числе
`FP16/BF16`, градиент превратится в `NaN` или `Inf`, и при первом же
`AllReduce` заразит `NaN`-значениями **все узлы кластера**, испортив
чекпоинт. Память с `ECC` автоматически исправляет одиночные битовые
ошибки (`SBE — Single-Bit Error`) на лету, а при обнаружении неисправимой
двойной ошибки (`DBE — Double-Bit Error`) сигнализирует о необходимости
вывести неисправный GPU-узел из кластера (`cordon + drain`).

**10. Как безопасно пробросить встроенную графику `Intel Arc iGPU`
(`/dev/dri/renderD128`) или `NPU` в Kubernetes Pod без выдачи контейнеру
полных прав `privileged: true`?**
*Ответ:* Использовать официальный **Intel Device Plugin for Kubernetes**
(`gpu_plugin`), который обнаруживает устройства `/dev/dri/renderD*` и
предоставляет их как стандартный ресурс `gpu.intel.com/i915: 1` (или
`gpu.intel.com/xe: 1`), автоматически монтируя только нужный
символьный девайс и добавляя GID группы `render` в `supplementalGroups`
контейнера при сохранении `allowPrivilegeEscalation: false`.
