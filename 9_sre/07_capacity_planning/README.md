# 07. Capacity Planning

## Зачем
Мощности, купленные «на глаз», либо простаивают, либо заканчиваются
в день распродажи. Планирование ёмкости связывает рост нагрузки,
пределы сервиса (найденные нагрузочным тестом) и время на закупку или
масштабирование.

## Файлы
- [01_theory/capacity_planning.md](./01_theory/capacity_planning.md) —
  зачем планировать, закон Литтла, методология (тренды, регрессия,

  (`k6 run capacity-k6.js --env BASE_URL=http://localhost:8080`).

Отдельных упражнений нет: скрипт k6 можно запустить против любого
тестового HTTP-сервиса (например, `app.py` из
[упражнений по Prometheus](../../8_observability/02_metrics_prometheus/04_exercises_answers/app.py)
с `BASE_URL=http://localhost:8001`: он отвечает 200 на любой путь,
кроме `/error`, включая `/api/data` из скрипта).

## Как проходить
1. Прочитать теорию; решить пример на закон Литтла вручную.
2. Запустить k6-тест против тестового сервиса и найти, при каком числе
   VU растут p95 latency и доля ошибок.
3. В Prometheus построить прогноз свободного места на диске через
   неделю: `predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[6h],
   7*24*3600)` — линейная регрессия по последним 6 часам.

## Когда двигаться дальше
- Можете по закону Литтла оценить нужный параллелизм из RPS и latency.
- Можете объяснить, почему планируют по пиковой нагрузке и p95/p99, а
  не по среднему.
- Можете найти break point сервиса нагрузочным тестом.
