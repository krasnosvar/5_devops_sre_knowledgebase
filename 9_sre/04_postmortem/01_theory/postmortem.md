# Postmortem — разбор инцидентов без поиска виноватых

## Принцип blameless postmortem

Цель — найти системные причины, а не виноватых людей.
Люди делают ошибки всегда. Система должна быть устроена так,
чтобы одна ошибка не приводила к инциденту.

**Что нужно объяснить команде:**
- «Мы разбираем систему, а не человека»
- «Ошибка — ценная информация о слабых местах»
- «Если боишься признать ошибку — следующий раз скроешь»

## Шаблон postmortem

```markdown
# Postmortem: Payment Service Outage 2024-01-15

## Сводка

**Дата:** 2024-01-15  
**Длительность:** 14:03 – 14:50 UTC (47 минут)  
**Severity:** SEV-2  
**Затронуто:** ~30% пользователей (checkout flow)  
**Обнаружение:** Alertmanager → Slack #alerts (14:05, lag 2 мин)  

## Влияние

- 12,400 неудавшихся транзакций (~$180k потенциальная потеря)
- 3,200 жалоб через support chat
- Degraded: payment-service error rate 45% (SLO: < 0.1%)
- Не затронуто: просмотр каталога, корзина, аккаунт

## Timeline (UTC)

| Время | Событие |
|-------|---------|
| 14:01 | Деплой payment-service v2.3.1 завершён |
| 14:03 | Error rate начал расти (первые 5xx) |
| 14:05 | Алерт ErrorBudgetBurnRateFast → Slack |
| 14:08 | On-call инженер подтвердил инцидент, открыл #incident-2024-01-15 |
| 14:12 | Идентифицировали correlation с деплоем v2.3.1 |
| 14:15 | Решение откатиться принято |
| 14:17 | kubectl rollout undo deployment/payment-service |
| 14:22 | Error rate начал снижаться |
| 14:50 | Error rate вернулся к норме. Инцидент закрыт |

## Root Cause Analysis

### Что произошло

В v2.3.1 добавлена новая функция логирования детальных данных транзакции.
Реализация содержала N+1 запрос к PostgreSQL: для каждой транзакции
выполнялся SELECT к таблице `user_preferences` без JOIN.

При нормальной нагрузке (~500 TPS) это создало 500 дополнительных запросов/сек.
Пул соединений PostgreSQL (max_connections=100) был исчерпан за ~2 минуты после деплоя.

### Почему не поймали раньше

1. Staging окружение работало с 10% от prod нагрузки → N+1 не проявился
2. В load тестах не было данных в таблице `user_preferences` → запрос был быстрым
3. Code review не выявил N+1: функция логирования вызывается в цикле, но это неочевидно
4. Нет мониторинга количества SQL запросов на транзакцию

## Contributing Factors (без blame)

- Отсутствие реалистичного load testing в staging
- Отсутствие метрики "DB queries per business transaction"
- Feature flag не использовался (постепенное включение снизило бы риск)
- EXPLAIN ANALYZE не запускался для нового кода при code review

## Action Items

| # | Действие | Ответственный | Срок |
|---|---------|---------------|------|
| 1 | Добавить метрику db_queries_per_transaction в Prometheus | @backend-team | 2024-01-22 |
| 2 | Настроить алерт при db_queries > 10 на транзакцию | @platform-team | 2024-01-22 |
| 3 | Увеличить staging нагрузку до 50% от prod | @platform-team | 2024-01-29 |

## Что сработало хорошо

- Алерт сработал через 2 минуты после начала инцидента
- Корреляция с деплоем найдена за 7 минут
- Rollback занял 2 минуты
- Коммуникация в incident channel была чёткой и своевременной

## Что можно улучшить

- Staging должен проверять N+1 паттерны автоматически
- Feature flags снизили бы blast radius
```

## 5 Почему — техника поиска root cause

```
Проблема: payment-service вернул 503 Error

Почему 1: Исчерпан пул соединений PostgreSQL
Почему 2: Слишком много одновременных запросов к PostgreSQL
Почему 3: N+1 запрос добавлен в v2.3.1
Почему 4: Code review не выявил N+1
Почему 5: Нет автоматической проверки количества SQL запросов

→ Fix: метрика + алерт на db_queries_per_transaction
```

Важно: 5 «почему» — не буквально 5. Идти вглубь до системной причины которую можно исправить.

## Когда писать postmortem

- Любой SEV-1 / SEV-2
- Инциденты повторяющиеся даже при низком severity
- Инциденты которые «почти случились» (near-miss)
- Когда команда чувствует что могло быть хуже

**Срок:** написать в течение 48 часов пока события свежи.

## Follow-up — как не дать action items потеряться

- Каждый action item создаётся как тикет в трекере (Jira, Linear)
- Postmortem привязывается к тикетам
- Ретроспектива через 4 недели: что закрыто?
- Метрика: % action items выполненных в срок
