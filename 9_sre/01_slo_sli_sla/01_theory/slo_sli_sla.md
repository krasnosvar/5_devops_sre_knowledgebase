# SLO, SLI, SLA

## Определения

**SLI (Service Level Indicator)** — измеримая характеристика работы сервиса.
Конкретная метрика: «доля успешных запросов за последние 30 дней».

**SLO (Service Level Objective)** — цель для SLI.
«99.9% запросов должны быть успешными».

**SLA (Service Level Agreement)** — договор с пользователем/клиентом о SLO.
Обычно SLA немного мягче чем внутренний SLO. При нарушении — штрафные санкции.

```
SLI: доля успешных запросов = 99.95%
SLO: SLI >= 99.9%              ← внутренняя цель
SLA: SLI >= 99.5%              ← договор с клиентом (мягче, запас)
```

## Какие SLI выбирать

**Для request-based сервисов (API, web):**
- Availability: доля успешных запросов (2xx/3xx vs 5xx)
- Latency: доля запросов быстрее порога (< 300ms)
- Quality: доля запросов с корректными данными

**Для pipeline/batch сервисов:**
- Freshness: насколько свежи данные (lag от источника)
- Completeness: доля обработанных записей
- Throughput: записей/сек

**Для хранилищ:**
- Durability: вероятность потери данных
- Availability: доля успешных read/write

## Числа — что реально означают проценты

| SLO | Downtime/месяц | Downtime/год |
|-----|---------------|-------------|
| 99% | 7.2 часа | 3.65 дня |
| 99.9% | 43 минуты | 8.7 часа |
| 99.95% | 21.6 минуты | 4.4 часа |
| 99.99% | 4.3 минуты | 52 минуты |
| 99.999% | 26 секунд | 5.3 минуты |

Важно: это budget — можно потратить весь за один инцидент или равномерно.

## Error Budget

```
Error Budget = 1 - SLO

При SLO 99.9% за 30 дней:
  Всего запросов: ~10 млн
  Allowed failures = 10 млн * 0.001 = 10 000
  Allowed downtime = 30 days * 24h * 60m * 0.001 = 43.2 минуты
```

**Error budget policy** — что делать когда бюджет заканчивается:
- > 50% потрачено: внимание, анализ
- > 75% потрачено: приоритизировать reliability задачи
- 100% потрачено: feature freeze, только reliability работы до следующего периода

## Prometheus запрос для SLO

```promql
# SLI: доля успешных запросов за 30 дней
(
  1 - (
    increase(http_requests_total{status=~"5.."}[30d])
    / increase(http_requests_total[30d])
  )
) * 100

# Остаток error budget в %
(
  1 - (
    rate(http_requests_total{status=~"5.."}[30d])
    / rate(http_requests_total[30d])
  )
) / 0.001   # 0.001 = 1 - SLO (0.999)
# > 1.0 = бюджет не потрачен
# < 0.0 = бюджет исчерпан
```

## Burn Rate — скорость сжигания бюджета

```
Burn Rate = 1 означает: бюджет тратится ровно с нужной скоростью
Burn Rate = 2 означает: бюджет закончится вдвое быстрее

При SLO 99.9% и burn rate 14.4:
  Error rate = 14.4 * 0.1% = 1.44%
  Весь месячный бюджет сгорит за 30 / 14.4 = 2.08 дня
```

```promql
# Burn rate за последний час
(
  rate(http_requests_total{status=~"5.."}[1h])
  / rate(http_requests_total[1h])
) / 0.001   # делим на (1 - SLO)
```

## Типичные ошибки при выборе SLO

**Слишком высокий SLO** — команда постоянно нарушает бюджет, нет времени
на features, люди выгорают. Начни с 99.5%, повышай по мере стабилизации.

**Неправильный SLI** — измеряешь не то что важно пользователю.
«Сервер отвечает 200» ≠ «пользователь получил корректный результат».

**Измерять из внутри** — смотришь метрики сервиса, а не клиентский опыт.
Лучше: измерять из load balancer/ingress или с клиентской стороны.

**Нет error budget policy** — SLO есть, но нет договорённости что делать
при исчерпании. Тогда SLO бесполезен.
