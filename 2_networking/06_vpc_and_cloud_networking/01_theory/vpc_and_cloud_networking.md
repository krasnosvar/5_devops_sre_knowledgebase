## 1. VPC: своя изолированная сеть внутри чужого дата-центра

**VPC (Virtual Private Cloud)** — логически изолированный кусок сети облачного провайдера, выделенный только вашему аккаунту. Физически коммутаторы и провода общие с тысячами других клиентов облака, но VPC гарантирует, что ваши пакеты никогда не будут видны или доступны чужим VPC без явного разрешения (peering, см. §5).

Задаётся диапазоном адресов (CIDR-блок), например `10.0.0.0/16` — 65536 адресов, которые вы дальше делите на подсети сами.

## 2. Subnets: public vs private

Подсеть привязана к конкретной зоне доступности (Availability Zone) внутри региона и получает свой кусок CIDR-диапазона VPC (например, `10.0.1.0/24` из `10.0.0.0/16`).

- **Public subnet** — имеет маршрут по умолчанию (`0.0.0.0/0`) на **Internet Gateway** (см. §3). Ресурсы с публичным IP в такой подсети напрямую доступны из интернета.
- **Private subnet** — не имеет прямого маршрута наружу через Internet Gateway. Типичное размещение для баз данных, внутренних сервисов — недоступны напрямую снаружи, но могут ходить в интернет через NAT Gateway (одностороннее исходящее подключение).

Best practice — минимум 2 AZ на каждый тип подсети (для отказоустойчивости при падении одной зоны), и всегда разносить stateful-ресурсы (БД) по private subnets.

## 3. Internet Gateway, NAT Gateway, Route Tables

- **Internet Gateway (IGW)** — компонент VPC, дающий двусторонний доступ в интернет. Прикрепляется к VPC один раз, дальше на него ссылаются route table'ы public-подсетей.
- **NAT Gateway** — работает аналогично SNAT/MASQUERADE (см. [`../../05_iptables_and_nftables/`](../../05_iptables_and_nftables/) §4), но как managed-сервис облака: живёт в public subnet, имеет собственный Elastic IP, и private-ресурсы маршрутизируют через него исходящий (только исходящий!) трафик в интернет.
- **Route Table** — привязана к подсети, определяет, куда идёт трафик по каждому CIDR-назначению. Это ровно тот же принцип longest prefix match, что и в обычной таблице маршрутизации Linux (см. [`../../04_bgp_and_routing/`](../../04_bgp_and_routing/) §1) — просто управляется через API облака, а не `ip route`.

```
Public subnet route table:   10.0.0.0/16 -> local | 0.0.0.0/0 -> Internet Gateway
Private subnet route table:  10.0.0.0/16 -> local | 0.0.0.0/0 -> NAT Gateway
```

## 4. Security Groups vs Network ACL

Частый источник путаницы — два разных механизма фильтрации трафика на разных уровнях:

- **Security Group (SG)** — привязан к конкретному ресурсу (instance, ENI). **Stateful**: если разрешён входящий трафик, ответный исходящий разрешается автоматически (аналог conntrack ESTABLISHED — см. [`../../05_iptables_and_nftables/`](../../05_iptables_and_nftables/) §5), явно прописывать правило на ответ не нужно. Поддерживает только правила **Allow** (нет явного Deny — что не разрешено, то запрещено по умолчанию).
- **Network ACL (NACL)** — привязан к подсети целиком, действует на ВСЕ ресурсы в ней. **Stateless**: входящее и исходящее правило нужно прописывать раздельно и явно, включая правила для ответного трафика. Поддерживает и Allow, и Deny с явным приоритетом по номеру правила.

Практическое следствие: SG обычно достаточно для 95% случаев (проще, меньше шансов на ошибку из-за stateful-природы); NACL добавляют, когда нужно явно ЗАБЛОКИРОВАТЬ конкретный IP/диапазон для всей подсети разом (SG не умеет Deny в принципе).

## 5. VPC Peering и Transit Gateway

- **VPC Peering** — прямое соединение двух VPC (в том числе между разными аккаунтами/регионами) — трафик идёт напрямую, без промежуточных узлов, но топология "каждый с каждым" плохо масштабируется (N VPC требуют `N*(N-1)/2` peering-соединений).
- **Transit Gateway** — центральный хаб, к которому подключаются десятки VPC разом (топология "звезда" вместо "каждый с каждым"), с централизованным управлением маршрутизацией между ними — стандартное решение для организаций с 10+ VPC.

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Ресурс находится в private subnet, но вам нужно, чтобы он мог скачать обновление пакетов из интернета (исходящий трафик), не будучи доступным снаружи. Как это настроить?**
*Ответ:* Добавить в route table приватной подсети маршрут `0.0.0.0/0 -> NAT Gateway` (NAT Gateway при этом располагается в public subnet и имеет собственный Elastic IP). Ресурс сможет инициировать исходящие соединения (пакеты пройдут NAT Gateway, который подменит source IP на свой публичный, аналогично MASQUERADE), но входящие соединения снаружи по-прежнему не смогут достучаться до ресурса напрямую — у него нет ни публичного IP, ни маршрута через Internet Gateway.

**2. В чём принципиальная разница между Security Group и Network ACL, если оба фильтруют трафик по IP/портам?**
*Ответ:* Security Group привязан к конкретному ресурсу и **stateful** — разрешив входящий трафик, вы автоматически разрешаете и ответный исходящий, без отдельного правила; поддерживает только Allow. Network ACL привязан к целой подсети и **stateless** — входящие и исходящие правила надо описывать раздельно и явно (включая правила для ответного трафика), но зато поддерживает явный Deny с приоритетом по номеру правила. NACL нужен, когда требуется явно заблокировать что-то на уровне всей подсети — SG для этого не подходит принципиально, там нет механизма Deny.

**3. Почему при большом количестве VPC (20+) архитекторы переходят с VPC Peering на Transit Gateway?**
*Ответ:* VPC Peering — это связи "точка-точка": чтобы соединить N VPC между собой напрямую, требуется `N*(N-1)/2` отдельных peering-соединений — при росте N число связей растёт квадратично, и управлять маршрутизацией/политиками в такой сетке становится нереально. Transit Gateway меняет топологию на "звезда": каждый VPC подключается только к одному центральному хабу (N соединений вместо квадратичного числа), а маршрутизация между всеми VPC управляется централизованно через этот хаб.

**4. Почему приватная подсеть без NAT Gateway и без маршрута на Internet Gateway всё равно может общаться с ресурсами В ТОЙ ЖЕ VPC, но не может выйти в интернет?**
*Ответ:* Route table подсети всегда содержит "local"-маршрут для CIDR-диапазона всей VPC — он добавляется автоматически при создании VPC и не может быть удалён, поэтому связность внутри VPC (между public и private подсетями, между разными подсетями одной VPC) работает всегда, независимо от наличия NAT/Internet Gateway. Выход же за пределы VPC (в интернет, `0.0.0.0/0`) требует ЯВНОГО маршрута на Internet Gateway (для двустороннего доступа) или NAT Gateway (только исходящий) — без этого маршрута пакеты, адресованные за пределы локального CIDR, просто некуда маршрутизировать.

**5. Ресурс с публичным IP размещён в подсети, у которой route table указывает `0.0.0.0/0` на NAT Gateway (а не на Internet Gateway). Будет ли этот ресурс доступен снаружи по его публичному IP?**
*Ответ:* Нет. Наличие публичного IP само по себе не делает ресурс доступным — маршрутизация решает, куда фактически пойдёт трафик. Если route table подсети направляет весь исходящий (и не имеет входящего пути через Internet Gateway) трафик на NAT Gateway, то по определению это приватная подсеть — публичный IP на ресурсе в такой конфигурации бесполезен и не работает так, как ожидается: входящие пакеты извне не смогут быть корректно маршрутизированы к этому ресурсу, потому что сама VPC-инфраструктура определяет подсеть как приватную через её route table, а не через факт наличия публичного IP у конкретного ресурса.
