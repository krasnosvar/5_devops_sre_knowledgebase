## 1. Netfilter: единый framework под капотом обоих инструментов

И `iptables`, и `nftables` — это не отдельные реализации firewall'а, а разные пользовательские интерфейсы к одному и тому же механизму ядра — **netfilter**: набору хуков (hook points) на пути пакета через сетевой стек, куда можно подвесить свои правила. Ядро вызывает зарегистрированные на хуке правила в строго определённых точках (см. §3) — `iptables`/`nftables` лишь компилируют человекочитаемые правила в структуры, которые netfilter реально исполняет.

## 2. Таблицы и цепочки iptables

- **Таблицы (tables)** — группы правил по назначению: `filter` (разрешить/запретить), `nat` (подмена адресов), `mangle` (модификация пакета), `raw` (до conntrack).
- **Цепочки (chains)** внутри таблиц — привязаны к конкретным точкам пути пакета: `INPUT` (пакет предназначен этому хосту), `OUTPUT` (пакет рождён этим хостом), `FORWARD` (пакет транзитом через этот хост), `PREROUTING`/`POSTROUTING` (до/после принятия решения о маршрутизации).

```bash
iptables -L -v -n --line-numbers          # правила таблицы filter (дефолтная)
iptables -t nat -L -v -n                  # правила таблицы nat
iptables -A INPUT -p tcp --dport 22 -j ACCEPT   # добавить правило в конец цепочки
iptables -I INPUT 1 -p tcp --dport 22 -j ACCEPT # добавить ПЕРВЫМ (порядок важен!)
```

## 3. Порядок обработки пакета: через какие цепочки он реально проходит

```
Входящий пакет, предназначенный этому хосту:
  PREROUTING (nat/mangle/raw) → routing decision → INPUT (filter) → приложение

Входящий пакет, идущий транзитом (форвардинг):
  PREROUTING → routing decision → FORWARD (filter) → POSTROUTING (nat) → наружу

Исходящий пакет, рождённый локальным приложением:
  routing decision → OUTPUT (filter/nat) → POSTROUTING (nat) → наружу
```

Частая ошибка новичков: добавить правило DROP в `INPUT`, ожидая заблокировать транзитный трафик через хост (например, если он работает как роутер/gateway) — но транзитный трафик идёт через `FORWARD`, а не через `INPUT` вообще. `INPUT` видит только пакеты, адресованные ЭТОМУ хосту напрямую.

## 4. NAT: DNAT vs SNAT/MASQUERADE

- **DNAT (Destination NAT)** — подменяет адрес НАЗНАЧЕНИЯ пакета. Классика — port forwarding: внешний запрос на `1.2.3.4:8080` перенаправляется на `10.0.0.5:80` внутри частной сети. Происходит в `PREROUTING` — до того, как ядро решило, куда маршрутизировать пакет.
  ```bash
  iptables -t nat -A PREROUTING -p tcp --dport 8080 -j DNAT --to-destination 10.0.0.5:80
  ```
- **SNAT / MASQUERADE** — подменяет адрес ИСТОЧНИКА. Нужен, чтобы ответ вернулся правильным путём: сервер за NAT видит запрос от внутреннего IP `10.0.0.5`, а не от реального внешнего клиента — обратный пакет, посланный на `10.0.0.5`, никуда не уйдёт наружу, если внутренний адрес не маршрутизируется в интернете. SNAT подменяет source IP на "выходной" адрес роутера ДО отправки пакета наружу (`POSTROUTING`).
  ```bash
  iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
  ```
  `MASQUERADE` — частный случай SNAT для динамического внешнего IP (typичный домашний роутер/VPS с DHCP-адресом): в отличие от чистого `SNAT --to-source X.X.X.X`, MASQUERADE сам узнаёт текущий IP исходящего интерфейса на каждый пакет, не требуя перенастройки при смене адреса.

## 5. conntrack: как ядро помнит про существующие соединения

Netfilter отслеживает состояние каждого соединения через модуль **conntrack** — это то, что позволяет писать правила вида "разрешить входящий трафик, только если он ЧАСТЬ уже установленного соединения":
```bash
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A INPUT -p tcp --dport 22 -j ACCEPT
iptables -A INPUT -j DROP
```
Без этого правила пришлось бы вручную открывать порт для КАЖДОГО возможного ответа на исходящий запрос (например, эфемерные порты для FTP passive mode) — conntrack автоматически "помнит", что этот входящий пакет — ответ на исходящее соединение, которое сам хост инициировал, и пропускает его без явного правила.

```bash
conntrack -L                 # посмотреть текущую таблицу отслеживаемых соединений
cat /proc/sys/net/netfilter/nf_conntrack_max   # максимальный размер таблицы
```
При исчерпании `nf_conntrack_max` (частый инцидент на высоконагруженных NAT-шлюзах) новые соединения начинают тихо отбрасываться ядром без единого явного правила firewall'а, отвечающего за это — диагностировать без знания о существовании conntrack практически невозможно.

## 6. nftables: почему замена, а не просто новая версия

`nftables` — не "iptables 2.0" с тем же синтаксисом, а новый интерфейс к тому же netfilter, спроектированный с нуля:
- Один инструмент вместо четырёх (`iptables`, `ip6tables`, `arptables`, `ebtables`) — nftables работает с любым семейством адресов через единый синтаксис.
- Правила компилируются в собственный псевдокод (BPF-подобный), исполняемый эффективнее, чем последовательный проход по длинному линейному списку правил iptables.
- Атомарная замена всего набора правил разом (`nft -f ruleset.nft`) — не бывает промежуточного "полуприменённого" состояния, которое возможно при накатывании iptables-правил по одному.

```bash
nft list ruleset                          # весь текущий набор правил
nft add table inet filter
nft add chain inet filter input { type filter hook input priority 0 \; }
nft add rule inet filter input tcp dport 22 accept
```

Большинство современных дистрибутивов (начиная с определённых версий) используют nftables "под капотом" даже когда пользователь вызывает команду `iptables` — она стала тонкой совместимой обёрткой (`iptables-nft`) поверх nftables-бэкенда, а не отдельной реализацией.

## 7. Типовые вопросы на собеседовании (Interview Q&A)

**1. Сервер настроен как роутер между двумя сетями. Администратор добавил `iptables -A INPUT -j DROP`, ожидая заблокировать весь транзитный трафик, но трафик между сетями продолжает проходить. Почему?**
*Ответ:* Цепочка `INPUT` обрабатывает только пакеты, адресованные непосредственно этому хосту (его собственным IP-адресам). Транзитный (форвардящийся через хост) трафик проходит через цепочку `FORWARD`, а не `INPUT` — это разные, независимые точки в пути пакета. Чтобы заблокировать транзитный трафик, правило нужно добавлять в `FORWARD`, а не в `INPUT`.

**2. Зачем нужен SNAT/MASQUERADE, если сервер за NAT и так может отправлять пакеты наружу без него?**
*Ответ:* Без SNAT исходящий пакет уходит с исходным (частным, немаршрутизируемым в интернете) IP-адресом источника, например `10.0.0.5`. Внешний сервер получит запрос и попытается отправить ответ обратно на `10.0.0.5` — но этот адрес нигде не маршрутизируется в публичном интернете, ответ никогда не дойдёт. SNAT/MASQUERADE подменяет адрес источника на реальный, маршрутизируемый внешний IP шлюза ДО отправки пакета наружу — тогда ответ приходит на этот внешний IP, и уже conntrack (§5) сопоставляет его с исходным внутренним соединением и доставляет обратно правильному внутреннему хосту.

**3. В чём разница между `SNAT --to-source X.X.X.X` и `MASQUERADE`, если оба меняют исходящий IP на "правильный" внешний адрес?**
*Ответ:* `SNAT --to-source` требует явного указания конкретного, статического IP-адреса в правиле — если внешний IP интерфейса поменяется (DHCP, эластичный IP в облаке), правило перестанет работать и потребует ручного обновления. `MASQUERADE` не хранит статический адрес в правиле вообще — при каждом пакете он динамически узнаёт текущий IP исходящего интерфейса и подставляет его. Это делает `MASQUERADE` предпочтительным выбором именно для интерфейсов с динамическим адресом (типичный домашний роутер, VPS с DHCP), а `SNAT` — для случаев со стабильным, известным заранее IP (обычно чуть эффективнее по производительности, так как не требует смотреть текущий адрес интерфейса на каждый пакет).

**4. На высоконагруженном NAT-шлюзе новые соединения внезапно начинают отбрасываться, хотя ни одно правило iptables не менялось. С чего начать диагностику?**
*Ответ:* Проверить заполненность таблицы conntrack: `conntrack -L | wc -l` и сравнить с `cat /proc/sys/net/netfilter/nf_conntrack_max`. При интенсивном NAT-трафике (множество коротких соединений) таблица отслеживаемых состояний может исчерпаться — ядро начинает молча отбрасывать НОВЫЕ соединения, для которых не может создать запись в conntrack, при этом ни одно явное правило firewall'а не участвует в этом решении, что делает проблему крайне неочевидной без знания о существовании этого лимита.

**5. Почему `nftables` считается архитектурным улучшением, а не просто новым синтаксисом для тех же правил iptables?**
*Ответ:* iptables последовательно проверяет пакет против линейного списка правил одно за другим (`O(n)` в худшем случае для длинных списков), и для каждого семейства адресов (IPv4, IPv6, ARP, Ethernet-мосты) существует ОТДЕЛЬНЫЙ инструмент (`iptables`, `ip6tables`, `arptables`, `ebtables`) с дублирующейся логикой. `nftables` — единый инструмент для всех семейств адресов, компилирующий правила в эффективный псевдокод (byte-code, похожий на BPF), и позволяющий атомарно заменить весь набор правил разом одной командой, без промежуточного "полуприменённого" состояния, которое возможно при последовательном накатывании отдельных iptables-правил.

**6. Разработчик написал правило `iptables -A INPUT -p tcp --dport 443 -j ACCEPT` для веб-сервера, но забыл добавить правило для conntrack ESTABLISHED,RELATED. Что произойдёт с уже установленными HTTPS-соединениями при следующем добавлении DROP-правила в конец цепочки?**
*Ответ:* Правило `ACCEPT` для порта 443 разрешает НОВЫЕ входящие SYN-пакеты на этот порт, но если позже добавлен общий `DROP` в конец цепочки, а между `ACCEPT`-правилом и `DROP` нет явного разрешения для ESTABLISHED-соединений, дальнейшие пакеты уже установленного соединения (не только SYN, но и последующие ACK/данные) могут быть корректно приняты ТОЛЬКО если совпадают с правилом `--dport 443` на каждый отдельный пакет — что технически работает для этого конкретного случая (порт всегда 443), но является анти-паттерном: явное правило `ESTABLISHED,RELATED -j ACCEPT` в начале цепочки — стандартная практика, которая одним правилом покрывает ВСЕ уже разрешённые ранее соединения, независимо от порта, и работает быстрее (conntrack lookup дешевле повторной проверки всех последующих правил).
