## 1. L4 vs L7: где именно принимается решение

- **L4 (транспортный уровень)** — балансировщик смотрит только на IP+порт (5-tuple, см. [`../../00_osi_and_tcpip/`](../../00_osi_and_tcpip/) §5) и перекладывает TCP/UDP-пакеты на один из backend'ов, не разворачивая содержимое. Быстро (минимум overhead), но "вслепую" — не видит ни путь URL, ни заголовки, ни куки.
- **L7 (уровень приложения)** — балансировщик терминирует TCP-соединение полностью, разбирает HTTP (путь, Host-заголовок, куки) и ТОЛЬКО ПОСЛЕ ЭТОГО решает, к какому backend'у открыть новое, отдельное соединение. Умеет маршрутизировать `/api/*` на один сервис, а `/static/*` — на другой, делать A/B-тестирование по заголовку.

Ключевое следствие: L7-балансировщик — это фактически два TCP-соединения (клиент↔LB и LB↔backend), а не одно сквозное — отсюда дополнительная задержка (обычно незначительная), но и дополнительная гибкость.

## 2. Алгоритмы балансировки

- **Round Robin** — по кругу, следующий backend для следующего запроса. Просто, но не учитывает реальную загрузку серверов.
- **Least Connections** — на сервер с наименьшим числом активных соединений. Лучше для долгих/неравномерных запросов (одни клиенты качают большой файл, другие делают лёгкий GET).
- **IP Hash / Consistent Hashing** — backend выбирается по хэшу от IP клиента — один и тот же клиент почти всегда попадает на один и тот же backend (полезно для in-memory кэшей на backend'е, но ломается неравномерно при добавлении/удалении серверов, если хэш не consistent).
- **Weighted** (любой из вышеперечисленных + вес) — сервер помощнее получает больше трафика.

```nginx
upstream backend {
    least_conn;
    server 10.0.0.1:8080 weight=3;
    server 10.0.0.2:8080 weight=1;
}
```

**Ловушка на низком трафике**: в Nginx счётчик round-robin/least-conn — **отдельный на каждый worker-процесс**, не общий на весь сервер. При `worker_processes auto` (по умолчанию — по числу ядер CPU) и небольшом, редком трафике запросы могут разлетаться по разным воркерам, каждый из которых начинает свой цикл заново — на практике это выглядит как "балансировщик почему-то шлёт всё на один backend", хотя конфиг стратегии абсолютно верный. Проявляется только под низкой нагрузкой; под настоящей нагрузкой все воркеры быстро выравниваются статистически. Если нужна детерминированная проверка алгоритма на малом числе запросов (как в лабе этого раздела) — временно выставьте `worker_processes 1`.

## 3. Health checks: активные и пассивные

- **Активные** — балансировщик сам, по расписанию, стучится на `/healthz` каждого backend'а; не отвечает N раз подряд — выводится из ротации.
- **Пассивные** — балансировщик не делает отдельных запросов, а следит за реальным трафиком: если N реальных запросов подряд к backend'у завершились ошибкой/таймаутом, backend временно выводится из ротации (`max_fails`/`fail_timeout` в nginx).

Частая ошибка: healthcheck-эндпоинт сам стучится дальше по цепочке (проверяет БД, кэш, соседние сервисы) — тогда падение ЛЮБОЙ зависимости мгновенно выводит из ротации ВСЕ backend'ы разом (Cascading Failure), хотя сами backend'ы живы и могли бы обслуживать хотя бы часть трафика.

## 4. Sticky sessions и почему их лучше избегать

**Sticky sessions** (session affinity) — балансировщик запоминает (обычно через cookie), какой backend обслуживал клиента в прошлый раз, и направляет туда же снова. Нужны, если приложение хранит состояние сессии в памяти конкретного процесса (а не во внешнем сторе типа Redis).

Проблема: если этот backend упадёт, все "прилипшие" к нему клиенты потеряют сессию целиком (нужно логиниться заново), и балансировка становится неравномерной (сервер, который жил дольше, накопил больше "прилипших" клиентов). Правильное архитектурное решение — вынести состояние сессии во внешнее хранилище (Redis, Memcached) и сделать backend'ы полностью **stateless** — тогда sticky sessions не нужны вообще, любой backend одинаково хорош для любого запроса.

## 5. Reverse Proxy vs Load Balancer — не одно и то же

Термины часто путают, хотя технически это разные роли одного и того же ПО (Nginx, HAProxy, Envoy умеют и то, и другое):
- **Reverse Proxy** — принимает запрос от клиента **от имени** backend'а, может делать одно из: кэшировать, терминировать TLS, сжимать ответ, добавлять заголовки. Backend может быть один единственный.
- **Load Balancer** — распределяет запросы между **несколькими** backend'ами по алгоритму.

Nginx перед одним Django-приложением (терминирует TLS, отдаёт статику) — это reverse proxy без балансировки. Тот же Nginx перед пятью репликами того же приложения с `least_conn` — это уже load balancer (и заодно reverse proxy).

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему L4-балансировщик не может маршрутизировать `/api/v1/*` на один backend, а `/static/*` на другой, хотя оба пути идут на один и тот же порт 443?**
*Ответ:* L4-балансировщик принимает решение по 5-tuple (IP/порт), не разворачивая содержимое TCP-потока — он физически не видит HTTP-путь, потому что путь находится внутри зашифрованного (или хотя бы не разобранного) payload'а, до которого L4 не добирается. Чтобы маршрутизировать по пути URL, нужен L7-балансировщик, который терминирует TLS/TCP полностью, разбирает HTTP-запрос и только тогда решает, куда его направить — открывая новое, отдельное соединение к выбранному backend'у.

**2. В чём опасность healthcheck-эндпоинта, который сам проверяет доступность базы данных перед тем, как ответить `200 OK`?**
*Ответ:* Если БД временно недоступна (сетевой блип, перегрузка), healthcheck начнёт возвращать ошибку СРАЗУ у ВСЕХ backend'ов одновременно (они все стучатся в одну и ту же БД) — балансировщик выведет из ротации сразу весь пул серверов, хотя сами backend-процессы живы и часть эндпоинтов (не требующих БД) могли бы продолжать отвечать. Это превращает частичный сбой зависимости в полный отказ всего сервиса (Cascading Failure). Healthcheck обычно должен проверять только то, что сам процесс жив и готов принимать трафик (liveness), а не всю цепочку зависимостей.

**3. Приложение хранит сессию пользователя в оперативной памяти процесса и использует sticky sessions на балансировщике. Что произойдёт при плановом rolling-обновлении (по одному backend'у за раз)?**
*Ответ:* Когда балансировщик выводит backend из ротации для обновления, все клиенты, "прилипшие" к этому конкретному backend'у, теряют доступ к своей сессии в памяти этого процесса — при следующем запросе их перенаправят на другой backend, где этой сессии нет, и приложение потребует повторной аутентификации. Правильное решение — вынести хранение сессии во внешний stateless store (Redis), чтобы rolling update не зависел от того, к какому конкретно backend'у "прилип" клиент.

**4. Чем Reverse Proxy архитектурно отличается от Load Balancer, если оба термина часто применяют к одному и тому же серверу (например, Nginx)?**
*Ответ:* Это про роль, а не про конкретный софт. Reverse Proxy — сервер, принимающий запрос от имени backend'а (может делать TLS termination, кэширование, сжатие) вне зависимости от того, сколько backend'ов за ним стоит — хоть один. Load Balancer — сервер, распределяющий трафик между НЕСКОЛЬКИМИ backend'ами по алгоритму (round robin, least connections). Один и тот же Nginx может быть чистым reverse proxy (один backend) или одновременно reverse proxy + load balancer (несколько backend'ов, есть алгоритм выбора).

**5. Почему consistent hashing (а не обычный hash от IP по модулю числа серверов) считается более правильным алгоритмом для кэширующих backend'ов при динамическом масштабировании пула?**
*Ответ:* Обычный `hash(client_ip) % N` при изменении `N` (добавили/убрали сервер) пересчитывает результат практически для ВСЕХ клиентов сразу — почти каждый клиент внезапно попадает на другой backend, теряя локальность кэша целиком. Consistent hashing размещает и серверы, и клиентов на одном хэш-кольце так, что при добавлении/удалении ОДНОГО сервера перераспределяется только доля ключей, соответствующая этому серверу (примерно `1/N` клиентов), а не все клиенты сразу — резко снижая "перетасовку" кэша при масштабировании.
