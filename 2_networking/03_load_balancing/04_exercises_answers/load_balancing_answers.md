# Ответы — упражнения по балансировке нагрузки

## Ответ 01
```
backend1, backend2, backend3, backend1, backend2, backend3, backend1, backend2, backend3
```
Ровно 3/3/3 — с `worker_processes 1` у nginx единственный внутренний счётчик состояния upstream'а, поэтому `least_conn` (при равных 0 активных соединениях у всех) ведёт себя предсказуемо циклически.

## Ответ 02
После `docker compose stop backend2` первая же попытка достучаться до него завершается ошибкой соединения; `max_fails=2 fail_timeout=10s` в конфиге означает, что после 2 неудачных попыток backend2 исключается из ротации на 10 секунд — оставшиеся запросы идут только на backend1/backend3 (проверено: реально видно чередование только этих двух). После `docker compose start backend2` backend всё ещё считается "в бане" до истечения полного `fail_timeout` — **3-4 секунды ожидания недостаточно**, нужно выждать полные 10+ секунд, иначе backend2 не появится в ответах, хотя контейнер уже физически поднят и отвечает.

## Ответ 03
Если `/healthz` каждого backend'а сам стучится в общую БД, а БД легла — ВСЕ backend'ы одновременно начнут проваливать healthcheck (они все зависят от одной и той же упавшей БД), и балансировщик выведет из ротации весь пул разом: `502 Bad Gateway` для 100% пользователей, хотя сами backend-процессы живы и, возможно, могли бы обслужить хотя бы часть запросов (например, эндпоинты, не требующие БД, или отдавать закэшированные данные). Текущий `/healthz` (`return 200` без проверок) свободен от этой проблемы — он проверяет только "жив ли сам процесс nginx/приложения", а не здоровье всей цепочки зависимостей, поэтому падение БД не каскадируется на доступность самого сервиса.

## Ответ 04
Без sticky sessions один и тот же клиент может попасть на любой из N backend'ов на каждый следующий запрос — если счётчик хранится в памяти конкретного процесса (обычная переменная), у клиента будет N разных, независимо растущих (или обнуляющихся) счётчиков вместо одного правильного. Два архитектурных решения: (а) sticky sessions — заставить клиента всегда попадать на тот же backend, но это ломается при падении этого backend'а (см. теорию §4) и неравномерно распределяет нагрузку; (б) правильное решение — вынести счётчик во внешнее хранилище (Redis `INCR`), сделав backend полностью stateless — тогда неважно, какой backend обработал запрос, состояние всегда одно и то же для всех.

## Ответ 05
С `worker_processes 4` первые несколько запросов часто прилетают на один и тот же backend (например, 4 подряд на backend1), и только затем распределение начинает выравниваться — потому что у каждого из 4 воркеров nginx свой независимый счётчик round-robin/least-conn, и на малом числе последовательных запросов какие-то воркеры принимают несколько запросов подряд, пока остальные вообще не задействованы. Это не баг конфигурации — это описанное в теории (§2) реальное поведение nginx: балансировка становится статистически честной только под настоящей, параллельной нагрузкой, а не на десятке последовательных curl-запросов.
