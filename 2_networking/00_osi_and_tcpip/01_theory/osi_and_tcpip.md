## 1. OSI vs TCP/IP: зачем два разных стека

**OSI (7 уровней)** — это академическая эталонная модель, придуманная для стандартизации ДО того, как реальные протоколы победили. Её никто не реализует буквально, но её терминологией пользуется вся индустрия ("L4 firewall", "L7 load balancer").

**TCP/IP (4 уровня)** — это то, что реально работает в проде:
- **Application** (HTTP, DNS, gRPC) — соответствует OSI L5-L7.
- **Transport** (TCP, UDP) — OSI L4.
- **Internet** (IP, ICMP) — OSI L3.
- **Link** (Ethernet, ARP) — OSI L1-L2.

Практическая польза модели — не в зазубривании 7 уровней, а в **локализации проблемы**: "не резолвится DNS" — это L7, "нет маршрута" — L3, "порт закрыт" — L4, "кабель не воткнут / нет линка" — L1-L2. Диагностика всегда идёт снизу вверх: `ip link` (L1-2) → `ip route`/`ping` (L3) → `ss`/`nc` (L4) → `curl`/`dig` (L7).

## 2. Инкапсуляция: как данные проходят через уровни

Когда приложение вызывает `send()`, данные оборачиваются в заголовки сверху вниз, каждый уровень добавляет свой конверт:

```
[ HTTP payload ]
[ TCP header | HTTP payload ]                    ← порт назначения/источника, seq/ack
[ IP header | TCP header | HTTP payload ]         ← IP назначения/источника, TTL
[ Ethernet header | IP header | ... | FCS ]       ← MAC назначения/источника
```

На принимающей стороне процесс идёт в обратном порядке (декапсуляция): сетевая карта смотрит MAC, ядро смотрит IP (себе ли пакет), затем порт TCP/UDP (какому сокету отдать), и только потом байты payload'а долетают до `read()` в приложении. Важное следствие: L7 load balancer (Nginx, Envoy) должен полностью терминировать TCP-соединение и **распаковать** его до HTTP, чтобы посмотреть путь/хост — L4 balancer этого не делает, он просто перекладывает пакеты, не разворачивая их.

## 3. TCP: three-way handshake и почему он нужен

```
Client                          Server
  |------ SYN (seq=x) ---------->|
  |<--- SYN-ACK (seq=y,ack=x+1) --|
  |------ ACK (ack=y+1) --------->|
  |         [соединение установлено]
```

Handshake решает конкретную задачу: обе стороны должны согласовать **начальные номера последовательности (ISN)** — на их основе строится вся дальнейшая логика надёжности (какие байты уже доставлены, что нужно ретрансплитить). Пока не завершены все три шага, соединение не в состоянии `ESTABLISHED` — приложение не получит ни байта данных.

```bash
# посмотреть реальный handshake
tcpdump -i any -n 'tcp[tcpflags] & (tcp-syn|tcp-ack) != 0' -c 6

# состояния TCP-соединений на хосте
ss -tan state syn-sent
ss -tan state established
```

**SYN flood** (DoS-атака) эксплуатирует именно этот механизм: атакующий шлёт тысячи SYN, не отвечая на SYN-ACK, сервер держит их в очереди полуоткрытых соединений (backlog), пока не кончится память под неё. Защита — `SYN cookies` (ядро не хранит состояние до получения финального ACK, а зашифровывает его прямо в SYN-ACK).

## 4. TCP vs UDP: за что вы платите надёжностью

- **TCP**: гарантирует доставку (retransmit), порядок байтов (seq numbers), контроль перегрузки (congestion control — замедляется, если сеть перегружена). Цена — задержка (handshake) и оверхед заголовков (20+ байт против 8 у UDP).
- **UDP**: "выстрелил и забыл" — ни гарантии доставки, ни порядка. Зато нет handshake (на 1 RTT быстрее) и нет буферизации на приёме.

Почему DNS исторически ходит по UDP (см. [`../../01_dns/`](../../01_dns/)): запрос+ответ помещаются в один пакет, задержка handshake не оправдана для микросекундного запроса. Почему видеозвонки/игры на UDP: устаревший кадр видео бесполезен, ждать его ретрансмита хуже, чем просто потерять и показать следующий — TCP в этой ситуации только тормозит (Head-of-Line Blocking).

## 5. Sockets: как процесс получает доступ к сети

Сокет — это файловый дескриптор (см. [`../../../1_linux_and_shell/03_file_descriptors_and_io/`](../../../1_linux_and_shell/03_file_descriptors_and_io/)), через который процесс говорит с сетевым стеком ядра. Связка, которая однозначно определяет TCP-соединение — **5-tuple**: `(протокол, src IP, src port, dst IP, dst port)`. Именно поэтому один и тот же порт `:80` на сервере может одновременно обслуживать тысячи клиентов — уникальность обеспечивает вся пятёрка, а не только порт назначения.

```bash
# какие процессы держат какие сокеты
ss -tlnp                  # слушающие TCP-сокеты + PID/имя процесса
ss -tnp state established # активные соединения

# curl 100 раз к одному порту — увидеть разные src port у каждого соединения
```

## 6. MTU и фрагментация

**MTU (Maximum Transmission Unit)** — максимальный размер пакета на канальном уровне, обычно 1500 байт для Ethernet. Если IP-пакет крупнее MTU следующего хопа, он либо фрагментируется (режется на части, каждая с копией IP-заголовка), либо, если стоит флаг `DF` (Don't Fragment), отбрасывается с ICMP `Fragmentation Needed`.

Это не абстракция — это ежедневная головная боль в оверлейных сетях (VXLAN в k8s CNI, VPN): туннель добавляет свои заголовки (VXLAN — 50 байт), и если внутренний MTU не уменьшен, пакеты на границе туннеля либо фрагментируются (просадка производительности), либо тихо теряются, если где-то на пути заблокирован ICMP (Path MTU Discovery black hole — классика: TCP handshake проходит нормально маленькими пакетами, а большие HTTP-ответы зависают).

```bash
ip link show eth0 | grep mtu        # текущий MTU интерфейса
ping -M do -s 1472 8.8.8.8          # 1472+28(IP+ICMP)=1500 — проверка без фрагментации
```

## 7. Типовые вопросы на собеседовании (Interview Q&A)

**1. Приложение зависает при передаче больших файлов через VPN, хотя маленькие запросы (типа `curl -I`) проходят мгновенно. В чём может быть причина?**
*Ответ:* Классический признак Path MTU Discovery black hole. VPN-туннель добавляет свои заголовки, уменьшая эффективный MTU. Маленькие пакеты (handshake, HEAD-запрос) укладываются в любой MTU и проходят. Большие пакеты превышают MTU промежуточного узла; тот должен вернуть ICMP `Fragmentation Needed, DF set`, чтобы отправитель уменьшил размер пакетов. Если где-то по пути ICMP заблокирован файрволом, отправитель никогда не узнаёт о проблеме и просто ждёт ретрансмита до таймаута. Решение — либо разрешить ICMP, либо явно понизить MSS/MTU на туннельном интерфейсе.

**2. Почему TCP использует three-way handshake, а не two-way (SYN → ACK)?**
*Ответ:* Two-way handshake не даёт клиенту подтверждения, что сервер действительно получил его начальный sequence number и готов его использовать. Third ACK от клиента подтверждает серверу, что клиент видел и принял ISN сервера — только после этого обе стороны синхронизированы в обе стороны (full-duplex). Без третьего шага возможна ситуация, когда сервер думает, что соединение установлено (отправил SYN-ACK), а клиент из-за потери пакета так и не подтвердил — server держит "полуоткрытое" соединение впустую.

**3. В чём разница между `ss -tan state established` и `ss -tan state syn-sent` с точки зрения диагностики проблемы?**
*Ответ:* `established` показывает полностью рабочие соединения — если проблема здесь, дело не в сети, а в приложении (медленно отвечает, зависло). `syn-sent` показывает попытки подключения, застрявшие на первом шаге handshake — это значит, что SYN либо не долетает до сервера (файрвол, нет маршрута), либо сервер не отвечает SYN-ACK'ом (порт не слушается, перегружен backlog). Это разные классы проблем: L7-приложение vs L3/L4-связность.

**4. Почему DNS в основном использует UDP, а не TCP, хотя UDP не гарантирует доставку?**
*Ответ:* Типичный DNS-запрос и ответ малы и помещаются в один пакет — гарантии TCP (ретрансмит, порядок) избыточны для такого обмена, а лишний RTT на handshake ощутимо замедлил бы КАЖДЫЙ DNS-запрос (а их за секунду просвистывают сотни). Если ответ не помещается в UDP-пакет (большие DNSSEC-записи, зонные передачи AXFR), DNS автоматически переключается на TCP — оба протокола поддерживаются одновременно, UDP по умолчанию для скорости.

**5. Что произойдёт с TCP-соединением, если на пути пропадёт сеть на 2 минуты, а потом появится снова?**
*Ответ:* TCP не имеет встроенного "heartbeat" по умолчанию (если не включён `TCP keepalive`). Отправитель, не получив ACK на отправленные пакеты, начнёт экспоненциально увеличивать интервалы ретрансмита. Если keepalive выключен и приложение не пишет активно в сокет, соединение может формально "висеть" в состоянии `ESTABLISHED` на обеих сторонах сколь угодно долго, хотя фактически мертво — обнаружить это можно только при попытке записи (вернёт ошибку после исчерпания ретраев) или явно включив `SO_KEEPALIVE`.

**6. Приложение открывает тысячи исходящих соединений к одному и тому же серверу с одного и того же хоста. Какое реальное ограничение вы упрётесь первым?**
*Ответ:* Диапазон исходящих (эфемерных) портов — обычно 28232-32768 записей (~28000-60000 в зависимости от `net.ipv4.ip_local_port_range`). Поскольку соединение уникально идентифицируется 5-tuple, а IP-адреса и порт назначения фиксированы, единственная переменная — src port клиента, и его не хватит на большее количество одновременных соединений. Это классическая проблема исчерпания портов (port exhaustion) при агрессивном connection pooling без keep-alive/переиспользования соединений.

**7. Почему увеличение MTU интерфейса иногда УХУДШАЕТ производительность вместо улучшения?**
*Ответ:* Jumbo frames (MTU 9000) снижают оверхед заголовков на большой объём данных внутри одной сети (меньше пакетов на тот же объём — меньше interrupt'ов CPU). Но если MTU не согласован end-to-end (например, промежуточный сетевой узел или другой сервер в той же L2-сети настроен на 1500), пакеты либо фрагментируются на границе (дополнительный оверхед хуже исходного), либо тихо дропаются без ICMP в некорректно настроенных сетях — то есть выигрыш применим только внутри полностью согласованного jumbo-frame сегмента, не end-to-end через интернет.
