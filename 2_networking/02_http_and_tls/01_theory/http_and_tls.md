## 1. HTTP/1.1: keep-alive и Head-of-Line Blocking

HTTP/1.0 открывал новое TCP-соединение (см. [`../../00_osi_and_tcpip/`](../../00_osi_and_tcpip/) §3) на каждый запрос — дорого при десятках ресурсов на странице. HTTP/1.1 ввёл **keep-alive** (`Connection: keep-alive`) — одно TCP-соединение переиспользуется для нескольких запросов подряд.

Проблема: запросы в одном соединении обрабатываются **строго последовательно** (запрос №2 не может начать выполняться, пока не завершится ответ на №1) — это и есть **Head-of-Line (HoL) Blocking** на уровне приложения. Браузеры обходили это, открывая 6-8 параллельных TCP-соединений к одному хосту — что само по себе дорого (каждое соединение — свой TCP handshake + slow start).

## 2. HTTP/2: мультиплексирование и его цена

HTTP/2 решает HoL Blocking на уровне HTTP: множество запросов и ответов передаются **одновременно** внутри ОДНОГО TCP-соединения, разбитые на кадры (frames) с идентификатором потока (stream ID) — сервер и клиент перемежают кадры разных потоков и собирают их обратно по ID. Больше не нужно 6 параллельных соединений — один канал эффективно используется полностью.

Цена: HTTP/2 мультиплексирует на уровне HTTP, но под ним всё ещё TCP. Если теряется **один TCP-сегмент**, TCP не может доставить приложению ничего из данных, идущих ПОСЛЕ него в очереди — даже если эти данные относятся к другому, совершенно независимому HTTP/2-потоку. Так HoL Blocking переезжает с уровня приложения на уровень транспорта — и полностью не исчезает, просто становится куда менее заметным.

## 3. HTTP/3 и QUIC: почему ушли с TCP на UDP

HTTP/3 решает проблему §2 радикально: полностью отказывается от TCP и строит **QUIC** — протокол поверх UDP, реализующий надёжность (ретрансмиты, порядок) сам, в user space, отдельно **для каждого потока**. Если теряется пакет одного потока — тормозит только он, остальные потоки того же соединения продолжают идти. TCP решает это на уровне всего соединения сразу, QUIC — на уровне каждого потока в отдельности.

Дополнительный бонус QUIC: TLS встроен внутрь самого протокола (а не является отдельным уровнем поверх TCP, как в HTTP/1.1 и HTTP/2 с TLS) — handshake одновременно устанавливает и транспорт, и шифрование за меньшее число round-trip'ов.

```bash
curl -I --http2 https://example.com     # проверить, что сервер отвечает по HTTP/2
curl -I --http3 https://example.com     # HTTP/3 — если сервер и curl его поддерживают
```

## 4. TLS handshake: как устанавливается шифрованный канал

Упрощённо (TLS 1.3, современный минимум round-trip'ов):
```
Client                                  Server
  |--- ClientHello (поддерживаемые шифры, keyshare) --->|
  |<-- ServerHello + сертификат + keyshare -------------|
  |          [обе стороны вычисляют общий секрет]
  |--- Finished ----------------------------------------->|
  |          [канал зашифрован, начинается HTTP-трафик]
```
Ключевая идея — **асимметричная криптография используется только для установления общего симметричного ключа** (Diffie-Hellman keyshare), а весь дальнейший трафик шифруется симметрично (AES) — она на порядки быстрее асимметричной и годится для потокового шифрования гигабайт данных.

```bash
# посмотреть детали TLS-хендшейка вручную
openssl s_client -connect example.com:443 -tls1_3 </dev/null 2>/dev/null | head -20
```

## 5. Сертификаты и цепочка доверия

Сертификат сервера подписан не сам собой (тогда любой мог бы выписать себе сертификат для чужого домена), а **промежуточным CA (Certificate Authority)**, чей сертификат, в свою очередь, подписан **корневым CA**, встроенным в доверенное хранилище ОС/браузера. Проверка — восходящая цепочка подписей до корня, которому клиент доверяет изначально:

```
Root CA (встроен в ОС/браузер, доверяем "по умолчанию")
  └─ Intermediate CA (подписан Root CA)
       └─ example.com сертификат (подписан Intermediate CA)
```

Доменная валидация (DV, как у Let's Encrypt) подтверждает только владение доменом (см. [`../../01_dns/`](../../01_dns/) §6 про DNS-01 challenge) — не личность организации. Organization Validation (OV) и Extended Validation (EV) требуют реальной юридической проверки компании.

## 6. Кэширование: заголовки, которые реально экономят RTT

- `Cache-Control: max-age=3600` — браузер/CDN может отдавать ресурс из локального кэша ближайший час, вообще не обращаясь к серверу.
- `ETag` / `If-None-Match` — сервер выдаёт "отпечаток" версии ресурса; при повторном запросе клиент присылает его обратно, и если ресурс не менялся, сервер отвечает `304 Not Found` **без тела** — экономит трафик, но не RTT (запрос всё равно уходит на сервер).
- `Cache-Control: no-store` vs `no-cache` — частая путаница: `no-cache` разрешает кэшировать, но требует ревалидации (ETag-проверки) перед каждой отдачей; `no-store` запрещает сохранять вообще (используется для чувствительных данных).

## 7. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему HTTP/2 не полностью решает проблему Head-of-Line Blocking, хотя и вводит мультиплексирование потоков?**
*Ответ:* HTTP/2 мультиплексирует запросы на уровне приложения (HTTP), но под ним по-прежнему работает один TCP-поток. TCP гарантирует байтам порядок доставки: если теряется один сегмент, все данные, идущие после него в TCP-очереди (даже принадлежащие другому, независимому HTTP/2-потоку), не могут быть доставлены приложению, пока потерянный сегмент не будет ретранслирован. HoL Blocking не исчезает, а переезжает с уровня HTTP на уровень транспорта.

**2. В чём принципиальное архитектурное отличие HTTP/3 от HTTP/2, решающее проблему из вопроса 1?**
*Ответ:* HTTP/3 отказывается от TCP как транспорта и строится поверх QUIC — протокола на базе UDP, который реализует надёжность (ретрансмиты, порядок доставки) самостоятельно, отдельно для каждого потока. Если теряется пакет одного потока, ретрансмит и связанная задержка касаются только этого потока — остальные независимые потоки того же QUIC-соединения продолжают доставляться без задержки.

**3. Зачем TLS-хендшейк использует асимметричную криптографию только на этапе установления соединения, а не для шифрования всего трафика?**
*Ответ:* Асимметричная криптография (RSA, ECDHE) на порядки медленнее симметричной (AES) на больших объёмах данных. Поэтому TLS использует асимметричную схему (Diffie-Hellman key exchange) только для того, чтобы обе стороны безопасно согласовали ОБЩИЙ симметричный ключ, даже если канал прослушивается — а весь дальнейший HTTP-трафик шифруется уже быстрым симметричным алгоритмом с этим согласованным ключом.

**4. Браузер показывает ошибку "certificate not trusted" для внутреннего корпоративного сайта, хотя сертификат технически валиден и не просрочен. Наиболее вероятная причина?**
*Ответ:* Сертификат, скорее всего, выпущен внутренним (self-signed или корпоративным) CA, чей корневой сертификат не установлен в доверенное хранилище браузера/ОС клиента. Цепочка доверия проверяется восходящим образом до Root CA, которому клиент доверяет по умолчанию (обычно это публичные CA вроде Let's Encrypt, DigiCert). Если корневой сертификат внутреннего CA не добавлен вручную в систему клиента, браузер не может выстроить цепочку доверия до известного корня и считает сертификат недоверенным, даже если он технически корректно подписан и не просрочен.

**5. В чём разница между DV (Domain Validation), OV (Organization Validation) и EV (Extended Validation) сертификатами с точки зрения того, что они реально гарантируют?**
*Ответ:* Все три типа одинаково шифруют трафик — разница только в том, что именно CA проверяет перед выпуском. DV (например, Let's Encrypt) подтверждает только факт контроля над доменом (через HTTP-01/DNS-01 challenge, см. `01_dns` §6) — не проверяя, кто вы такие. OV дополнительно проверяет юридическое существование организации. EV требует наиболее строгой юридической верификации компании. Технической разницы в стойкости шифрования между ними нет — разница исключительно в уровне проверки личности владельца сертификата.

**6. Клиент получает `304 Not Modified` в ответ на запрос ресурса. Означает ли это, что запрос вообще не дошёл до сервера?**
*Ответ:* Нет, запрос дошёл до сервера — это частое заблуждение. Клиент отправил заголовок `If-None-Match` со значением `ETag`, полученным ранее. Сервер сравнил присланный ETag с текущей версией ресурса, увидел совпадение (ресурс не менялся) и вернул `304` БЕЗ тела ответа — экономится передача данных (трафик), но не сам факт обращения к серверу (задержка на round-trip всё равно присутствует). Это отличается от `Cache-Control: max-age`, при котором браузер вообще не обращается к серверу, пока не истечёт `max-age`.
