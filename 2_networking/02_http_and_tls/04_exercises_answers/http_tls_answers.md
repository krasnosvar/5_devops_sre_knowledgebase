# Ответы — упражнения HTTP и TLS

## Ответ 01
```
HTTP/2 200
```
Без `-k` curl проверяет цепочку доверия сертификата (см. теорию §5) до корневого CA из системного хранилища. Наш сертификат self-signed — подписан сам собой, а не встроенным в ОС корневым CA — поэтому curl откажется подключаться с ошибкой `SSL certificate problem: self-signed certificate`. `-k` явно отключает эту проверку (только для лабы — никогда не делайте так в проде).

## Ответ 02
Первый запрос с правильным (текущим) ETag вернёт `304 Not Modified` без тела. После изменения `html/index.html` файл получит новый `Last-Modified`/`ETag`, и повторный запрос со **старым** ETag вернёт `200` с новым телом — сервер видит, что присланный клиентом ETag не совпадает с текущим, и отдаёт актуальную версию целиком.

## Ответ 03
Проверено экспериментом: если `Cache-Control` объявлен на уровне `server`, а `location /` объявляет СВОЙ `add_header X-Debug` — в финальном ответе `Cache-Control` пропадает, остаётся только `X-Debug`. Это фундаментальное поведение nginx: `add_header` не аккумулируется вверх по уровням, если текущий уровень вложенности сам объявляет хотя бы одну директиву `add_header` — тогда наследуются ТОЛЬКО директивы этого уровня, а всё, что задано выше, полностью игнорируется. Правильная практика — держать все нужные `add_header` на одном уровне (как в исходном `nginx.conf`, где `Cache-Control` явно продублирован в `location /`).

## Ответ 04
```
HTTP/1.1 301 Moved Permanently
Location: https://localhost/
```
Код `301` (постоянный редирект) — браузеры и некоторые клиенты закэшируют этот редирект и в будущем сразу пойдут на HTTPS, даже не спрашивая HTTP-версию снова. `Location` указывает на тот же путь, но со схемой `https://` — за счёт переменной `$host$request_uri` в конфиге редиректа.
