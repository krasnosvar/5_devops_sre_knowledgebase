## 1. Дерево DNS: от корня до A-записи

DNS — иерархическая распределённая база данных, а не один большой сервер. Дерево читается справа налево: `www.example.com.` — это `.` (root) → `com` (TLD) → `example.com` (домен) → `www` (хост).

Разрешение `www.example.com` с нуля (без кэша) — это цепочка запросов:
```
Резолвер → Root server:        "кто обслуживает .com?"     → NS для .com
Резолвер → .com TLD server:    "кто обслуживает example.com?" → NS для example.com
Резолвер → example.com NS:     "какой A у www.example.com?"  → 93.184.216.34
```
Каждый уровень знает только про своих прямых "детей" — root-серверы ничего не знают про `www.example.com`, только про то, кто отвечает за `.com`.

## 2. Recursive resolver vs Authoritative server

Это разные роли, и их частая путаница — источник многих багов:

- **Recursive resolver** (8.8.8.8, 1.1.1.1, DNS вашего роутера) — делает всю цепочку запросов из §1 **за клиента** и кэширует результат. Клиентское приложение обращается только к нему.
- **Authoritative server** — хранит реальные записи конкретной зоны (например, NS-сервер example.com, куда вы прописали A-запись в панели регистратора). Он не делает рекурсивных запросов сам, только отвечает за свою зону.

```bash
# Спросить рекурсивный резолвер (как это делает обычное приложение)
dig www.example.com

# Спросить authoritative-сервер зоны напрямую, в обход резолвера и кэша
dig @a.iana-servers.net example.com

# Проследить всю цепочку от root вручную
dig +trace www.example.com
```

## 3. Типы записей: не только A

- **A / AAAA** — имя → IPv4 / IPv6.
- **CNAME** — имя → другое имя (алиас). Нельзя сосуществовать с другими записями на том же имени (RFC-ограничение) — частая причина "CNAME can't coexist with other records".
- **MX** — куда слать почту для домена, с приоритетом.
- **TXT** — произвольный текст: SPF/DKIM для антиспама, верификация владения доменом (Let's Encrypt DNS-01, Google Search Console).
- **NS** — кто authoritative-сервер для (под)зоны — именно эти записи и формируют дерево делегирования.
- **SRV** — имя+протокол → хост+порт (используется, например, для service discovery).

## 4. Кэширование и TTL

Каждая запись несёт TTL (в секундах) — сколько времени резолвер имеет право отдавать её из кэша, не переспрашивая authoritative-сервер. Это прямой компромисс между скоростью (высокий TTL — меньше запросов, быстрее ответы) и скоростью распространения изменений (низкий TTL — быстрее подхватывается смена IP при инцидентах).

**Практическое SRE-правило**: перед плановой миграцией (смена IP, blue/green на уровне DNS) TTL нужно **заранее** (за время, равное старому TTL) понизить до минимума — иначе часть клиентов будет ходить по старому адресу ещё сутки после переключения, потому что уже закэшировала запись со старым TTL.

```bash
dig example.com +noall +answer      # покажет текущий TTL записи
```

## 5. DNS в контейнерах и Kubernetes (кратко)

Внутри контейнера DNS настраивается через `/etc/resolv.conf` (nameserver, search domains). В Kubernetes каждый под получает `resolv.conf`, указывающий на **CoreDNS** — внутрикластерный DNS-сервер, который резолвит `service.namespace.svc.cluster.local` в ClusterIP, а для внешних имён проксирует запрос дальше, во внешний резолвер. Подробный разбор Service discovery и Headless Service — в [`../../../4_kubernetes/03_networking/`](../../../4_kubernetes/03_networking/).

## 6. DNSSEC: зачем подписывать записи

Обычный DNS-ответ ничем не защищён от подмены — атакующий на пути (или скомпрометированный резолвер) может вернуть поддельный IP (DNS spoofing/cache poisoning), и клиент никак не проверит подлинность. **DNSSEC** добавляет криптографическую подпись к записям зоны (RRSIG) и цепочку доверия от корня (DS-записи у родителя, подтверждающие ключ ребёнка) — резолвер может математически проверить, что ответ действительно пришёл от владельца зоны и не был подменён по пути. Не шифрует сам ответ (это по-прежнему открытый текст) — только гарантирует подлинность и целостность.

## 7. Типовые вопросы на собеседовании (Interview Q&A)

**1. Вы сменили IP-адрес сервера в A-записи, но часть пользователей всё ещё ходит на старый IP через 12 часов после изменения. Почему, и как этого избежать в следующий раз?**
*Ответ:* Резолверы пользователей закэшировали старую запись на срок её TTL (например, 24 часа) и имеют полное право не переспрашивать authoritative-сервер до истечения этого времени. Правильная процедура миграции: заранее (минимум за время, равное текущему TTL) понизить TTL записи до минимального значения (например, 60 секунд), подождать, пока старый TTL истечёт у всех резолверов, и только потом менять сам IP — тогда переключение распространится быстро.

**2. В чём разница между рекурсивным резолвером и authoritative-сервером — и почему `dig @8.8.8.8 mycompany-internal.local` не найдёт внутренний домен, а `dig @ns1.mycompany.com mycompany-internal.local` может найти?**
*Ответ:* Публичный рекурсивный резолвер (8.8.8.8) идёт по публичному дереву DNS от корня и не знает ничего про приватные внутренние зоны, которые нигде не делегированы публично. Внутренний authoritative-сервер компании (`ns1.mycompany.com`), если он настроен обслуживать эту зону, ответит напрямую — при условии, что клиент имеет к нему сетевой доступ (обычно только из внутренней сети/VPN).

**3. Почему нельзя создать CNAME-запись на корне зоны (`example.com`), только на поддомене (`www.example.com`)?**
*Ответ:* На корневом имени зоны обязательно должны существовать записи типа `SOA` и `NS` (описывающие саму зону), а по правилам DNS (RFC 1034) CNAME запрещено сосуществовать с любыми другими записями на том же имени — CNAME значит "все запросы к этому имени переадресуй на другое", и совмещать это с "а ещё здесь NS-запись" протокол не позволяет. Для корня зоны в таких случаях используют ALIAS/ANAME (нестандартное расширение некоторых DNS-провайдеров) или прямую A-запись.

**4. DNS-запрос для маленькой A-записи идёт по UDP, но при запросе DNSSEC-подписанной записи резолвер вдруг переключается на TCP. Почему?**
*Ответ:* Стандартный UDP-пакет DNS ограничен (исторически 512 байт, с EDNS0 — до нескольких KB). DNSSEC добавляет к ответу криптографическую подпись (RRSIG), которая заметно увеличивает размер ответа — если итоговый пакет не помещается в UDP (или на пути есть фрагментация/MTU-ограничения), сервер возвращает флаг `TC` (truncated), и резолвер по протоколу обязан повторить тот же запрос по TCP, где ограничения на размер намного мягче.

**5. Вы поменяли TTL записи с 24 часов на 60 секунд прямо перед миграцией и сразу выключили старый сервер. Часть трафика всё равно продолжает идти на старый IP. Что упущено?**
*Ответ:* Понижение TTL само по себе не заставляет уже закэшированные (со старым, длинным TTL) записи у резолверов пользователей обновиться раньше времени — резолверы продолжат отдавать из кэша старую запись до истечения ЕЁ (старого) TTL, даже если authoritative-сервер уже отдаёт новую запись с новым TTL. Правильный порядок: сначала понизить TTL и ПОДОЖДАТЬ, пока истечёт старый TTL по всему интернету, и только потом менять сам IP/выключать старый сервер.

**6. Как DNSSEC защищает от подмены ответа, если сам ответ по-прежнему передаётся открытым текстом (без шифрования)?**
*Ответ:* DNSSEC не решает задачу конфиденциальности (кто угодно на пути всё ещё видит, какое имя резолвится) — он решает задачу **целостности и подлинности**. Каждая запись в подписанной зоне сопровождается криптографической подписью (RRSIG), а цепочка DS-записей от родительской зоны к дочерней позволяет резолверу проверить подпись математически, восходя до корня (который все резолверы доверяют изначально). Если атакующий подменит ответ (DNS spoofing), подпись не совпадёт, и резолвер отклонит поддельный ответ как невалидный — даже не зная заранее правильный IP.
