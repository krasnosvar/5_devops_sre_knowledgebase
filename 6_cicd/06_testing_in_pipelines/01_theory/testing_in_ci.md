## 1. Пирамида тестирования в CI пайплайнах

Архитектура пайплайна должна строиться по принципу "Fail Fast" (Упади как можно раньше). Нельзя запускать тяжелые 30-минутные браузерные тесты, если код даже не компилируется.
1. **Unit-тесты (Юнит)**: Основа пирамиды. Сотни тестов (на уровне функций Java/Python). Не обращаются к базе данных или сети. Все зависимости замоканы (Mock). Выполняются за миллисекунды. Запускаются при каждом пуше.
2. **Интеграционные тесты**: Проверяют связки (например, логику SQL запросов к реальной БД). Занимают минуты.
3. **E2E (End-to-End)**: Вершина пирамиды. Разворачивается полный стенд (Фронтенд + Бэкенд + БД). Эмулируется клик пользователя в браузере. Занимают десятки минут. Часто запускаются только перед релизом (на ветке main).

## 2. Статический анализ кода (SAST) и SonarQube

До (или параллельно) с Unit-тестами запускается статический анализ. Он вообще не выполняет код, он парсит его как текст (AST-деревья).
**SonarQube** — индустриальный стандарт для проверки качества кода.
- Ищет "Code Smells" (дублирование кода, слишком длинные функции, неиспользуемые переменные).
- Считает **Coverage (Покрытие)** — процент строк кода, по которым пробежались Unit-тесты.
- Ищет Security уязвимости (SAST) (например, конкатенация SQL-строк, ведущая к SQL Injection).
*Quality Gate (Врата качества)*: SonarQube может заблокировать CI пайплайн (остановить деплой), если покрытие тестами нового кода (New Code) меньше 80% или найдена критическая уязвимость.

## 3. Интеграционные тесты и Testcontainers

Классическая проблема интеграционных тестов: скриптам нужна реальная база данных PostgreSQL для тестирования.
Где ее взять в CI? Если поднять одну общую БД где-то на сервере, два параллельных пайплайна очистят таблицы друг друга (Race Condition).
**Решение — Testcontainers (библиотека для Java/Python/Go)**.
Она использует Docker API (в CI нужен Docker-out-of-Docker). В самом коде теста (на Java) вы пишете класс `PostgreSQLContainer`. При запуске теста библиотека сама на лету поднимет изолированный Docker-контейнер с БД, пробросит случайный порт, передаст Credentials тесту. Тест выполнит SQL запросы, проверит результат. При завершении теста библиотека сама убьет и удалит контейнер. Максимальная изоляция!

## 4. E2E (End-to-End) тесты: Selenium и Cypress

Эти тесты симулируют реального человека в браузере.
В CI/CD (например, GitLab CI) для E2E тестов разворачивают эфемерное (временное) окружение — **Review Apps**. На каждый Pull Request динамически создается namespace в Kubernetes (с базой и бекендом).
Тестовые фреймворки (Cypress или Selenium/Playwright) запускаются в режиме `headless` (без графического интерфейса GUI, используя эмулятор браузера Chromium в фоне). Они ходят по URL временного стенда, кликают "Добавить в корзину" и проверяют появление элемента. После прохождения тестов (и аппрува PR), временный namespace в k8s уничтожается для экономии ресурсов.

## 5. Нагрузочное тестирование в CI (k6 / JMeter)

Обычно нагрузочное тестирование (Performance) делают редко, перед большими релизами. Но современный подход — выявлять "Деградацию производительности" прямо в пайплайнах.
Инструменты вроде **k6** (написан на Go, скрипты на JS) интегрируются в CI.
Вы пишете скрипт, который подает 100 RPS (Requests Per Second) на API. В пайплайне настраиваются пороги (Thresholds). Если новая версия кода начала отдавать ответ за `500ms` (а по требованиям `p(95) < 200ms`), k6 возвращает Exit Code 1 и проваливает пайплайн. Это предотвращает выкатку медленного кода в продакшен.

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Объясните концепцию "Shift-Left Testing". Почему важно сдвигать тесты влево?**
*Ответ:* "Сдвиг влево" означает перенос тестирования и проверок безопасности (SAST, SCA) на самые ранние этапы цикла разработки (написание кода, первый коммит, Pull Request) — то есть в левую часть пайплайна. Традиционно тестирование проводилось "справа" (на стадии Release или перед Prod). Исправление бага, найденного на этапе QA (когда код уже слит с другими ветками), стоит в 10 раз дороже и дольше по времени, чем исправление того же бага, найденного линтером или Unit-тестом прямо в IDE разработчика или за минуту в CI.

**2. Ваш интеграционный пайплайн падает, потому что два разработчика одновременно пушат код, и их CI-джобы используют общую базу данных для тестов, перетирая данные друг друга (Race Condition). Как SRE решают эту проблему?**
*Ответ:* Использовать статичную разделяемую инфраструктуру (Shared DB) для тестов в CI — это фундаментальный антипаттерн (Stateful tests). Решение состоит в изоляции тестовых сред: 1) В старом подходе: использовать GitLab Services (Docker-compose-like), поднимая базу данных (Service контейнер) рядом с каждой джобой локально. 2) В современном подходе: Разработчики должны переписать тесты с использованием паттерна **Testcontainers**. Тестовый фреймворк сам поднимет изолированный Docker-контейнер с чистой базой данных на случайном порту эксклюзивно для конкретного прогона тестов, а затем уничтожит его.

**3. Что такое Quality Gate (Врата качества) в SonarQube и как они блокируют плохой код в пайплайне?**
*Ответ:* Quality Gate — это набор жестких метрик (условий), которым должен соответствовать код, чтобы пройти проверку. Например: "Покрытие нового кода (Coverage) >= 80%", "0 критических уязвимостей", "Меньше 5 Code Smells". В пайплайне (после этапа сборки) запускается Sonar-сканер. Он отправляет код на сервер SonarQube, который анализирует его и вычисляет метрики. Пайплайн (через webhook или polling) ждет статуса `Quality Gate`. Если условия не выполнены, статус возвращается как `FAILED`, и джоба CI завершается с ошибкой (Exit code 1), не позволяя мержить Pull Request.

**4. В чем разница между SAST, DAST и SCA в контексте безопасности пайплайнов (DevSecOps)?**
*Ответ:* 
- **SAST (Static Application Security Testing)**: Анализирует *исходный код* (как текст) на уязвимости (SQL-иньекции, переполнения буфера) без его запуска. Интегрируется рано в пайплайне (SonarQube).
- **DAST (Dynamic Application Security Testing)**: Атакует *запущенное* приложение (внешний black-box тест). Пытается отправить вредоносные HTTP-запросы (XSS) на развернутый тестовый стенд.
- **SCA (Software Composition Analysis)**: Анализирует `package.json` или `pom.xml`. Ищет устаревшие OpenSource библиотеки (зависимости), в которых найдены известные уязвимости (CVE). (Инструменты: Trivy, Snyk).

**5. Разработчики жалуются, что CI пайплайн идет 45 минут из-за E2E тестов в Cypress. Как DevOps инженер может кардинально ускорить это время?**
*Ответ:* Главная проблема E2E тестов — они выполняются строго последовательно в одном браузере. Решение — **Распараллеливание (Parallelization / Test Sharding)**. Большинство CI платформ (GitLab, GitHub Actions) поддерживают Matrix-сборки или Node-сплиттинг. Вы запускаете 5 параллельных джоб-раннеров. Тестовый фреймворк (или CI скрипт) разбивает 100 E2E тестов на 5 шардов (по 20 тестов). Раннеры выполняют их одновременно. В итоге время выполнения сокращается с 45 минут до 9 минут (ценой увеличения вычислительных ресурсов раннеров).

**6. Зачем собирать Code Coverage (Покрытие кода тестами)? Означает ли показатель 100% покрытия, что в приложении нет багов?**
*Ответ:* Code Coverage показывает процент строк кода в приложении, которые были затронуты (выполнены) во время прогона Unit-тестов. Он выявляет слепые зоны ("Мертвый код" или ветки `if/else`, которые никогда не тестировались). Однако 100% покрытие **не гарантирует** отсутствие багов. Оно говорит лишь о том, что код был выполнен. Разработчик мог написать тест, который вызывает функцию, но "забыть" написать `assert` (проверку правильности результата). Логические ошибки (бизнес-логика) покрытие кода не находит.

**7. Как тестировать микросервисы в изоляции (Unit/Integration), если микросервис А при запуске требует обязательного ответа от микросервиса B? Поднимать оба в пайплайне?**
*Ответ:* Поднимать десятки зависимых микросервисов в CI тяжело и долго (это E2E подход). Для изолированного тестирования микросервиса А используют **Mocks/Stubs** (заглушки) или более продвинутый паттерн **Contract Testing (Pact)**. Контрактное тестирование гарантирует, что микросервис А отправляет HTTP-запрос в правильном формате, а микросервис В (тестируется отдельно в своем пайплайне) возвращает ответ строго по контракту (JSON-схеме). Тестирование идет без физического развертывания соседних систем, опираясь только на контракты (API Specifications).

**8. В чем суть паттерна "Review Apps" (Эфемерные окружения) в GitLab CI? Для тестирования какого этапа пирамиды они критически важны?**
*Ответ:* Review Apps — это динамическое создание копии всей вашей инфраструктуры (приложения, БД) специально для каждого отдельного Pull Request'а (обычно в изолированном k8s namespace с уникальным URL `pr-123.example.com`). Они критически важны для вершины пирамиды — **E2E тестов** (Selenium, Cypress) и ручного приемочного тестирования (UAT) продакт-менеджерами. Когда PR вливается в main (или закрывается), GitLab триггерит джобу `stop_review`, которая уничтожает эти ресурсы облака.

**9. Что такое `headless` режим браузера и зачем он нужен в CI/CD для UI-тестов?**
*Ответ:* Браузеры (Chrome, Firefox) обычно требуют графического окружения (X11, Wayland) и видеокарты для отрисовки окошек. Серверы-раннеры CI/CD работают в консольном режиме Linux (сервера без мониторов). Запуск браузера с графикой там упадет с ошибкой. `Headless` (безголовый) режим заставляет движок браузера (Chromium) выполнять рендеринг HTML/CSS, запускать JavaScript и симулировать клики исключительно в оперативной памяти (в фоне), без попытки отрисовать реальные пиксели на экране. Это позволяет гонять Cypress/Selenium-тесты в консольных CI-контейнерах.

**10. Почему при интеграции нагрузочного тестирования (Load Testing, например, JMeter или k6) в CI-пайплайн, результаты (RPS, Latency) могут сильно "скакать" (флуктуации) между сборками, вызывая ложные срабатывания (Flaky pipelines)?**
*Ответ:* Нагрузочное тестирование критически зависит от качества железа, сети и соседних процессов ("шумные соседи"). Если ваш CI-раннер развернут в публичном облаке на Shared CPU (например, AWS T3 инстансы с кражей ресурсов — Steal Time), или на том же узле внезапно запустилась тяжелая компиляция Java от другой команды, скрипт `k6` получит меньше процессорного времени. Он сгенерирует меньше запросов, а задержки (Latency) вырастут. Пайплайн упадет. Для стабильных Perfomance-тестов в CI нужны выделенные (Dedicated) раннеры на Bare-Metal или Dedicated EC2 инстансах со стабильной сетью и изоляцией.
