## 1. Где заканчивается CI и начинается GitOps (CD)?

В парадигме GitOps граница между CI (Интеграция) и CD (Развертывание) строго проведена:
- **CI пайплайн (GitHub Actions, GitLab CI)**: Собирает код, гоняет Unit/SAST тесты, компилирует Docker-образ и пушит его в Registry (например, `harbor.myorg/app:v1.2`). *На этом работа CI-инструмента заканчивается. Он не делает `helm upgrade`!*
- **Промежуточный шаг (Bridge)**: CI-пайплайн (или бот Image Updater) делает **Git Commit** в репозиторий с манифестами инфраструктуры, меняя в конфигурации версию образа с `v1.1` на `v1.2`.
- **CD (ArgoCD / Flux)**: Внутренний агент в кластере (Pull-модель) замечает новый коммит в Git-репозитории с манифестами, скачивает их и синхронизирует состояние кластера k8s.

## 2. Паттерны разделения репозиториев (App Repo vs Ops Repo)

Хранение исходного кода на Python (App) и k8s-манифестов (Ops) в одном Git-репозитории — это антипаттерн (хотя допустимо для пет-проектов).
**SRE Стандарт — Two-Repo Pattern**:
1. **App Repo**: Только код (Java/Go), тесты и Dockerfile. Здесь работает CI.
2. **Infra/Ops Repo**: Только YAML-манифесты (Kustomize/Helm) и настройки ArgoCD. Здесь работает CD.
*Почему?* Разделение доступа (разработчикам не обязательно иметь право править Helm-чарты продакшена). Разрыв бесконечных циклов: если CI делает коммит с новой версией образа в тот же App Repo, это может снова триггернуть CI пайплайн (infinite loop).

## 3. Продвижение (Promotion) между средами: Dev -> Stage -> Prod

Как правильно катить версию приложения по окружениям (Promotion) в GitOps, если нет кнопок пайплайнов?
Это делается через архитектуру веток (Branches) или папок (Directories) в Ops-репозитории.
**Паттерн Директорий (Environment Folders)** (Предпочтительный вариант):
В Ops-репозитории лежат 3 папки: `envs/dev`, `envs/stage`, `envs/prod`.
- CI пайплайн обновляет тег образа `v1.2` только в файле `envs/dev/kustomization.yaml`. ArgoCD выкатывает это на Dev кластер.
- QA-команда тестирует Dev. Дает аппрув.
- SRE или бот создает Pull Request: копирует изменения (тег `v1.2`) из `dev` в папку `envs/stage`. После аппрува PR, ArgoCD применяет его на Stage.

## 4. Kustomize и Helm в связке с GitOps

GitOps-агенты (ArgoCD, Flux) не обязаны использовать сырые YAML. Они отлично интегрируются с шаблонизаторами.
Частый SRE-паттерн: **Kustomize поверх Helm**.
У вас есть базовый (Generic) Helm-чарт, который лежит в отдельном репозитории (или публичном). Вы не модифицируете сам чарт для каждого окружения. Вместо этого в Ops-репозитории в папке `envs/prod` лежит `kustomization.yaml`, который:
1. Декларирует `helmCharts` (скачать чарт и подсунуть ему `values-prod.yaml`).
2. Использует механизмы патчей (patches) Kustomize, чтобы наложить уникальные метки или инжектировать sidecar-контейнеры (Datadog) поверх отрендеренного Helm'ом YAML перед тем, как ArgoCD применит это в k8s.

## 5. Откат (Rollback) в парадигме GitOps

В традиционном CD при поломке продакшена вы нажимали в GitLab кнопку `Rollback` на предыдущую джобу.
В GitOps источник истины — это Git.
Если новая версия `v1.2` сломала Prod-базу данных, ваш откат — это **`git revert`** (откат коммита) в Ops-репозитории (в ветке/папке продакшена). Вы делаете revert, тег образа в Git меняется обратно на `v1.1`. ArgoCD видит дифференц, моментально синхронизирует кластер, и Kubernetes сам делает Rolling Update подов на старую стабильную версию. Инфраструктурный аудит (почему и кто откатил) навсегда остается в истории Git.

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему хранение манифестов Kubernetes (Helm-чартов) в том же репозитории, что и исходный код приложения (Mono-repo), считается антипаттерном в GitOps?**
*Ответ:* Главная причина — разделение жизненных циклов (Separation of Concerns). 1) Безопасность: Вы не можете выдать разработчику права на merge в код (App repo), не выдав ему заодно права на изменение архитектуры Prod-кластера (Ops repo). 2) Аудит: История коммитов смешивается (сложно понять, где правили фичу, а где увеличили CPU Limit). 3) Триггеры: Механизм обновления тега образа требует совершения коммита ботом. Если бот коммитит в App-repo, это часто триггерит повторный запуск всего CI-пайплайна сборки кода, создавая цикл (Infinite loop).

**2. Объясните, как происходит "Promotion" (продвижение) релиза от Dev к Prod в GitOps (ArgoCD), если там нет кнопок "Deploy" в интерфейсе пайплайна?**
*Ответ:* В GitOps продвижение релиза (Promotion) — это операция над **Git-деревом**. Если используется паттерн директорий (Environment Directories), продвижение — это создание Pull Request (Merge Request), который переносит (копирует) обновление тега Docker-образа из файла `kustomization.yaml` папки `dev/` в файл папки `prod/`. Review (одобрение) этого PR выступает в роли преграды (Manual Approval). Как только PR влит в `main`, ArgoCD замечает обновление папки `prod/` и выкатывает релиз в Production.

**3. Как в GitOps (Flux/ArgoCD) автоматизировать коммиты новых версий образов, чтобы не заставлять CI-пайплайн делать `git commit` с bash-скриптами (что усложняет CI)?**
*Ответ:* Для этого используются специализированные контроллеры (например, `ArgoCD Image Updater` или `Flux Image Automation Controller`). Эти демоны живут внутри кластера Kubernetes. Они регулярно опрашивают (polling) Docker Registry (Harbor/ECR) по заданному regex (например, `v1.2.*`). Когда они видят публикацию нового образа, они **сами** клонируют Ops-репозиторий, меняют YAML файл, делают `git commit -m "Update image"` и пушат обратно в Git (операция Write-back).

**4. Вы случайно нажали кнопку `Sync` в UI ArgoCD с включенной галочкой `Prune`. ArgoCD удалил из кластера важный ConfigMap. Можно ли восстановить его из Git?**
*Ответ:* Нельзя. ArgoCD (и концепция GitOps в целом) оперирует однонаправленным потоком (One-way sync): от Git к Кластеру. Если ConfigMap был удален из Git-репозитория, и ArgoCD синхронизировал удаление (Prune), данные потеряны навсегда (спасет только инфраструктурный бэкап типа Velero). GitOps защищает от Дрейфа (ручных изменений в кластере), но он слепо верит Git-репозиторию как абсолютному Источнику Истины.

**5. Разработчик через `kubectl edit deployment` изменил лимиты CPU на проде, спасая приложение от OOM. В GitOps-репозитории лимиты старые. Что произойдет через 3 минуты (по дефолту)?**
*Ответ:* ArgoCD / Flux выполнит свой цикл сверки (Reconciliation loop) и обнаружит расхождение (Configuration Drift). Статус приложения станет `OutOfSync`. Дальнейшее поведение зависит от настроек. Если включен режим `Self-Heal` (Автоисцеление), GitOps-агент **безжалостно затрет (overwrite)** спасительные лимиты разработчика старыми значениями из Git, вернув OOM. Правильный паттерн (Day-2 Ops) — делать изменения спасения прямо через экстренный коммит в Git, а не руками в кластере.

**6. Зачем использовать Kustomize поверх Helm-чарта в ArgoCD? Разве Helm сам по себе не достаточно мощный шаблонизатор?**
*Ответ:* Helm мощный, но он ограничен тем, что заложил автор чарта. Если вы скачали сторонний чарт базы данных (например, от Bitnami), а вам нужно добавить к StatefulSet нестандартный sidecar-контейнер для сбора логов или кастомную аннотацию (которой нет в `values.yaml`), вы не сможете этого сделать без форка всего чарта (что ломает обновления). Связка "Kustomize поверх Helm" позволяет ArgoCD сначала отрендерить чужой Helm-чарт, а затем с помощью Kustomize `patches` наложить сверху ваши хирургические изменения (JSON Patch) перед деплоем в кластер.

**7. Как в GitOps реализовать Canary Deployments (Канареечный релиз), если `kubectl apply` не поддерживает постепенное распределение трафика?**
*Ответ:* Сам по себе ArgoCD занимается только синхронизацией манифестов (Deployment -> Pods). Для продвинутых стратегий (Canary, Blue/Green) используется специализированный контроллер **Argo Rollouts**. В Git вы коммитите объект `Rollout` (вместо `Deployment`). В нем прописаны шаги (Steps): направить 10% трафика, ждать анализ метрик, направить 50%. Argo Rollouts интегрируется с Ingress Controllers (Nginx, Istio, ALB) и сам управляет весами трафика на стороне кластера, опираясь на метрики из Prometheus.

**8. У вас мульти-кластерная архитектура (10 кластеров по всему миру). Как с помощью ArgoCD задеплоить одно приложение на все 10 кластеров, не копипастя 10 манифестов `Application` в Git?**
*Ответ:* Использовать паттерн **ApplicationSet** (Генератор приложений). Это CRD контроллер в экосистеме ArgoCD. Вы пишете один базовый манифест `ApplicationSet`. В нем настраивается `Generator` (например, Cluster Generator, который читает список подключенных кластеров из секретов ArgoCD, или Git Generator, читающий папки). Контроллер автоматически динамически "разожмет" этот шаблон и сгенерирует 10 обычных `Application`, параметризовав их URL'ами целевых кластеров. Добавление 11-го кластера произойдет автоматически без написания YAML.

**9. В чем отличие "Hard" и "Soft" Multitenancy в ArgoCD, если им пользуются 5 независимых команд разработки?**
*Ответ:* Soft Multitenancy (Мягкая) достигается встроенной системой RBAC ArgoCD. Вы создаете "Проекты" (`AppProject`) и даете команде А права синхронизировать приложения только в Namespace `team-a`. Проблема в том, что ArgoCD контроллер всё равно работает с высокими правами (ClusterAdmin), и изоляция только логическая на уровне UI/API. Hard Multitenancy (Жесткая) — это запуск отдельного инстанса ArgoCD (ArgoCD Core) в каждом Namespace команды (Namespaced-scope). В этом случае контроллеры ArgoCD физически не имеют прав выхода за пределы своего неймспейса на уровне k8s RBAC, что защищает от эксплойтов повышения привилегий.

**10. Почему при использовании Sealed Secrets (или SOPS) в GitOps, манифесты с паролями можно безопасно держать даже в публичном репозитории GitHub?**
*Ответ:* Sealed Secrets применяет асимметричную криптографию. В открытом доступе хранится (публичный ключ контроллера. С помощью этого ключа вы локально шифруете пароль. Полученный YAML (SealedSecret) содержит криптографический мусор. Расшифровать его математически можно **только** с помощью Приватного ключа (Private Key). Приватный ключ жестко зашит внутри кластера Kubernetes (в оперативной памяти контроллера Sealed Secrets) и никогда не покидает периметр. Если хакер склонирует GitHub репо, без доступа к кластеру он не сможет получить пароль.
