## 1. Что такое GitOps (кратко) и где граница с CI

**GitOps** — способ доставки, при котором желаемое состояние кластера
описано в Git, а агент внутри кластера (ArgoCD или Flux) постоянно
сверяет кластер с Git и применяет изменения сам. Для CI это значит одно:
пайплайн больше не деплоит, он **меняет Git**.

Граница проходит так:
- **CI-пайплайн (GitLab CI, GitHub Actions)** собирает код, гоняет тесты,
  собирает образ и пушит его в registry (`registry.example.com/app:3f2c1a9`).
- **Мост**: CI (или контроллер обновления образов в кластере) делает
  коммит в репозиторий с манифестами — меняет тег образа.
- **CD (ArgoCD / Flux)**: агент видит новый коммит и синхронизирует
  кластер. Как именно — см.
  [4_kubernetes/09_gitops](../../../4_kubernetes/09_gitops/).

## 2. Push vs Pull с точки зрения пайплайна

**Push** (классический CD): джоба держит kubeconfig/облачные права и
выполняет `kubectl apply` или `helm upgrade`. Пайплайн видит результат
сразу (`kubectl rollout status`) и падает, если раскатка не удалась.
Цена — у CI есть права на запись в продакшен-кластер.

**Pull** (GitOps): джоба держит только токен на запись в Ops-репозиторий.
Что меняется для пайплайна:
- **Права**: вместо kubeconfig — токен Git с минимальными правами
  (Project Access Token / deploy key на один репозиторий).
- **Результат**: зелёная джоба означает «коммит в Git сделан», а не
  «приложение работает». Если нужен статус раскатки, пайплайн отдельно
  ждёт агента (`argocd app wait <app> --health`, `flux events`) или
  агент сам сообщает статус обратно (ArgoCD Notifications, Flux
  notification-controller пишут commit status в GitLab/GitHub).
- **Повтор**: перезапуск джобы не «передеплоит» — если тег в Git не
  изменился, коммитить нечего, агент ничего не сделает.

## 3. Паттерны разделения репозиториев (App Repo vs Ops Repo)

Хранить код приложения и манифесты окружений в одном репозитории можно
для пет-проектов, но в командах обычно применяют **Two-Repo Pattern**:
1. **App Repo**: код, тесты, Dockerfile. Здесь работает CI.
2. **Ops Repo**: только манифесты (Kustomize overlays / Helm values) по
   окружениям. Отсюда читает GitOps-агент.

*Почему?*
- **Доступ**: право мержить код ≠ право менять прод-окружение.
- **Аудит**: история Ops-репо — это чистая история релизов.
- **Нет бесконечного цикла**: если CI коммитит новый тег в тот же App
  Repo, этот коммит снова запускает CI. В отдельный Ops Repo — нет.

## 4. Обновление тега образа из CI

Есть два способа «перевести» новый образ в Git:
1. **CI делает коммит** (рассмотрен здесь): после `docker push` джоба
   клонирует Ops-репо, выполняет `kustomize edit set image` (или `yq` по
   `values.yaml`) и пушит. Плюс — явная связь «коммит кода → коммит
   релиза» в одном пайплайне.
2. **Контроллер в кластере** (ArgoCD Image Updater, Flux Image
   Automation) сам следит за registry и коммитит. CI тогда только пушит
   образ. Подробно — [4_kubernetes/09_gitops](../../../4_kubernetes/09_gitops/).

Практика для варианта 1 (см.
[../02_examples/.gitlab-ci-gitops.yml](../02_examples/.gitlab-ci-gitops.yml)):
- **Неизменяемые теги**: `$CI_COMMIT_SHORT_SHA` или semver, никогда
  `latest` — иначе в Git нечего менять и откат невозможен. Ещё строже —
  фиксировать digest (`app@sha256:...`).
- **Минимальный токен**: Project Access Token только на Ops-репо,
  `write_repository`; не личный токен инженера.
- **Гонки**: десять сервисов коммитят в один Ops-репо одновременно —
  `git push` отклоняется (non-fast-forward). Решение: `git pull --rebase`
  и повтор, плюс сериализация (`resource_group` в GitLab, `concurrency`
  в GitHub Actions).
- **Идемпотентность**: если тег уже стоит, `git commit` упадёт с
  «nothing to commit» — это нужно либо считать ошибкой (повторный запуск
  того же коммита), либо явно проверять `git diff --quiet`.

## 5. Продвижение (Promotion) между средами: Dev -> Stage -> Prod

Кнопок «Deploy to prod» в пайплайне нет — продвижение делается
изменением Git. Предпочтительный паттерн — **папки окружений** в
Ops-репо: `envs/dev`, `envs/stage`, `envs/prod`.
- CI обновляет тег только в `envs/dev/kustomization.yaml` (прямой коммит).
  Агент выкатывает это на dev.
- После проверки dev CI (ручная джоба) или бот создаёт **Merge Request**,
  который переносит тот же тег в `envs/stage`. Ревью MR — это и есть
  ручной аппрув; после мержа агент выкатывает stage.
- Prod — так же, отдельным MR, обычно с Protected Branch и обязательными
  ревьюерами.

Альтернатива — ветки на окружение (`dev`/`stage`/`prod`) — хуже:
окружения расходятся, мержи между ветками тянут лишние изменения.

## 6. Откат (Rollback) в парадигме GitOps

Источник истины — Git, поэтому откат — это **`git revert`** коммита с
тегом в папке нужного окружения Ops-репо. Тег возвращается к `v1.1`,
агент синхронизирует кластер, Kubernetes делает Rolling Update назад.
Кто и почему откатил — остаётся в истории Git.

Ловушка для CI: старая джоба «redeploy previous version» в пайплайне
App-репо, которая делает `kubectl set image`, ломает модель — агент
увидит drift и вернёт состояние из Git (если включён self-heal).

## 7. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему CI-бот, коммитящий новый тег образа, не должен коммитить в тот же
репозиторий, где лежит код приложения?**
*Ответ:* Коммит бота в App Repo сам является событием `push` и снова запускает
CI-пайплайн: сборка → новый тег → новый коммит → новая сборка (бесконечный
цикл). Его можно разорвать `[skip ci]` или `rules`, но остаются другие проблемы:
смешанная история (фичи вперемешку с релизами), права (кто может мержить код,
тот может менять прод). Отдельный Ops Repo решает все три.

**2. Объясните, как происходит "Promotion" (продвижение) релиза от Dev к Prod в
GitOps, если там нет кнопок "Deploy" в пайплайне?**
*Ответ:* Продвижение — это операция над Git. При паттерне папок окружений это
Merge Request, переносящий тег образа из `envs/dev/kustomization.yaml` в
`envs/stage/` (затем в `envs/prod/`). Одобрение MR — и есть ручной аппрув; после
мержа агент выкатывает версию. CI может автоматизировать создание MR (ручная
джоба вызывает API), но не сам мерж в prod.

**3. Как автоматизировать коммиты новых версий образов, чтобы не писать в CI
bash-скрипты с `git commit`? Какие у этого минусы?**
*Ответ:* Использовать контроллер в кластере: ArgoCD Image Updater или Flux Image
Automation. Он опрашивает registry, по правилу (semver/regex) находит новый тег
и делает write-back коммит в Git. Минусы: контроллеру нужен доступ на запись в
Git и чтение registry; связь «какой коммит кода дал этот релиз» становится
неявной; опрос registry добавляет задержку. Поэтому многие команды оставляют
коммит тега в CI.

**4. Почему тег `latest` не работает в GitOps-пайплайне?**
*Ответ:* GitOps-агент реагирует на изменения в Git. Если в манифесте всегда
`image: app:latest`, Git не меняется — агенту нечего синхронизировать, поды не
перезапускаются (а при `IfNotPresent` нода ещё и держит старый образ из кэша).
Откат через `git revert` тоже невозможен: в истории нет предыдущей версии. Нужны
неизменяемые теги (SHA коммита, semver) или digest.

**5. Десять микросервисов одновременно завершили сборку и пушат новые теги в
один Ops-репозиторий. Часть джоб падает с `rejected (non-fast-forward)`. Как
исправить?**
*Ответ:* Каждая джоба клонировала репо до чужого пуша, поэтому её `main`
устарел. Решение: при отказе делать `git pull --rebase` и повторять push
(ограниченное число раз), так как сервисы меняют разные файлы и конфликтов нет.
Дополнительно — сериализовать пуши (`resource_group` в GitLab, `concurrency`
group в GitHub Actions) или разнести сервисы по разным Ops-репо.

**6. Джоба `update-dev` зелёная, но приложение на dev не обновилось. Где
искать?**
*Ответ:* Зелёная джоба означает только «коммит в Git сделан». Дальше по цепочке:
дошёл ли коммит до нужной ветки/папки, которую читает агент (`path`,
`targetRevision`); увидел ли его агент (интервал опроса, webhook); прошла ли
синхронизация (статус `OutOfSync`/`Degraded`, ошибки рендера Kustomize/Helm);
совпадает ли имя образа в `kustomize edit set image` с `images[].name` — при
несовпадении тег молча не применяется ни к одному контейнеру.

**7. Какие права должен иметь токен, которым CI пушит в Ops-репозиторий?**
*Ответ:* Минимальные: токен уровня проекта (Project Access Token, deploy key с
write, fine-grained PAT в GitHub) только на Ops-репо, только на запись в
репозиторий (и API, если CI создаёт MR). Не личный токен инженера (уволится —
сломается пайплайн, плюс права на всё). Переменная — Masked и Protected, чтобы
её не получили джобы из feature-веток. Ветку `envs/prod` защищают так, чтобы бот
мог только создавать MR, но не мержить.

**8. Как пайплайну узнать, что раскатка через ArgoCD действительно прошла, если
CI в кластер не ходит?**
*Ответ:* Два варианта. 1) Пайплайн ждёт сам: `argocd app wait myapp-dev --health
--timeout 300` (нужен токен ArgoCD API с правом только на чтение этого
приложения). 2) Обратный канал: ArgoCD Notifications или Flux
notification-controller ставят commit status в GitLab/GitHub, и MR/коммит
показывает результат синхронизации. Второй вариант лучше сочетается с
pull-моделью: CI не получает доступа к кластеру.

**9. Ночью прод сломался, дежурный в пайплайне App-репо перезапустил старую
джобу `deploy`, которая делает `kubectl set image` на предыдущую версию. Через 3
минуты всё снова сломалось. Почему?**
*Ответ:* В Ops-репо по-прежнему записана новая (сломанная) версия. Агент с
включённым self-heal увидел расхождение кластера и Git (drift) и вернул
состояние из Git. Правильный откат — `git revert` коммита с тегом в `envs/prod`
(или срочный MR), после чего агент сам откатит кластер. Старые push-джобы деплоя
после перехода на GitOps нужно удалить.

**10. Зачем фиксировать в манифестах digest образа (`app@sha256:...`), если тег
уже уникальный (SHA коммита)?**
*Ответ:* Тег в registry изменяем: его можно перезаписать `docker push` с тем же
тегом (случайно или при атаке на registry), и кластер получит другой образ при
том же манифесте. Digest — хеш содержимого манифеста образа, он однозначно
определяет байты. CI знает digest после `docker push`/`buildx --push` и может
записать его в Ops-репо; подпись образа (cosign) тоже привязывается к digest.
