## 1. Архитектура: Workflows, Jobs и Steps

В GitHub Actions структура пайплайна описывается в YAML файлах в директории `.github/workflows/`.
Иерархия строится так:
- **Workflow (Рабочий процесс)**: Триггерится событиями (`push`, `pull_request`, `schedule`, `workflow_dispatch` для кнопок).
- **Jobs (Задания)**: По умолчанию выполняются **параллельно** на разных раннерах (серверах). Вы можете сделать их последовательными через `needs: [job1]`. Каждая джоба — это чистая свежая ВМ.
- **Steps (Шаги)**: Выполняются строго **последовательно** внутри одной джобы (на одном сервере). Шаг может быть либо bash-скриптом (`run: make build`), либо вызовом готового Action (`uses: actions/checkout@v4`).

## 2. Marketplace и Custom Actions (Composite, Docker, JS)

Киллер-фича GitHub — это Marketplace. Вам не нужно писать bash-скрипты для установки Python или настройки AWS ключей, вы используете готовые компоненты (Actions).
Например: `uses: actions/setup-node@v4`.
Вы можете писать свои переиспользуемые Actions тремя способами:
1. **Composite**: Обычный набор `steps` в отдельном файле, который можно вызывать из разных репозиториев (самый частый паттерн для DRY).
2. **Docker**: GitHub скачает ваш образ, запустит контейнер и передаст туда параметры. Работает только на Linux-раннерах.
3. **JavaScript (Node.js)**: Работают быстрее Docker, кросс-платформенные (Windows, macOS), но требуют написания кода на JS/TS.

## 3. Self-hosted Runners (ARC - Actions Runner Controller)

По умолчанию GitHub дает свои ВМ (GitHub-hosted runners: Ubuntu, macOS, Windows). Они бесплатны, но медленные, каждый раз чистые (нет кэша docker-образов) и не имеют доступа в ваш приватный контур (базы данных за VPN).
Поэтому компании ставят **Self-hosted runners**.
В Kubernetes индустриальный стандарт — это **ARC (Actions Runner Controller)**. Это оператор, который слушает API GitHub. Когда в очередь поступает новая джоба, ARC мгновенно поднимает эфемерный Pod (Ephemeral runner) в вашем кластере, джоба выполняется, и Pod уничтожается. Это безопасно и масштабируется до нуля.

## 4. Управление окружениями (Environments & Protection Rules)

Как не дать джуниору задеплоить код на прод по кнопке?
В GitHub есть сущность **Environments** (Окружения).
В коде вы пишете: `environment: production`.
В настройках репозитория вы создаете Environment `production` и настраиваете **Protection Rules (Правила защиты)**:
- **Required reviewers**: Джоба встанет на паузу (Waiting) и не выполнится, пока 2 сеньора не зайдут в интерфейс и не нажмут "Approve".
- **Wait timer**: Принудительная задержка перед стартом.
Только Environment может хранить уникальные секреты (`prod-db-password`), доступ к которым будет только у джоб, развертывающихся в эту среду.

## 5. OIDC: Отказ от статических ключей (AWS/GCP)

Самая большая боль ИБ — это хранение `AWS_ACCESS_KEY_ID` в секретах GitHub. Эти ключи могут утекли, и их никто никогда не ротирует.
GitHub поддерживает **OIDC (OpenID Connect)**.
Как это работает:
1. Вы настраиваете AWS IAM доверять провайдеру `token.actions.githubusercontent.com`.
2. В workflow вы запрашиваете JWT токен (через `permissions: id-token: write`).
3. GitHub подписывает этот короткоживущий токен. В нем указано: "Я — репозиторий `my-org/my-repo`, ветка `main`".
4. Action (`aws-actions/configure-aws-credentials`) отправляет токен в AWS.
5. AWS проверяет подпись и выдает временные ключи на 1 час. Никаких статических секретов!

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Что произойдет, если в Workflow две джобы (`build` и `test`) не связаны через `needs`? На одном ли сервере они запустятся и увидят ли они файлы друг друга?**
*Ответ:* Без `needs` джобы запускаются абсолютно **параллельно** и независимо. Более того, GitHub распределит их на разные серверы-раннеры. Джоба `test` запустится на совершенно пустой машине и **не увидит** файлов (скомпилированного кода) из джобы `build`. Чтобы передать файлы между джобами, необходимо использовать экшены `actions/upload-artifact` в первой джобе и `actions/download-artifact` во второй.

**2. Объясните, зачем каждый Workflow почти всегда начинается с шага `uses: actions/checkout@v4`? Что будет, если его пропустить?**
*Ответ:* По умолчанию, когда GitHub выделяет сервер для джобы, он дает вам абсолютно пустую файловую систему. Исходный код из вашего репозитория там не лежит! Экшен `actions/checkout` — это обертка над командой `git clone`, которая скачивает исходный код в рабочую директорию раннера. Если его пропустить, любые шаги (например, `run: npm install` или `docker build .`) упадут с ошибкой "file not found".

**3. Как правильно шарить общий код пайплайна между 50 микросервисами в GitHub Actions, чтобы не копипастить YAML-файлы?**
*Ответ:* Использовать **Reusable Workflows (Переиспользуемые процессы)** или **Composite Actions**.
Reusable Workflows позволяют вынести целиком Workflow (с джобами и матрицами) в центральный репозиторий (например, `org/ci-templates`). В репозиториях микросервисов вы пишете всего 2 строчки: `uses: org/ci-templates/.github/workflows/build.yml@v1`. Это работает как вызов функции (с возможностью передать `inputs` и `secrets`).

**4. Вы запускаете сборку Docker-образа на GitHub-hosted раннерах (Ubuntu-latest). Каждая сборка занимает 10 минут, потому что скачивание библиотек происходит с нуля. Как SRE может ускорить это?**
*Ответ:* GitHub-hosted раннеры уничтожаются после каждой джобы, поэтому Docker-кеш теряется. Для ускорения нужно настроить **Remote Docker Cache**. Либо кэшировать слои прямо в GitHub Actions Cache (используя бекенд `gha` в Buildx), либо пушить кэш слоев (Inline cache или Registry cache) в удаленный Docker Registry (например, AWS ECR или GitHub Container Registry) при помощи параметра `--cache-to` и `--cache-from`.

**5. Почему для доступа к облаку (AWS, GCP) SRE рекомендуют использовать OIDC, а не хранение токенов в GitHub Secrets?**
*Ответ:* Статические ключи (Access Keys), сохраненные в GitHub Secrets, живут вечно. Если инженер их скомпрометирует (или случайно выведет в логи), они могут быть использованы хакером спустя месяцы. OIDC (OpenID Connect) полностью избавляет от необходимости хранить пароли. GitHub динамически генерирует криптографически подписанный JWT-токен на время работы джобы. AWS валидирует токен (проверяя название репы и ветки) и выдает ключи, которые "сгорят" (Expire) через 60 минут. Если хакер их и перехватит, окно атаки минимально.

**6. Зачем в пайплайнах нужен блок `permissions` и почему его важно всегда указывать явно (Principle of Least Privilege)?**
*Ответ:* У GitHub есть встроенный токен `GITHUB_TOKEN`, который инжектируется в каждую джобу. По умолчанию в старых настройках он мог иметь права `write` на весь репозиторий (коммитить код, создавать релизы). Если вы используете сторонний Action из маркетплейса, он может оказаться зловредным (supply chain attack) и использовать этот токен, чтобы запушить вредоносный код в вашу `main` ветку. Явное указание `permissions: { contents: read }` обрезает права токена до Read-Only, защищая инфраструктуру.

**7. У вас есть скрипт в шаге 1: `export VERSION=v1.2`. В шаге 2 вы делаете `echo $VERSION`, но переменная пустая. Почему? Как передать переменную между шагами?**
*Ответ:* Каждый шаг (step) в джобе выполняется в **отдельном bash-процессе** (оболочке). Экспортированные переменные умирают вместе с завершением процесса шага 1. Чтобы передать переменную в последующие шаги этой же джобы, нужно записать её в специальный системный файл GitHub. Правильный синтаксис: `echo "VERSION=v1.2" >> $GITHUB_ENV`. Начиная со следующего шага, переменная будет доступна через контекст `${{ env.VERSION }}` или `$VERSION`.

**8. В чем архитектурная разница между GitHub Actions и классическим Jenkins/GitLab? Что такое `Matrix builds`?**
*Ответ:* GitHub Actions построен вокруг мощной системы событий (Webhook-driven) и маркетплейса (модульности компонентов), чего нет в Jenkins. `Matrix builds` (Матричные сборки) — это встроенная фича для запуска сотен параллельных комбинаций одной джобы без дублирования кода. Например, вы можете указать `matrix: os: [ubuntu, windows], node: [14, 16]`. GitHub автоматически создаст 4 параллельных раннера и проверит ваш код на всех комбинациях ОС и версий Node.js.

**9. Разработчик хочет запускать тяжелые E2E тесты (занимающие 1 час) на Self-Hosted раннере в Kubernetes. В чем проблема использования классического постоянного (Persistent) раннера и почему индустрия перешла на Ephemeral (ARC)?**
*Ответ:* Если раннер постоянно запущен в k8s (Persistent), первая сборка скачает библиотеки, оставит временные файлы базы данных, и завершится. Вторая сборка, попав на этот же раннер, столкнется с "грязным" состоянием (конфликты портов, старые кэши), что приведет к ложноотрицательным тестам (Flaky tests). ARC (Actions Runner Controller) в режиме Ephemeral решает это: он поднимает Pod под каждую конкретную джобу, и как только она завершается, Pod **уничтожается**. Каждая сборка гарантированно стартует в чистой и идентичной среде (Clean State).

**10. Можно ли в GitHub Actions запустить шаг (step) только если предыдущий шаг упал с ошибкой (Failed)?**
*Ответ:* Да, через функции контроля состояния (Status Check Functions). По умолчанию GitHub прерывает выполнение джобы при первой же ошибке. Но если к шагу (например, к шагу отправки алерта в Slack) добавить блок `if: failure()`, он выполнится **исключительно** в том случае, если любой из предыдущих шагов вернул не-нулевой код ошибки (упал). Также существуют `always()` (выполнять даже при отмене пайплайна пользователем) и `success()` (дефолтное поведение).
