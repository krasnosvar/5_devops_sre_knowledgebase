Подробности и объяснения — в

## CI / Continuous Delivery / Continuous Deployment

| Этап | Что делает | Чем заканчивается | Человек в цикле |
| :--- | :--- | :--- | :--- |
| CI | lint, unit, сборка образа | артефакт в registry | ревью PR |
| Continuous Delivery | деплой на staging, E2E | артефакт готов к prod | ручной approve на prod |
| Continuous Deployment | всё автоматически до prod | версия в prod | только ревью PR |

## Стратегии деплоя: когда что

| Стратегия | Доп. ресурсы | Откат | Трафик во время выкатки | Когда брать |
| :--- | :--- | :--- | :--- | :--- |
| Rolling Update | +1 инстанс (`maxSurge`) | медленный, тоже rolling | v1 и v2 одновременно | дефолт для stateless, API обратно совместим |
| Recreate | нет | новый деплой | даунтайм | несовместимые версии, singleton |
| Blue/Green | x2 на время деплоя | секунды: LB обратно на Blue | 100% переключение разом | нужен мгновенный откат, хватает бюджета |
| Canary | небольшие | автоматический по метрикам | 1–5% → 10% → 50% → 100% | высокий риск, есть метрики и L7-роутинг |
| Shadow (mirror) | копия v2 | не нужен: ответы v2 игнорируются | копия реального трафика | большой рефакторинг, проверка под нагрузкой |
| Feature flag / dark launch | нет | выключить флаг | код в prod, фича скрыта | trunk-based, отвязать релиз от деплоя |
| A/B test | нет | — | по сегментам пользователей | продуктовый эксперимент, не стратегия деплоя |

## Инструменты для canary/blue-green в Kubernetes

| Задача | Чем |
| :--- | :--- |
| Rolling Update | `Deployment.spec.strategy.rollingUpdate` (`maxSurge`, `maxUnavailable`) |
| Точный процент трафика | Ingress NGINX (canary-аннотации), Gateway API (`weight`), Istio `VirtualService` |
| Canary с автоанализом метрик | Argo Rollouts (`AnalysisTemplate`), Flagger |
| Shadow/mirror трафика | Istio `mirror`, Envoy `request_mirror_policies` |
| Feature flags | LaunchDarkly, Unleash, OpenFeature-провайдеры, ConfigMap |

## Миграции БД: Expand and Contract

| Шаг | Релиз | Что делаем |
| :--- | :--- | :--- |
| 1. Expand | v1.1 | добавить новую колонку; код пишет в обе |
| 2. Migrate | фон | перенести старые данные в новую колонку |
| 3. Switch | v2 | код читает и пишет только новую колонку |
| 4. Contract | v3 | удалить старую колонку |

## Типичные значения

| Параметр | Значение |
| :--- | :--- |
| Шаги canary | 1–5% → 10% → 50% → 100%, пауза + анализ между шагами |
| Сигналы отката canary | рост 5xx, p95/p99 latency против baseline |
| `maxSurge` / `maxUnavailable` по умолчанию | 25% / 25% |
| Доля трафика на под при ClusterIP | 1 / число эндпоинтов (4 v1 + 1 v2 → 20% на v2) |

## Симптом → куда смотреть

| Симптом | Причина / куда смотреть |
| :--- | :--- |
| Во время rolling update периодические 500 | v2 сломала схему БД для v1 → Expand and Contract |
| Canary: пользователь «теряет» заказ между кликами | сессия в памяти + случайная балансировка → sticky sessions или вынести сессии наружу |
| Нельзя дать ровно 1% на canary | kube-proxy не знает весов → L7 (Ingress/Mesh/Argo Rollouts) |
| Перевесили тег `v1.0.0` — пайплайн не запустился | тег переиспользован; кэш/инструменты считают его уже задеплоенным → новый тег `v1.0.1` |
| Merge Hell после долгой ветки | long-lived branches → trunk-based + feature flags |

## Ловушки

- ⚠️ Никогда не перезаписывать теги Git/образов (кроме `latest`) — только
  новый тег.
- ⚠️ Blue/Green не удваивает БД: обе версии работают с одной базой, схема
  должна подходить обеим.
- ⚠️ Canary без автоматического анализа метрик — это просто медленный
  rolling update.
- Shift-left: SAST на PR, сканирование образа сразу после сборки.
