## 1. EKS (Elastic Kubernetes Service) и Fargate

**EKS** — это managed k8s от AWS. AWS забирает на себя управление Control Plane (etcd, API-сервер, Scheduler) и прячет его от вас. Вы платите $0.10 в час за каждый кластер просто за существование Control Plane.
Для Worker-нод (Где крутятся поды) есть три варианта:
- **Self-managed nodes**: Вы сами настраиваете ASG и EC2 инстансы.
- **Managed Node Groups**: AWS сам обновляет ОС (AMI) и крутит автоскейлинг.
- **AWS Fargate**: Serverless подход для контейнеров. У вас вообще нет EC2 серверов (Worker-нод). Когда вы деплоите Pod, AWS Fargate "на лету" выделяет под него изолированную MicroVM (через Firecracker) с нужным количеством vCPU/RAM. Идеально для изоляции безопасности. *Минус*: Нет DaemonSets (нельзя запустить агенты Datadog/Fluentbit на ноде, потому что ноды нет).

## 2. Serverless: AWS Lambda и Cold Starts (Холодные старты)

**AWS Lambda** — это функция как сервис (FaaS). Вы пишете кусок кода (на Node, Python, Go) и платите только за **миллисекунды** работы. (Масштабируется от 0 до 10 000 параллельных вызовов автоматически).
- **Cold Start (Холодный старт)**: Когда функция вызывается впервые за долгое время (или масштабируется), AWS нужно время, чтобы скачать код, поднять MicroVM, запустить рантайм (JVM, Node) и запустить функцию. Это может занять секунды.
- *Решение:* `Provisioned Concurrency`. Вы платите небольшую сумму, чтобы AWS всегда держал 10 экземпляров вашей функции "теплыми" (Warm) в оперативной памяти, готовыми ответить за 1 миллисекунду.

## 3. Очереди и Pub/Sub (Асинхронная архитектура SQS/SNS)

Для создания микросервисов (слабой связности - Decoupling) используются SQS и SNS.
- **SQS (Simple Queue Service)**: Очередь (Pull-модель). Сообщения копятся, воркеры (EC2 или Lambda) забирают их по одному.
  - *Standard*: Огромная пропускная способность, но порядок не гарантирован (может прийти дубль).
  - *FIFO (First-In-First-Out)*: Строгий порядок, отсутствие дублей (Exactly-once), но низкая скорость (300 tps).
- **SNS (Simple Notification Service)**: Шина сообщений (Push-модель). Издатель (Publisher) кидает сообщение в SNS Topic. SNS мгновенно рассылает (Fan-out) копии сообщения всем подписчикам (на SQS очереди, на email, в Lambda).
- **DLQ (Dead Letter Queue)**: Очередь для "мертвых писем". Если воркер пытается обработать сломанное сообщение из SQS 3 раза и падает (Exception), SQS автоматически перекладывает это сообщение в DLQ, чтобы оно не блокировало очередь, а SRE могли разобрать баг руками.

## 4. Route53: DNS и стратегии маршрутизации

Managed DNS сервер от AWS (с SLA 100%).
Кроме обычных A и CNAME записей, поддерживает сложные стратегии (Routing Policies):
- **Simple**: Возвращает один IP.
- **Weighted**: Раскидывает трафик по весам (например, 90% на старый ALB, 10% на новый ALB). Используется для Canary Deployment.
- **Latency**: Пингует клиента и направляет его в тот AWS-регион, где задержка (Ping) наименьшая.
- **Geolocation**: Роутит европейцев на сервера в Ирландии, а американцев в Вирджинию.
- **Failover**: Если Health Check видит, что основной дата-центр (Primary) упал, DNS перенаправит трафик на резервный (Secondary).

## 5. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему при помещении Lambda-функции внутрь VPC время холодного старта (Cold Start) в прошлом было огромным (иногда более 10 секунд), и как AWS архитектурно решил эту проблему?**
*Ответ:* Исторически, чтобы Lambda могла ходить в вашу VPC (например, в приватную RDS базу), AWS каждый раз при старте функции был вынужден создавать и прикреплять к ней Elastic Network Interface (ENI) в вашей подсети. Создание ENI занимает 10-15 секунд (вызов API EC2). В 2019 AWS внедрил `AWS Hyperplane`. Теперь ENI создаются заранее и кэшируются на границе VPC (Hyperplane ENI). При запуске Lambda просто устанавливает легковесный NAT-туннель до готового ENI за миллисекунды. Холодный старт в VPC больше не отличается от обычного.

**2. У вас микросервисная архитектура. Микросервис `Order` отправляет сообщение в SQS очередь `Inventory`. Если микросервис `Inventory` зависает и падает по тайм-ауту во время обработки сообщения, что произойдет с этим сообщением?**
*Ответ:* Оно не потеряется. В SQS есть механизм **Visibility Timeout** (Таймаут видимости). Когда воркер забирает сообщение, оно не удаляется из очереди, а просто становится "невидимым" для других воркеров на заданное время (например, на 30 секунд). Воркер обязан обработать заказ и явно послать API вызов `DeleteMessage`. Если он завис (упал) и не удалил сообщение, по истечении 30 секунд сообщение снова появится в очереди, и его подхватит другой, живой воркер (Retry-механизм).

**3. Разработчик утверждает, что AWS Fargate лучше, чем Managed Node Groups для EKS, потому что не нужно обновлять ОС (AMI) и чинить ноды. Какие есть технические ограничения Fargate, из-за которых его нельзя использовать для всего подряд?**
*Ответ:* 1) **DaemonSets**: Fargate не поддерживает DaemonSets. Если вашей безопасности нужен агент Falco (eBPF) или Splunk-агент на ноде, вы не сможете их запустить. 2) **Privileged Containers**: Fargate жестко запрещает privileged поды (запуск Docker-in-Docker или правка sysctl невозможна). 3) **Хранилища**: Fargate долго не поддерживал EBS (поддерживает EFS), что делает его плохим выбором для тяжелых Stateful-нагрузок (БД). 4) Метрики уровня ноды недоступны (нет доступа к ядру хоста).

**4. В чем разница между `Alias` записью в Route53 и обычной `CNAME` записью? Почему Alias обязателен при роутинге на корневой домен (Apex/Root domain, например, `mycompany.com`)?**
*Ответ:* Стандарты DNS (RFC) строго запрещают создавать `CNAME` запись на корневом (Apex) домене (разрешено только на поддоменах вроде `www.mycompany.com`). В корне можно писать только A-записи (IP-адреса). Но у AWS ALB, CloudFront или S3 нет статических IP (только DNS-имена). `Alias` — это проприетарное расширение Route53. Оно выглядит для внешнего мира как А-запись, но внутри AWS сам резолвит имя балансировщика в IP-адреса и отдает их клиенту. Также запросы к Alias-записям на ресурсы AWS (ALB/S3) бесплатны (не тарифицируются).

**5. Объясните паттерн `Fan-out` (Размножение сообщений) при использовании связки SNS + SQS.**
*Ответ:* Паттерн `Fan-out` нужен, когда одно событие (создание пользователя) должны параллельно обработать несколько независимых систем (Служба рассылки Welcome-email, Служба биллинга, Служба аналитики). Вместо того чтобы сервис регистрации писал сообщения в 3 разные очереди, он пишет **одно** сообщение в топик (Topic) `SNS`. К этому топику (SNS) подписаны (Subscribed) три независимые очереди `SQS`. SNS асинхронно размножает это сообщение и кладет копию в каждую SQS-очередь, развязывая архитектуру (Decoupling).

**6. У вас есть EKS кластер с Role-Based Access Control (RBAC). Как Kubernetes API узнает, какому пользователю AWS (IAM User) принадлежит токен `kubectl`, если k8s ничего не знает про IAM?**
*Ответ:* В EKS эта интеграция реализована через компонент `aws-iam-authenticator` (или встроенную EKS фичу) и ConfigMap `aws-auth` в неймспейсе `kube-system`. При вызове `kubectl`, плагин AWS CLI генерирует токен (Presigned URL) на основе ваших ключей AWS (`~/.aws/credentials`) и передает его API-серверу k8s. API-сервер просит AWS STS расшифровать токен и получает в ответ ARN пользователя IAM. Затем API-сервер заглядывает в таблицу `aws-auth` (маппинг), чтобы узнать, какой группе RBAC в Kubernetes (например, `system:masters`) соответствует этот IAM-пользователь.

**7. Как защитить внутренний API, развернутый на AWS API Gateway + Lambda, от DDOS-атак (Throttling)?**
*Ответ:* AWS API Gateway имеет встроенные механизмы защиты:
1. Настройка **Throttling/Rate Limiting**: Задать лимиты, например `1000 RPS (Requests per second)` и `Burst 500`. Всё, что выше, получит ошибку HTTP 429 (Too Many Requests).
2. Использование **Usage Plans & API Keys**: Выдавать клиентам токены доступа и лимитировать квоты индивидуально (100 запросов в день на фри-тарифе).
3. Интеграция с **AWS WAF** (Web Application Firewall), который заблокирует зловредные IP-адреса до того, как они дойдут до Lambda функции (сэкономив вам деньги за запуск).

**8. У вас настроена маршрутизация Route53 с политикой Failover (Active-Passive). При падении основного сайта в регионе EU, переключение на регион US занимает 5 минут, из-за чего клиенты видят ошибки. В чем причина задержки?**
*Ответ:* Основная причина — это **TTL (Time to Live)** DNS-записи и кэширование на стороне провайдеров интернета (ISP) и браузеров клиентов. Если вы поставили TTL = 300 секунд (5 минут), то клиентский браузер, получив IP-адрес упавшего европейского сервера, запомнит его на 5 минут и даже не попытается сделать новый DNS-запрос к Route53. Для критичных архитектур Failover необходимо устанавливать TTL = 60 секунд. (Однако, некоторые плохие интернет-провайдеры игнорируют низкий TTL, поэтому для идеального (0 downtime) переключения используют AWS Global Accelerator (Anycast IP)).

**9. Что такое SQS Long Polling (Длинный опрос) и почему он снижает затраты на AWS счет?**
*Ответ:* По умолчанию SQS использует Short Polling. Ваш воркер (EC2) отправляет API-запрос к очереди "Есть сообщения?", и если очередь пуста, SQS немедленно отвечает "Нет". Воркер делает так 100 раз в секунду. AWS берет деньги за каждый API-запрос. `Long Polling` (настройка `ReceiveMessageWaitTimeSeconds` до 20 секунд) меняет поведение: если сообщений нет, SQS **удерживает соединение открытым (зависает)** на 20 секунд. Как только сообщение появится, оно тут же вернется воркеру. Это уменьшает количество "пустых" API-запросов (Empty responses) в тысячи раз и кардинально снижает биллинг.

**10. В чем сложность мониторинга Serverless-приложений (Lambda) и что такое AWS X-Ray?**
*Ответ:* В микросервисной Serverless-архитектуре запрос пользователя прыгает через API Gateway -> Lambda A -> SNS -> SQS -> Lambda B -> DynamoDB. Если транзакция тормозит на 5 секунд, понять, в каком из звеньев проблема, по обычным разрозненным логам CloudWatch невозможно. **AWS X-Ray** — это сервис распределенной трассировки (Distributed Tracing, аналог Jaeger/Zipkin). Он добавляет уникальный `Trace ID` к каждому HTTP-запросу на входе (в API Gateway) и прокидывает его через все сервисы AWS. X-Ray рисует визуальную карту сервисов (Service Map) и показывает задержку на каждом отрезке графа.
