## 1. Архитектура VPC: Subnets, Route Tables

**VPC (Virtual Private Cloud)** — это ваша изолированная локальная сеть в AWS. При создании VPC вы задаете CIDR-блок (например, `10.0.0.0/16`).
Внутри VPC создаются **Subnets (Подсети)** (например, `10.0.1.0/24`).
*Важное правило AWS:* Одна подсеть жестко привязана ровно к одной **Availability Zone (AZ)** (дата-центру). VPC живет в рамках Региона (Region) и охватывает несколько AZ.
За маршрутизацию трафика отвечает **Route Table (Таблица маршрутизации)**. Вы привязываете Route Table к подсети. Именно записи в ней определяют, публичная это подсеть или приватная.

## 2. Шлюзы (Gateways): IGW vs NAT Gateway

- **Internet Gateway (IGW)**: Чтобы подсеть стала **Публичной**, вы привязываете к ней Route Table с маршрутом `0.0.0.0/0 -> IGW`. Инстансы в публичной подсети обязаны иметь публичный IP-адрес. Из интернета можно достучаться до инстанса (если разрешают фаерволы).
- **NAT Gateway**: Устанавливается в публичную подсеть. Инстансы в **Приватной** подсети не имеют публичных IP-адресов. Их таблица маршрутизации отправляет трафик `0.0.0.0/0 -> NAT Gateway`. NAT берет приватный пакет, подменяет IP на свой публичный (Elastic IP) и отправляет в интернет. *Отличие:* Инстанс может скачивать обновления из интернета, но никто из интернета не может инициировать соединение с инстансом.

## 3. Сетевая безопасность: Security Groups vs NACL

Это два слоя защиты вашей сети.
- **Security Groups (SG)**: Работают на уровне **инстанса (ENI)**. 
  - Они **Stateful** (С сохранением состояния): если вы разрешили входящий трафик (Ingress) по порту 443, ответный исходящий трафик (Egress) разрешается автоматически.
  - По дефолту: весь Ingress закрыт, весь Egress открыт.
- **NACL (Network Access Control List)**: Работают на уровне **всей подсети (Subnet)**.
  - Они **Stateless** (Без сохранения состояния): если вы разрешили Ingress 443, вам придется явно писать правило Egress для эфемерных портов (1024-65535), чтобы ответ смог уйти.
  - В отличие от SG, в NACL можно писать правила `DENY` (заблокировать конкретный IP).

## 4. Внутренний трафик: VPC Peering и Transit Gateway

Если у вас несколько VPC (например, Prod VPC и Data VPC), их нужно связать.
- **VPC Peering**: Точка-Точка (Point-to-Point). Если у вас 10 VPC, вам нужно создать 45 Peering-соединений (Full Mesh). Peering не транзитивен (А связан с B, B связан с С -> А не видит С). Очень дешев и быстр.
- **Transit Gateway (TGW)**: Звезда (Hub-and-Spoke). Центральный роутер. Вы подключаете все 10 VPC к TGW. Управлять правилами маршрутизации становится в 100 раз проще. Стоит денег (почасовая оплата + плата за ГБ трафика).

## 5. VPC Endpoints (PrivateLink)

Сервисы AWS (S3, DynamoDB, SQS) живут вне вашей VPC (в публичном облаке AWS).
Если инстанс в приватной подсети хочет скачать файл из S3, трафик пойдет через NAT Gateway -> Интернет -> S3. Это дорого (вы платите за NAT трафик) и менее безопасно.
**VPC Endpoints** решают это:
- **Gateway Endpoint**: (Только для S3 и DynamoDB). В Route Table добавляется маршрут к специальному шлюзу. Трафик к S3 идет внутри магистрали AWS бесплатно.
- **Interface Endpoint (PrivateLink)**: (Для SQS, SNS, KMS и др.). В вашу подсеть устанавливается виртуальный сетевой интерфейс (ENI) с локальным IP-адресом (`10.0.1.55`). Ваш инстанс отправляет запросы к KMS на этот локальный IP. Трафик не покидает VPC.

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Вы создали EC2 инстанс в публичной подсети (маршрут к IGW есть). У инстанса есть Public IP. В Security Group разрешен Ingress 22 (SSH). Однако вы не можете подключиться. Вы проверяете NACL, там всё `Allow`. Что вы забыли проверить на уровне ОС инстанса или AWS?**
*Ответ:* Если маршрут (IGW) на месте, SG и NACL открыты, возможные причины: 1) Отсутствует SSH-ключ (.pem) или неверно указан пользователь (`ec2-user` vs `ubuntu`). 2) Security Group привязан к неверному VPC (если их несколько). 3) На уровне ОС запущен локальный Firewall (например, `ufw` или `iptables`), который блокирует порт. 4) Таблица маршрутизации не привязана (Associated) именно к той подсети, где запущен инстанс.

**2. Почему использование NAT Gateway может стать одной из самых больших статей расходов в счете AWS? Как SRE снижают эти косты?**
*Ответ:* AWS берет плату не только за час работы NAT Gateway, но и **за каждый Гигабайт трафика**, проходящий через него (около $0.045/GB). Если приватные EKS-ноды скачивают огромные Docker-образы из публичного ECR или перекачивают терабайты данных в S3 через NAT, счет может составить тысячи долларов. *Оптимизация:* 1) Использовать VPC Endpoints для S3/ECR, чтобы трафик шел бесплатно минуя NAT. 2) Заменить управляемый NAT Gateway на самостоятельный EC2 NAT Instance (для некритичных сред).

**3. Чем `Security Group` отличается от `Network ACL (NACL)` в контексте обработки правил?**
*Ответ:* 
- **SG (Stateful)**: Правила оцениваются все вместе (нет приоритета). Вы просто говорите "Allow 80". Если пакет прошел проверку на вход, ответ автоматически пропускается на выход (даже если Egress пуст). Нельзя писать Deny-правила.
- **NACL (Stateless)**: Правила имеют порядковые номера (Rule #100, #110). Они оцениваются строго по порядку (сверху вниз). Если пакет подошел под правило 100 (Allow), оценка прекращается. Вы можете создать Rule #50 (Deny IP хакера) и Rule #100 (Allow All). Ответный трафик нужно разрешать вручную.

**4. Вы настраиваете VPC Peering между `VPC A` (10.0.0.0/16) и `VPC B` (10.0.0.0/16). Платформа выдает ошибку. Почему?**
*Ответ:* Главное правило VPC Peering (и Transit Gateway) — CIDR-блоки сетей **не должны пересекаться (No overlapping CIDRs)**. Если обе VPC имеют `10.0.0.0/16`, маршрутизатор не сможет понять, пакет с назначением `10.0.5.5` нужно отправить внутрь локальной сети или в Peering. Чтобы избежать этого в будущем, SRE обязаны выделять уникальные CIDR-диапазоны для каждой VPC еще на этапе архитектуры инфраструктуры (IPAM).

**5. Объясните концепцию `Ephemeral Ports` (Эфемерных портов) и как они связаны с настройкой NACL.**
*Ответ:* Когда клиент (инстанс) отправляет запрос на сервер (порт 443), операционная система клиента открывает случайный временный (эфемерный) порт (например, 54321) для получения ответа. В Security Groups (Stateful) этот порт пробросится автоматически. А в NACL (Stateless) вам нужно явно прописать Ingress/Egress правило, разрешающее трафик на диапазоне портов `1024-65535` со стороны серверов, иначе ответный пакет от сервера к клиенту будет сброшен (Dropped) на границе подсети.

**6. У вас есть VPC с CIDR `10.0.0.0/24` (256 адресов). Вы создаете подсеть, занимающую весь этот диапазон. Сколько IP-адресов вы реально сможете раздать инстансам (EC2)?**
*Ответ:* Не 256. В AWS в каждой подсети **5 IP-адресов резервируются** самой платформой и недоступны для использования.
1. `10.0.0.0` (Network address).
2. `10.0.0.1` (Резерв AWS для VPC Router).
3. `10.0.0.2` (Резерв AWS для DNS сервера / Route 53 Resolver).
4. `10.0.0.3` (Резерв AWS для будущего использования).
5. `10.0.0.255` (Broadcast address, хотя broadcast в AWS VPC не поддерживается).
Итого: `256 - 5 = 251` IP-адрес.

**7. Зачем нужны `Egress-Only Internet Gateway`?**
*Ответ:* Это аналог NAT Gateway, но предназначенный **исключительно для IPv6**. Протокол IPv6 не использует NAT в традиционном понимании (так как адресов хватает на всех, каждый инстанс получает глобальный публичный IPv6). Но если инстанс с публичным IPv6 находится в приватной подсети, и мы не хотим, чтобы к нему подключались из интернета, мы ставим `Egress-Only IGW`. Он пропускает исходящий трафик в интернет, но блокирует любые входящие соединения, инициированные снаружи.

**8. У вас настроен Interface VPC Endpoint (PrivateLink) для доступа к сервису AWS STS. При обращении по DNS имени `sts.amazonaws.com` трафик всё равно уходит в интернет. Как заставить трафик идти в Endpoint?**
*Ответ:* При создании Interface Endpoint необходимо включить опцию **Private DNS Name (Enable DNS resolution)**. Если эта опция включена, AWS автоматически подменяет публичную DNS-запись `sts.amazonaws.com` внутри вашего VPC (в Route53 Resolver) на локальный IP-адрес вашего Interface Endpoint (например, `10.0.1.50`). Приложению не нужно менять конфигурацию URL — сетевой вызов прозрачно уйдет во внутреннюю сеть.

**9. Разработчики просят открыть доступ из EC2 инстанса к партнерской API (`api.partner.com`), которая имеет динамические IP-адреса. Вы идете в Security Group, чтобы разрешить Outbound, но там нельзя ввести доменное имя. Как это решают SRE?**
*Ответ:* Security Groups в AWS принимают только IP-адреса и CIDR-блоки (L3/L4 уровень). Они не умеют резолвить DNS (L7 уровень). Решений несколько:
1. Использовать сторонний Firewall-прокси (например, Squid Proxy или AWS Network Firewall), который умеет фильтровать Egress-трафик по доменным именам (FQDN/SNI).
2. Написать Lambda-функцию, которая по крону резолвит `api.partner.com` и автоматически обновляет IP-адреса в правилах Security Group через AWS API.

**10. Что такое `VPC Flow Logs` и для чего их используют?**
*Ответ:* VPC Flow Logs — это фича захвата метаданных о сетевом трафике (IP-источник, IP-назначение, порт, байты, статус ACCEPT/REJECT). Логи не захватывают тело пакета (Payload), только заголовки (NetFlow). Данные складываются в CloudWatch Logs или S3. Это главный инструмент SRE для дебага сети ("Почему мой пакет дропается?") и офицеров безопасности (ИБ) для расследования сетевых аномалий и вторжений.
