## 1. Архитектура IAM: Users, Groups, Roles

**IAM (Identity and Access Management)** — это глобальный сервис AWS (не привязан к регионам).
- **Users**: Конкретные люди или приложения (имеют статические логин/пароль или `AccessKey`). *SRE Best Practice:* Избегать IAM Users для приложений.
- **Groups**: Группы пользователей (удобно для назначения прав всем разработчикам сразу).
- **Roles (Роли)**: Сущность без паролей. Роль может быть "примерена" (Assumed) доверенной сущностью (например, EC2 инстансом, Lambda-функцией или пользователем из другого AWS аккаунта). Когда EC2 берет роль, он получает **временные ключи** (STS Token), которые сгорают через пару часов. Это основа безопасности AWS.

## 2. IAM Policies: Identity-based vs Resource-based

Права описываются JSON-документами (Policies).
1. **Identity-based policies**: Прикрепляются к субъекту (User/Role). Отвечают на вопрос "Что может делать этот юзер?". (Например: `User A` может делать `s3:GetObject`).
2. **Resource-based policies**: Прикрепляются к самому ресурсу (S3 Bucket, SQS Queue, KMS Key). Отвечают на вопрос "Кто имеет доступ к этому ресурсу?". (Например: В `Bucket Policy` указано, что `User A` может читать этот бакет, а весь остальной интернет — нет).

*Для доступа к ресурсу в одном аккаунте достаточно, чтобы разрешало хотя бы одно из двух. Для кросс-аккаунт доступа (Cross-Account) необходимо, чтобы разрешали ОБА (и политика юзера, и политика бакета).*

## 3. Логика вычисления прав (Evaluation Logic)

AWS вычисляет доступ по строгому алгоритму:
1. По умолчанию **ВСЁ запрещено** (Default Deny).
2. Оцениваются все применимые политики.
3. Если есть хотя бы один явный `Deny` (Explicit Deny) — доступ блокируется мгновенно. **Явный запрет перекрывает любые разрешения.**
4. Если есть хотя бы один явный `Allow` (Explicit Allow) и нет `Deny` — доступ разрешается.

## 4. KMS (Key Management Service) и Envelope Encryption

KMS — сервис управления криптографическими ключами. В AWS используется паттерн **Envelope Encryption** (Шифрование конвертом).
- У вас есть данные (10 ГБ видео).
- AWS генерирует уникальный Data Key (Ключ данных). Видео шифруется этим Data Key.
- Затем сам Data Key шифруется мастер-ключом из KMS (CMK - Customer Master Key).
- Зашифрованное видео и зашифрованный Data Key сохраняются вместе на диск (в S3 или EBS).
*Плюсы:* Чтобы прочитать данные, вам нужно иметь IAM права на `kms:Decrypt`, чтобы KMS расшифровал ваш Data Key. Сам CMK никогда не покидает аппаратные модули (HSM) AWS.

## 5. Интеграция OIDC (Identity Federation)

Классическая ошибка — создание IAM User для GitLab/GitHub Actions и сохранение `AWS_ACCESS_KEY_ID` в секретах пайплайна (ключ живет вечно, при утечке — катастрофа).
*SRE стандарт:* Использование **OIDC (OpenID Connect)**.
Вы создаете IAM Role в AWS и настраиваете ее на доверие к OIDC-провайдеру GitHub.
Пайплайн GitHub генерирует JWT токен и отправляет его в AWS STS (`AssumeRoleWithWebIdentity`). AWS проверяет подпись GitHub, видит имя репозитория и выдает пайплайну временные ключи на 1 час.

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. У вас есть IAM Role A с правами Full Access к S3. К ней прикреплен Permission Boundary, в котором разрешен доступ только к EC2. Сможет ли эта роль загрузить файл в S3?**
*Ответ:* Нет, не сможет. `Permission Boundary` (Граница разрешений) — это продвинутая фича IAM. Она сама по себе ничего не разрешает, она лишь задает **максимально возможный** спектр прав. Итоговые права роли — это пересечение (Intersection) её реальной политики (S3) и границы (EC2). Пересечение пустое, поэтому AWS вернет `Access Denied`.

**2. Разработчик утверждает, что EC2 инстанс не может получить доступ к S3, хотя он прикрепил к нему правильную IAM Роль. Вы проверяете логи, и видите, что запрос идет, но падает по таймауту, а не с ошибкой Access Denied. В чем проблема?**
*Ответ:* Проблема не в IAM, а в **сети (VPC)**. IAM Роль выдает права на уровне API, но чтобы запрос дошел до API-серверов S3, у инстанса должен быть доступ в интернет (через NAT Gateway / IGW) ИЛИ должен быть настроен `VPC Endpoint` для S3. Если инстанс находится в приватной подсети без NAT и без Endpoint, пакеты просто дропаются (таймаут).

**3. Чем отличается AWS Managed Key (aws/s3) от Customer Managed Key (CMK) в сервисе KMS?**
*Ответ:* AWS Managed Key (например, `aws/s3`) бесплатен, создается автоматически сервисом, но у вас **нет контроля** над ним. Вы не можете менять политику этого ключа (Key Policy), не можете ротировать его по расписанию и не можете использовать его для кросс-аккаунт доступа (Cross-Account). Customer Managed Key (CMK) стоит $1/месяц, вы полностью управляете его политиками, можете дать доступ к нему из другого аккаунта AWS и настроить автоматическую ротацию ключа раз в год.

**4. Вы настраиваете Cross-Account доступ. Аккаунт А (Dev) хочет прочитать S3 бакет в Аккаунте Б (Prod). IAM Роль в Аккаунте А имеет права `s3:GetObject`. Bucket Policy в Аккаунте Б не имеет явных `Deny`. Почему доступ запрещен?**
*Ответ:* При меж-аккаунтном (Cross-Account) доступе действует другое правило Evaluation Logic. Разрешение должно быть выдано **явно с обеих сторон**. Роль в Аккаунте А разрешает исходящий запрос, но Bucket Policy в Аккаунте Б **обязана** явно содержать `Allow` с указанием ARN роли из Аккаунта А в секции `Principal`. Без этого Bucket Policy не доверяет чужому аккаунту.

**5. Объясните принцип работы `sts:AssumeRole`. Как один ресурс "становится" другим?**
*Ответ:* Сервис STS (Security Token Service) отвечает за выдачу временных ключей. Когда пользователь или сервис вызывает API `AssumeRole` (передавая ARN роли), STS проверяет `Trust Policy` (Политику доверия) этой роли. В ней написано, кому разрешено эту роль принимать (например, сервису `ec2.amazonaws.com`). Если проверка пройдена, STS динамически генерирует `AccessKeyId`, `SecretAccessKey` и `SessionToken`, которые действительны от 15 минут до 12 часов, и возвращает их клиенту.

**6. У вас есть IAM Policy с `Effect: Allow` на `s3:*` к бакету `my-bucket`, но в конце добавлено `Condition: { StringNotEquals: { aws:SourceIp: "10.0.0.0/16" } }`. Что делает это правило?**
*Ответ:* Блок `Condition` задает условия срабатывания политики. Политика разрешает полный доступ к S3, НО **только если** IP-адрес источника запроса (SourceIp) НЕ РАВЕН подсети 10.0.0.0/16. Это частый паттерн гео-блокинга или запрета прямого доступа из корпоративной сети (хотя двойное отрицание часто путает новичков).

**7. Как защитить root-аккаунт AWS (почту, на которую зарегистрирован аккаунт)? Что можно делать из-под root?**
*Ответ:* SRE-стандарт: Root-аккаунт не должен использоваться для повседневной работы (никогда не генерируйте для него Access Keys). Защита: Установить невероятно сложный пароль, обязательно включить аппаратный MFA (YubiKey), и спрятать токен в сейф. Root-пользователь может закрыть (удалить) весь аккаунт AWS, изменить план поддержки (Support Plan) и изменить платежные реквизиты. Никакой IAM User (даже с `AdministratorAccess`) этого сделать не может.

**8. Разработчик закоммитил `AWS_SECRET_ACCESS_KEY` в публичный GitHub репозиторий. Вы это увидели через 10 минут. Вы удалили коммит через `git push --force`. Инцидент исчерпан?**
*Ответ:* Нет! В AWS публичные утечки парсятся хакерами за миллисекунды. Хакеры сразу сканируют аккаунт и запускают майнеры (EC2) во всех 30 регионах. Удаление коммита не поможет. Действия SRE: 1) Немедленно зайти в AWS Console и **деактивировать (Deactivate) или удалить** утекший Access Key. 2) Проверить CloudTrail на предмет подозрительной активности (запуск инстансов в регионе eu-north-1, создание новых IAM ролей). 3) Выпустить новый ключ разработчику.

**9. Что такое `AWS CloudTrail` и чем он отличается от `AWS CloudWatch Logs`?**
*Ответ:* `CloudWatch Logs` собирает логи ваших приложений (STDERR/STDOUT из EC2, Lambda или контейнеров). `CloudTrail` — это сервис аудита ИБ (Audit Trail). Он непрерывно записывает **все API-вызовы** к контрол-плейну AWS. "Кто (IAM Role), когда, с какого IP и какой API-метод (например, `TerminateInstances`) вызвал". CloudTrail — это главный инструмент Security-инженеров при расследовании инцидентов и взломов.

**10. В чем разница между `AWS Secrets Manager` и `AWS Systems Manager Parameter Store (SSM)`? За что стоит платить?**
*Ответ:* Оба сервиса хранят секреты, но:
- `SSM Parameter Store`: Базовый сервис. Хранение `SecureString` ключей (зашифрованных KMS) бесплатно (до 10,000 ключей). Отлично подходит для паролей.
- `Secrets Manager`: Платный сервис ($0.40 за секрет). Его главная киллер-фича — **Автоматическая ротация (Auto-Rotation)**. Он может сам подключаться к базе RDS (вызывая Lambda-функцию) раз в 30 дней, генерировать новый пароль, менять его в базе и сохранять у себя без простоя (downtime).
