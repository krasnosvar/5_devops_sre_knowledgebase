## 1. S3 (Simple Storage Service): Обзор и Консистентность

**Amazon S3** — это объектное хранилище (Object Storage). В отличие от файловых систем (EBS, EFS), в S3 нет иерархии папок, нет концепции "дописать 1 байт в конец файла". Файл (Object) хранится целиком по уникальному ключу (Key). То, что выглядит как папки в веб-интерфейсе — просто длинные ключи со слешами `images/2024/photo.jpg`.

*С 2020 года S3 обеспечивает **Strong Consistency** (Строгую согласованность) (Read-after-Write).* Если вы успешно загрузили файл (PUT), любой последующий запрос на чтение (GET) немедленно получит именно эту новую версию.

## 2. S3 Storage Classes (Типы хранилищ) и Lifecycle Policies

S3 предлагает разные классы хранения для оптимизации затрат:
- **Standard**: Дефолт. Высокая доступность (Multi-AZ). Идеально для часто запрашиваемых данных.
- **Intelligent-Tiering**: Сам переносит файлы между дорогим и дешевым классом на основе машинного обучения.
- **Standard-IA (Infrequent Access)**: Дешевое хранение, но вы **платите за каждый гигабайт извлечения (Retrieval)**. Выгодно для бэкапов, которые скачивают раз в полгода.
- **Glacier (Flexible / Deep Archive)**: Архив. Самое дешевое хранение (копейки за ТБ). Но чтобы скачать файл, нужно отправить запрос и ждать от 12 часов до 2 суток (пока робот на ленте в дата-центре найдет данные).

**Lifecycle Policies (Жизненные циклы)**: SRE настраивают правила автоматического перемещения файлов. Например: "Через 30 дней перенести логи из Standard в Glacier. Через 365 дней — безвозвратно удалить (Expire)".

## 3. Безопасность S3: Bucket Policies, WORM и Шифрование

Утечки из S3 — самая частая причина взломов компаний.
- **Block Public Access (BPA)**: Галочка на уровне аккаунта/бакета, которая жестко переопределяет (запрещает) любые публичные ACL или политики, предотвращая утечку.
- **Bucket Policy**: Ресурсная IAM политика (JSON), задающая кто может скачивать файлы (например, разрешить доступ только с определенного VPC Endpoint).
- **S3 Versioning (Версионирование)**: Если вы перезаписали или удалили файл, старая версия скрывается, но остается на диске (спасает от случайного удаления).
- **Object Lock (WORM - Write Once, Read Many)**: Защита от Ransomware. Включается на бакет. Позволяет заблокировать файлы так, что даже `root` пользователь AWS не сможет их удалить или изменить в течение заданного периода (например, 5 лет). Обязательно для финансового аудита.

## 4. EFS (Elastic File System) против EBS

- **EBS** (Block Storage): Диск, который можно примонтировать **только к одному** EC2 инстансу одновременно (за исключением сложных Multi-Attach для кластерных ФС). Работает в одной AZ.
- **EFS** (File Storage): Полноценный сетевой NFS-сервер (NFSv4.1). Вы можете примонтировать его к **тысячам EC2 инстансов или подов k8s** одновременно, причем в разных AZ одного региона. Он сам масштабируется до петабайт.
*Минусы EFS:* Высокая задержка (Latency) и низкие IOPS. Не подходит для баз данных. Идеально для расшаривания статических файлов (аватарки, плагины WordPress) между кластерами.

## 5. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему SRE не рекомендуют использовать S3 как хранилище для логов приложения, если приложение пишет в один файл построчно?**
*Ответ:* S3 — это **объектное хранилище (Object Storage)**, а не блочное (как EBS). В S3 нет операции `append` (дописать в конец файла). Чтобы обновить файл логов в S3, вам придется скачивать весь старый файл (например, 1 ГБ), добавлять к нему новую строку в оперативной памяти и загружать весь 1 ГБ обратно (операция PUT перезаписывает объект целиком). Это невероятно медленно и дорого. Для логов используют CloudWatch Logs, Kinesis Firehose или Fluentbit, которые пачками (батчами) отправляют логи раз в минуту.

**2. Разработчик настроил Lifecycle Policy в S3: переносить файлы в `Standard-IA` через 30 дней. Вы анализируете счет AWS и видите, что затраты не упали, а выросли! Почему?**
*Ответ:* У класса `Standard-IA` (Infrequent Access) есть две ловушки ценообразования. Во-первых, вы платите за **извлечение (Retrieval fee)**. Если приложение часто скачивает эти файлы (например, это популярные картинки на сайте), штрафы за чтение сожрут всю экономию. Во-вторых, класс `IA` имеет минимальный порог хранения (Minimum billable size) в **128 KB** на объект. Если в бакете лежат миллионы текстовых файлов по 5 KB, AWS будет тарифицировать каждый из них как 128 KB, что приведет к катастрофическому росту счета.

**3. Ваша команда отправляет видеоролики в S3. Разработчик использует команду `aws s3 cp video.mp4 s3://bucket/`. Иногда для 50-гигабайтных файлов загрузка обрывается посередине из-за плохой сети. Как правильно заливать большие файлы в S3?**
*Ответ:* Обычный PUT (до 5 ГБ) загружает файл единым куском. Для больших файлов (от 100 МБ до 5 ТБ) необходимо использовать **Multipart Upload** (API AWS CLI использует его автоматически под капотом при копировании больших файлов). Файл разбивается на тысячи кусков (частей), которые загружаются параллельно в несколько потоков. Если один кусок не загрузился (обрыв сети), переотправляется только он, а не все 50 ГБ. После загрузки всех частей S3 собирает файл воедино на своей стороне.

**4. В бакете S3 включено версионирование (Versioning). Разработчик случайно выполняет API-запрос `DeleteObject` для файла `config.json`. Данные потеряны? Как их восстановить?**
*Ответ:* Данные не потеряны. Когда версионирование включено, запрос `DeleteObject` (без указания конкретного `VersionId`) не удаляет файл физически. Вместо этого S3 вставляет специальный невидимый маркер — **Delete Marker**. Файл просто перестает отдаваться по запросу `GET`. Чтобы восстановить файл, администратору достаточно найти этот `Delete Marker` в истории версий объекта и удалить сам маркер (удалив маркер удаления, предыдущая версия файла снова становится активной).

**5. Вам нужно раздавать приватные файлы (отчеты PDF) клиентам вашего SaaS приложения, но вы не хотите делать бакет S3 публичным и не хотите гонять трафик через ваши Backend-серверы. Как это архитектурно решить?**
*Ответ:* Использовать **Pre-signed URLs** (Заранее подписанные ссылки). Ваш Backend (имеющий IAM-права на чтение S3) генерирует с помощью AWS SDK специальный URL. В этот URL зашиты криптографическая подпись и точное время истечения срока действия (например, 15 минут). Вы отдаете этот URL клиенту в браузер. Клиент качает файл напрямую с серверов Amazon S3. Бакет остается полностью закрытым (Private), а ссылка сгорит через 15 минут, защищая от пересылки.

**6. У вас есть EFS, примонтированный к 10 инстансам. Вы пытаетесь запустить на нем компиляцию Java-проекта или базу данных SQLite. Процесс идет в 100 раз медленнее, чем на локальном диске (EBS). Почему?**
*Ответ:* EFS — это сетевая распределенная файловая система (NFS). В отличие от EBS, EFS требует сетевого обмена (Network round-trip) для абсолютно каждой мета-операции файла (открыть файл, проверить права, залочить файл). Компиляция кода или SQLite создают десятки тысяч мелких файлов и замков (Locks), что генерирует лавину синхронных сетевых запросов. Высокая задержка (Latency) EFS убивает производительность IOPs. EFS хорош для последовательного чтения больших статических файлов, а не для высокочастотных транзакций.

**7. Как защитить бэкапы (Snapshots) и архивы в S3 от атаки типа Ransomware (Вирус-шифровальщик), когда хакер взломал AWS-аккаунт с полными правами `AdministratorAccess`?**
*Ответ:* Единственный способ защиты на уровне хранилища — включение **S3 Object Lock в режиме Compliance Mode**. В этом режиме на каждый файл вешается аппаратный таймер (Retention period), например на 7 лет. Операция перезаписи или удаления файла блокируется на уровне ядра S3. Никакая политика IAM, даже с правами Root-аккаунта AWS, не способна обойти или отключить Compliance Mode. Хакер просто не сможет затереть ваши бэкапы физически.

**8. Объясните паттерн интеграции S3 и AWS Lambda. Как автоматически реагировать на загрузку файлов?**
*Ответ:* S3 имеет встроенную систему событий (Event Notifications). Вы можете настроить S3 так, что при событии `s3:ObjectCreated:Put` (когда файл .jpg успешно сохранен в бакет), S3 асинхронно вызовет AWS Lambda функцию (отправит ей JSON с именем бакета и ключом файла). Lambda-функция запустится, скачает картинку, создаст Thumbnail (уменьшенную копию) и сохранит её в другой бакет. Это классический паттерн Event-Driven Architecture (Событийно-ориентированная архитектура).

**9. Что такое S3 Transfer Acceleration и какую физическую проблему глобальной сети он решает?**
*Ответ:* Представьте, что ваш S3 бакет находится в регионе `us-east-1` (США), а ваши пользователи загружают видео из Австралии. Загрузка идет по обычному интернету (BGP-маршрутизация, много прыжков провайдеров), что вызывает потери пакетов и огромные задержки (Latency). S3 Transfer Acceleration решает это. Пользователь отправляет файл на ближайшую границу AWS (Edge Location / CloudFront в Австралии). Оттуда файл идет по выделенной, оптимизированной, приватной оптоволоконной магистрали AWS прямо до S3 бакета в США, ускоряя загрузку на 50-300%.

**10. В чем смысл включения опции `KMS Customer Managed Key (CMK)` для шифрования S3 (SSE-KMS), если S3 и так предлагает бесплатное дефолтное шифрование (SSE-S3)?**
*Ответ:* Обычное шифрование SSE-S3 (AES-256) прозрачно: любой юзер/роль, имеющий права `s3:GetObject`, сможет скачать файл (S3 сам зашифрует и расшифрует его). Это просто "галочка для комплаенса".
Шифрование SSE-KMS добавляет **второй слой авторизации**. Теперь, чтобы скачать файл, IAM-роль должна иметь не только права `s3:GetObject`, но и **явно прописанные права `kms:Decrypt`** на тот самый ключ CMK, которым зашифрован файл. Плюс, каждый факт расшифровки KMS-ключа фиксируется в логах аудита (CloudTrail), что недоступно в простом SSE-S3.
