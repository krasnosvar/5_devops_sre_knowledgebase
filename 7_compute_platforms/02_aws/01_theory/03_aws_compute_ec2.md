## 1. Типы EC2 инстансов и ценообразование

Семейства инстансов делятся на буквы (Например: `t3.micro`, `m5.large`, `c6g.xlarge`).
- `t` — Burstable (накапливают кредиты процессора). Хороши для пет-проектов.
- `m` — General Purpose (Баланс CPU/RAM).
- `c` — Compute Optimized (Много CPU, мало RAM). Идеально для CI/CD раннеров.
- `r` — Memory Optimized (Много RAM). Для in-memory БД (Redis, Memcached).
- `g` — Graviton (ARM-процессоры от AWS). На 20% дешевле и холоднее Intel.

**Ценообразование**:
- **On-Demand**: Платишь по секундам. Самый дорогой вариант.
- **Reserved Instances (RI) / Savings Plans**: Обязательство платить за 1 или 3 года. Скидка до 72%.
- **Spot Instances**: AWS продает простаивающие мощности на аукционе со скидкой до 90%. *Риск:* AWS может забрать инстанс в любой момент (даст 2 минуты на завершение процессов). Идеально для воркеров и k8s (через Karpenter).

## 2. Хранилища: EBS против Instance Store

- **EBS (Elastic Block Store)**: Сетевой жесткий диск. Подключается по сети (SAN). Если инстанс перезагрузить или удалить (с флагом сохранить диск), данные останутся.
  - `gp3`: SSD общего назначения (дешевый, 3000 IOPS из коробки).
  - `io2`: Provisioned IOPS. Очень дорогой, для тяжелых БД (до 64000 IOPS).
- **Instance Store (Ephemeral Storage)**: Физический жесткий диск (NVMe), воткнутый прямо в материнскую плату сервера. Максимальная скорость. *Риск:* Если вы нажмете `Stop` (выключение) инстансу, данные будут уничтожены навсегда (они эфемерны). Используется только для кэшей.

## 3. Масштабирование: Auto Scaling Groups (ASG) и Launch Templates

Чтобы сервера не падали под нагрузкой, используется паттерн **ASG**.
Вы создаете `Launch Template` (Шаблон запуска: какая AMI, какой тип инстанса, какие SSH ключи). ASG использует этот шаблон для запуска серверов.
ASG следит за `Desired Capacity` (Желаемое количество). Если сервер сломался (упал health check), ASG сам его убьет (Terminate) и поднимет новый.
Автоскейлинг настраивается по метрикам (Например, если CPU > 70%, создать +1 инстанс).

## 4. Балансировщики нагрузки (ELB): ALB, NLB, GLB

- **ALB (Application Load Balancer)**: Работает на **L7 (HTTP/HTTPS)**. Умеет читать заголовки, пути (`/api`, `/images`) и перенаправлять трафик на разные Target Groups. Декодирует SSL. Работает медленнее, чем L4, но умнее.
- **NLB (Network Load Balancer)**: Работает на **L4 (TCP/UDP)**. Ничего не знает про HTTP. Просто перебрасывает пакеты (миллионы в секунду) с минимальной задержкой. У него есть **статические IP-адреса**.
- **GLB (Gateway Load Balancer)**: Работает на **L3 (IP)**. Используется исключительно для интеграции сторонних Firewall-апплайнсов (Palo Alto, Fortinet).

## 5. User Data и Метаданные (IMDSv2)

При создании инстанса можно передать `User Data` — bash-скрипт, который выполнится от root **ровно один раз** при самом первом старте сервера (за это отвечает утилита `cloud-init`). Используется для скачивания Ansible, установки Docker.
Сам инстанс может узнать информацию о себе (какой у него IP, регион, IAM роль) обратившись к внутреннему адресу `169.254.169.254` (Instance Metadata Service). *Best Practice:* Обязательно требовать IMDSv2 (версия с токенами), чтобы защититься от атак SSRF (когда хакер через дыру в сайте пытается вытащить ключи IAM).

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Вы выбрали `t3.medium` для продакшен базы данных. Первые два часа база работает идеально, а затем нагрузка падает, и база начинает жутко "тормозить", CPU упирается в 100%. Что произошло?**
*Ответ:* Семейство `T` работает по принципу накопления кредитов CPU (Burstable). Если инстанс простаивает (CPU < 20%), он копит кредиты. Если нагрузка подскакивает до 100%, он тратит кредиты. Когда вы запустили БД, она потратила все накопленные кредиты за 2 часа (Burn out). После этого AWS принудительно "отрезал" производительность (Throttling) до базовой линии (Baseline, около 20% CPU). Инстансы T-серии запрещено использовать для постоянных тяжелых нагрузок в Prod (нужно брать M, C или R).

**2. Ваш EBS том `gp2` (размером 100 ГБ) упирается в ограничение скорости (IOPS), база данных тормозит. Как это исправить с минимальными затратами без простоя?**
*Ответ:* У старого поколения `gp2` количество IOPS жестко привязано к размеру диска (3 IOPS на 1 ГБ). 100 ГБ диск имеет всего 300 IOPS. Лучшее решение — "на лету" изменить тип тома с `gp2` на современный `gp3` (Modify Volume). Это делается без даунтайма (Zero Downtime). `gp3` на 20% дешевле и дает гарантированные 3000 IOPS из коробки, независимо от размера диска.

**3. У вас есть ASG с минимальным размером 2, максимальным 10. Происходит всплеск нагрузки, и ASG начинает поднимать 8 новых инстансов. Однако приложение на них большое и стартует (прогревается) 10 минут. В этот момент ASG убивает их и пытается поднять новые. Почему?**
*Ответ:* Это классическая проблема `Health Check Grace Period`. В ASG есть настройка, которая говорит "Сколько секунд ждать после старта инстанса, прежде чем начать проверять его Health Check?". По умолчанию это обычно 300 секунд (5 минут). Через 5 минут ASG дергает балансировщик (ALB), балансировщик видит, что приложение еще не поднялось (прогрев 10 минут), помечает инстанс как Unhealthy. ASG видит больной инстанс, убивает его и запускает цикл заново. Нужно увеличить `Grace Period` до 15-20 минут (или оптимизировать старт приложения).

**4. В чем разница между Target Group в ALB и Target Group в NLB при регистрации IP адресов из другой VPC?**
*Ответ:* ALB работает на L7 и выступает прокси-сервером. NLB работает на L4. Главная фича NLB в том, что он умеет сохранять (Preserve) исходный IP-адрес клиента при передаче трафика на EC2 инстансы (Target Type: Instance). ALB всегда заменяет исходный IP-адрес клиента на свой собственный IP (чтобы приложение узнало реальный IP юзера, оно должно читать HTTP-заголовок `X-Forwarded-For`).

**5. Как можно сделать бэкап (Snapshot) EBS-тома консистентным, если на нем крутится реляционная база данных (например, PostgreSQL)?**
*Ответ:* Если просто нажать "Create Snapshot", диск будет сфотографирован в состоянии Crash-consistent (как будто выдернули шнур питания). Данные в оперативной памяти (буферы БД) будут потеряны. Чтобы сделать консистентный бэкап (Application-consistent), необходимо заморозить файловую систему. SRE пишут скрипт через Systems Manager: 1) Команда в БД `FLUSH TABLES WITH READ LOCK` или `pg_start_backup()`. 2) Заморозка ФС `fsfreeze /data`. 3) Триггер API Snapshot. 4) `fsfreeze -u` (разморозка).

**6. Зачем нужны `Lifecycle Hooks` в Auto Scaling Group? Приведите пример использования.**
*Ответ:* Lifecycle Hooks (Хуки жизненного цикла) позволяют поставить на паузу процессы запуска (Launching) или завершения (Terminating) инстанса в ASG. Например, при Scale-In (сокращении), ASG решает убить сервер. Если на сервере обрабатывается долгая фоновая задача (Job), она прервется. С помощью Lifecycle Hook `Terminating:Wait`, ASG не убивает сервер сразу, а отправляет сообщение в SNS/SQS. Ваш сервер ловит сообщение, дорабатывает задачу, заливает логи в S3 и отправляет API-сигнал `CompleteLifecycleAction`. Только после этого ASG физически убивает инстанс.

**7. У вас настроен ALB, за которым работает ASG из 5 серверов. Один из серверов начинает возвращать HTTP 500. Что сделает ALB и что сделает ASG?**
*Ответ:* 
- ALB: Его Health Checks заметят 500-е ошибки. ALB пометит этот таргет как `Unhealthy` и перестанет роутить на него новый клиентский трафик (чтобы спасти юзеров).
- ASG: По умолчанию ASG следит только за метрикой `EC2 Status Checks` (Живо ли железо сервера? Сеть есть?). Железо живо, поэтому ASG **ничего не сделает**. Сервер останется висеть мертвым грузом. Чтобы ASG убил и пересоздал сервер, нужно изменить настройку ASG `Health Check Type` с `EC2` на **`ELB`**. Тогда ASG доверится решению балансировщика и заменит зависший инстанс.

**8. Клиент жалуется, что домен вашего сервиса (привязанный к ALB) иногда возвращает таймаут, хотя серверы в порядке. Вы смотрите DNS записи и видите, что IP адреса ALB меняются. Это баг ALB?**
*Ответ:* Нет, это архитектурная особенность ALB (Application Load Balancer). ALB динамически масштабируется под нагрузкой. При сильном скачке трафика AWS автоматически создает новые узлы балансировщика "под капотом", и их IP-адреса постоянно меняются. Поэтому в DNS (Route 53) к ALB можно привязывать только `ALIAS` или `CNAME` записи. Если клиенты (или партнеры с файрволами) жестко закэшировали старые IP-адреса ALB на своей стороне (или прописали их в IP-whitelist), они получат таймаут. Если клиенту нужны статичные IP, нужно использовать NLB (Network Load Balancer) или AWS Global Accelerator.

**9. Что такое `Spot Fleet` и зачем он нужен, если обычный ASG тоже умеет запускать Spot инстансы?**
*Ответ:* Spot-инстансы могут быть принудительно отобраны AWS в любой момент (Interruption), если в зоне доступности возник дефицит мощностей. Обычный ASG пытается пересоздать точно такой же тип инстанса (например, `c5.large`). Если этот пул пуст, ASG не поднимет сервер. `Spot Fleet` (или ASG с опцией Mixed Instances Policy / Attribute-based selection) позволяет вам указать: "Мне не важен тип инстанса, мне нужно 100 vCPU. Бери любые типы (c5, m5, r5) с любых пулов, где цена ниже $0.05". Это гарантирует, что ваше приложение выживет даже при массовом изъятии спотов в определенных зонах.

**10. Объясните концепцию Placement Groups (Группы размещения) в EC2. Когда стоит использовать `Cluster`, а когда `Spread`?**
*Ответ:* Placement Groups влияют на то, как физически 서버ы размещаются в стойках дата-центра AWS.
- **Cluster**: AWS пытается упаковать ваши инстансы максимально близко друг к другу (в одной стойке). Дает 10 Gbps сеть с микросекундной задержкой. Идеально для High-Performance Computing (HPC) и узлов баз данных. *Минус*: Если стойка сгорит, вы потеряете все сервера сразу.
- **Spread**: AWS принудительно раскидывает ваши 7 инстансов по 7 разным физическим стойкам (разное питание, разные свитчи). Идеально для NoSQL кластеров (Cassandra, Kafka) или узлов ZooKeeper, где потеря двух узлов одновременно недопустима.
