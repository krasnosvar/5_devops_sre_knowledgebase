## 1. Amazon RDS: Multi-AZ vs Read Replicas

**RDS (Relational Database Service)** — это managed-сервис для PostgreSQL, MySQL, MariaDB, Oracle.
Различают два архитектурных паттерна масштабирования/отказоустойчивости:
- **Multi-AZ (Отказоустойчивость - High Availability)**: AWS автоматически создает второй (Standby) сервер в другом дата-центре (AZ) и настраивает **синхронную репликацию** на уровне жесткого диска (EBS). Standby сервер не принимает запросы (вы не можете с него читать). Если Master падает, AWS переключает DNS на Standby сервер за 1-2 минуты. Нулевая потеря данных (RPO = 0).
- **Read Replicas (Масштабирование чтения - Scalability)**: Создается копия БД с **асинхронной репликацией** (через transaction logs). Реплика активно принимает SQL-запросы на чтение (SELECT). Разгружает Master. Из-за асинхронности возможна задержка (Replication Lag). Можно создать до 15 реплик.

## 2. Amazon Aurora: Архитектура облачного Storage

**Aurora** — это переписанные движки MySQL и PostgreSQL под архитектуру Cloud-Native.
Обычный RDS пишет данные в EBS (сетевой диск), а репликация идет через сетевой слой БД.
*Архитектура Авроры:* Вычислительный слой (EC2) полностью отделен от слоя хранения (Storage). Слой хранения Aurora — это распределенный кластер SSD-накопителей по 3 зонам доступности (AZ). Аврора автоматически записывает ваши данные в **6 копий** (по 2 копии в каждой из 3 AZ). База данных может пережить потерю целой AZ (2 копий) без потери консистентности (Quorum writes).
*Плюсы:* До 15 Read Replicas, и у них **нулевой Replication Lag** (порядка миллисекунд), потому что реплики читают прямо из того же общего Storage-слоя, а не копируют данные к себе!

## 3. DynamoDB: Архитектура NoSQL, Партиции и Лимиты

**DynamoDB** — это Serverless Key-Value (и Document) NoSQL база данных от AWS. Отдает данные за 1-9 миллисекунд при любом объеме.
- Нет концепции таблиц и JOIN-ов в привычном смысле. Основа — это **Partition Key (PK)** и **Sort Key (SK)**. AWS использует хэш от PK, чтобы понять, на какой физический SSD-сервер положить запись.
- **Provisioned Mode**: Вы заранее покупаете мощности в виде WCU (Write Capacity Units) и RCU (Read Capacity Units). Дешево при предсказуемой нагрузке.
- **On-Demand Mode**: Платишь за каждый запрос. Идеально для Serverless приложений со скачкообразной нагрузкой (спайками).
- **DAX (DynamoDB Accelerator)**: Встроенный in-memory кэш перед DynamoDB, снижающий задержку до микросекунд (Microseconds).

## 4. Кэширование: Amazon ElastiCache (Redis vs Memcached)

Managed сервис для In-Memory баз данных (хранение в оперативной памяти).
- **Memcached**: Простой. Многопоточный (Multi-threaded). Используется только для тупого кэширования HTML-страниц или объектов. Нет репликации и бэкапов.
- **Redis**: Однопоточный (Single-threaded). Сложные структуры данных (Списки, Sets, Hash, Geo-пространственные индексы). Поддерживает Multi-AZ (автоматический Failover), бэкапы (Snapshots), Pub/Sub, и транзакции. Де-факто стандарт индустрии.

## 5. Безопасность баз данных в AWS

- Шифрование **At Rest** (на диске): Включается при создании RDS через интеграцию с AWS KMS (шифруются сами EBS-тома). Выполняется ядром Linux без деградации производительности БД.
- Шифрование **In Transit** (в сети): Настройка `sslmode=require` в драйвере, RDS имеет встроенные сертификаты AWS.
- **IAM Database Authentication**: Вместо генерации паролей в PostgreSQL, вы можете настроить RDS доверять IAM Ролям. Lambda или EC2-инстанс генерирует временный IAM-токен (Auth Token) на 15 минут, и драйвер PostgreSQL логинится в базу с этим токеном.

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему при настройке Multi-AZ (синхронной репликации) в Amazon RDS производительность записи (Write Latency) может немного ухудшиться по сравнению с Single-AZ?**
*Ответ:* В Multi-AZ RDS используется синхронная репликация на уровне хранилища. Когда вы делаете SQL `INSERT`, первичный сервер пишет данные на свой диск, затем отправляет блоки по сети в другую зону доступности (Standby сервер), ждет, пока тот запишет блоки на свой диск, и только после получения подтверждения (ACK) от Standby-сервера отвечает приложению об успешной транзакции (Commit). Сетевой прыжок между дата-центрами (AZ) добавляет несколько миллисекунд к каждой операции записи.

**2. Разработчик спроектировал таблицу в DynamoDB для хранения логов IoT датчиков. В качестве Partition Key (PK) он выбрал `Date` (текущая дата в формате YYYY-MM-DD), а в качестве Sort Key — `SensorID`. Какую архитектурную проблему вызовет такой дизайн базы?**
*Ответ:* Это классическая проблема **Hot Partition (Горячая партиция)**. DynamoDB распределяет данные по физическим серверам на основе хэша от Partition Key. В этой архитектуре ВСЕ датчики в мире будут писать данные в один и тот же Partition Key (сегодняшнюю дату). Вся колоссальная нагрузка на запись ляжет на один физический сервер в кластере DynamoDB, что быстро приведет к исчерпанию лимитов WCU партиции и ошибке `ProvisionedThroughputExceededException`. Правильный дизайн — сделать PK `SensorID`, а SK — `Timestamp`.

**3. В чем фундаментальное преимущество архитектуры хранилища Amazon Aurora (Storage) перед классическим Amazon RDS (MySQL) при необходимости быстро добавить Read Replica?**
*Ответ:* В классическом RDS Read Replica требует создания нового сервера и **полного копирования (синхронизации)** всех данных (терабайт) с Master-узла, что может занять часы. В Amazon Aurora вычислительный слой (Compute) отвязан от Storage. Все данные хранятся на общем распределенном Cluster Volume. Когда вы создаете новую Read Replica в Aurora, она поднимается за пару минут, так как ей вообще не нужно копировать данные! Она просто подключается (монтирует) тот же самый общий Storage слой в режиме Read-Only.

**4. Вы используете ElastiCache for Redis. Внезапно Master-узел упал. Сколько времени займет Failover (переключение на реплику), и как ваше приложение узнает, по какому IP-адресу стучаться в новую Master-базу?**
*Ответ:* Failover в ElastiCache Multi-AZ занимает около 1-3 минут. Приложение не должно жестко зашивать в конфиги IP-адреса конкретных узлов. ElastiCache выдает один **Primary Endpoint (DNS-имя)**, который всегда указывает на актуальный Master-узел. При падении Master-а, AWS повышает реплику до Master и автоматически обновляет CNAME-запись DNS под капотом. Приложение временно (пару минут) будет получать таймауты, пока DNS кэш не обновится, после чего соединение восстановится.

**5. Объясните концепцию Global Databases в Amazon Aurora. Чем она отличается от Cross-Region Read Replicas в RDS?**
*Ответ:* Aurora Global Databases использует аппаратную, встроенную репликацию на физическом уровне (уровне Storage), а не логическую репликацию движка MySQL/Postgres (как это делает классический RDS). Благодаря этому репликация данных в другой континент (например, из Европы в США) происходит с минимальной задержкой (Lag обычно меньше 1 секунды). В случае падения основного региона (Disaster Recovery), вторичный регион можно повысить до Master менее чем за 1 минуту (RTO < 1min), обеспечивая глобальную выживаемость бизнеса.

**6. У вас есть база PostgreSQL в AWS RDS. Вы хотите создать точную копию (Клон) 5-терабайтной базы для отдела аналитики, чтобы они могли гонять тяжелые отчеты (с возможностью записи временных таблиц), не грузя Prod. Копирование Snapshot'а займет 10 часов. Есть ли более быстрый вариант?**
*Ответ:* Да, если вы используете **Aurora Postgres** (а не базовый RDS). У Aurora есть фича **Fast Database Cloning** (Быстрое клонирование). Клонирование 5-ТБ базы занимает несколько минут, так как используется технология "Copy-on-Write". Новый кластер просто указывает на те же самые блоки данных (Storage) оригинальной базы без их физического копирования. Вы платите только за новые/измененные данные, которые пишет отдел аналитики в своем независимом клоне.

**7. Как защитить базу данных DynamoDB от вируса-шифровальщика или случайного скрипта, который `DROP`нул все таблицы? DynamoDB же Serverless, там нет серверов для бэкапа?**
*Ответ:* DynamoDB поддерживает функцию **PITR (Point-In-Time Recovery)**. Если вы включаете её, AWS непрерывно (в фоне) записывает все изменения ваших таблиц в течение последних 35 дней (без малейшего влияния на производительность базы). В случае катастрофы вы можете указать **любую секунду** из последних 35 дней, и AWS восстановит таблицу (создаст новую таблицу с тем же содержимым) в точности на тот момент времени, до того, как хакер запустил скрипт.

**8. В чем разница между Eventual Consistency (Слабая консистентность) и Strongly Consistent (Строгая консистентность) чтением в DynamoDB? За что с вас берут больше денег (RCU)?**
*Ответ:* По умолчанию чтение в DynamoDB является `Eventually Consistent`. База пишет данные в 3 копии (в разных AZ). Когда вы делаете запрос на чтение, он может попасть на копию, которая еще не успела синхронизироваться (вы получите старые данные, но задержка минимальна). Это стоит 0.5 RCU за 4 KB.
`Strongly Consistent` чтение (указывается флагом в API-запросе) гарантирует возврат самых свежих данных (база дождется синхронизации перед ответом). Но такое чтение стоит в 2 раза дороже (1 RCU за 4 KB) и увеличивает сетевую задержку.

**9. Разработчики просят выдать им логин и пароль от Production RDS базы для дебага приложения. Как SRE должен подойти к этому вопросу с точки зрения безопасности, не раздавая постоянные пароли?**
*Ответ:* Использование статичных паролей для людей (Human Users) — это антипаттерн (Security Risk). SRE настраивают интеграцию **IAM Database Authentication**. Разработчик (пользователь AWS) генерирует временный токен с помощью AWS CLI (`aws rds generate-db-auth-token`). Этот токен действует всего 15 минут. Разработчик вставляет этот токен в поле "Пароль" в своем SQL-клиенте. База проверяет токен через AWS IAM и пускает юзера. Если разработчик уволится, доступ к БД аннулируется автоматически вместе с удалением IAM юзера.

**10. В чем главная архитектурная слабость Redis (ElastiCache) при вертикальном масштабировании (Scale Up), и почему Memcached в этом плане проще?**
*Ответ:* Redis является **Single-Threaded** (однопоточным) приложением. Он выполняет все команды в одном цикле ядра. Если вы масштабируете сервер Redis, увеличивая количество CPU ядер с 4 до 64 (огромный EC2 инстанс), Redis не сможет утилизировать больше 1 ядра для обработки команд (соответственно, пропускная способность не вырастет). Масштабировать Redis нужно горизонтально (через Redis Cluster / Sharding). Memcached изначально спроектирован как **Multi-Threaded** (многопоточный), и он отлично использует дополнительные ядра при вертикальном масштабировании.
