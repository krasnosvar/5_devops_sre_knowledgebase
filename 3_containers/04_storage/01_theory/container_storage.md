## 1. Почему файловая система контейнера не подходит для данных?

Как мы разбирали в разделе про слои (OverlayFS), запись данных прямо в файловую систему контейнера (в UpperDir) имеет две фатальные проблемы:
1. **Эфемерность (Loss of data):** При удалении/пересоздании контейнера слой UpperDir уничтожается, и данные исчезают.
2. **Ужасный I/O overhead:** Механизм Copy-on-Write (CoW) заставляет ядро копировать целые файлы из нижних слоев при малейшем их изменении. Базы данных умрут от задержек (Latency).

Чтобы обойти драйвер OverlayFS и писать данные **напрямую** на диск хоста, используются механизмы монтирования томов.

## 2. Docker Volumes и Bind Mounts

В классическом Docker есть 3 способа работы с диском:
- **Bind Mounts** (`-v /opt/data:/var/lib/mysql`): Ядро делает `mount --bind`. Директория с хоста проецируется внутрь контейнера. Зависит от структуры папок хоста, могут быть проблемы с правами (UID/GID).
- **Volumes** (`-v myvol:/var/lib/mysql`): Управляются самим Docker (лежат в `/var/lib/docker/volumes/`). Независимы от файловой системы хоста, их проще бэкапить, можно использовать плагины (например, volume-плагин для подключения к NFS). Это Best Practice.
- **tmpfs** (`--tmpfs /app/cache`): Монтирует RAM (оперативную память) как файловую систему. Идеально для секретов и быстрых, но временных кэшей. Не пишет на диск вообще.

## 3. Kubernetes CSI (Container Storage Interface)

В раннем Kubernetes драйверы для работы с дисками (AWS EBS, Ceph, NFS) были "In-Tree" (вкомпилированы в исходный код самого Kubernetes). Это было ужасно: чтобы обновить драйвер диска, нужно было обновлять весь кластер k8s.

Теперь стандарт — **CSI (Container Storage Interface)**. Это gRPC-интерфейс, аналогичный CNI для сети. Вендоры систем хранения (AWS, Yandex, NetApp) пишут свои бинарные плагины.
Жизненный цикл через CSI:
1. **Provision (Создание)**: CSI-контроллер стучится в API облака и создает физический диск (например, через AWS API).
2. **Attach (Привязка)**: Диск аппаратно прикрепляется (attached) к нужной виртуальной машине (Node).
3. **Mount (Монтирование)**: На самой ноде kubelet вызывает CSI-node плагин, который форматирует диск (в ext4/xfs) и делает `mount` в директорию пода.

## 4. Абстракции k8s: PV, PVC и StorageClass

Kubernetes разделяет роли "Админа" и "Разработчика" через абстракции:
- **PV (PersistentVolume)**: Сущность кластера, представляющая физический кусок диска (например, созданный LUN в SAN или AWS EBS). Создается админом или автоматически через CSI.
- **PVC (PersistentVolumeClaim)**: "Заявка" разработчика на место. Разработчик пишет в манифесте пода: "Мне нужно 10 ГБ быстрого SSD".
- **StorageClass (SC)**: Шаблон "класса" диска (например, `fast-ssd`, `slow-hdd`). Он содержит параметры для CSI-драйвера, как именно провижинить диск (тип файловой системы, IOPS, зона доступности).

Когда разработчик создает PVC со ссылкой на StorageClass, срабатывает механизм **Dynamic Provisioning**: контроллер k8s видит заявку, вызывает CSI-плагин, тот идет в облако, создает диск (PV) нужного размера и связывает (binds) PV с PVC.

## 5. Режимы доступа (Access Modes) и блокировки

При создании PVC разработчик обязан указать Access Mode:
- **ReadWriteOnce (RWO)**: Диск может быть смонтирован для чтения и записи только **одной 노дой** (Node) одновременно. Типично для блочных устройств (AWS EBS). Если вы попробуете запустить Deployment с 2 репликами на разных нодах с таким PVC, второй под зависнет в состоянии `ContainerCreating` из-за блокировки.
- **ReadWriteMany (RWX)**: Диск может быть смонтирован для чтения и записи **многими 노дами** одновременно. Поддерживается только файловыми/сетевыми системами хранения (NFS, CephFS, GlusterFS).
- **ReadOnlyMany (ROX)**: Многие ноды могут читать, никто не может писать.

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. В чем фундаментальная разница между Bind Mount и Docker Volume с точки зрения SRE?**
*Ответ:* Bind mount жестко привязывает контейнер к конкретным путям на физическом хосте (например, `/home/user/data`). Это ломает переносимость: на другом сервере этой папки может не быть. Также часто возникают проблемы с правами, так как UID пользователя в контейнере может не совпадать с UID владельца папки на хосте. Volumes управляются самим Docker демоном, абстрагированы от хостовой ФС, безопасны и могут использовать сторонние плагины (например, для бэкапов прямо в S3).

**2. Разработчик создал Deployment на 3 реплики с привязанным PVC (StorageClass: aws-ebs). Поды распределились по 3 разным нодам. Только один под перешел в Running, остальные висят в `ContainerCreating`. Почему?**
*Ответ:* Блочные устройства (AWS EBS, Yandex Compute Disks) поддерживают режим доступа только **ReadWriteOnce (RWO)**. Это физическое ограничение — блочное устройство нельзя одновременно прикрепить к разным серверам во избежание порчи файловой системы (corruption). Первый под захватил диск на своей ноде, а остальные поды на других нодах не могут сделать Attach этого же диска. Для Deployment с несколькими репликами нужен либо NFS/CephFS (режим **RWX**), либо использование StatefulSet с параметром `volumeClaimTemplates` (чтобы каждому поду выдавался свой уникальный диск).

**3. Что такое `volumeClaimTemplates` и почему он используется в StatefulSet?**
*Ответ:* При использовании обычного Deployment и одного PVC, все поды будут пытаться писать в один и тот же диск. Для баз данных (например, кластер PostgreSQL) это фатально: каждой реплике БД нужен свой собственный, изолированный диск. `volumeClaimTemplates` в StatefulSet указывает контроллеру Kubernetes динамически создавать **новый** уникальный PVC (и, следовательно, PV) для каждого запускаемого пода (pod-0, pod-1, pod-2).

**4. Вы случайно удалили PVC в Kubernetes, но диск в облаке остался и продолжает тарифицироваться. Какой параметр за это отвечает?**
*Ответ:* За поведение диска при удалении PVC отвечает параметр `ReclaimPolicy` у StorageClass (или PV). Если он установлен в `Retain`, то после удаления PVC сам PersistentVolume (и физический диск в облаке) переходит в состояние Released, но не удаляется, чтобы админ мог спасти данные вручную. По умолчанию при Dynamic Provisioning обычно используется `Delete`, который сразу удаляет диск в облачном провайдере через CSI.

**5. Зачем Kubernetes перешел от встроенных in-tree драйверов к CSI (Container Storage Interface)?**
*Ответ:* Чтобы отвязать релизные циклы драйверов хранилищ от релизов самого Kubernetes. Раньше код для работы с дисками AWS или VMware лежал прямо в исходниках k8s. При обнаружении бага в драйвере приходилось ждать нового релиза k8s и обновлять весь кластер. CSI вынес драйверы в подключаемые модули (плагины), работающие через gRPC. Теперь вендоры (Dell, AWS) обновляют свои CSI-драйверы как обычные поды (DaemonSet/Deployment) независимо от версии ядра Kubernetes.

**6. Может ли база данных (например, MongoDB) внутри Docker-контейнера безопасно использовать tmpfs?**
*Ответ:* Нет, если это основная база. Файловая система `tmpfs` монтируется исключительно в оперативную память (RAM). Она невероятно быстрая, но при перезапуске контейнера или ребуте сервера все данные мгновенно исчезают. Однако это отличный выбор для секретов (чтобы ключи шифрования никогда не попали на жесткий диск) или кэширующих серверов (вместо Redis), которым не нужна персистентность.

**7. Как kubelet понимает, что нужно смонтировать диск к поду, если pod создается на новой ноде?**
*Ответ:* Когда Scheduler назначает Pod на ноду, контроллер `attach/detach` в Kubernetes API понимает, что диску нужен Attach. Он подает команду облачному провайдеру (через CSI) подключить диск к этой 노де аппаратно (например, по iSCSI). Kubelet на ноде замечает новый device (например, `/dev/sdb`), вызывает CSI Node Plugin, форматирует его (если нужно) и выполняет системный вызов `mount` в директорию `/var/lib/kubelet/pods/.../volumes/`, которая проброшена (bind mount) внутрь контейнера.

**8. В чем разница между PersistentVolume (PV) и PersistentVolumeClaim (PVC)?**
*Ответ:* PV — это физический ресурс кластера (как оперативная память ноды). Это "Предложение" места. PVC — это запрос от приложения в рамках определенного Namespace. Это "Спрос". Разделение нужно для абстракции: разработчик (пишущий манифесты приложения) просит "дайте мне 100 ГБ" (PVC), и ему не нужно знать, что под капотом (NFS, SAN, EBS). Этим сложным бэкендом управляет админ через StorageClass и PV.

**9. Разработчик пробросил сокет Docker (`/var/run/docker.sock`) с хоста внутрь контейнера через Bind Mount. Чем это опасно с точки зрения ИБ?**
*Ответ:* Это эквивалент выдачи `root` прав на самом хосте (Host Takeover). Если злоумышленник прорвется внутрь такого контейнера, он сможет использовать клиент Docker для общения с этим сокетом. Через него он может запустить новый привилегированный контейнер, пробросить в него корень хоста (`-v /:/host`) и полностью захватить сервер, прописав свой ssh-ключ или изменив системные файлы. 

**10. Почему при запуске базы данных в контейнере часто рекомендуют настраивать права на volume через Init Containers (`chown`)?**
*Ответ:* Когда Kubernetes (CSI) монтирует блочное устройство (volume), его владельцем по умолчанию становится пользователь `root` (UID 0). Но по правилам безопасности хорошие образы баз данных работают от непривилегированных пользователей (например, `postgres` с UID 999). База данных упадет с ошибкой "Permission denied" при попытке записи. Init-контейнер запускается от root до старта основного пода, делает `chown -R 999:999 /data`, и подготавливает папку для основного процесса БД. (Также в k8s для этого есть фича `fsGroup` в SecurityContext).
