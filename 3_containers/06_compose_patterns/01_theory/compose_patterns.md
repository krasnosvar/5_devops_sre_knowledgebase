## 1. Императивный vs Декларативный подход

До появления Compose разработчикам приходилось писать сложные bash-скрипты из множества императивных команд `docker run --network mynet -e VAR=1 ...`. 
`docker-compose.yml` ввел **Декларативный подход**: мы описываем желаемое конечное состояние (набор сервисов, сетей и дисков) в YAML-файле, а бинарник `docker compose` сам вычисляет диффы (что нужно создать, пересоздать или удалить) и взаимодействует с Docker API.
Это концептуально похоже на Kubernetes-манифесты (Deployment, Service), но предназначено для локальной разработки и тестирования (или Single-Node продакшена).

## 2. Управление порядком запуска (depends_on и healthcheck)

Частая проблема: Backend-сервис стартует быстрее Базы Данных (PostgreSQL), падает с ошибкой "Connection refused" и завершается (Exit 1).
Базовый `depends_on: [db]` лишь гарантирует, что Compose сначала отправит команду старта контейнера БД, а потом бэкенда. Но готовность *процесса внутри* БД не проверяется.

*Современный подход (Best Practice):*
Использовать `depends_on` в связке с секцией `healthcheck`. Бэкенд будет ждать, пока скрипт проверки внутри БД не вернет успешный статус.
```yaml
services:
  db:
    image: postgres
    healthcheck:
      test: ["CMD", "pg_isready", "-U", "user"]
      interval: 5s
      retries: 5
  backend:
    image: myapp
    depends_on:
      db:
        condition: service_healthy # Ждать успешного healthcheck!
```

## 3. Управление переменными окружения (.env vs env_file)

Существует огромная путаница в работе с переменными в Compose. Есть два разных механизма:
1. **Файл `.env` (Подстановка в самом YAML)**: Читается самим бинарником `docker compose` на хосте перед парсингом YAML. Используется для интерполяции внутри YAML: `image: myapp:${VERSION:-latest}`. Контейнеры эти переменные по умолчанию **не видят**.
2. **Директива `env_file: [.env.production]`**: Говорит Compose передать содержимое файла внутрь контейнера (в Environment Variables самого процесса Linux). Compose этот файл не парсит для подстановок в YAML.

## 4. Переопределение (Override) и профили (Profiles)

Для разделения локальной разработки и CI/CD (или продакшена) не нужно копировать файлы (создавать `docker-compose.prod.yml`).
Механизм **Overrides**:
По умолчанию, если выполнить `docker compose up`, он найдет `docker-compose.yml`, а затем, если в папке лежит файл `docker-compose.override.yml`, он **наложит** его поверх основного (слияние словарей). В override-файле разработчик пробрасывает порты (`ports`) и монтирует локальный код (`volumes: .:/app`), не портя основной production-ready YAML.

**Профили (Profiles)**:
Позволяют включать/отключать сервисы. Например, тяжелый ML-воркер нужен не всем.
`profiles: ["ml"]` внутри сервиса. Сервис запустится только при флаге `docker compose --profile ml up`.

## 5. Сети и Volumes в Compose

- **Сети (Networks)**: Compose по умолчанию создает одну новую Bridge-сеть для всего проекта (имя директории + `_default`). Встроенный DNS-сервер Docker позволяет сервисам обращаться друг к другу по именам (названию сервиса в YAML, например `http://db:5432`).
- **Именованные тома (Named Volumes)**: Указываются в корневом блоке `volumes:`. Compose не удаляет их при `docker compose down` (если не передан флаг `-v`). Они гарантируют сохранность данных базы при пересоздании контейнеров.

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему базовый параметр `depends_on: [db]` не спасает бэкенд от падения при отсутствии коннекта к базе данных?**
*Ответ:* Базовый `depends_on` контролирует только порядок запуска **контейнеров** (инфраструктурный старт). Compose подает ядру команду "запустить контейнер B, как только запустился контейнер A". Однако процесс СУБД внутри контейнера A (например, PostgreSQL) может инициализировать кэши и восстанавливать WAL-журналы еще 20 секунд после старта. Контейнер Бэкенда запустится мгновенно, попытается подключиться, получит Connection Refused и упадет. Решение: использовать `depends_on: <service>: condition: service_healthy` в связке с `healthcheck`.

**2. В чем разница между использованием `.env` файла и секцией `env_file:` в docker-compose?**
*Ответ:* Файл `.env` (лежащий рядом с docker-compose.yml) считывается самой CLI утилитой `docker compose` на хост-машине. Его значения используются для интерполяции (подстановки переменных, `${VAR}`) **внутри самого YAML-кода**. Процесс внутри контейнера эти переменные не увидит. Секция `env_file:` в YAML, наоборот, указывает демону Docker прочитать файл и инжектировать эти переменные напрямую в Environment процесса контейнера. YAML-парсер этот файл не обрабатывает.

**3. Как в Compose прокинуть переменную окружения с хоста в контейнер, не записывая её значение ни в какие файлы?**
*Ответ:* Нужно указать имя переменной в блоке `environment:` без присвоения значения. Например:
```yaml
environment:
  - AWS_SECRET_KEY
```
В этом случае `docker compose` возьмет текущее значение переменной `AWS_SECRET_KEY` из терминала хост-машины (export) и передаст его внутрь контейнера.

**4. Что произойдет, если в папке лежат файлы `docker-compose.yml` и `docker-compose.override.yml`, и вы запустите `docker compose up`?**
*Ответ:* Compose автоматически прочитает оба файла и выполнит операцию "Merge" (слияние). Файл `override.yml` наложится поверх базового `yml`. Если в базовом был прописан образ `image: myapp`, а в override прописан `build: .`, то Compose соберет образ локально. Списки (например, `ports`) объединятся, а скалярные значения (например, `image` или `command`) перезапишутся из override-файла.

**5. Разработчик делает `docker compose down`, а затем `up`. Все данные в базе данных PostgreSQL пропадают. А если делает `docker compose restart`, то не пропадают. Почему?**
*Ответ:* Потому что для БД не был настроен Volume в compose-файле. При `restart` контейнер останавливается и запускается заново, сохраняя свой Read-Write слой (UpperDir). При `down` контейнер физически **удаляется** из демона Docker вместе с его файловой системой. Без использования именованных томов (Named Volumes, монтирования на хост) данные гарантированно уничтожаются при удалении контейнера.

**6. Зачем нужны Docker Compose Profiles?**
*Ответ:* Профили (Profiles) позволяют избирательно запускать группы сервисов из одного большого `docker-compose.yml`. Например, у вас есть 10 сервисов микросервисного приложения, но фронтендеру для разработки локально нужны только "frontend" и "api". Пометив остальные базы и воркеры в профиль (например, `profiles: ["backend_full"]`), они не будут запускаться по умолчанию при `docker compose up`, экономя память на ноутбуке разработчика.

**7. Как масштабировать (Scale) сервис в Docker Compose и какие с этим связаны проблемы?**
*Ответ:* Масштабировать можно командой `docker compose up --scale web=3`. Docker запустит три идентичных контейнера (web-1, web-2, web-3). Встроенный DNS будет балансировать трафик по Round-Robin при обращении к имени `web`. **Проблема:** Если в YAML жестко проброшен порт на хост (`ports: ["8080:80"]`), масштабирование упадет с ошибкой Bind Mount Conflict (порт 8080 на хосте уже занят первой репликой). Решение — либо не пробрасывать порты (обращаться через Nginx-балансировщик в той же сети), либо использовать динамические порты на хосте (`ports: ["80"]`).

**8. В чем отличие `docker compose up` от `docker compose run`?**
*Ответ:* `up` поднимает все сервисы (или указанный и его зависимости), связывает их сети, выводит логи в консоль и оставляет работать как долгоживущие демоны. `run` предназначен для выполнения разовых задач (one-off commands). Команда `docker compose run web bash` запустит отдельный (одноразовый) контейнер сервиса `web`, привяжет к нему ваш терминал (interactive) и не будет публиковать его порты на хост, чтобы не конфликтовать с уже запущенным через `up` сервисом.

**9. Что делает флаг `--build` в `docker compose up` и когда его нужно применять?**
*Ответ:* По умолчанию, если образ для сервиса (с директивой `build:`) уже существует локально на хосте, Compose не будет его пересобирать, даже если вы изменили исходный код на жестком диске. Флаг `--build` принудительно запускает пересборку (Rebuild) образов перед стартом контейнеров, гарантируя, что ваши последние изменения в коде попадут в запущенную среду.

**10. В чем отличие `docker-compose` (с дефисом) от `docker compose` (через пробел)?**
*Ответ:* `docker-compose` (с дефисом) — это старая версия (Compose V1), написанная на Python как отдельный скрипт. Она устарела (Deprecated) и больше не поддерживается. `docker compose` (через пробел) — это новая версия (Compose V2), написанная на Go. Она встроена в CLI-плагин самого Docker (Docker CLI plugin), работает быстрее, потребляет меньше памяти и лучше интегрируется с новыми фичами (вроде BuildKit).
