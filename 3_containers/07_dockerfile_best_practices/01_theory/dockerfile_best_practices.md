## 1. Форматы команд: Shell Form vs Exec Form

В Dockerfile директивы `RUN`, `CMD` и `ENTRYPOINT` можно записывать двумя способами:

- **Shell Form**: `CMD node server.js`
  Docker подставит вызов оболочки: `/bin/sh -c "node server.js"`. 
  Процесс оболочки (`/bin/sh`) получит PID 1. А ваше приложение `node` станет дочерним (PID 2+). Переменные окружения (`$VAR`) будут интерполироваться оболочкой.
- **Exec Form (JSON Array)**: `CMD ["node", "server.js"]`
  Docker вызывает системный вызов `execve` напрямую, без `/bin/sh`. Ваше приложение `node` запускается напрямую и получает PID 1. Переменные окружения оболочкой **не парсятся** (потому что оболочки нет).

*Best Practice:* Всегда используйте **Exec Form** (массив).

## 2. Проблема PID 1 и сигналы (SIGTERM)

Почему Exec Form так важен?
В Linux процесс с PID 1 имеет особую роль. Ядро не применяет к нему дефолтные обработчики сигналов.
Если вы используете **Shell Form**, то PID 1 становится `/bin/sh`. Когда Kubernetes решает обновить под, он шлет сигнал `SIGTERM` процессу с PID 1.
Но `/bin/sh` не умеет пересылать сигналы дочерним процессам! Ваш `node` сервер не узнает о том, что нужно завершаться. Kubernetes подождет 30 секунд (grace period) и жестоко убьет контейнер сигналом `SIGKILL (9)`. Это приведет к обрыву активных HTTP-соединений и порче данных.

Даже если использовать Exec Form, само приложение (например, Java или Node.js) может быть плохо написано и не обрабатывать `SIGTERM`.
*Решение:* Использовать легковесные init-системы вроде `tini` или `dumb-init`.
`ENTRYPOINT ["tini", "--", "node", "server.js"]`. Tini станет PID 1, корректно пробросит сигналы детям и уберет "зомби-процессы".

## 3. Паттерн ENTRYPOINT + CMD

`ENTRYPOINT` задает неизменяемую часть команды запуска (исполняемый файл).
`CMD` задает аргументы по умолчанию, которые легко переопределить при запуске.

Классический паттерн для баз данных (Redis/Postgres) — это **Entrypoint-скрипт**.
```dockerfile
COPY docker-entrypoint.sh /usr/local/bin/
ENTRYPOINT ["docker-entrypoint.sh"]
CMD ["postgres"]
```
Скрипт проверяет переданные аргументы, делает нужную инициализацию (например, создает базу данных, меняет владельца файлов `chown`), а в самом конце вызывает `exec "$@"` (где `$@` — это аргументы из CMD, то есть `postgres`). Команда `exec` заменяет процесс bash-скрипта процессом базы данных, делая базу данных процессом с PID 1.

## 4. BuildKit: Секреты и кэширование (Cache Mounts)

Старый сборщик Docker (builder) оставлял секреты в истории образа. Современный BuildKit (включен по дефолту) позволяет безопасно монтировать секреты только на время сборки.
```dockerfile
# Секрет не попадет в итоговый образ и в docker history
RUN --mount=type=secret,id=aws_creds \
    AWS_ACCESS_KEY_ID=$(cat /run/secrets/aws_creds) pip install my-private-package
```

**Кэширование пакетов (Cache Mounts):**
Чтобы не скачивать `npm install` или `apt-get` заново при каждом изменении `package.json`, можно смонтировать постоянный кэш между сборками:
```dockerfile
RUN --mount=type=cache,target=/root/.npm \
    npm install
```

## 5. Раздувание контекста и .dockerignore

При запуске `docker build -t app .`, первое, что делает Docker-клиент — архивирует **всю текущую папку** (Build Context) и отправляет её Docker-демону (часто через сокет/сеть).
Если в папке лежит папка `node_modules` (на 1 ГБ) или `.git` (на 500 МБ), сборка будет начинаться с отправки 1.5 ГБ данных в демон.
*Решение:* Всегда создавать `.dockerignore` и добавлять туда `.git`, `node_modules`, `venv`, `*.log`. Это ускоряет сборку в десятки раз.

## 6. Типовые вопросы на собеседовании (Interview Q&A)

**1. Почему при использовании `CMD npm start` (Shell form) приложение в Kubernetes завершается с задержкой в 30 секунд (Graceful shutdown не работает)?**
*Ответ:* При использовании Shell form Docker оборачивает вызов в `/bin/sh -c "npm start"`. Оболочка `sh` получает PID 1. При удалении пода Kubernetes отправляет сигнал SIGTERM процессу с PID 1. Проблема в том, что `/bin/sh` не передает сигналы своим дочерним процессам. Ваше приложение (node) не получает сигнал и продолжает работать. Kubelet ждет `terminationGracePeriodSeconds` (по умолчанию 30 секунд) и принудительно убивает весь контейнер сигналом SIGKILL (9). Решение: использовать Exec form `CMD ["npm", "start"]`.

**2. Зачем в bash-скриптах, используемых в качестве ENTRYPOINT, в конце пишут `exec "$@"`?**
*Ответ:* Команда `exec` в Linux не создает новый дочерний процесс. Она полностью заменяет текущий процесс (наш bash-скрипт с PID 1) на новую программу (переданную через аргументы `$@`, например, бинарник postgres). Если не написать `exec`, то bash-скрипт останется висеть с PID 1, запустив postgres как PID 2, и мы снова получим проблему недоставленных сигналов (SIGTERM улетит в bash, а не в postgres).

**3. В чем фундаментальная разница между `ENTRYPOINT` и `CMD`?**
*Ответ:* `ENTRYPOINT` — это непереопределяемая команда, которая выполняется всегда (чтобы переопределить ее, нужен специальный флаг `--entrypoint` в CLI). `CMD` — это либо аргументы по умолчанию для `ENTRYPOINT`, либо команда, которая выполнится, если `ENTRYPOINT` не задан. Главное отличие: параметры из `CMD` очень легко переопределить, просто добавив аргументы в конец команды `docker run myimage bash`.

**4. Вы написали `ENTRYPOINT ["echo", "$VAR"]`. Но переменная вывелась как пустая строка, хотя она задана в `ENV`. Почему?**
*Ответ:* Потому что использована Exec form (JSON-массив). В этом режиме ядро Linux запускает бинарник `echo` напрямую, без участия командной оболочки (`bash` или `sh`). А интерполяцией переменных (раскрытием знака `$`) занимается именно командная оболочка. Чтобы переменная раскрылась, нужно использовать Shell form `ENTRYPOINT echo $VAR` или явно вызвать оболочку: `ENTRYPOINT ["sh", "-c", "echo $VAR"]`.

**5. Что делает утилита `tini` или `dumb-init` и почему их часто ставят PID 1 в контейнерах?**
*Ответ:* В Linux процесс с PID 1 обязан выполнять функцию "жнеца" (Reaper) для процессов-сирот (orphans) и корректно перенаправлять сигналы. Базы данных и многие языки программирования (например, Java/Node.js) не умеют быть хорошим PID 1: они плодят зомби-процессы при форках и не пробрасывают SIGTERM. `tini` — это микро-init система, которая берет на себя роль PID 1, собирает зомби (вызывает `waitpid`) и транслирует сигналы всем детям.

**6. Зачем нужна директива `COPY --chown=user:group`? Разве нельзя сделать `COPY . .` а потом `RUN chown -R user:group /app`?**
*Ответ:* Сделать можно, но это фатально увеличит размер образа. `COPY` создает один слой файлов (от root). Если затем сделать `RUN chown`, драйвер OverlayFS скопирует все эти файлы (Copy-on-Write) из нижнего Read-Only слоя в новый слой, чтобы изменить метаданные прав доступа. Итоговый образ будет весить ровно в 2 раза больше (файлы будут лежать и в первом, и во втором слое). Флаг `--chown` позволяет задать права сразу в момент копирования, избегая дублирования.

**7. Как передать секретный SSH-ключ (для `git clone`) внутрь `docker build`, чтобы он не остался в истории слоев?**
*Ответ:* Нельзя использовать `COPY key ~/.ssh/` или `ARG KEY`, так как они навсегда останутся в `docker history` и слоях образа. В современном Docker (с включенным BuildKit) используется механизм секретов: `RUN --mount=type=secret,id=ssh_key git clone ...`. Ключ монтируется в оперативную память (tmpfs) только на время выполнения этой конкретной инструкции `RUN` и гарантированно не попадает в итоговый образ.

**8. У вас есть папка с проектом весом 10 МБ, но сборка `docker build .` на сервере зависает на этапе "Sending build context to Docker daemon" на 5 минут. Что случилось?**
*Ответ:* Вероятно, в папке проекта лежит скрытая директория (например, `.git` с историей на гигабайты, или локальная БД). При запуске сборки CLI-клиент архивирует ВСЮ папку контекста и отправляет демону. Чтобы этого избежать, нужно создать файл `.dockerignore` и добавить туда `.git`, `node_modules` и другие папки, не требующиеся для компиляции образа.

**9. Что такое Build Cache Mount (`--mount=type=cache`) и зачем он нужен?**
*Ответ:* Обычное кэширование слоев ломается, если меняется файл `package.json` (инвалидируется слой, и `npm install` качает весь интернет заново). С помощью BuildKit можно смонтировать постоянный кэш (папку `/root/.npm`) с хост-машины внутрь сборочного контейнера. Тогда даже при изменении `package.json` утилита `npm` найдет скачанные пакеты в смонтированном кэше и установка займет пару секунд.

**10. Почему не стоит использовать `LATEST` теги для базовых образов (например, `FROM ubuntu:latest`)?**
*Ответ:* Это нарушает принцип воспроизводимости (Reproducibility). Если вы соберете образ сегодня, он скачает Ubuntu 22.04. Через пару лет тот же `Dockerfile` скачает Ubuntu 26.04, где могут обновиться библиотеки (glibc, Python), и ваше приложение внезапно перестанет компилироваться или работать в production. SRE-практика требует жестко фиксировать мажорные и минорные версии (Pinning), например `FROM ubuntu:22.04` или даже использовать SHA-хэши (`FROM ubuntu@sha256:...`).
