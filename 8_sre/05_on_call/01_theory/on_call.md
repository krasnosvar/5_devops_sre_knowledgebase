# On-Call

## Здоровый on-call

On-call — не "кто-то следит за мониторингом". Это структурированная роль с чёткими правилами.

**Признаки нездорового on-call:**
- Частые ночные пробуждения (> 2 раза в неделю)
- Алерты без runbook ("что делать — непонятно")
- Один человек постоянно on-call ("незаменимый")
- Нет компенсации за дежурство

## Ротация

```
Минимум: 2 уровня (первичный + вторичный)
Рекомендуемый размер ротации: 4-8 человек на каждый уровень

Первичный on-call: отвечает первым (SLA: 5-15 мин)
Вторичный on-call: берёт если первичный недоступен (SLA: 30 мин)

Частота ротации:
  - Еженедельная: меньше burnout, больше контекста за неделю
  - Ежедневная: меньше усталости, но сложнее набрать контекст

Правило: каждый инженер в команде должен быть в ротации.
"Я не умею это чинить" → нужно научить, а не исключить из ротации.
```

## SLA on-call response

```
Severity 1 (P0): Ответить за 5 минут / Исправить за 1 час
Severity 2 (P1): Ответить за 15 минут / Исправить за 4 часа
Severity 3 (P2): Ответить в рабочее время
Severity 4 (P3): Ответить в течение недели
```

## Runbooks — инструкции для дежурного

```markdown
# Runbook: PaymentService High Latency

## Симптомы
- Алерт: PaymentLatencyHigh (p95 > 2s)
- Пользователи сообщают о медленном checkout

## Диагностика (2 мин)
1. Grafana: https://grafana/d/payments — смотреть latency breakdown
2. Проверить зависимости: `kubectl get pods -n payments`
3. Проверить error rate Stripe API: https://status.stripe.com/

## Митигация

Если БД медленная:
```bash
kubectl exec -n payments db-0 -- psql -U app -c "SELECT * FROM pg_stat_activity WHERE wait_event_type='Lock'"
```

Если Stripe медленный — включить fallback режим:
```bash
kubectl set env deployment/payment-service PAYMENT_PROVIDER=backup
```

Если memory OOM:
```bash
kubectl rollout restart deployment/payment-service -n payments
```

## Escalation
- Не решено за 15 мин: @tech-lead-payments
- Потеря данных: @vp-engineering

## Постмортем требуется если: > 30 мин downtime
```

## Toil — что это и как сокращать

**Toil** — ручная, повторяющаяся, автоматизируемая работа связанная с эксплуатацией сервисов.

Признаки toil:
- Делается вручную (не автоматически)
- Повторяется регулярно
- Не добавляет долгосрочной ценности
- Масштабируется линейно с ростом системы

Примеры:
- Ручное создание пользователей каждый раз
- Перезапуск сервиса по расписанию (workaround вместо фикса)
- Ручное изменение конфигов без автоматизации
- Проверка логов вручную вместо алерта

**Google SRE правило:** не более 50% времени on-call команды на toil. Остальное — на инженерию.

## Burnout prevention

```
Ранние признаки burnout:
  - Нарастающий страх before on-call смены
  - Нет времени на "нормальную" работу
  - Одни и те же инциденты повторяются

Действия:
  1. Quantify: считать MTTA, количество pages/night
  2. Ревью ротации: справедлива ли нагрузка?
  3. Postmortem незакрытых action items — почему повторяется?
  4. Временно уменьшить ротацию / нанять людей
  5. Компенсация: дополнительный день отдыха после тяжёлой недели
```
